# hMailServer wave (~20 GHSAs): loopback REST reachable by browser rebinding

**Wave in one line:** COM service as a local-privilege surface, loopback REST reachable by browser rebinding, and DANE/TLS fail-open on the outbound mail path

Source: hourly offensive-security scan of GitHub Security Advisories, 2026-10-08 (wave published 2026-10-08T12:34Z, ~20 advisories for Progressive Robot hMailServer, CVE-2026-107503-adjacent band CVE-2026-107570–107587 plus CVE-2026-103010/103011/103517-adjacent CVE-2026-103647/103649/104658/104659/104660; affected band **6.0.0 through 6.3.5**, webmail legs 6.3.2–6.3.5).

One theme: **a mail server aggregates DNS trust, TLS trust, attachment handling, a Windows COM service, and a loopback admin API in one process — and this wave breaks every one of those boundaries independently.** hMailServer is a very common Windows mail server in SMB and MSP environments; the wave is a ready-made test matrix for any authorized engagement where a mail host is in scope, and several legs generalize to any mail server or any Windows service that registers COM classes.

## Why this is an operator page

Mail servers are dense trust-boundary hosts: they consume **untrusted DNS answers, untrusted certificate material, untrusted attachment bytes, and untrusted network input** in one privileged process, and they usually run on Windows hosts that are also domain members. The wave hands you a replayable checklist:

1. **Windows COM services are a standing local-privilege surface.** Any Windows service that registers COM classes deserves a DCOM-permission audit — `Win32_DCOMApplication`/SD checks, or just try activation from a foothold account. Service-privileged file read/write (`Attachments.Add`/`SaveAs` shapes) plus unauthenticated send-as-any-sender is a full credential-theft + pivot kit on a mail host, from a *lowest-privilege interactive login*, with no hMailServer credential at all. Grep the registry `AppID`/`AccessPermission` keys, not the vendor docs.
2. **Loopback-bound admin listeners are browser-reachable without any Host check.** The listener here validated nothing on `Host` and applied no loopback rate limit — the DNS-rebinding class the July 8 page tracks (folded there for the rebinding mechanics). Test: from an owned rebinding domain, drive a lab browser on the target host and watch whether the loopback API answers with a foreign `Host`; also confirm whether failed local logins burn the account or run unthrottled. Unthrottled loopback auth = a web page becomes a password oracle.
3. **Update helpers that run as root and read unprivileged files invert the trust direction.** On any Linux service with a privileged updater, read the helper first and ask which fields it takes from files the service user writes — here the *signature-verification program itself* was attacker-chosen, so "verified signature" was theater. General rule: the verifier binary/path must never be data from a lower trust tier.
4. **Windows path-reparse trust: admin-rights tools operating in service-writable folders.** Junction/mount-point following by elevated install/maintenance operations over directories a low-priv account can modify is the same reparse-point genealogy as symlink LPEs on the Sept 23 updater page — check log/cert/data folder ACLs on any appliance-style Windows service.
5. **DNSSEC/DANE fail-open is a durable mail-path interception primitive.** Both TLS legs are *validation-to-decision drift*: an incomplete or unusable secure answer selects the *insecure* delivery path instead of the fail-closed path. If you hold an on-path position (network, resolver, or between resolver and authoritative NS), test DANE behavior by serving TLSA sets that are (a) DANE-TA-only, (b) RRSIG-stripped, (c) SERVFAIL/dropped, and observe whether STARTTLS is still required. Any mail stack that maps "secure data unavailable" to "not secured" is downgradable — check Postfix/exim/sendmail DANE patches similarly.
6. **Decrypt-then-render is a new webmail sink context.** Browser-side S/MIME/OpenPGP decryption that hands plaintext parts back as blob URLs with attacker-declared media types puts *decrypted content* in the web app's own origin — and encryption raises click-through. Probe any webmail that decrypts client-side: request a decrypted attachment declared `text/html`, open in new tab, observe origin. Pair with the cert-store poisoning leg: **auto-saved signer certs (trusted or not) silently steer future reply encryption** — after receiving an encrypted correspondence test, inspect the per-contact certificate set.
7. **The quadratic-complexity pack is the fuzzing map.** Twelve parser legs (FETCH/SEARCH, DKIM/ARC verify, MIME, Sieve, SPF macros, JSON, header decode, bounce processing) tell you exactly where to point a mail-protocol fuzzer on *any* mail server: length- and repetition-sensitive parsing of inbound-signed data. Availability-only for reports, reachability-map for research.

## Validation boundaries

Lab instances only (owned VMs, disposable mail domains with DNSSEC control for the DANE legs; owned rebinding domain + lab browser for the loopback leg; local foothold accounts you own for the COM leg). No production mail queues, no real user mailboxes, no cleartext capture of third-party mail, no send-as-any-sender against real domains — prove queue injection to yourself only. On third-party hosts, route-level evidence (version, listener presence, folder ACL read where permitted) stays inside scope; brute force and COM activation are lab-only assertions.

## October 19 follow-up: second hMailServer wave — DKIM signing oracle from plain inbound mail, Sieve header-edit sender spoofing, and a negative inbound loop counter (5 GHSAs, band extended to 6.3.6)

GitHub Security Advisories published a second coordinated hMailServer set on 2026-10-19T18:32Z (CVE-2026-107566/107567/107568/107569/107571, affected **6.0.0 through 6.3.6** — the first wave's band extended by one release). Four of the five legs are new boundaries, and the DKIM leg is a durable spoofing primitive for any mail server:

- **DKIM signs whatever the unauthenticated `From` says** — [GHSA-8h9p-r7cp-qhr5](https://github.com/advisories/GHSA-8h9p-r7cp-qhr5) / [CVE-2026-107567](https://nvd.nist.gov/vuln/detail/CVE-2026-107567) (high). With DKIM signing enabled for a hosted domain, the server signed **every message on its first delivery pass as the domain named in its `From` header, before local delivery, whatever the message's origin and without checking that the sender authenticated**. A sender anywhere could send the server — as ordinary **inbound** mail — a message whose `From` is any address at such a domain; the server signed it with that domain's key, and every copy it then relayed outward (an account forward, a redirect) carried a valid signature aligned with the forged `From`, whatever the domain's DMARC policy. The signing oracle is reachable with zero credentials: the trigger is mail *to* the server, the sink is mail *out* of it.
- **Sieve `editheader` + redirect = authenticated send-as-any-address, DKIM-signed** — [GHSA-87p7-4v38-33c9](https://github.com/advisories/GHSA-87p7-4v38-33c9) / [CVE-2026-107566](https://nvd.nist.gov/vuln/detail/CVE-2026-107566) (med). A stored Sieve script's `addheader`/`deleteheader` could delete and re-add `From` (only `Received`/`Return-Path` were blocked), and header edits are applied **before** a queued redirect — so the redirected copy left as the script wrote it, and leg 1's sign-on-first-delivery-pass made it DKIM-valid for any hosted domain.
- **Sieve `notify :from` and mail-rule `Reply` skip the sender check** — [GHSA-625v-xcvx-8hhv](https://github.com/advisories/GHSA-625v-xcvx-8hhv) / [CVE-2026-107568](https://nvd.nist.gov/vuln/detail/CVE-2026-107568) (med). `notify`'s `:from` was used verbatim with no check that the address belongs to the account — while the sibling `vacation` action **does** check its own `:from`, as does the COM/webmail send path. Same-product, same-action-family, one action checked and two didn't.
- **`X-hMailServer-LoopCount` arrives from outside and negative values pass every limit** — [GHSA-95hv-g278-w9p8](https://github.com/advisories/GHSA-95hv-g278-w9p8) / [CVE-2026-107569](https://nvd.nist.gov/vuln/detail/CVE-2026-107569) (high). The server bounds rule-forwards/auto-replies by a counter carried in its own `X-hMailServer-LoopCount` header, compared against a signed limit — but the header is **not stripped from inbound external mail** and is read with a signed conversion without validation, so a negative value passed every test against the limit and unbounded mail generation stopped the server carrying mail.
- **Installer inherits writable-parent ACLs** — [GHSA-xgwq-m9m9-pgw3](https://github.com/advisories/GHSA-xgwq-m9m9-pgw3) / [CVE-2026-107571](https://nvd.nist.gov/vuln/detail/CVE-2026-107571) (high). The installer never sets permissions on the program/`Bin` folder, so an install at a drive root inherits Authenticated-Users/Users write — local user code execution as the mail server's privileged accounts. Same install-folder genealogy as the first wave's folder-ACL leg.

### Durable rules from this wave

1. **Audit signing as an oracle keyed on unauthenticated input.** Ask of every DKIM/ARC-capable product: is the signing decision keyed on the message's `From` **before** sender authentication and independent of who submitted it? Black-box probe on an owned-or-lab host: inbound message with `From:` at a signed hosted domain, an account forward to your owned receiver, then `dkim=pass` + `d=` aligned with the forged domain in the receiver's Authentication-Results. This primitive generalizes far beyond hMailServer — any MTA that signs on first delivery pass should be checked for the authenticate-then-sign ordering. Pair with the first wave's COM queue-injection leg: unauthenticated signing now composes with local send-as-any-sender for full-domain DMARC-pas spoofing.
2. **Run the sibling-action parity battery on user-scriptable mail policy.** `vacation :from` checked, `notify :from` and `editheader From` unchecked — enumerate every user-scriptable action (Sieve extensions, mail rules, filters) and test the sender/recipient/header fields each can set against the checks the *most-defensive* sibling enforces. Genealogy: the Zimbra Sieve `notify` bypasses-disabled-forwarding leg (GHSA-p88h-50055) on the Oct 8 wave context above — Sieve `notify` is now a two-product policy-bypass sink.
3. **Inbound counter/loop-guard headers must be stripped at the border.** Any product that bounds its own generated mail with a header it also *reads from inbound mail* (loop counts, hop counts, `X-` state headers) has an unauthenticated state-injection surface; test negative values, huge values, and non-numeric spellings against signed comparisons. Availability-class for reporting, but the *unstripped inbound state header* fingerprint applies to routing, rate-limiting, and dedup headers on any protocol.

Validation boundary: lab hMailServer installs with disposable signed domains you own; prove the signing oracle to your own receiving listener only, never against real third-party domains. The loop-count leg is lab-only (server-stop DoS). Tracked no-publish from this wave: Sieve/COM siblings already covered by the Oct 8 page.
