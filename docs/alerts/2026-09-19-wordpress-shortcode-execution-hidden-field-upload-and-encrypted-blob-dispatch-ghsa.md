# WordPress shortcode-execution primitives, hidden-field upload bypass, encrypted-blob dispatch, and header-derived bot identity (Sept 19 03:32Z wave)

Source: hourly offensive-security scan of GitHub Security Advisories, 2026-09-19 (wave published 2026-09-19T03:32Z).

One theme ties the durable records: **a protective transformation is applied to the wrong side of the trust boundary.** The PDFCrowd plugin AES-encrypts attacker-influenced option state and later dispatches a callable field out of it; WP Recipe Maker strips shortcodes *after* `do_shortcode()` has already executed them; Gravity Forms validates visible fields but persists rejected files through a hidden-field code path; Better Messages identifies its privileged internal bot by prefix-matching a field the client fills in via `X-Real-IP`.

## Why this is worth an operator page

- **Server-side encryption of attacker-influenced state is not sanitization.** The PDFCrowd blob is only trusted *because the server made it*: a Contributor places a shortcode with `pdf_created_callback=<function>`, the plugin encrypts that into the public page, and the anonymous AJAX endpoint decrypts-and-dispatches. Audit rule: find every decrypt/read-then-act endpoint and check whether **any field inside the envelope reaches a callable, path, URL, or SQL sink** — integrity protection says nothing about field semantics. Same shape as the Sept 18 React Router unsigned-cookie item's mirror image: *signed/encrypted* ≠ *sanitized*.
- **Field visibility settings are validator-skip switches.** Hidden Gravity Forms fields never reach the extension check, yet the persistence pipeline still consumes their upload state. On any form builder or multi-stage pipeline (validate stage ≠ persist stage), enumerate per-field configuration toggles (hidden, disabled, conditional-logic) and test whether the *persist* leg re-validates. Send an inert PHP-marker file with a dangerous extension through a hidden upload field on a lab form and record whether `upload_file()` is reached.
- **`do_shortcode()` is an execution primitive and the shortcode registry is an internal function namespace.** Both recipes (WP Recipe Maker, Forminator) execute untrusted text as shortcodes; WP Recipe Maker adds a **rendered-output disclosure channel** (JSON-LD) that makes the primitive a data-read, not just a nuisance. Bug-hunt sweep: grep plugin code for `do_shortcode(` where the argument can originate from comment content, `$_POST`, or option/user meta; then enumerate the site's registered shortcodes (`rest_shortage`-style discovery or logged-out page fuzz for `[shortcode]` residue) and probe each one for an unauthenticated read/write side effect. Sanitize-vs-execute ordering ("strip after run") is the tell.
- **Privileged internal identities must never be derived from client-controlled fields.** Better Messages' bot check is the request-derived-identity axis (see the Sept 17 kcp `X-Remote-*` and Tina `clientID` pages) applied to an *application-internal service account*: an identity discriminator read from `X-Real-IP`, `X-Forwarded-For`, user-agent, or guest-name fields is spoofable. Sweep: find feature names of the form "AI bot", "system", "internal" in JS bundles/AJAX actions and ask what marks a caller as that principal.

## Validation workflow (authorized scope only)

!!! warning "Lab installs and inert proofs only"
    Use disposable WordPress installs with the vulnerable plugin versions, synthetic users, fake API keys, and inert marker files. Never invoke production callables, read real wp_users rows, upload executable code to a target, or post into real user chat rooms.

1. **Encrypted-blob dispatch (PDFCrowd class):** in a lab install, place the plugin's shortcode as a lab Contributor with `pdf_created_callback` set to a no-op function that writes a marker file or returns a benign value; POST the page-embedded blob to the nopriv AJAX endpoint as an anonymous curl session. Evidence: marker hit / options-array reflection in the response, plus the fixed-version behavior (allowlist or removal of the callable path). Redact the plugin API key if it reflects.
2. **Hidden-field upload matrix (Gravity Forms):** build a lab form with a File Upload field, toggle Visibility visible→hidden. Submit an inert marker file (`.php` name, GIF content) on both variants; record the validation verdict vs whether the file lands in `wp-content/uploads/gravity_forms/`. Evidence is the upload-state decision table + file listing; do not execute the uploaded marker.
3. **Shortcode-execution probe (WP Recipe Maker / Forminator class):** on a lab site, register a trivial lab shortcode that echoes a static canary token (no data access); inject `[lab-canary]` into a rated comment or Forminator action param and diff rendered page/JSON-LD bytes for the canary. Positive proof = canary text appears in *rendered output sourced from the metadata*, not the raw stored comment. Enumerate third-party shortcode read sinks only against installed lab plugins.
4. **Header-derived identity spoof (Better Messages class):** two lab users; from an anonymous session register a guest with `X-Real-IP: ai-chat-bot-lab`, then attempt join/read on a room whose `only_joined_can_read` is flipped to `1` (so the default-open axis is excluded). Evidence: join verdict + presence-only message visibility in the decision table using synthetic lab messages only.
5. **Pipeline-revalidation greps:** for any plugin with a validate→persist split, read the persist function and list which validations it repeats. A persist leg that consumes stored upload/validation state without re-checking is the Gravity Forms class, regardless of the visibility trigger.

## Reporting checklist

- exact plugin slug, version, form/field configuration state (hidden vs visible, `only_joined_can_read`, comment auto-approval), route/action, and auth context (anonymous vs Contributor);
- for blob dispatch: encrypt-site, decrypt-site, callable-field name, invoking session, and the fixed-version control (allowlist/removed);
- for upload pipelines: field config, validation verdict per leg, persisted path, and file-content proof (marker bytes, never execution);
- for shortcode execution: source field (comment content / action param), approval-gate state, executing render context, and the output channel where canary text surfaced (JSON-LD field, page region);
- for header spoof: header name, stored field written, principal matched, and the short-circuited authorization functions named;
- bounded impact language: shortcode execution ≠ code execution unless a registered shortcode with a dangerous sink is demonstrated; encrypted-blob callable invocation ≠ API-key disclosure until the key actually reflects in lab output.

## October 8 09:31Z follow-up: Bricksforge ≤3.1.8.9 — a public nonce-mint endpoint plus validate-path/write-name divergence = unauth PHP upload (CVE-2026-85097 / [GHSA-jfvp-gc8p-45gp](https://github.com/advisories/GHSA-jfvp-gc8p-45gp), critical)

Unauthenticated RCE chain on one of the larger WordPress builder plugins, and it is a two-key chain where each key is its own durable audit axis:

- **Nonce-minting AJAX endpoints collapse the nonce gate.** The plugin exposes `bricksforge_regenerate_nonce` as an ordinary `wp_ajax_(nopriv?)` action that hands **any anonymous caller a valid nonce**. Every "nonce required" protection on the plugin's other handlers inherits this hole. Hunt rule: before theorizing around a WP nonce, enumerate AJAX actions for *generators* (`regenerate_nonce`, `get_nonce`, `refresh`, `token` shapes in the action-name space) — a nonce is an anti-CSRF capability, not an authorization token, and any endpoint that mints it on request makes the nonce a free parameter for anonymous scripts. Grab the nonce, then attack the upload handler in the same session.
- **Validation target ≠ write target is the upload-boundary escape.** The multipart leg enforces MIME/type validation *correctly* on the uploaded file (GIF content with a polyglot payload passes as GIF). The divergence is in the submitted `temporaryFileUploads` parameter: it carries **both** a server-side path pointing at the validated GIF **and** an attacker-controlled `url` field ending `.php` — the server persists/renames the validated content under the attacker's name, and the temp upload directory executes it. This page's Gravity Forms leg was a validate-leg/persist-leg mismatch by field visibility; this is the same mismatch by **parameter pair**: one field says *what was checked*, the other says *what it becomes*. Sweep rule for any form builder with staged/temp uploads: for every parameter that names a stored file, list every co-submitted field that names a destination path/name/extension and test whether validation is re-applied at the rename/copy step. Proof stays inert: GIF-header marker bytes + a `.php` name that only ever reaches `file_get_contents` of a `phpinfo()`-free marker — never a web shell.
- Report framing: chain the two keys explicitly (nonce source action → handler action → parameter fields → final resolved path + execution proof by benign marker echo), and version-pin; ≤3.1.8.9 is the vulnerable band.

## October 14 03:30Z follow-up: Abandoned Cart Pro ≤10.8.0 — MAC-free CTR with attacker-selected key + optional HMAC = any-cart ATO, and Click to Chat for WhatsApp ≤4.44 — sanitize-before-substitute ordering (Oct 14 WP wave)

Two legs land directly on this page's "protective transformation applied to the wrong side of the boundary" invariant, and the first one is the strongest crypto-misuse ATO this product family has published.

- **Abandoned Cart Pro for WooCommerce ≤10.8.0 authentication bypass via malleable encryption** ([CVE-2026-97657 / GHSA-j8r3-gcq3-h8jj](https://github.com/advisories/GHSA-j8r3-gcq3-h8jj), critical 9.8): cart-recovery tokens are **AES-CTR with no MAC**; the 8-byte CTR nonce travels *inside* the ciphertext blob, and the decryption key is **looked up by the attacker-supplied `user_email` GET parameter**. The HMAC check in `wcap_email_track_links()` runs **only when `wcap_nonce` is non-empty — omit it and the check never fires**. Result: an attacker abandons one cart with their own email, gets one legitimate recovery link, **recovers the keystream from known plaintext, XOR-forge a ciphertext that decrypts to any victim's `abandoned_id`** (IDOR on the decrypted value, no ownership check), and the recovery flow calls `wp_set_auth_cookie()` for the victim user — **full ATO of any user who ever abandoned a cart, admins included**. The auto-login feature defaults ON and is force-enabled on plugin upgrade, so every install is exploitable as shipped. Durable axes: (1) **unauthenticated-CTR keystream recovery is a first-class hunt target** — any token format that embeds its own IV/nonce and decrypts under a key the caller can influence (email, username, tenant slug as key-selector) leaks keystream to anyone with one valid token; grep crypto helpers for key derivation from request parameters and nonce-inside-blob layouts; (2) **conditional integrity checks fail by omission** — the Oct 8 Enswitch absent-parameter battery applies to *crypto* gates: build the decision table {HMAC valid, HMAC wrong, HMAC **absent via omitted companion param**} × {accept, reject}; a check gated on `if ($nonce !== '')` is a check that requests to be skipped; (3) **decrypted value still needs an authorization check** — the page's dispatch-decrypted-blob rule generalizes: decrypt ≠ authenticate, and here the plaintext's subject ID is trusted with zero binding to the key-selected identity. Validation boundary: two disposable accounts on a lab install, forge against your *own* second account's cart only, never real shops.
- **Same product, same wave — second-order SQLi through stored cart meta** ([CVE-2026-97668 / GHSA-xc7m-7p9h-4hfm](https://github.com/advisories/GHSA-xc7m-7p9h-4hfm) 9.8; [CVE-2026-102251 / GHSA-fwwh-fmqj-qv4w](https://github.com/advisories/GHSA-fwwh-fmqj-qv4w) 7.5): the guest cart's `abandoned_cart_info` — populated from checkout fields like the SMS-consent input — passes through `stripslashes()` and is concatenated into an `UPDATE wp_usermeta` while the *adjacent* SELECT/INSERT use prepared statements; the `validate` parameter leg is the same shape wrapped in the forgeable CTR token from the leg above. The UPDATE-on-usermeta sink **writes a `wp_capabilities` row = admin elevation from an unauthenticated checkout field**. Axes: (1) **prepared-statement sibling parity** — when one statement in a function is parameterized and its neighbor concatenates, the neighbor is the bug; read every SQL statement in a handler, not just the one you fuzzed; (2) **`stripslashes()` is not escaping, and stored-field sinks get a second chance** — the payload rides checkout fields → cart meta → later UPDATE; trace stored untrusted values forward to every query that *consumes* them (this page's deferred-detonation cousin); (3) crypto-malleable tokens convert any downstream SQLi into a stealth channel — the token validates structurally while the SQL rides inside.
- **Click to Chat for WhatsApp ≤4.44 arbitrary shortcode execution** ([CVE-2026-92097 / GHSA-4768-hg42-39c5](https://github.com/advisories/GHSA-4768-hg42-39c5), critical 9.1): `greetings_dialog()` builds the `{url}` template placeholder from `sanitize_text_field($_SERVER['REQUEST_URI'])` on archive pages and substitutes it into greeting content that then goes to `do_shortcode()` — but **`wp_kses()` runs against `main_content` BEFORE the `{url}` substitution**, so attacker-controlled URL bytes skip the sanitizer entirely and reach the shortcode executor unfiltered (unauthenticated). This is the WP Recipe Maker ordering rule with a new mechanism: the sanitizer's target and the substituted content are **different strings at different times** — sanitizing the template *before* placeholder fill sanitizes everything except the payload. Sweep rule: for every template/placeholder pipeline (`{url}`, `{name}`, mail-merge style), ask whether filtering happens pre-substitution (broken, attacker bytes survive into the sink) or post-substitution (correct); then test by putting shortcode delimiters `[` `]` in the *URL path*, not the field. Same page's invariant, third mechanism after strip-after-run and callable-in-blob.

## October 15 06:30Z follow-up: 10Web Booster ≤2.34.10 — cron-minted nonce serialized to a world-readable uploads file = unauthenticated arbitrary file upload to RCE (38rr/CVE-2026-108587, critical)

The `compressCustom` function lacks file-type validation and extension filtering on the `page_id` parameter; the only gate is the plugin's REST nonce `tenwebio_rest` — which is **automatically serialized to a world-readable file under `wp-content/uploads/` whenever a bulk optimisation batch pauses**, and because it is generated in a cron/loopback context with **user ID 0, it is valid for unauthenticated visitors**. Grab the leaked nonce → upload an executable file → RCE, no credentials.

- **Nonces minted in background contexts carry the background identity, and "unguessable" is not "unpublished".** Any token generated by cron/loopback/CLI logic inherits user 0 (or a service identity) — check where such tokens get *persisted*: options tables exposed via REST, transients surfaced by ajax handlers, and above all **artifacts written into web-served upload dirs**. Standing recon step for any plugin with a background-processing feature (optimizers, queues, importers): enumerate `wp-content/uploads/` for plugin-written JSON/state files (batch status, job manifests, progress logs) and grep them for nonce/token/secret fields — status files are an afterthought and rarely get the `.htaccess` protection that uploads themselves get.
- **Auth-gate inventory must include alternate nonce sources per endpoint.** Before theorizing around a nonce gate, enumerate every place the same nonce string appears: page HTML, REST discovery, `admin-ajax` responses, and filesystem leaks (this is the Sept 19 Bricksforge `bricksforge_regenerate_nonce` rule extended from endpoint-mint to file-mint). Decision table: nonce absent/own/leaked-file × upload handler accept/reject.
- Validation boundary: lab install, trigger the pause condition locally, prove with a marker upload whose name only reaches a benign read — never a web shell.

## October 16 06:30Z follow-up: My Calendar ≤3.8.7 — shortcode attribute dispatched through call_user_func = unauth arbitrary-function RCE ladder to user-1 takeover, and ELEX HelpDesk ≤3.3.7 — IMAP attachment path skips the upload validator entirely (CVE-2026-104798 / [GHSA-jcj4-jrhq-cjvh](https://github.com/advisories/GHSA-jcj4-jrhq-cjvh), CVE-2026-103768 / [GHSA-cmp5-h7xc-wwx6](https://github.com/advisories/GHSA-cmp5-h7xc-wwx6), both critical)

- **My Calendar**: the public `mcs` GET parameter is reflected into post content **unsanitized before `do_shortcode()` runs** (the page's founding sanitize-after-run ordering rule again), letting an anonymous visitor inject a nested `[my_calendar above=...]` shortcode. The novel leaf is what the *attribute* then does: `mc_generate_calendar_nav()` splits `above` on commas and **dispatches each element via `call_user_func()`** with no auth, authz, or callable allowlist → arbitrary loaded PHP function invocation. The published chain passes the shortcode `$params` array to `edit_user()`, which PHP **coerces to integer `1`** as `$user_id` → overwrite user 1's credentials → full wp-admin. The vulnerable page (`/my-calendar/`) is auto-generated and public on activation — zero-precondition RCE.
  - Durable axes: (1) **shortcode attributes are a function-invocation namespace when any handler forwards them to a callable** — the Sept 19 invariant "the shortcode registry is an internal function namespace" escalates from *executing registered shortcodes* to *executing arbitrary PHP callables*, and the audit grep is `call_user_func`/`call_user_func_array`/`array_map` fed from shortcode `$atts`/`$params`; (2) **PHP type juggling turns loose types into privileged IDs** — array→int coercion equals `1`, and `1` is the admin in WordPress; every handler param that eventually reaches an ID-typed core function deserves a shape battery (string, array, `true`, `"0"`, `"1"`, object); (3) unauth reachability comes from the *plugin's own public artifact* (auto-generated page), so recon = just crawl the default plugin routes. Validation boundary: lab install, dispatch a no-op marker function (e.g., a function that writes a scratch file), never `edit_user` against real users; user-ID-1 targeting proves impact in a lab with a synthetic admin only.
- **ELEX HelpDesk**: unauthenticated arbitrary file upload **via `initMailPart` — the IMAP email-to-ticket ingestion path** has no file-type validation on attachments, so anything emailed to the support address lands as a possibly-executable file → RCE. This is the page's validate-leg/persist-leg mismatch in its purest form: the plugin's ticket-attachment *upload form* may validate, but the *mail-parsing* pipeline persists attachments through a different function that never calls the validator. Sweep rule: for any plugin with an inbound-mail bridge (support tickets, posting-by-email, comment-by-email), enumerate every persist path — HTTP upload handler vs IMAP/POP fetcher vs webhook importer — and diff file-validation per path; the mail leg is the lax one, and its trigger (sending an email) requires no web credential at all. Proof: lab ticket box, inert marker attachment, record landing path + extension; never execute.
