# WordPress shortcode-execution primitives, hidden-field upload bypass, encrypted-blob dispatch, and header-derived bot identity (Sept 19 03:32Z wave)

Source: hourly offensive-security scan of GitHub Security Advisories, 2026-09-19 (wave published 2026-09-19T03:32Z).

One theme ties the durable records: **a protective transformation is applied to the wrong side of the trust boundary.** The PDFCrowd plugin AES-encrypts attacker-influenced option state and later dispatches a callable field out of it; WP Recipe Maker strips shortcodes *after* `do_shortcode()` has already executed them; Gravity Forms validates visible fields but persists rejected files through a hidden-field code path; Better Messages identifies its privileged internal bot by prefix-matching a field the client fills in via `X-Real-IP`.

## Why this is worth an operator page

- **Server-side encryption of attacker-influenced state is not sanitization.** The PDFCrowd blob is only trusted *because the server made it*: a Contributor places a shortcode with `pdf_created_callback=<function>`, the plugin encrypts that into the public page, and the anonymous AJAX endpoint decrypts-and-dispatches. Audit rule: find every decrypt/read-then-act endpoint and check whether **any field inside the envelope reaches a callable, path, URL, or SQL sink** — integrity protection says nothing about field semantics. Same shape as the Sept 18 React Router unsigned-cookie item's mirror image: *signed/encrypted* ≠ *sanitized*.
- **Field visibility settings are validator-skip switches.** Hidden Gravity Forms fields never reach the extension check, yet the persistence pipeline still consumes their upload state. On any form builder or multi-stage pipeline (validate stage ≠ persist stage), enumerate per-field configuration toggles (hidden, disabled, conditional-logic) and test whether the *persist* leg re-validates. Send an inert PHP-marker file with a dangerous extension through a hidden upload field on a lab form and record whether `upload_file()` is reached.
- **`do_shortcode()` is an execution primitive and the shortcode registry is an internal function namespace.** Both recipes (WP Recipe Maker, Forminator) execute untrusted text as shortcodes; WP Recipe Maker adds a **rendered-output disclosure channel** (JSON-LD) that makes the primitive a data-read, not just a nuisance. Bug-hunt sweep: grep plugin code for `do_shortcode(` where the argument can originate from comment content, `$_POST`, or option/user meta; then enumerate the site's registered shortcodes (`rest_shortage`-style discovery or logged-out page fuzz for `[shortcode]` residue) and probe each one for an unauthenticated read/write side effect. Sanitize-vs-execute ordering ("strip after run") is the tell.
- **Privileged internal identities must never be derived from client-controlled fields.** Better Messages' bot check is the request-derived-identity axis (see the Sept 17 kcp `X-Remote-*` and Tina `clientID` pages) applied to an *application-internal service account*: an identity discriminator read from `X-Real-IP`, `X-Forwarded-For`, user-agent, or guest-name fields is spoofable. Sweep: find feature names of the form "AI bot", "system", "internal" in JS bundles/AJAX actions and ask what marks a caller as that principal.

## Validation workflow (authorized scope only)

!!! warning "Lab installs and inert proofs only"
    Use disposable WordPress installs with the vulnerable plugin versions, synthetic users, fake API keys, and inert marker files. Never invoke production callables, read real wp_users rows, upload executable code to a target, or post into real user chat rooms.

1. **Encrypted-blob dispatch (PDFCrowd class):** in a lab install, place the plugin's shortcode as a lab Contributor with `pdf_created_callback` set to a no-op function that writes a marker file or returns a benign value; POST the page-embedded blob to the nopriv AJAX endpoint as an anonymous curl session. Evidence: marker hit / options-array reflection in the response, plus the fixed-version behavior (allowlist or removal of the callable path). Redact the plugin API key if it reflects.
2. **Hidden-field upload matrix (Gravity Forms):** build a lab form with a File Upload field, toggle Visibility visible→hidden. Submit an inert marker file (`.php` name, GIF content) on both variants; record the validation verdict vs whether the file lands in `wp-content/uploads/gravity_forms/`. Evidence is the upload-state decision table + file listing; do not execute the uploaded marker.
3. **Shortcode-execution probe (WP Recipe Maker / Forminator class):** on a lab site, register a trivial lab shortcode that echoes a static canary token (no data access); inject `[lab-canary]` into a rated comment or Forminator action param and diff rendered page/JSON-LD bytes for the canary. Positive proof = canary text appears in *rendered output sourced from the metadata*, not the raw stored comment. Enumerate third-party shortcode read sinks only against installed lab plugins.
4. **Header-derived identity spoof (Better Messages class):** two lab users; from an anonymous session register a guest with `X-Real-IP: ai-chat-bot-lab`, then attempt join/read on a room whose `only_joined_can_read` is flipped to `1` (so the default-open axis is excluded). Evidence: join verdict + presence-only message visibility in the decision table using synthetic lab messages only.
5. **Pipeline-revalidation greps:** for any plugin with a validate→persist split, read the persist function and list which validations it repeats. A persist leg that consumes stored upload/validation state without re-checking is the Gravity Forms class, regardless of the visibility trigger.

## Reporting checklist

- exact plugin slug, version, form/field configuration state (hidden vs visible, `only_joined_can_read`, comment auto-approval), route/action, and auth context (anonymous vs Contributor);
- for blob dispatch: encrypt-site, decrypt-site, callable-field name, invoking session, and the fixed-version control (allowlist/removed);
- for upload pipelines: field config, validation verdict per leg, persisted path, and file-content proof (marker bytes, never execution);
- for shortcode execution: source field (comment content / action param), approval-gate state, executing render context, and the output channel where canary text surfaced (JSON-LD field, page region);
- for header spoof: header name, stored field written, principal matched, and the short-circuited authorization functions named;
- bounded impact language: shortcode execution ≠ code execution unless a registered shortcode with a dangerous sink is demonstrated; encrypted-blob callable invocation ≠ API-key disclosure until the key actually reflects in lab output.
