# Next.js middleware, cache, and render-boundary batch

Source: GitHub Security Advisories REST fallback updated 2026-05-11.

This batch is durable because it shows one framework lesson from several angles: internal routing headers, data routes, Server Component variants, image optimization, WebSocket upgrades, and CSP/script serialization are all trust boundaries when an app is self-hosted or sits behind shared caches.

## Advisories covered

- **Middleware/proxy redirects can be cache-poisoned**, [GHSA-3g8h-86w9-wvmq](https://github.com/advisories/GHSA-3g8h-86w9-wvmq): external `x-nextjs-data` requests could transform redirect handling into non-browser `x-nextjs-redirect` responses that shared caches might store. Affects `next >=12.2.0,<15.5.16` and `>=16.0.0,<16.2.5`.
- **App Router CSP nonce XSS**, [GHSA-ffhc-5mcf-pf4q](https://github.com/advisories/GHSA-ffhc-5mcf-pf4q): malformed request-derived nonce values could be reflected into cached HTML. Affects `next >=13.4.0,<15.5.16` and `>=16.0.0,<16.2.5`.
- **RSC cache-busting collision**, [GHSA-vfv6-92ff-j949](https://github.com/advisories/GHSA-vfv6-92ff-j949): `_rsc` cache-busting collisions could poison shared cache variants. Affects `next >=13.4.6,<15.5.16` and `>=16.0.0,<16.2.5`.
- **`beforeInteractive` script XSS**, [GHSA-gx5p-jg67-6x7h](https://github.com/advisories/GHSA-gx5p-jg67-6x7h): untrusted serialized script content could break out of the intended script context. Affects `next >=13.0.0,<15.5.16` and `>=16.0.0,<16.2.5`.
- **Cache Components connection exhaustion**, [GHSA-mg66-mrh9-m8jx](https://github.com/advisories/GHSA-mg66-mrh9-m8jx): crafted POST requests could deadlock request-body handling and exhaust open connections. Affects `next >=15.0.0,<15.5.16` and `>=16.0.0,<16.2.5`.
- **Image Optimization API local-image OOM**, [GHSA-h64f-5h5j-jqjh](https://github.com/advisories/GHSA-h64f-5h5j-jqjh): self-hosted default image loader could fetch local assets into memory without a maximum size. Affects `next >=10.0.0,<15.5.16` and `>=16.0.0,<16.2.5`.
- **WebSocket upgrade SSRF**, [GHSA-c4j6-fc7j-m34r](https://github.com/advisories/GHSA-c4j6-fc7j-m34r): self-hosted built-in Node.js server could proxy crafted upgrade requests to arbitrary targets. Affects `next >=13.4.13,<15.5.16` and `>=16.0.0,<16.2.5`; Vercel-hosted deployments are reported unaffected.
- **Dynamic route parameter middleware bypass**, [GHSA-492v-c6pp-mqqv](https://github.com/advisories/GHSA-492v-c6pp-mqqv): external parameters could alter the dynamic route value seen by the page while middleware saw the visible path. Affects `next >=15.4.0,<15.5.16` and `>=16.0.0,<16.2.5`.
- **RSC response cache poisoning**, [GHSA-wfc6-r584-vfw7](https://github.com/advisories/GHSA-wfc6-r584-vfw7): shared caches could serve component payload variants from the original URL. Affects `next >=14.2.0,<15.5.16` and `>=16.0.0,<16.2.5`.
- **App Router segment-prefetch middleware bypass**, [GHSA-267c-6grr-h53f](https://github.com/advisories/GHSA-267c-6grr-h53f): `.rsc` and segment-prefetch route variants could miss intended middleware rules. Affects `next >=15.2.0,<15.5.16` and `>=16.0.0,<16.2.5`.
- **Turbopack middleware/proxy incomplete-fix follow-up**, [GHSA-26hh-7cqf-hhc6](https://github.com/advisories/GHSA-26hh-7cqf-hhc6) / CVE-2026-45109: the CVE-2026-44575 fix did not cover `middleware.ts` with Turbopack, so App Router segment-prefetch bypasses still require newer patches. Affects `next >=15.2.0,<15.5.18` and `>=16.0.0,<16.2.6`.
- **Pages Router i18n data-route middleware bypass**, [GHSA-36qx-fr4f-26g5](https://github.com/advisories/GHSA-36qx-fr4f-26g5): locale-less `/_next/data/<buildId>/<page>.json` requests could retrieve protected SSR JSON without the expected middleware check. Affects `next >=12.2.0,<15.5.16` and `>=16.0.0,<16.2.5`.

## Operator triage

1. Upgrade all affected Next.js applications to **15.5.18** or **16.2.6** or later; earlier 15.5.16/16.2.5 builds did not fully cover Turbopack `middleware.ts` for the segment-prefetch bypass.
2. For self-hosted deployments, place explicit deny/allow rules in front of `/_next/data/`, `/_next/image`, `.rsc`, segment-prefetch URLs, WebSocket upgrades, and internal-only Next.js headers.
3. Review CDN and reverse-proxy cache keys. Include `RSC`, `_rsc`, data-route classification, relevant locale, authorization state, and response type, or bypass shared caching for authenticated pages.
4. Audit middleware/proxy authorization assumptions: verify protected content cannot be fetched through JSON data routes, RSC route variants, prefetch paths, or dynamic-route parameter confusion.
5. Set request body, response size, local-image size, header count, and connection-timeout limits at the edge while app upgrades roll out.

## Durable controls

- Treat framework-internal headers as untrusted unless injected by a trusted hop and stripped from the public edge.
- Authorization belongs at the final data/render handler too; middleware is a routing optimization, not the only policy boundary.
- Shared caches must partition on representation and identity, not just URL.
- Server-side WebSocket upgrade paths need the same SSRF canonicalization as normal HTTP fetch/proxy paths.
- Script, CSP nonce, and server-component serialization must escape untrusted values before any cacheable HTML or component payload is produced.

## October 7 20:3xZ follow-up: SSG/ISR cache substitution pair, `use cache` draft-mode fill leak, dev-server MCP endpoint, and Image Optimization allow-listed-host SSRF

New Next.js wave (published 20:30-20:32Z), fixed 16.3.8 (+15.5.27 for the cache legs). Four legs add axes beyond this page's middleware/variant family:

- **Shared response-cache substitution via root catch-all** ([GHSA-mcj8-r9mp-w47p](https://github.com/advisories/GHSA-mcj8-r9mp-w47p) / [CVE-2026-94484](https://nvd.nist.gov/vuln/detail/CVE-2026-94484), 4.8) and **SSG/ISR entry replacement across routes** ([GHSA-4jqv-mc3x-m676](https://github.com/advisories/GHSA-4jqv-mc3x-m676) / [CVE-2026-94543](https://nvd.nist.gov/vuln/detail/CVE-2026-94543), self-hosted Pages Router): a single unauthenticated crafted request makes a *different route's* content serve for a victim page until revalidation, cross-user content substitution plus persistent DoS. Unlike the May `_rsc`/header-variant poisoning legs, these need **no shared front-end cache**: the framework's own on-disk/in-memory SSG-ISR cache is the confusion surface, so Vercel-exempt notices do not protect self-hosters. Probe rule: on self-hosted Next, request a crafted URL against any root-level `catch-all` route and check whether another page's served body changes hash; prove with two marker pages you control and revalidate immediately.
- **`use cache` fill shared across Draft Mode boundary** ([GHSA-3w37-wq28-93x7](https://github.com/advisories/GHSA-3w37-wq28-93x7) / [CVE-2026-94544](https://nvd.nist.gov/vuln/detail/CVE-2026-94544)): pending fills keyed without distinguishing draft vs regular requests, an unauthenticated request overlapping an editor's draft request receives the *unpublished content*, and an on-demand prerender can persist it. Timing-race disclosure of draft content with zero credentials. Rule: any key-value cache-fill that omits a request-attribute dimension (auth state, draft flag, locale, tenant) is a cross-boundary leak once requests overlap, hammer the endpoint concurrently with a draft view open in your own lab CMS and diff bodies for unpublished marker text.
- **`next dev` MCP endpoint trusts any origin** ([GHSA-39w2-rjm5-chcv](https://github.com/advisories/GHSA-39w2-rjm5-chcv) / [CVE-2026-94486](https://nvd.nist.gov/vuln/detail/CVE-2026-94486)): the dev server's Model Context Protocol endpoint does origin-check, so a malicious site the *developer* visits reads project disk paths, error-report source snippets, route inventory, dev logs. Browser-pivoted recon primitive against developer workstations, same desktop-bridge class as the Sept 23 desktop page; for red-team workstation recon, probe `http://localhost:3000` MCP/dev routes from a driven browser before hunting tokens.
- **Image Optimization SSRF via allow-listed remote host** ([GHSA-cjq9-62q9-8jv4](https://github.com/advisories/GHSA-cjq9-62q9-8jv4) / [CVE-2026-94483](https://nvd.nist.gov/vuln/detail/CVE-2026-94483), 6.5): an `images.remotePatterns`-allowed host whose DNS you control sends the optimizer to private IPs. `remotePatterns` allow-lists validate the *hostname pattern*, not the resolved address, check-listed-but-yours DNS is the bypass (pair with the Oct 7 Docling DNS-rebinding leg below and the Sept 20 media page's fetcher rules). Operator checklist on any Next target using remote images: enumerate allowed hosts for ones on registrar- or subdomain-takeover-attainable domains; the optimizer request comes from the server with no auth needed beyond the URL.

## October 22 follow-up: Sentry tunnel-route middleware skip wider than the rewrite, nested `use cache` root-param key omission, and Image Optimization SVG RCE via native dependency

New wave (published 15:50-16:08Z), fixed next 15.5.28/16.4.1 (+16.3.8 for the cache leg). Three legs extend this page's middleware-bypass and cache-key families:

- **Sentry-JS `tunnelRoute` middleware skip is wider than the tunnel rewrite** ([GHSA-mchm-gjx6-7h55](https://github.com/advisories/GHSA-mchm-gjx6-7h55) / [CVE-2026-114139](https://nvd.nist.gov/vuln/detail/CVE-2026-114139), critical, `@sentry/nextjs` <9.47.2/<10.75.2, webpack builds only): the SDK's envelope-route middleware skip applied to **everything under** the tunnel path, while the rewrite only serves the exact tunnel path with `o`/`p` params. Rule: **allow/skip predicates must be proven narrower-or-equal to the handler predicate they exist for**, diff the match-set of every framework `skip`/`matcher`/`bypass` list against the route it's paired with, and treat root-level `[segment]` routes as prefix-collision multipliers for *every* middleware-exempt path convention (tunnel routes, health checks, `_next/*` internals). On engagements with Sentry tunneling configured: request your marker route with the tunnel prefix prepended and compare middleware markers present/absent; webpack vs Turbopack build = fingerprint precondition.
- **Nested `use cache` entry keyed without the inner function's root param** ([GHSA-h694-7cp9-m8p3](https://github.com/advisories/GHSA-h694-7cp9-m8p3) / [CVE-2026-103004](https://nvd.nist.gov/vuln/detail/CVE-2026-103004), `next` <16.3.8, `cacheComponents: true`): an outer cached function calling an inner cached function that reads a root param gets a cache key that **omits that param** when the inner call hits an existing entry, one entry then serves every param value, and shared cache headers redistribute it. Second independent `use cache` key-dimension bug on this page family (Oct 7 draft-fill leg was the first); cross-tenant content read with zero credentials, first-writer-wins value selection. Rule: cached-composition key audit, for any framework with auto-derived cache keys, nest two cached primitives over a routing dimension and compare served bodies per dimension value; *inner-cache-hit timing* changes the outer key, so run sequential and concurrent orders separately.
- **Image Optimization API unauthenticated RCE via SVG → native parser** ([GHSA-2464-fhr4-w9xw](https://github.com/advisories/GHSA-2464-fhr4-w9xw), critical, glibc Linux; fix = `sharp >= 0.35.5` under patched next 15.5.28/16.4.1): the memory bug is in the upstream optimization dependency, but the *reachable surface* is Next's public `/_next/image` endpoint, no auth, accepts remote/uploaded SVG, parses natively. ## October 22 17:1xZ follow-up: unauthenticated RCE in `use cache` functions returning typed arrays, the Server Component transport protocol is the bug ([GHSA-673q-mjm6-r5xr](https://github.com/advisories/GHSA-673q-mjm6-r5xr), critical, `next` >=16.0.0 <=16.4.0, fixed 16.4.1)

Third independent `use cache` bug on this page family (Oct 7 draft-fill key leak, Oct 22 nested-key omission, now this one), and the first with RCE impact. Vendor conditions: App Router with Cache Components and at least one `use cache` function that **returns multiple typed arrays**; no known workaround, and the vendor explicitly says to upgrade even if you believe you have no such function.

The fix commit ([a4cea6ae](https://github.com/vercel/next.js/commit/a4cea6aec5da89d116b8960e113189cf51745d2f), "Improve Server Component transport protocol") rewrites the react-server-dom Flight/Form-Data wire format: stream parts move from `formFieldPrefix + streamId` to a separate `formFieldPrefix + "S" + streamId` **prefix namespace** (blob ids and stream ids previously shared one numeric namespace), and every typed array gets a defensive copy/`slice()` of its underlying buffer before being appended as a Blob (view offset/length/resizable-buffer shapes handled separately). Read that diff as the bug report: a cache entry containing multiple typed arrays serialized with colliding or aliased field/backing-store references, and the cache read path (attacker-reachable: hitting a page populates and serves cache entries without credentials) deserializes the flight payload back through the same naming scheme, a serialization round-trip collision in a custom wire format for exotic types, escalated across the cache boundary.

Operator rules:

- **Custom-serialization framework transports are a standing attack surface.** Any framework that serializes return values through a bespoke typed-value protocol (RSC flight, `Next-Action` form parts, cache payloads, RPC bridges) should be probed with exotic-type shapes the app never intends to cache: `ArrayBuffer`/`Uint8Array` returns, multiple binary parts, stream+value mixes. The bug class is id/field collision between part kinds, not injection into one field.
- **Fingerprint the precondition from outside, cheaply:** presence of `Next-Action`/`RSC` headers, `cacheComponents`/`use cache` markers in bundles, and `_next/image`-style internal cache routes tells you the surface is live before spending time. Treat "no known workaround, upgrade regardless" language from a vendor as a prevalence signal.
- **Validation boundary: passive only on third-party targets.** Prove on your own lab app with a `use cache` function returning two typed arrays and compare served cache payloads pre/post 16.4.1; do not attempt the RCE leg against any target you don't own.
- Same-product re-sweep rule again: three `use cache` bugs in 15 days, when one cache-key/serialization bug is published for a framework feature, re-audit every other dimension of that feature the same week.

## November 16 follow-up: `unstable_cache()` joins the in-flight `use cache` fill during cold start, root-param check skipped, entry stored keyless on the param (GHSA-mfr8-8qww-v76h / CVE-2026-119790, medium, `next` >= 16.3.0 <= 16.4.4, fixed 16.4.5)

Fourth independent `use cache` bug on this page family (Oct 7 draft-fill leak, Oct 22 nested-key omission, Oct 22 typed-array RCE, now this one), and the first gated on **process lifecycle** rather than request shape alone. Mechanism: when the same `'use cache'` function that reads a root param is called both directly during rendering and through `unstable_cache()`, the nesting normally throws (`'use cache' inside unstable_cache() is unsupported`). But during a **cold process start**, a cross-request deduplication race lets the `unstable_cache()` call *join the in-flight fill* of a concurrent direct call and receive its result, bypassing the reject-the-nesting check entirely. `unstable_cache()` then stores that result under a cache key **without root params**, so every subsequent request for other root param values (locale, tenant, theme, anything the root layout scopes) receives the same entry until revalidation or eviction. Exploitation requires the `unstable_cache()` request to land while the function's first post-start fill is still in flight.

Operator rules:

- **Cold start is an attack state.** Deduplication/single-flight/join-the-in-flight-fill machinery is only exercised on the first request after a process start, and the guards that reject unsupported combinations often sit on the *entry path*, not on the deduplication join path. For any framework or app with request coalescing, restart-condition is a scheduling variable: bounce or wait for a scale-up/scale-down event, then fire the race pair (direct call + wrapper call) concurrently. The probe battery for cache-key dimensions should always run both warm (steady state) and immediately post-restart.
- **"This combination throws" is not a precondition, it's a fingerprint.** A guard that rejects a call shape under sequential conditions still describes the exact code path an adversary wants; race the join before theorizing the gate is impassable. Same rule lineage as the absent-param branch (Oct 5 Joomla) and the reachable-despite-disabled-flag legs: enumerate what the *guard rejects*, then find a second route to the same sink.
- **Cross-root-param read with zero credentials** whenever a target mixes `use cache` functions reading root params with any `unstable_cache()` usage; the value is first-writer-wins, so the locale-A visitor's cached payload serves locale B. Passive proof on third-party targets: alternate root-param values (e.g. `/en/...` vs `/fr/...` on the same route) immediately after an observed cold start, diff bodies for another param value's marker content. Active race proof only on your own lab app with two locales and a marker in each cached payload.
- Same-product re-sweep rule keeps paying: four `use cache` bugs since Oct 7. The feature-level audit for Next targets is now a standing checklist (draft-vs-regular fill keying, nested-call keying, typed-array transport, cold-start dedup keying), re-run the whole battery on every minor bump, not just the advertised fix.

Tracked same-wave without publication: Astro unescaped `<script>/<style>` content in JSX/MDX rendering ([GHSA-98hj-9722-w3j8](https://github.com/advisories/GHSA-98hj-9722-w3j8) / CVE-2026-114128, known rawtext-escape-skip class) + View Transitions CSS injection ([GHSA-mpr7-6m5w-76rw](https://github.com/advisories/GHSA-mpr7-6m5w-76rw) / CVE-2026-114127); Electron six-leg pack (SameSite on link-opened windows, permission attribution to wrong frame/origin, GPU-supplied frame geometry trust, extension `tabs.query` no-permission read); fastify case-sensitive `propertyNames` header-validation bypass ([GHSA-389g-gv7q-r4x8](https://github.com/advisories/GHSA-389g-gv7q-r4x8) / CVE-2026-107832, known case-variant class); GraphQL-core comment-token `max_tokens` bypass + quadratic `OverlappingFieldsCanBeMerged` DoS (parser-budget legs, availability-only); toml-node prototype pollution + three quadratic DoS legs; pypdf three parse-amplification DoS legs; Pillow bundled `libopenjp2` re-listing (the bundled-native-lib-is-the-fingerprint rule is already on the Sept 20 media page).

## November 17 follow-up: the h694 fix missed the early-stream leg, nested use cache entries get keyed without the root param again ([GHSA-vc7v-qv4w-wrv8](https://github.com/advisories/GHSA-vc7v-qv4w-wrv8) / CVE-2026-119351, medium, `next` >= 16.2.0 <= 16.4.4, fixed 16.4.5)

Fifth independent `use cache` bug on this page family (Oct 7 draft-fill leak, Oct 22 nested-key omission, Oct 22 typed-array RCE, Nov 16 cold-start dedup join, now this one), and an explicit **incomplete-fix twin**: the vendor says this is a variant of [GHSA-h694-7cp9-m8p3](https://github.com/advisories/GHSA-h694-7cp9-m8p3) (the Oct 22 nested-key leg) that the fix for that advisory does not cover, because it requires **neither** the inner call to hit an existing entry **nor** a slow cache handler.

Mechanism, with Cache Components enabled: an outer `'use cache'` function calls an inner `'use cache'` function that reads a root param via `next/root-params` and returns a value **still containing pending promises** (an object with one field ready immediately and a slower field unresolved). React Flight delivers the ready portion to the outer function *before* the inner entry has finished publishing its root-param dependencies. The outer function finishes and its entry is persisted under a key that omits that root param. The entry is written once and served for **all** root param values, so a response for one param value serves content produced for another. Entries written this way also **ignore tag invalidation and cache lifetimes** of the nested caches they consumed. Which value leaks is not attacker-controlled; it is first-writer-wins, same as every other leg in this family.

Operator rules:

- **A published fix closes the observable trace, not the trigger class.** The h694 remediation eliminated the known paths (inner cache hit, slow handler) while the underlying condition, outer key computed before inner dependencies settle, stayed reachable through partial/staggered delivery. After any framework cache fix, re-run the full key-dimension battery (sequential, concurrent, cold-start, and now mixed-latency-shape payloads); retesting only the published PoC will report the bug dead.
- **Async partial delivery is a key-poisoning window.** Wherever a cache composition consumes results from a transport that can deliver *part* of a result early (streamed serialization, promises, lazy hydration, chunked RPC), the outer key can be computed from incomplete dependency metadata. The probe shape is trivial and generic: make the cached function return one fast field plus one slow field (`{ quick: marker, slow: await delay(...) }`), invoke it nested one level deep, then alternate root-param values (`/en/` vs `/fr/` on the same route) and diff served bodies for the other param value's marker. Passive-safe on third-party targets.
- **Invalidation-skip is its own observable.** If a poisoned entry survives tag invalidation or lifetime expiry of the nested entry it consumed, staleness becomes the oracle that proves the entry bypassed normal bookkeeping; hammer the invalidation path (revalidateTag-style) and check whether the wrong-param content persists. On a bounty target, persistent cross-param content after forced revalidation is the report-quality evidence.
- Same-product re-sweep rule now at five legs in six weeks. Treat "framework feature with auto-derived cache keys" as a standing audit: draft-vs-regular fill keying, nested-call keying, typed-array transport, cold-start dedup keying, and mixed-latency nested delivery, re-run on every minor bump.
- Validation boundary: proof on your own lab app with two root-param locales and a marker in each cached payload; on third-party targets stay passive (header/body diffing of alternate param values, no entry poisoning attempts).

## November 19 22:1xZ follow-up: the fallback shell treats a request-supplied path segment as its own unfilled placeholder, one GET poisons the whole route family ([GHSA-vvgp-ww4w-46vf](https://github.com/advisories/GHSA-vvgp-ww4w-46vf) / CVE-2026-119350, medium, `next` <= 16.4.4, fixed 16.4.5)

Sixth independent `use cache`/Cache Components leg on this page family in six weeks (Oct 7 draft-fill leak, Oct 22 nested-key omission, Oct 22 typed-array RCE, Nov 16 cold-start dedup join, Nov 17 early-stream keying, now this one), and the first where **the attacker supplies the placeholder token itself**. Mechanism: apps served with `next start`, built with `cacheComponents: true` but `partialPrefetching` unset/false, keep never-prerenderable params as placeholders inside a shared blocking fallback shell, so every value of those params shares one cache entry. A request whose path segment equals the percent-encoded bracketed name of its own route param (e.g. `/%5Bparam%5D`) is treated as an *unresolved placeholder*: only that param is deferred, and a layout above it renders its concrete value into the shell during the blocking render. The result, including HTTP status, is stored under the shared key. Two outcomes: the layout calls `notFound()` and the entry becomes a **persistent 404 served to every URL under the shell key with `revalidate: false`, surviving server restarts, with no error logged**; or the layout renders the value and every visitor's server-rendered HTML shows the attacker's param value in place of their own (client hydration corrects it; no script injection, no data disclosure). Preconditions: dynamic route with `generateStaticParams` where the requested value was not built, at least two never-prerenderable params below it (a layout reading the shallower one inside Suspense, the deeper one supplied as the placeholder), blocking fallback shell.

Operator rules:

- **Placeholder syntax is attack surface.** Any cache/renderer that represents unfilled slots with a predictable textual token must be probed for request-supplied placeholder injection: fire the bracketed param name, percent-encoded and raw (`/[param]`, `/%5Bparam%5D`, mixed case, double-encoded), at every dynamic segment you find. If the router resolves user input *as* a placeholder marker, you have converted a read into a shared-key write.
- **Persistent-404-with-no-log is a stealth state, and a reportable one.** A one-GET, unauthenticated poison that pins a route family to 404 across restarts, survives revalidation (`revalidate: false`), and logs nothing, is availability impact with an integrity root cause. Probe on your own lab app first (marker value that triggers `notFound()` in the layout); on third-party targets, the passive check is requesting the bracketed-encoded param name and diffing status/body stability against a normal value, no poisoning attempts.
- **Attribution-substitution beats 404 for proof quality.** When the layout renders rather than rejects, the substitution is visible in first bytes before hydration corrects it, so capture with `curl` (no JS), not a browser. The screenshot-after-hydration test will show the correct value and bury the bug.
- Same-product re-sweep rule now at six legs since Oct 7. The Cache Components standing audit is: draft-vs-regular fill keying, nested-call keying, typed-array transport, cold-start dedup keying, mixed-latency nested delivery, and placeholder-token injection; re-run the whole battery on every minor bump, and check `partialPrefetching` config state as the first fingerprint (its absence is the precondition gate).

## November 19 23:1xZ follow-up: same-evening quartet, use-cache binary-argument key collision, Edge-runtime cookie duplication in the public response, self-hosted upstream-response framing desync, and image-optimizer SVG rejection bypass ([GHSA-rhh4-g77r-rqx2](https://github.com/advisories/GHSA-rhh4-g77r-rqx2) / CVE-2026-119349, [GHSA-f3mh-rxg3-f5g2](https://github.com/advisories/GHSA-f3mh-rxg3-f5g2) / CVE-2026-119346, [GHSA-pc58-hwjq-p385](https://github.com/advisories/GHSA-pc58-hwjq-p385) / CVE-2026-119348, [GHSA-7qx7-33qx-rqx2](https://github.com/advisories/GHSA-7qx7-33qx-rqx2) / CVE-2026-119347, all medium, `next` fixed 16.4.5 / 15.5.29)
