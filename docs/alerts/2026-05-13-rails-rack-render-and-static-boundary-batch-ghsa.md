# Rails, Rack, render, and static-boundary batch

Source: GitHub Security Advisories updated 2026-05-13.

This batch is durable because framework helper APIs are easy to treat as inherently safe. The advisories show that escaping, formatting, debug output, byte-range handling, and static-file path matching all need their own trust-boundary tests.

## Advisories covered

- **Active Support `SafeBuffer#%` XSS**, [GHSA-89vf-4333-qx8v](https://github.com/advisories/GHSA-89vf-4333-qx8v): formatted strings could cross an HTML-safety boundary in `activesupport` before `7.2.3.1`, `8.0.4.1`, and `8.1.2.1`.
- **Active Support `number_to_delimited` ReDoS**, [GHSA-cg4j-q9v8-6v38](https://github.com/advisories/GHSA-cg4j-q9v8-6v38): delimiter formatting could consume excessive CPU on crafted input. Patch `activesupport` to the fixed Rails release line.
- **Action View tag-helper XSS**, [GHSA-v55j-83pf-r9cq](https://github.com/advisories/GHSA-v55j-83pf-r9cq): Rails tag helpers could produce unsafe output in affected `actionview` versions before the fixed Rails release lines.
- **Action Pack debug-exception XSS**, [GHSA-pgm4-439c-5jp6](https://github.com/advisories/GHSA-pgm4-439c-5jp6): debug exception rendering could become scriptable in `actionpack 8.1.0` through `<8.1.2.1`.
- **Decidim user-name XSS**, [GHSA-fc46-r95f-hq7g](https://github.com/advisories/GHSA-fc46-r95f-hq7g): attacker-controlled user names could become stored XSS in `decidim-core` before `0.30.5` and in `0.31.0.rc1`.
- **Rack multipart byte-range DoS**, [GHSA-x8cg-fq8g-mxfx](https://github.com/advisories/GHSA-x8cg-fq8g-mxfx): excessive overlapping ranges could exhaust request-processing resources. Patch Rack to `2.2.23`, `3.1.21`, or `3.2.6`.
- **Rack::Static `header_rules` bypass**, [GHSA-q4qf-9j86-f5mh](https://github.com/advisories/GHSA-q4qf-9j86-f5mh): URL-encoded paths could bypass header rules before the fixed Rack releases.
- **Rack::Static prefix exposure**, [GHSA-h2jq-g4cq-5ppq](https://github.com/advisories/GHSA-h2jq-g4cq-5ppq): prefix matching could expose unintended files under the static root before the fixed Rack releases.

## Operator triage

1. Patch Rails/Rack stacks first when they expose user profile names, debug pages, static-file roots, or large file downloads.
2. Confirm production disables debug exception rendering and that staging debug hosts are not internet-accessible.
3. Search access logs for overlapping `Range` headers, URL-encoded static paths, unusually long numeric delimiters, and stored profile-name payloads.
4. Add regression tests that render representative untrusted strings through helper APIs rather than only testing direct template interpolation.

## Durable controls

- Treat “safe string” helpers as context-sensitive encoders, not blanket declassification of user input.
- Put length, count, and overlap budgets on `Range` handling before framework multipart helpers allocate work.
- Canonicalize URL paths once before static-file allow/deny/header-rule decisions; do not mix decoded and raw prefix checks.
- Keep debug renderers behind auth, network policy, and production-off switches because they often combine stack metadata with HTML output.

## November 11 follow-up: Rails 8.1 batch, representation-variant cache poisoning, session resurrection, and serializer round-trip trust

The Rails November 10-11 security releases (published 21:14-21:34Z alongside the Rack header legs already covered on the Sept 15 parser page) add six more framework trust-boundary legs worth keeping as bug-hunt checks:

- **Vary-omission cache poisoning**, [GHSA-r9jg-fmfx-2gv6 / CVE-2026-126073](https://github.com/advisories/GHSA-r9jg-fmfx-2gv6): format negotiation reads `Accept`, `X-Requested-With`, and (for XHR without `Accept`) `Content-Type`, but `Vary: Accept` was only added when the request carried a usable `Accept` header and no prior `Vary`. A shared cache that honours `Vary` (Thruster, `Rack::Cache`, CDNs) can store a no-`Accept`/XHR variant and serve it to later clients, visitors get layout-stripped HTML in place of JSON (or vice versa) until expiry. **Bug-hunt shape:** behind a Vary-honouring cache, request the same public action with `{no Accept}`, `X-Requested-With: XMLHttpRequest` with no `Accept`, and an app-set `Vary: Accept-Language` (which blocked the append), then re-request as a normal browser and compare representations. Precondition to check first: actions rendered `public`/`expires_in` (`cache-control` headers on the response are the tell). Attacker can't choose content, so price it as representation-confusion/defacement-adjacent, not full poisoning.
- **Session resurrection on CacheStore logout**, [GHSA-2586-8ghr-69fj / CVE-2026-126076](https://github.com/advisories/GHSA-2586-8ghr-69fj): `ActionDispatch::Session::CacheStore` wrote the session back at end-of-request without checking the entry still exists, so a slow request finishing after a concurrent `reset_session`/server-side delete **restores the destroyed session under its original ID**, stolen cookies survive logout and server-side revocation. Fix records loaded-session identity and skips the write (one extra cache read per writeback = the fingerprint of patched builds). **Lifecycle probe for any session backend:** issue a long-running request holding the session, log out mid-flight, then finish the slow request and replay the old cookie. CookieStore unaffected; Dalli ≥4.0.0 unaffected, backend/version parity is the predicate.
- **Unauthenticated Action Cable → attacker-chosen regex**, [GHSA-8474-xrp6-wh69 / CVE-2026-126080](https://github.com/advisories/GHSA-8474-xrp6-wh69): `safe_constantize` built a `Regexp` from the requested constant name on `LoadError`; Action Cable passes the `channel` value of every `subscribe` command to `safe_constantize` **before any authentication**, a default-mounted unauthenticated `/cable` endpoint reaches Ruby's regex compiler with attacker bytes. "Safe" nil-vs-raise wrappers that internally compile regexes from names are the audit target; grep app/framework code for `Regexp.new`/`=~` fed by constant/error strings. Proof: unauthenticated WS `subscribe` with regex-metachar channel names against a lab `/cable`, watching worker CPU/crash only.
- **MessagePack round-trip resurrects `html_safe?`**, [GHSA-2w9f-fxwj-w2qf / CVE-2026-126075](https://github.com/advisories/GHSA-2w9f-fxwj-w2qf): `ActiveSupport::MessagePack` serialized `SafeBuffer` as bare bytes and restored it as `SafeBuffer`, so a buffer made unsafe by in-place `gsub!` came back `html_safe`, auto-escaping bypass after a cookie/cache round-trip (Rails 8.1 `:message_pack`/`:message_pack_allow_marshal` serializers). Hunter angle: if the app serializes user-influenced strings through MessagePack cookies/cache, the deserialized value renders raw, try mutating-in-place paths and watch for unescaped reflection. Rolling-deploy incompatibility (old builds can't read fixed-format payloads) doubles as a version fingerprint. HackerOne researcher report, bounty-visible sink class.
- **GCS direct-upload length unbinding**, [GHSA-hfr4-8rjc-97m2 / CVE-2026-126085](https://github.com/advisories/GHSA-hfr4-8rjc-97m2): `GCSService#url_for_direct_upload` never bound declared `byte_size` into the signed URL (the exact weakness CVE-2020-8162 fixed for S3 years earlier), upload larger than declared, stored blob keeps the *declared* size, defeating app-side size validations and quotas. **Service-parity rule: when a framework fixed a signed-URL constraint for one storage backend, immediately test every sibling backend (GCS, Azure, S3-compatible, disk-proxy) for the missing header** (`x-goog-content-length-range` absent in the pre-fix `headers_for_direct_upload` response is the external tell). Pair with the Sept 20 media-page analyzer chain, oversized uploads then hit ffmpeg/ImageMagick.
- **NUL-byte filename persistent DoS (DB-dialect differential)**, [GHSA-p2pm-g2h6-7j5j / CVE-2026-126074](https://github.com/advisories/GHSA-p2pm-g2h6-7j5j): Active Storage passes stored filenames unmodified to `File.basename`/`File.extname`, which raise on NUL, persists on SQLite/MySQL/MariaDB (they accept NUL in string columns), so every later variant/preview render raises. **PostgreSQL rejects the row = the dialect decides exploitability.** Same rule class as the DB-behind-feature findings on the Sept 18 ORM page: reproduce input-validation bugs per dialect, and treat "who can upload" as the precondition; proof = disposable upload + request the variants route, purge after.

Cross-cutting: five of six legs carry HackerOne researcher credits, this batch is an active Rails bounty surface, and the precondition gates (session store choice, serializer config, storage service, cache backend, public caching headers) are enumerable from config leakage and response headers before any attack attempt.
