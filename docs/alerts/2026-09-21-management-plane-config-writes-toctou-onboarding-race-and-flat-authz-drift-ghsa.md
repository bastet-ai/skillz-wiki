## Why it matters for operators

1. **Setup/onboarding endpoints are a standing recon question.** "Has this product been initialized yet?" is remotely answerable (`GET /api/users/onboarding/status` was also anonymous here) and, when the finish handler is TOCTOU-raced, is a first-contact admin-creation primitive. Fingerprint version, probe the status endpoint, then fire N parallel finish requests with distinct payloads; multiple 200s + distinct JWTs is the proof. This is the Keycloak flow-restart and CuteNews media-panel precedent generalized: **the bootstrap affordance is part of the security model.**
2. **Generated-config injection is its own class.** Octavia's rule: when a control-plane API renders user fields into HAProxy/nginx/systemd/iptables files, (a) fuzz every string field for CR/LF and directive-shaped content, (b) find fields where the validator normalizes (percent-encodes, trims, rewrites) but storage keeps the raw value — that delta is the injection, (c) don't stop after one field: the `tls_ciphers` sibling shipped alongside the `redirect_url` fix target unpatched-in-spirit because nobody enumerated the sink's input set.
3. **Remote config-set APIs are RCE with a delay.** ZLMediaKit's two-endpoint chain (write `ffmpeg.snap` → invoke `getSnap`) shows why "it only changes settings" is the wrong severity frame: sweep every `set*Config`/`updateOption`/`saveSettings` route on media servers, proxies, and panel software, and diff which parameters later reach shell, file, or path sinks. Grep the source for parameter consumers, not just the setter's auth check.
4. **Session invalidation is a per-transport property.** The Airflow logout-revokes-only-`_token` finding (same day, sibling page) and x-ui's signed-cookie panel are the same audit question asked of each credential transport: after password change / logout / role strip, **replay the old credential on every transport** (cookie, bearer, API key, gRPC metadata) and record which ones survive. A signed-but-self-contained cookie with no server-side session version can never be revoked by design.
5. **Low-role users who can edit config templates control exposure.** Any panel field that lands in a generated listen/bind/restart path lets an untrusted role move services onto public interfaces. When enumerating a management panel, diff what *each* role can change in settings, then restart/reload and re-scan listening sockets from an external vantage.
6. **One shared service layer = one authz drift per endpoint, by default.** The jshERP cluster is the clearest single-product exemplar of the route-family authz sweep we keep citing: enumerate the CRUD family, then for each verb test (a) privilege to perform the action, (b) ownership of the target object, (c) tenant scope, (d) what the *response* returns. A generic `updateOneValueByKeyIdAndType` that dispatches on a caller-supplied `type` is remote state-dispatch — every accepted `type` value inherits every missing check.

## Replayable validation boundaries (authorized labs / owned instances only)

1. Race proof: lab instance reset to pre-onboarding state; fire ≤10 parallel finish requests with distinct synthetic users; record status codes + returned JWTs; delete created users immediately. On production: dispatch/evidence only (status endpoint + 403-vs-200 verdict) — never create accounts.
2. Config-injection proof: private OpenStack lab project only; inject a **comment-line** marker (`# canary`) rather than an active directive, then read the rendered HAProxy config from the amphora (approved lab access) to prove the raw byte survived the validator→sink leg. Never inject working directives on a shared proxy.
3. Config-write proof: disposable ZLMediaKit in a container; set `ffmpeg.snap` to a marker command that writes a temp file, invoke `getSnap`, observe the file, remove config. Never against reachable streaming infrastructure.
4. Cookie-replay proof: your own lab admin account; capture the session cookie, rotate the password from a second session, replay the old cookie; record survival. Never hold a real user's cookie across rotation.
5. jshERP-class sweep: two lab tenants × two role tiers; canary rows per tenant; for each endpoint run the four-question matrix (privilege/ownership/tenant/response-content). Password-hash disclosure proof stops at "field present, value redacted in report" — never crack or replay real digests.

## September 23 follow-up: ManageEngine OpManager/NCM five-GHSA ladder — config-generation SSTI, import-path privesc, and device-scope drift

- **ManageEngine OpManager / NetFlow Analyzer / NCM / Firewall Analyzer** shipped five high-severity GHSAs across two version windows (≤12.8.671 and ≤12.8.710): **SSTI → RCE in Configlet processing** ([CVE-2026-12370 / GHSA-rxm6-4vc4-h8j2](https://github.com/advisories/GHSA-rxm6-4vc4-h8j2)), **unauthorized path traversal** in OpManager+NCM (CVE-2026-15358 / [GHSA-gjx4-2qj7-4q8h](https://github.com/advisories/GHSA-gjx4-2qj7-4q8h)), **SQLi in Rule Management Search Reports** (CVE-2026-14913 / [GHSA-prpv-x87v-q3xv](https://github.com/advisories/GHSA-prpv-x87v-q3xv)), **privilege escalation to Administrator via Report Profile import** (CVE-2026-84787 / [GHSA-x45x-ww3c-35pv](https://github.com/advisories/GHSA-x45x-ww3c-35pv)), and **low-privilege users creating alert notifications / modifying report schedules for firewalls outside their assigned scope** (CVE-2026-84789/84791).
- Durable axes for management-plane audits:
  1. **Config-generation templates are SSTI sinks.** Configlets (network-device config snippets) are templated from user-editable fields on an NCM platform — user-controlled template material rendered by a server-side template engine = template injection → RCE on the appliance that holds CLI credentials for every managed switch/firewall. Audit rule: on any network-management/automation platform, every "custom template / config snippet / report template / script field" feature is an SSTI candidate; the sink runs with the appliance's fleet-wide device credentials, so severity = fleet takeover.
  2. **Import features bypass the export-side authz model.** Report Profile *import* reaching Administrator while ordinary paths don't is the import/export asymmetry (this wiki's import-gated/export-open ScadaBR mirror, OpenXML/Report Profile families): sweep import endpoints of any role-relevant object type at the lowest authenticated role.
  3. **"Outside assigned scope" is the appliance tenant check that's missing.** Alert-notification and report-schedule writes for devices the requester doesn't manage = the by-id CRUD matrix (jshERP four-question rule) applied to device scope: run every create/modify verb with foreign device/device-group IDs as a low-privilege lab user.
- Validation boundary: lab OpManager instance, synthetic devices/discovered rows, canary template expressions that resolve a marker (not device CLI execution); never push configlets to real gear.

## October 5 follow-up: Camunda setup-availability predicate computed over the wrong population (CVE-2026-77226)

[GHSA-mx4r-g275-wg5r](https://github.com/advisories/GHSA-mx4r-g275-wg5r) / CVE-2026-77226 (critical): Camunda 7.24.0 before 7.24.15 — the Admin webapp's first-run `SetupResource` decides whether setup is still available by **counting only direct members of the `camunda-admin` group**, not all configured administrators. On an instance that is fully administered through any other path (authorizations granted without group membership, alternate admin groups, LDAP-mapped admins), the group is empty, so the bootstrap endpoint stays open: an **unauthenticated** remote attacker calls the setup `user-create` endpoint and mints a new administrator — full account takeover, then process deployment with script tasks executing as the engine's service user (the admin→RCE leg the page's own ZLMediaKit ladder already documents).

- **Durable rule: "is it initialized?" and "who is an admin?" must be answered from the same population, and they routinely are not.** A bootstrap affordance gated on one narrow membership table keeps working forever on instances administered by any alternate mechanism. This is the generalized twin of the nginx-ignition TOCTOU above: there the gate raced; here the gate is permanently mis-evaluated on live production systems.
- **Operator probe:** on any Camunda/Workflow engine (or any product with a first-run wizard), request the setup-status and setup-user-create routes even when the login page looks fully configured. A 200/error-shape decision table on `/api/admin/setup/*`-family routes distinguishes "bootstrap closed" from "bootstrap still armed because my admins live elsewhere." Positive proof = create a synthetic admin, verify its auth token, delete it; never deploy real processes.
- Generalizes to every product family with a setup/init/onboarding endpoint: enumerate how availability is *computed* (which table, which group, which flag), not just whether a check exists.

## October 7 follow-up: Foreman restricted-sudo rake tasks as command-injection surface + FlexNet lmadmin hardcoded SOAP auth bypass (Red Hat enrichment, updated feed 2026-10-07 09:33Z)

The Red Hat enrichment wave that landed the Oct 2 Foreman legs returned with four *new* Foreman CLI/rake legs plus a license-management-plane bypass — all management-plane code-execution inputs outside the web app.

- **Restricted sudo to `foreman-rake` is an injection grant, not a read-only grant.** Three legs (all published Oct 1, enriched Oct 7): `foreman-rake errors:fetch_log` passes `request_id` into a shell-backed `grep` unquoted ([CVE-2026-12540 / GHSA-c5q9-9fc7-jgxp](https://github.com/advisories/GHSA-c5q9-9fc7-jgxp), 8.2 — inject `;`, `"`, `|`); `foreman-rake db:dump` / `db:import_dump` pass the `destination`/`file` parameters into a Ruby `system()` call ([CVE-2026-12541 / GHSA-rcq3-9wpf-p347](https://github.com/advisories/GHSA-rcq3-9wpf-p347), 8.2 — append commands to the file path); `foreman-tail` `eval`s user arguments to expand file paths ([CVE-2026-12542 / GHSA-79jg-9wx4-f5rr](https://github.com/advisories/GHSA-79jg-9wx4-f5rr), 5.3). The advisory text itself says the attacker profile is "an attacker with permissions to execute foreman-rake (e.g., via a restricted sudo configuration)". Durable rule: on any host where `sudo -l` names a framework CLI/rake runner, **every task that takes a path, id, or filename parameter is a command-injection candidate** — Ruby `system("grep #{x}")` and path-to-`eval` shapes are the two spellings to check per allowed task; argv-safe `system(*argv)` is the exception, not the default. Sweep: enumerate allowed rake verbs, fuzz each free parameter with `; touch /tmp/marker`, `"; "`, and pipe metacharacters on an authorized host.
- **Config parsed through two executable layers at init = boot-time RCE / supply-chain persistence.** `foreman-rake` initialization processes configuration data through **two distinct executable layers** in `/usr/share/foreman/config/settings.rb`, giving an SSTI + insecure-deserialization chain reachable from config content ([CVE-2026-12544 / GHSA-q8r6-95rf-344m](https://github.com/advisories/GHSA-q8r6-95rf-344m), 7.7, framed by Red Hat as supply-chain risk). Durable axis: **anything a config file can say, code runs at next boot** — if a lower-privilege role, installer, or API can write any part of a framework's settings file, that's deferred code execution as the service user, surviving app upgrades that don't touch config. Post-exploitation persistence check on any Foreman/Satellite-class host: find config files writable below root, plant an inert marker in the templated/deserialized field, observe execution on restart (lab hosts only; never restart a production provisioning server).
- **FlexNet Publisher `lmadmin` hardcoded authentication bypass in a SOAP handler → unauthenticated privileged admin session** ([CVE-2026-19572 / GHSA-98jh-cm22-cgp2](https://github.com/advisories/GHSA-98jh-cm22-cgp2), critical, vendor: Revenera). License servers are chronically forgotten perimeter assets: lmadmin listens in the 27000–27010 band, is routinely firewall-allowed for vendor license traffic, and its admin console holds full software-inventory data (who runs what, seat counts — recon-grade) plus the license-file write path. Hardcoded-bypass family twin of the Sept 19 `insecure=cool` rule, server-side this time: when a product ships a magic bypass, every unpatched deployment is permanently unauthenticated on that handler — fingerprint the version band, don't test the bypass against production license servers (a corrupt license file is an availability incident for the whole estate); proof is route-level auth gating plus version banner.
- Validation boundary: authorized Foreman/Satellite hosts only; marker-file proofs for the sudo-injection legs (no data exfil from backup/DB dump tasks); lab lmadmin instance for the bypass shape, version/route evidence on real license servers.
