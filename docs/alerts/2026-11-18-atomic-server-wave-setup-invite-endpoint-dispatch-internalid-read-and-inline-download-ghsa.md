# Atomic Server wave (4 GHSAs): unclaimed setup invite hands the whole Drive to the first caller

Source: GitHub Security Advisories published 2026-11-18T20:41-20:42Z for [joepmeneer/atomic-server](https://github.com/atomicserver/atomic-server) (unreviewed, GHSA version fields empty; fixes are on `develop`, no release cut at scan time). All four advisories ship source traces and working PoCs against a stock Docker deployment (`joepmeneer/atomic-server:develop`, port 9883).

**Wave in one line:** a self-hosted Linked-Data drive provisions a well-known `/setup` invite whose redemption binds nothing to the redeemer, its generic resource dispatcher returns before the authorization check whenever the path names an endpoint, the download handler trusts a user-settable stored property as a filesystem path, and uploaded files are rendered same-origin with no CSP, so the whole chain from anonymous to permanent account takeover is documented in the advisories themselves.

!!! warning "Authorized lab validation only"
    Validate against your own disposable `joepmeneer/atomic-server` container. The `/setup` leg is first-claim-wins: redeeming it on any instance you do not own destroys the owner's claim state. Never probe third-party instances, never redeem invites, never write commits outside your own lab Drive.

## Why this is worth an operator page

- **Provisioning artifacts are first-class recon targets, and first-claim-wins means timing is the attack.** The `/setup` invite is created automatically, sits at a guessable path, and authenticates by *possession of the URL* alone: the redeeming identity is literally discarded (`for_agent: _`). This is the same transient-state family as the Oct 14 Collabora "not-running window" and the Nov 13 NocoDB empty-admin bootstrap: a product has an unowned interval between install and claim, and whoever hits the claim endpoint during it owns the instance. Audit rule for any app with an install/claim flow: enumerate `GET /setup`, `/install`, `/welcome`, `/claim`, `/init`, check whether redemption binds the redeemer (session, CSRF, capability, existing account) or just the URL, and check whether the artifact exists **before** any admin action. For bug hunters, fresh-deploy SaaS trials and community instances are the harvest; the `usagesLeft = 1` counter means this is a race you can win passively by polling.
- **Authorization order in a generic dispatcher is the whole security model.** The SSRF is not a missing auth annotation on the bookmark handler; it is `if is_endpoint { return self.call_endpoint(...) }` sitting **above** `hierarchy::check_read` (`db.rs:1010-1017`). Any path that names a registered endpoint escapes the permission hierarchy entirely, and `call_endpoint` itself performs no check. This is the path-class carve-out rule (siblings: Sept 19 WP nopriv AJAX, Oct 7 Backstage `/services` route, Nov 12 Payara admin-header waiver) in its purest readable form. Decision-table proof shape for any dispatcher-style app: request the same resource path as a *resource read* (expect 403 for anonymous) vs. as an *endpoint invocation* (observed 200) and publish the mismatch. Grep pattern: `return` statements in the authorization function that precede the permission check.
- **Sanitize-on-write does not cover read; audit every reader of every stored field.** The `internalId` leg is the validate-target-vs-read-target mismatch: upload sanitizes filenames, download trusts the stored string as a path, and the property write that plants it needs no special privilege because Commit apply has **no server-managed-property denylist**. Two greps find this class anywhere: (1) consumers of stored string fields that hit `PathBuf::push` / `path.join` / file open without a containment check, remembering that absolute-path push *replaces* the base (the join-escape variant of the July 28 extraction lessons), and (2) any "apply arbitrary property changes" API (JSON merge, PATCH, commit/import) asked: which properties are *server-managed* and rejected from external writes? Missing denylist = every confinement-by-trusted-writer assumption downstream is void.
- **The credential model changes what XSS costs.** Standard framing prices stored XSS as session theft; here the same-origin inline render plus JS-readable session cookie plus Ed25519 private key in IndexedDB means one `<script>` on a `/download` URL permanently takes over the identity, because the private key is the identity and it never rotates. Whenever a web app holds *client-held cryptographic keys* (agent keys, wallet keys, E2E vault keys), ask what an XSS sink can read beyond cookies, and price XSS accordingly in reports. The file-serving defaults battery is reusable on any product with a download route: `Content-Disposition` per MIME, `nosniff`, CSP coverage per *route family* (not just the SPA), and same-origin-vs-dedicated-domain for user content.
- **Full-response SSRF without a deny-list is an internal-network map.** The advisors' own repo-wide grep for `is_loopback|is_private|169.254|127.0.0.1` finding nothing is the model for documenting SSRF severity: prove loopback read, prove link-local metadata, and quote the absence of filtering code. The bookmark handler ignoring its `for_agent` parameter is the same-discarded-identity twin of the invite leg, worth noting as a code smell to grep: handlers that destructure the caller but use it nowhere.

## Validation workflow (authorized scope only)

1. **Spin up your own lab instance.** `docker run -p 9883:9883 joepmeneer/atomic-server`, fresh store. All PoCs in the advisories run against this; keep everything in your own container.
2. **Claim-state probe (positive control only).** `GET /setup` with `Accept: application/ad+json` on your *own* fresh instance: record `invite/write`, `invite/target`, `usagesLeft`. Redeem once with a key you generated, confirm 200 + `redirectAgent`, confirm the instance is now claimed. Evidence = the invite resource before/after.
3. **Endpoint-dispatch authz differential.** Build a table: same path, three principals (anonymous, synthetic low agent, admin), two request shapes (resource read vs. endpoint invocation). For `/bookmark`, point `url` at an owned canary and at your own container's loopback service, capture reflected-body mismatch tables. Cloud-metadata proof only against your own metadata-emulating canary, never 169.254.169.254 of a host you don't own.
4. **Stored-field read sink.** Create a resource in your own Drive, set `internalId` to a relative traversal into a disposable canary file you placed outside the data dir, then `GET /download`. Absolute-path push proof against a synthetic world-readable marker file, not `/etc/shadow`-equivalent secrets. Record the property-write decision table: what a low agent may set vs. what should be server-managed.
5. **Inline-render check.** Upload an inert marker `text/html` (no attack payload), fetch the `/download` response, and capture the header set: `Content-Disposition`, `Content-Security-Policy`, `X-Content-Type-Options`, cookie `HttpOnly`/`Secure` flags. The header diff *is* the finding; no script execution needed to prove the sink.
6. **Report as one wave.** Four GHSAs share two root causes (identity-discarding handlers, stored-value-trusting readers); grouping shows the codebase-level pattern and raises triage priority.
