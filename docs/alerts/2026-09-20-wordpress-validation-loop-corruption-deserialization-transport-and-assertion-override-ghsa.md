# WordPress validation-loop corruption, XML-RPC deserialization transport, and IdP assertion override (Sept 20 09:30Z wave)

Source: hourly offensive-security scan of GitHub Security Advisories, 2026-09-20 (wave published 2026-09-20T09:30Z, WPScan-style descriptions).

The recurring shapes this wave: **a validation loop whose own bookkeeping is broken so the check always passes**, **deserialization reachable over a transport your fuzzer doesn't drive (XML-RPC, stored AJAX data)**, **a nested composition path that skips the validation the parent path enforces**, and **an SSO plugin that ignores the identity-matching criterion the admin configured**.

## Why this is worth an operator page

- **Validation loops can be structurally dead.** NextGEN's archive-extension check reused the loop counter as the per-iteration validation result, so the final verdict was always "pass." Audit rule: on any multi-item validator (archive members, batch uploads, array fields), the test is **mixed-content batches** — one allowed item + one forbidden item in a single archive/array. Single-item tests cannot distinguish a working validator from a loop-corrupted one. This is the loop twin of the JetFormBuilder blocklist-omission lesson: test the *set*, not just the *element*.
- **XML-RPC is an un-fuzzed deserialization transport.** Forminator's unrestricted object graph arrives via `xmlrpc.php` request values, not the form endpoints that get exercised. For any WordPress (or PHP) target with XML-RPC enabled, enumerate methods and pass serialized-object-shaped parameters to each — the same PHP-object-injection battery you run on POST params deserves its own XML-RPC pass. Pair with the forms-permission pre-condition check: Forminator's own settings can grant forms-management below administrator, so the CVSS's "admin only" framing understates reachable roles on sites using that feature.
- **Stored-data AJAX handlers inherit the writer's trust problem.** Unlimited Elements deserializes *stored* plugin data through an unchecked AJAX action — the injection surface is whatever field any Subscriber can save. Sweep: for each AJAX action that reads plugin option/meta state into a deserializer, identify the lowest role that can write that state. Also note the **partial-fix differential** (2.0.18–2.0.19 raised the role instead of fixing the sink): fingerprint the exact minor version before concluding an advisory is patched, and re-test "fixed" versions for role-gated reachability of the same sink.
- **Composition paths skip the parent path's enforcement.** Forminator's quiz import accepts a nested registration form the ordinary editor and importer both refuse. When a platform has a "container" artifact (import formats, quiz/builder nests, blocks-in-blocks, templates-of-templates), build the artifact through **every** containment path and diff the validation verdicts — same transport-parity axis as the Sept 19 alternate-surface page, but applied to *nesting* rather than *route family*. End-state is a public self-serve admin-maker: quiz-import permission → any visitor becomes administrator.
- **Configured security criteria that the code ignores.** The SAML plugin's account-linking selector is admin-facing theater: the code always resolves by login name. Generalize the UsersWP email-assertion rule: after any SSO assertion, verify **which field** the server actually matches against (login, email, nameid, provider ID) by asserting *different* values per field in a lab IdP you control and observing which one binds. An attacker-controlled IdP assertion that binds on a guessable/enumerable login name = ATO up to admin. Decision-table proof: one lab user per field variant; record which assertion logs in as whom.
- **OAuth/OAuth-like code redemption is state-changing on the site's identity.** TikTok's callback redeems *any* visitor's supplied code with the *site's* platform credentials. Sweep every "connect account" callback for: (a) does it run outside the connecting admin's session (on every page hit?), (b) does it path-match loosely, (c) whose credentials does it spend? Attacker-supplied code + site-side credential = CSRF against the integration, with the ad/account platform's own account linkage as the mutation.

## Validation workflow (authorized scope only)

!!! warning "Lab installs, inert proofs"
    Disposable WordPress installs with the vulnerable plugin versions, synthetic users/roles/galleries, a lab IdP you control, and inert marker files. Never write real users' galleries, never grant real roles, never redeem third-party OAuth codes.

1. **Mixed-batch archive probe:** build a lab ZIP with one permitted (`.jpg`) + one forbidden (`.php`-named, GIF-content) member; upload via the archive path as a gallery-capability lab role. Evidence: extracted file listing + served-vs-parsed behavior of the marker (no execution), fixed-version rejection of the same batch.
2. **Ownership matrix:** gallery-capability users A and B; B attempts save/delete/copy/retag against A's gallery IDs, and saves the global sizing setting. Evidence: verdict table action × owner × result; record the filesystem-path settings field B can overwrite on A's gallery (point it at a second lab directory, never system paths).
3. **XML-RPC object-injection pass:** on a lab install, fingerprint `xmlrpc.php` methods, submit serialized-object canaries (no POP chain, no file writes) to each parameter position, and compare deserialization errors/behavior against the same payload on POST params. Evidence: reachability table transport × method × verdict. Do not run a real POP chain.
4. **Nesting parity:** create the role-granting registration form three ways — ordinary editor, ordinary import, nested-in-imported-quiz — as the quiz-importer lab role. Evidence: three-way verdict table; publish only in the lab, submit once from an anonymous session to confirm role mint, then delete.
5. **Assertion-field binding table:** staging install + lab IdP; assert login-only, email-only, and mismatched pairs against a lab victim account. Evidence: which asserted field logs you in as whom. Never test against real tenants.
6. **Callback redemption test:** instrument the connect-flow callback with a request log; load a lookalike URL as an anonymous session and record whether the redeem fires, whose credentials it uses, and whether the code came from the requester. Use only codes issued to your own integration test app.

## Reporting checklist

- for loop-corrupted validators: exact validator, mixed-batch composition, extracted-vs-validated listing diff;
- for deserialization: transport (xmlrpc method / AJAX action), writing-role for stored-data variants, exact fixed-version window, and the lowest role that reaches the sink after the "fix";
- for nesting drift: all containment paths tried, verdict table, and the end-state capability the nested artifact grants;
- for SSO binding: configured criterion vs actual matched field, per-field assertion decision table, lab IdP details redacted;
- bounded impact language: object injection ≠ RCE without a demonstrated POP chain to a write sink; arbitrary file write ≠ RCE without handler execution proof; same-origin SVG ≠ session compromise without an inline-serving path.
