# phpMyFAQ wave (27 GHSAs): shared session store lets one tenant replace another tenant admin passkeys

---

Source: GitHub Security Advisories published 2026-11-17T03:31Z, a coordinated 27-advisory wave against phpMyFAQ before 4.1.12 / 4.2.0-alpha before 4.2.0-RC.2. Two criticals (cross-tenant passkey takeover, web-installer takeover), plus a dense authz/lifecycle/API-disclosure cluster.

**Wave in one line:** phpMyFAQ multisite runs many sites on one codebase sharing session stores, Redis prefixes, config tables, and content blobs without tenant scoping, so an admin/editor on *your* tenant reads, overwrites, or destroys the *master and sibling tenants'* passkeys, configuration, ACLs, and files; the rest of the wave is the classic render-path-vs-API and check-target-vs-load-target field drift.

## The multisite shared-store thesis: tenant boundaries live in the backing stores, not the UI

phpMyFAQ multisite is the cleanest single-vendor demonstration of a rule that generalizes to every "many sites, one codebase" product (WordPress multisite, GitLab groups, Frappe sites, Keycloak realms, OJS): **the tenant boundary is only as real as the scoping of every shared backing store**. This wave found four separate unscoped stores:

1. **Session store shared across tenants** (130369): same PHP session namespace, so a WebAuthn ceremony begun on tenant A is valid on tenant B. Prove: two lab tenants, `prepare()` on A, `register()` on B with the same session cookie.
2. **Redis config store shared, prefix user-settable** (130351): tenant admin can reset `storage.redisPrefix` and write the master's config, including SMTP redirection and a known API token. The config knob itself is the weapon: `save config -> redirect master SMTP -> harvest password resets`.
3. **Content-addressed file blobs shared with local-only refcount** (130342): `linkedRecords()` counts local table only, so deleting your copy unlinks the shared md5 blob. Same genealogy as the MISP stale-correlation-snapshot trio (Sept 21 precedence page): derived/local views of shared data create destruction and authorization time bombs.
4. **DB rows keyed by (id, lang) with a global permission check** (130377, 130381, 130356): scope checks run against one language/route while the data load follows a different parameter. The delete leg is especially operator-shaped: a scoped right passes when the target language **has no translation**, an existence-shaped gap in the predicate.

Operator procedure for any multisite/multi-tenant web app in scope:

- Enumerate shared stores first: session backend (files vs Redis vs DB, and its key prefix), config/settings table (tenant column? who can write it?), cache, search index, and content-addressed storage (uploads, attachments, exports).
- For each store, run the cross-tenant pair probe: two disposable tenants A/B you both administer, initiate a stateful ceremony on A (login step, WebAuthn, token issuance), complete or replay it on B.
- For every scoped-permission check, build the parameter-pair decision table: route parameter vs body/query selector vs loaded row (check-target vs load-target, cf. the Sept 21 supplied-scope rule). Vary `lang`, `faqLanguage`, `solutionId`, and absent-translation states.
- Grep the admin API family for endpoints that authorize a **global** right while operating on **scoped** objects (copy/translate pages, import, dashboard widgets, search).

## Installer and lifecycle legs: keep the setup route and the reset flow on the checklist

- **The forgotten installer** (130371): upgrade paths that leave the web installer reachable, where the installer ignores the existing config file, are unauthenticated takeover: reinstall against your own DB, create admin. Standing recon rule: on any CMS/wiki/ERP fingerprint, probe installer leftovers (`/install/`, `/setup/`, `setup.php`, `setup/index.php`) and check whether they re-run when config exists. Same family as the Grav install-state drift (Oct 12 page).
- **External-identity accounts still have local passwords** (130347): OIDC/Keycloak/Entra/LDAP/WebAuthn users accepted password-reset and received a local password. Whenever a product supports external IdPs, enumerate whether **local recovery flows still issue local credentials** for federated accounts: request a reset for your own federated lab account and see if mail arrives. If it does, IdP MFA is bypassable with mailbox access, and every federated account becomes a mailbox-takeover target.
- **Registration activation gates can be alternate-route misses** (130354): the WebAuthn prepare path creates **active** accounts bypassing manual activation and domain whitelisting. Test activation/approval gates via every registration-adjacent endpoint, not just the main register form; a freely-issued CSRF token plus an unthrottled prepare endpoint also yields an unauthenticated account-enumeration oracle (130362).
- **CSRF token lifecycle is a rate-limit surface** (130362, 130368): unconsumed/reusable CSRF tokens turn any guarded endpoint into an unthrottled guessing oracle. Probe: fetch a token once, replay it 50x against a sensitive endpoint from your own account; if the token survives, throttle-bypass and enumeration findings follow. Step-up re-auth prompts (old-password checks) that reuse the ambient CSRF token are unlimited offline-dictionary-shaped oracles.

## Public API vs render path, and notification fan-out: the disclosure axes

Five legs share one defect: fields the **rendered HTML** hides (drafts, private notes, author e-mails, restricted categories) are still present in **list/detail API serializers** (`/api/v4.0/faqs` variants), bookmark side-channels, or **push-notification payloads** (130352, 130353, 130345, 130339, 130348). This is the wiki's standing field-ACL-in-read-verb rule (Payload Oct 6: field ACL in the read verb only, enumerate every document-returning verb) with two fresh carriers:

- **Notification fan-out is an unfiltered serializer.** Subscribe to Web Push with a frontend account, have an editor publish a restricted FAQ in your lab, and diff what your subscriber receives against the anonymous view.
- **Bookmark/sidecar tables echo hidden fields.** `bookmark_action=add` then reading `/user/bookmarks` exposed draft titles for ids you could never open. Sweep every sidecar feature (bookmarks, subscriptions, history, recently-viewed, share previews) for echo of fields the main view hides.
- Enumerate API version families (`/api/v3.1/` vs `/api/v4.0/`) independently: an old serializer keeps old leaks after the current version is fixed (also seen in the Keycloak versioned-account-route family).

## Input-parsing legs worth a probe battery

- **Scheme-degradation XSS** (130341): the sanitizer allows `https://javascript:443/` (scheme https, safe), then a later cosmetic pass strips the `https://` prefix, promoting the remainder to a `javascript:` URL. Rule: **a sanitizer verdict is valid only for the exact bytes it inspected**; any post-sanitize transformation (prefix strip, normalization, URL "pretty" rewrites) re-opens the check. Battery: submit `https://javascript:`, `javascript:` double-encoded, and protocol-relative shapes through every link field.
- **Namespace-prefix sanitizer gap** (130365): element denylists matched by local name miss `<x:script>` on parsers that resolve prefixes leniently (IIS noted). Add namespace-prefixed spellings of every denied element/attribute to any SVG/XML upload battery (siblings of the Sept 19 SVG/data-URI sanitizer legs and the Oct 9 MathML mXSS rule).
- **Empty-list semantics** (130350): rights-management endpoints treat `[]` as "set to nothing" without checking the caller holds the rights being removed. Include empty-array and null-array submissions in the standard authorization battery on every bulk-set endpoint (sibling of the empty-value fail-open family).

## Validation boundaries

- Lab phpMyFAQ only, two disposable multisite tenants you administer, your own Redis/Elasticsearch instances, owned mailboxes for reset/SMTP proofs, and a disposable browser subscription for Web Push. Never exercise cross-tenant legs against production SaaS or third-party hosts; the passkey-replacement and config-overwrite legs are destructive, prove on lab tenants and stop.
- XSS proofs to inert DOM markers in your own privileged test account. E-mail disclosure proofs to your own synthetic author accounts.
- phpMyFAQ is open source: read `WebAuthnController`, `ConfigurationController`, `File` deletion, `Utils::parseUrl()`, `SvgSanitizer`, and the API serializers against the version in scope before touching a customer instance; the fix diff between 4.1.11 and 4.1.12 is the per-leg map.
