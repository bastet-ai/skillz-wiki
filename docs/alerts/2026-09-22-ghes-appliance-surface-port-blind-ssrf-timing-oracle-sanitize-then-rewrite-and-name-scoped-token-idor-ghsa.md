## Why this is worth an operator page

- **Port is a first-class SSRF validation dimension, and "same host" is not "safe."** The notebook-viewer guard checked scheme + host and left port free — on a monolithic appliance, `http://<appliance-own-canonical-host>:<internal-port>` is a fully guard-passing URL whose destination is an internal service. Audit rule for every URL-fetching feature on an appliance/monolith: enumerate what is listening on other ports of the *approved host* (GHES historically runs a fleet of internal HTTP/management services on loopback and appliance IPs), and test the approved-host-plus-foreign-port tuple explicitly — the host allowlist is most often written assuming ports don't matter.
- **No response body ≠ blind.** The chain that matters here is the second leg: **timing as a character-by-character secret oracle**. When an internal service's response time depends on a guessable prefix (auth comparison, redirect-vs-404 fan-out per secret value), a bodyless SSRF still yields the secret byte-by-byte. Operator sequence: (1) establish a timing differential for one bit/character of the guessed value, (2) script the prefix extension, (3) only then look for the consumer that turns the secret into the sink. This is the blind-SSRF measurement pattern (Nuxt OG Image outer-status oracle, Sept 17) generalized from status codes to latency, and it is what turned a "medium-ish SSRF" into unauthenticated appliance RCE.
- **Sanitize-then-rewrite is a sanitizer bug, not a bypass.** The GHES XSS was not a filter evasion — the pipeline **mutated already-sanitized HTML (quote rewriting) and rendered the mutated copy without a second sanitizer pass**. Same invariant as the Aug 5 Grocy sanitize-then-transform item and the Sept 22 Svelte DOM-clobbering family: the security verdict is attached to a doc copy, and any later transformation invalidates it. Audit rule: for any rendering pipeline with a sanitizer, list every post-sanitizer transformation step (entity rewriting, quote normalization, linkification, syntax highlighting, html-post-processing) and treat each as an injection point — fuzz canaries that only become active after the rewrite (quote-containing attribute payloads are the canonical shape). CSP is not a negative control: a same-origin JS gadget corpus (existing routes/framework globals that consume DOM state) is usually enough to execute meaningfully under strict CSP; test attribute injection *with* the CSP policy enabled.
- **Token scoping by non-canonical identifier is an IDOR generator.** Diff tokens keyed on `(repo name, PR number)` accepted attacker-created colliding names. Anywhere an internal token/secret/URL is derived from a **human-readable identifier that another principal can register or duplicate** (repo names, slugs, org handles, namespaces, bucket names), mint your own colliding object and replay your token against the target's resource. Sweep rule: ask "is the token's scope key globally unique or name-unique?" — name-unique across a multi-tenant instance = collision IDOR. Cheaper than SQLi and lands in the same authz-drift class as the Sept 22 mcp-atlassian UUID-without-scope items.
- **Private-mode posture is a precondition probe, not a mitigation story.** The SSRF is unauthenticated only when private mode is disabled; report the posture as part of exploitability proof (same config-posture axis as Dancer2 `static_handler:0` and Give Tributes).

## Validation workflow (authorized scope only)

!!! warning "GHES instances hold real source code — evidence only"
    Run every leg against a **lab GHES instance** or an explicitly authorized target with synthetic repos. Never read real private diffs, never extract live instance secrets, never point a notebook URL at production internal services outside authorized scope.

1. **Port-blind URL check (lab):** in a disposable notebook, reference an external resource URL on the appliance's own canonical hostname with (a) the normal port (control), (b) an internal management port that accepts TCP, (c) a closed port. Evidence: connection-timing / error-class decision table only; no content pulled from internal services.
2. **Timing-oracle existence proof:** demonstrate a single-bit timing differential against a lab-only canary secret with a known-value comparison service on the appliance; show two distinguishable latency populations. Do not script the full extraction on any shared system — the differential *is* the finding.
3. **Sanitize-then-rewrite canary:** render a Markdown payload carrying a quote-shaped attribute canary that only fires after quote normalization (e.g., an attribute breakout whose active form exists solely in the rewritten copy) in a disposable PR body viewed by a second lab user; evidence is a marker fetch to an owned callback or DOM mutation record, with CSP left at default.
4. **Name-collision token probe:** two disposable orgs; org B creates a repo name colliding with org A's private repo, opens a PR to reach the same PR number, requests a raw-diff token for its own repo, and attempts reuse against org A's diff endpoint. Evidence: 200-vs-403 decision table against the synthetic private diff only; delete the collision repos after.
5. Record patched-version behavior for each leg (3.22.1 baseline) to prove the fix boundary.

## Reporting heuristic

Title by the broken binding: **URL guard omits port → same-appliance internal reachability**, **bodyless fetch with latency oracle → secret extraction → internal-service RCE**, **post-sanitizer quote rewrite renders an unsanitized copy**, **token scope keyed on name-unique instead of globally-unique identifier**. Include the posture precondition (private mode), the timing-vs-status oracle shape, the pre/post-rewrite HTML diff, and the collision decision table. Stop all proofs at the oracle/decision-table level; do not chain into real secret recovery or internal-service actions.

## October 6 follow-up: Atlassian Data Center family — one unauthenticated webapp-root file access CVE across eight products (GHSA-gr66-x5pq-8g2g / CVE-2026-21589)

Atlassian published a single advisory covering **Bitbucket, Confluence, Jira Software/JSM, Bamboo, Crowd Data Center, Crucible, and Fisheye**: an unauthenticated remote attacker can access **specific files inside the web application root directory**, provided they already know the exact name and path (no directory listing). Introduced across branches going back to 2016–2019 (Bitbucket ≥4.6.0, Confluence ≥5.10.0, Jira ≥7.1.0, Crowd ≥2.11.0), fixed per-product in October 2026 point releases (9.4.26 / 10.2.8 / 10.5.1 style fast-follow triples per product line).

Operator value:

1. **One CVE ID across a whole vendor family = shared platform component.** Eight Atlassian DC products sharing one file-serving bug means the vulnerable handler lives in their common web framework, not per-product code. Recon rule: when a vendor publishes a multi-product advisory, treat every listed product as in-scope for the *same probe* — and when a vendor ships point-release triples across product lines, fingerprint per-product exact build before assuming a patch level applies family-wide (same exact-build fingerprint rule as this page's NetScaler lesson).
2. **"Requires exact path knowledge" is not "requires secrets" — it means the enumeration leg is source code, not the network.** Webapp-root paths for these products are public: packaging manifests, `web.xml`/servlet mappings, `.properties` under `WEB-INF/classes`, plugin descriptors, and known config filenames are all discoverable from public sources, version-control history, or docs. Validation workflow in authorized scope: build a candidate path list from the product's own public packaging structure, request each path unauthenticated, and diff against an authenticated control; positive class = 200 with file bytes for a path that every authenticated route through the app's own auth filter would gate. Never fetch real config files with live secrets on a client network — stop at header/status evidence plus a known-public file, and report the reachable-file inventory concept.
3. **Same reach class as this page's port-blind SSRF pair: a monolith's static-serving layer is a second, unauthenticated API over the same filesystem.** Where GHES historically leaked internal services via host+port, Atlassian DC leaks webapp-root files via a legacy serving path. Standing check on any Atlassian DC engagement (and, more generally, any Java EE monolith): probe known webapp-root paths unauthenticated before concluding the login gate is the perimeter.
