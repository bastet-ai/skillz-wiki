# Fortinet wave (64 GHSAs): crafted HA packets run commands as super admin

**Published:** 2026-11-12 00:32-00:33Z, one Fortinet PSIRT batch across **FortiOS (7), FortiManager (4), FortiAnalyzer (19), FortiAuthenticator (12), FortiMail (14), FortiPAM (7 legs inside FortiOS records), FortiClientEMS (1), misc (1)**: 11 critical, 50 high. All 64 GHSAs have **empty package/version fields**, the vendor-advisory band-fingerprinting pattern: pivot fix bands to the referenced [FG-IR advisories](https://fortiguard.fortinet.com/psirt) (e.g. [FG-IR-26-273](https://fortiguard.fortinet.com/psirt/FG-IR-26-273), [FG-IR-26-271](https://fortiguard.fortinet.com/psirt/FG-IR-26-271), [FG-IR-26-272](https://fortiguard.fortinet.com/psirt/FG-IR-26-272)), not the GHSA.

**Wave in one line:** the crown jewels here are **peer-plane trust** (HA/FGSP/FGFM protocols that authenticate reachability instead of identity) and **FortiMail's IBE feature, which is almost the entire unauthenticated attack surface at once**.

**Audience:** red-team and bug-bounty operators working perimeter estates, MSP/managed-service chains, and any engagement touching Fortinet-managed networks. None of these CVEs are in KEV as of catalog 2026.11.10 = head-start window for your own lab validation.

!!! warning "Authorized validation only"
    All proofs below belong in owned labs or explicitly approved customer windows. Do not send HA/FGSP/FGFM packets at third-party production devices, do not touch IBE keystore or quarantine data, and keep all listeners/callbacks on owned infrastructure.

## 1. The peer plane is the new perimeter: HA/FGSP/FGFM packets as unauthenticated command channels

Four legs of this wave hit **machine-to-machine replication protocols**, not the GUI:

- [GHSA-f2f6-qwmc-g833](https://github.com/advisories/GHSA-f2f6-qwmc-g833) / [CVE-2026-126259](https://nvd.nist.gov/vuln/detail/CVE-2026-126259) (critical): **missing authentication for a critical function**: when HA FGSP with standalone-config-sync, or autoscale, is configured, an **unauthenticated attacker executing crafted HA packets runs commands as super admin**. No credential, no GUI, no session. The precondition (FGSP + standalone-config-sync or autoscale) is a deployment shape, so fingerprint the deployment, not the banner.
- [GHSA-94pv-xwr4-33w5](https://github.com/advisories/GHSA-94pv-xwr4-33w5) / [CVE-2026-126148](https://nvd.nist.gov/vuln/detail/CVE-2026-126148) (critical, FortiMail): **unauthenticated OS command injection via crafted HA join-request packets**. The join handshake is a pre-identity path: a device trying to join a cluster gets parsed by the incumbent before any trust is established, and the parser is the vuln.
- [GHSA-8xfm-8jxr-pcpm](https://github.com/advisories/GHSA-8xfm-8jxr-pcpm) / [CVE-2026-126181](https://nvd.nist.gov/vuln/detail/CVE-2026-126181) (high, FortiManager): **hard-coded pre-shared key** lets an adjacent-network authenticated user **join the FGFM configuration-sync mesh of the affected FortiGate deployment**. FGFM (541/tcp) membership is the master key to a Fortinet estate: mesh members receive/push device configuration. A default PSK converts adjacency into device-config control.
- [GHSA-4444-m7rm-3q68](https://github.com/advisories/GHSA-4444-m7rm-3q68) / [CVE-2026-126184](https://nvd.nist.gov/vuln/detail/CVE-2026-126184) (high, FortiAnalyzer/FortiManager): spoofing-based bypass lets an attacker **disrupt the HA state** = availability leg on the same protocol family, plus a state-transition oracle while probing.

Operator rules:

1. **Peer/replication ports are a separate attack surface from the management GUI, and they historically ship with weaker auth.** Inventory them per appliance family: FortiOS FGSP/HA (local-traffic, 8013/UDP and dedicated HA links), FGFM 541/tcp, FortiAnalyzer FortiView/collector replication (oftp, historically CVE-2024-23109 territory), FortiMail HA join. For each, the audit question is binary: does the handler authenticate the **peer identity**, or does it merely parse bytes because the packet **arrived**?
2. **Deployment-shape preconditioning is fingerprinting work, not a dead end.** 126259 rides FGSP+standalone-config-sync/autoscale; test `get system ha status`-equivalent observable artifacts (HA VIP behavior, config-sync side effects) from your approved vantage before theorizing.
3. **Cluster-join handshakes deserve a fuzz pass of their own.** Parse-before-identity is the join-request family's structural flaw (FortiMail 126148); join/announce/sync message grammars are unauthenticated input by design.

## 2. FortiAnalyzer/FortiManager: the collector port and the config generator are both RCE sinks

- [GHSA-frx4-vqjx-m6cm](https://github.com/advisories/GHSA-frx4-vqjx-m6cm) / [CVE-2026-126262](https://nvd.nist.gov/vuln/detail/CVE-2026-126262) (critical): SQL injection reachable **unauthenticated by anyone with access to the oftp port**, crafted OFTP packets = **code/command execution** on FortiAnalyzer and FortiManager. The replication/collector port is again the forgotten listener: often open across the management VLAN with no GUI auth in front of it.
- [GHSA-rm98-fc32-9ggj](https://github.com/advisories/GHSA-rm98-fc32-9ggj) / [CVE-2026-126170](https://nvd.nist.gov/vuln/detail/CVE-2026-126170) (critical): improper output encoding, **unauthenticated** HTTP request = code execution on FortiAnalyzer/FortiManager (bands to 8.0.2/7.6.7).
- [GHSA-p5xc-69mw-v3hr](https://github.com/advisories/GHSA-p5xc-69mw-v3hr) / [CVE-2026-126180](https://nvd.nist.gov/vuln/detail/CVE-2026-126180) (high): template-engine injection lets a **low-privileged Device Manager admin obtain super admin privilege on managed FortiGates**. The config generator is the command channel: when a central manager renders per-device config from templates, injection at the template layer fans out to every managed device. Same genealogy as Zimbra's Zimlet-config allowlist write (Oct 23 page): central-plane config fields are remote-code surfaces on the fleet.
- [GHSA-35c9-x69h-7h3g](https://github.com/advisories/GHSA-35c9-x69h-7h3g) / [CVE-2026-126218](https://nvd.nist.gov/vuln/detail/CVE-2026-126218) (high): FortiManager authenticated admin → **root** via crafted HTTP requests; [GHSA-83j8-m545-7j8q](https://github.com/advisories/GHSA-83j8-m545-7j8q) / CVE-2026-126183 (high): user-controlled key → commands **outside the expected scope**.
- [GHSA-gv7r-gwfj-rphx](https://github.com/advisories/GHSA-gv7r-gwfj-rphx) / [CVE-2026-126214](https://nvd.nist.gov/vuln/detail/CVE-2026-126214) (high): spoofing bypass lets an authenticated admin **impersonate internal services** via the GUI, the service-identity-not-user-identity family.
- [GHSA-jhfg-5wg8-xp87](https://github.com/advisories/GHSA-jhfg-5wg8-xp87) / [CVE-2026-126232](https://nvd.nist.gov/vuln/detail/CVE-2026-126232) (high): **RADIUS server certificate validation missing**, a MITM impersonates the RADIUS server with a rogue certificate. Auth-factor channels that skip cert validation turn network position into credential capture against the whole estate.
- [GHSA-4g35-w627-6669](https://github.com/advisories/GHSA-4g35-w627-6669) / [CVE-2026-126229](https://nvd.nist.gov/vuln/detail/CVE-2026-126229) (critical, FortiAnalyzer/Cloud + FortiManager/Cloud): user-controlled key → **an authenticated administrator reaches other VDOMs**. VDOM is the tenant boundary in MSSP deployments; cross-VDOM read/write is the cross-customer leg every MSP audit should attempt.
- [GHSA-gh34-c3f7-rp3c](https://github.com/advisories/GHSA-gh34-c3f7-rp3c) / CVE-2026-126248 and the FortiAuthenticator set: [GHSA-3jjw-p738-9hj8](https://github.com/advisories/GHSA-3jjw-p738-9hj8) / CVE-2026-126257 (**hard-coded password**, unauth credential-validation bypass), [GHSA-hgh4-pcf2-8q3f](https://github.com/advisories/GHSA-hgh4-pcf2-8q3f) / CVE-2026-126240 (**LDAP injection through SAML NameID**: exploitation needs a malicious/compromised upstream IdP or an IdP config letting users control the NameID/username attribute, then LDAP filter injection bypasses authentication; the federated-input-into-query-construction rule from the directory pages, again), [GHSA-9r63-2p2h-xm89](https://github.com/advisories/GHSA-9r63-2p2h-xm89) / CVE-2026-126247 (format string, privileged → code execution).

Operator rules:

1. **On any collector/log/replication appliance, enumerate the non-GUI ingestion ports first** (oftp here; syslog/TCP 514/601, FortiView, Kafka legs elsewhere). Unauthenticated parsing of attacker-influenced protocol frames is where the criticals land.
2. **Treat the central manager as the blast-radius amplifier it is**: FortiManager template-injection to managed-FortiGate super admin means one foothold on the manager (or one low-priv Device Manager account) is estate-wide. When auditing MSP infrastructure, the manager-to-managed trust edge is a first-class test, and template/preview/config-render fields are your injection battery.
3. **Check identity-provider channels for missing validation both ways**: RADIUS cert validation (network MITM captures auth traffic estate-wide) and SAML NameID into LDAP filters (IdP-controlled claim crosses a query-construction boundary). On federated FortiAuthenticator deployments, the "attacker controls the NameID" precondition is worth checking directly: many IdP configs let users edit the assertion username (profile field, external IdP mapping).

## 3. FortiMail IBE again: the whole feature is one unauthenticated boundary (14 legs)

The FortiMail legs concentrate on **IBE (Identity Based Encryption) webmail** and quarantine:

- [GHSA-4pf4-qxrv-h22x](https://github.com/advisories/GHSA-4pf4-qxrv-h22x) / [CVE-2026-126155](https://nvd.nist.gov/vuln/detail/CVE-2026-126155) (critical): unauthenticated attacker **obtains an authenticated IBE webmail session as any IBE recipient**, reads and sends their encrypted mail.
- [GHSA-jfjj-gm3c-hf2p](https://github.com/advisories/GHSA-jfjj-gm3c-hf2p) / [CVE-2026-126156](https://nvd.nist.gov/vuln/detail/CVE-2026-126156) (critical): user-controlled key → **takeover of an arbitrary IBE recipient account**.
- [GHSA-7g83-wgvw-67qx](https://github.com/advisories/GHSA-7g83-wgvw-67qx) / [CVE-2026-126157](https://nvd.nist.gov/vuln/detail/CVE-2026-126157) (critical): improper authentication → **access other users' secure email accounts**.
- [GHSA-gg72-56wf-8rvm](https://github.com/advisories/GHSA-gg72-56wf-8rvm) / [CVE-2026-126150](https://nvd.nist.gov/vuln/detail/CVE-2026-126150) (critical): weak password-recovery mechanism → **reset the password of an arbitrary IBE webmail user**, full account takeover via crafted HTTP requests.
- [GHSA-gqr2-q46q-4w7q](https://github.com/advisories/GHSA-gqr2-q46q-4w7q) / [CVE-2026-126147](https://nvd.nist.gov/vuln/detail/CVE-2026-126147) (critical): path traversal → **unauthenticated code/command execution**.
- Quarantine leg pair [GHSA-289g-jgr3-r2rc](https://github.com/advisories/GHSA-289g-jgr3-r2rc) / CVE-2026-126159 + [GHSA-53vv-vq62-6qjw](https://github.com/advisories/GHSA-53vv-vq62-6qjw) / CVE-2026-126160 (high): user-controlled key + improper auth → **release or delete quarantined messages for arbitrary mailboxes** unauthenticated, the recipient-address field as capability selector (the "recipient" is data, not identity, again).
- Plus blind XPath injection pair (CVE-2026-126162/126176-126177 family on Analyzer/FortiMail), format string (CVE-2026-126163), integer overflow, auth-algorithm flaws (CVE-2026-126151).

This is the **second coordinated FortiMail IBE wave in six weeks**: the Oct 1 KEV'd CVE-2026-104286 file-write also sat behind the IBE feature. Standing rule from that page, now twice-confirmed: **feature-gated pre-auth handlers are the appliance's real attack surface, enumerate feature endpoint families (IBE enrollment/decrypt, quarantine release, guest approval, password recovery) separately from the admin GUI and probe them with the full identity-forgery battery** (arbitrary recipient selector, absent param, cross-purpose token, recovery-flow abuse). Cross-tenant proof on an owned appliance: prove the recipient-selector legs with **two accounts on your own domain** and stop at the read-back boundary, never third-party mailboxes.

## 4. FortiOS network-plane legs

- [GHSA-j3f4-wmxp-qvcr](https://github.com/advisories/GHSA-j3f4-wmxp-qvcr) / [CVE-2026-126253](https://nvd.nist.gov/vuln/detail/CVE-2026-126253) (critical): authentication bypass letting an **unauthenticated attacker broadcast LSA** via a crafted request: routing-protocol state injection from the network (LSA broadcast = topology poisoning potential; treat as an OSPF-plane integrity break and verify against the FG-IR for the affected protocol/feature gate).
- [GHSA-g2g3-rvm3-h345](https://github.com/advisories/GHSA-g2g3-rvm3-h345) / [CVE-2026-126254](https://nvd.nist.gov/vuln/detail/CVE-2026-126254) (critical): numeric truncation lets a **configured IBGP neighbor send malicious/malformed attributes to all connected routers**: when the route reflector or peer passes attributes through unvalidated, one peering session fuzzes the whole routing domain.
- [GHSA-6xmr-2mg3-g5xq](https://github.com/advisories/GHSA-6xmr-2mg3-g5xq) / [CVE-2026-126255](https://nvd.nist.gov/vuln/detail/CVE-2026-126255) (high, FortiOS + FortiPAM all versions): path traversal in the **credential field**, crafted credentials bypass authentication: input-shape confusion inside the login handler itself.
- [GHSA-jx7c-cqh8-2v65](https://github.com/advisories/GHSA-jx7c-cqh8-2v65) / CVE-2026-126258 (high): wad-port stack overflow crashes proxy/ZTNA sessions, unauthenticated, on the same wad parser that hosts the historical SSL VPN criticals; availability legs on the ZTNA gateway are worth including in post-auth-impact assessments.
- [GHSA-wjjw-gh8j-ggrg](https://github.com/advisories/GHSA-wjjw-gh8j-ggrg) / CVE-2026-121528 (high): **SSLVPN web portal to backend destination channel accepts invalid certificates**, unauthenticated MITM between the portal and the internal destination: the VPN portal is itself a proxy, and its upstream TLS leg skipped chain validation. Check every "portal fetches internal resource" architecture (VPN portals, reverse-proxy consoles, bookmark launchers) for validated-downstream-TLS, the ONLYOFFICE nested-control and Sept 20 LDAPS-vault genealogy.

## Validation boundaries

Owned Fortinet lab (or customer-approved window) only: VM-based FortiGate/FortiAnalyzer/FortiMail trials run fine locally for HA/FGSP/FGFM and IBE battery work. Keep all proofs at: (1) peer-plane packets between **your own** cluster members with a third lab node as the attacker, (2) OFTP/GUI canary markers under disposable paths, (3) IBE/recipient-selector proofs with **two accounts you own** on your own domain, (4) template-injection to a disposable managed FortiGate, never a production fleet, (5) LSA/BGP legs on lab routing domains only. No production HA traffic interception, no real-mailbox IBE reads, no quarantine mutations outside disposable data.
