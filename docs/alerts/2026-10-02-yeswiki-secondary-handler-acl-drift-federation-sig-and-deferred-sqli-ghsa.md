# YesWiki 4.6.7 wave — secondary-handler ACL drift, federation signature binding, deferred identifier SQLi, and GET-mutation CSRF

Source: GitHub Security Advisory wave published 2026-10-02 12:31Z (YesWiki < 4.6.7, 36 GHSAs; CVE-2026-104438–104472). Related existing pages: [Sept 18 semantic-MediaWiki unauth API page](2026-09-18-semantic-mediawiki-unauth-api-tasks-unsigned-cursor-and-debug-sinks-ghsa.md), [Sept 21 management-plane flat-authz drift page](2026-09-21-management-plane-config-writes-toctou-onboarding-race-and-flat-authz-drift-ghsa.md), [Sept 19 WordPress alternate-surface page](2026-09-19-wordpress-alternate-surface-authz-drift-rest-ajax-import-wave-ghsa.md).

One rule covers the majority of this wave: **the ACL is written where the page renders, not where the page data is read or written.** YesWiki ships dozens of sibling handlers over the same storage — attachment download, RSS actions, the comments API, the triples API, Bazar entry creation, tag listings, image actions — and most of them never call the read/write ACL check. On any wiki/CMS with per-page ACLs, build the handler inventory first; the primary render path passing its ACL tests tells you nothing.

## Durable axes

1. **Per-page ACL is a property of the render path only — enumerate sibling handlers over the same storage.** This single CMS shipped unauthenticated reads (attachment download, RSS excerpts, tag listings, triples reads) and unauthenticated/low-priv writes (entry-creation-by-existing-id, pointimage save, comments-API page targeting) all around the same page ACL. On any wiki/CMS/knowledge-base target: list every action/API/output-format that touches page content, then replay both ACL axes (read restricted, write not-yours) through *each* handler. The primary view correctly denying you is the control, not the result.
2. **Feature flags change the route ceiling.** Public-API mode turned admin routes (`update_config`, archive list/download/delete) into unauthenticated surface. Rebuild the authorization matrix per feature-flag state; toggle flags you can influence via config write or trial installs and re-probe the API family.
3. **Empty/default filters on bulk APIs are apply-all by default.** An empty filter on a delete endpoint = site-wide destruction. Always send `{}` / omit the filter object; expect a validation error, and report when you get a mutation. Pair with the delete-then-repopulate reality (deleting your own lab group's membership triple as proof).
4. **Federation/webhook invariants: signature-verified must bind signer to actor.** Verify the identity *inside* the payload is the identity that *holds the key*. Test cross-actor Delete/Update with your own valid keypair on ActivityPub inboxes; test cross-tenant replay on every HMAC'd webhook receiver.
5. **Deferred identifier SQLi: the injection write and read are different requests by different code.** Your username, a planted Bazar option id, a stored tag token — anything persisted unescaped and later interpolated into a query. Sweep: store quote/backslash variants in every identity/config field you can set (including anonymously editable config), then trigger every listing, search, feed, and export consumer.
6. **MySQL backslash quote-parity breakout.** A trailing `\` in a value the app merely wraps in quotes swallows the closing quote under MySQL's default escaping and reopens the string. Include `\"` , `\` and double-encoded spellings in every quote-wrapped parameter battery; recover column arity for UNION via error/boolean probing.
7. **Destructive GET is a product-wide pattern, not a single bug.** Five separate handlers in one product deleted pages, attachments, tags, packages, and revisions on unauthenticated-for-CSRF GET. A GET sweep of mutating handlers with disposable state enumerates the whole class in an afternoon.
8. **Fetchers inherit their destination**: sync/preview/syndication legs read back (content persisted as viewable entries), crawl on (attacker-controlled `next` links), and localize (enclosures downloaded into webroot). Each leg upgrades blind SSRF into read, multi-hop, or file-write — test all three per fetcher.

## Validation boundaries

Lab YesWiki < 4.6.7 with disposable pages, two synthetic accounts, marker attachments, and synthetic Bazar lists only. SSRF proofs use owned callbacks and self-owned multi-hop JSON-LD responders; never target cloud metadata or third-party internal hosts. SQLi proofs read marker rows and stop — no real user-table dumps in reports (hash extraction described, not performed, on shared instances). ActivityPub proofs use your own keypairs and mirrored synthetic entries; never delete or overwrite real federated content. GET-mutation proofs fire only against your own disposable pages/packages. Fixation/reset proofs use lab victim sessions you control.

## October 4 18:3xZ follow-up: the `valeur.php` fetch-and-render pair — one handler, SSRF leg + stored-XSS leg

Two advisories for the same Bazar `valeur` action (`tools/bazar/actions/valeur.php`) landed split across waves — the SSRF leg published Oct 2 (surfaced in the updated feed Oct 4), the XSS leg Oct 4:

- **[GHSA-32r4-8mw9-77h4](https://github.com/advisories/GHSA-32r4-8mw9-77h4) / CVE-2026-104470 (medium)** — page-editor `url` parameter makes the server fetch arbitrary URLs (loopback/internal probing) *and* injects the fetched remote HTML unescaped into the rendered page.
- **[GHSA-4jc3-v5mf-cppg](https://github.com/advisories/GHSA-4jc3-v5mf-cppg) / CVE-2026-105224 (medium)** — same handler pointed at a controlled server returning `BAZ_fiche_titre` markup with an `img onerror` executes script in **every viewer's browser** — editor-privilege foothold becomes stored XSS against all readers.

Durable axes: (1) **a fetch-and-render action is two bugs wearing one coat** — probe it once for internal-URL acceptance (SSRF) and once for remote-HTML execution (viewer-side XSS); the impact split (editor-only authority vs all-viewer execution) makes the XSS leg the escalation path. (2) This extends durable axis 8 (fetchers inherit their destination) with a fourth leg: **render** — the fetched bytes are emitted into the page DOM, not just stored or followed. When you find any "embed/fetch/preview a URL" field, the full battery is read-back / crawl-on / localize / render. (3) Same-handler advisories split across days: when you fold one leg of a product's fetch handler, grep the advisory feed for the sibling CVE/param before closing the page.
