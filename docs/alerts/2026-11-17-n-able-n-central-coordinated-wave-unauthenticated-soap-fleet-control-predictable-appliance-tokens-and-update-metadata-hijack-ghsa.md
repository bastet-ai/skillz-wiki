# N-able N-central wave (15 GHSAs): unauthenticated SOAP fleet control and appliance token forgery

Source: hourly offensive-security scan of GitHub Security Advisories on 2026-11-17 (unreviewed wave published 2026-11-17T12:31Z, vendor CNA import, GHSA package version fields empty; vendor fix line: **before 2026.4.1 HF3**).

**Wave in one line:** the MSP fleet-management appliance trusts its own agent-facing API: appliance identity is a guessable identifier, a dozen SOAP operations skip session/permission/scope checks entirely, and the software-update metadata channel writes files and executes code as the service account.

This is the **third N-central advisory cluster in one quarter** on this wiki: the [Aug 3 control-plane identity page](2026-08-03-control-plane-identity-project-connection-boundaries-ghsa-kev.md) covers CVE-2026-18577 (incomplete auth-bypass fix), and the [Sept 9 page](2026-09-09-n-able-n-central-preauth-rce-static-code-injection-kev-cve-2026-86218.md) covers the KEV'd pre-auth RCE CVE-2026-86218. The repeat-KEV-product prior paid off: the whole agent-facing protocol family is the soft target, not the login page.

!!! warning "Authorized lab validation only"
    N-central is an internet-exposed MSP fleet-management server that talks to hundreds or thousands of managed endpoints. All validation below is for a disposable lab instance or owner-approved canary. Never send agent-protocol shapes at a production appliance, never impersonate a real appliance, never touch managed agents or their devices.

## Why this is worth an operator page

- **The agent-facing API is the product's real attack surface, and it was built for machines, not adversaries.** Fleet managers must accept high-frequency telemetry, task results, and asset data from thousands of agents, so operators habitually skip per-call session checks on those routes. The eight unauthenticated/missing-scope SOAP legs here are the canonical proof: `RemoteExecutionTaskSubmit`, `AssetDiscoSimplifiedInfoSubmit`, `MaintActionGet`, and `remoteControlMSPAStartEndTimeSubmit` accept **forged submissions attributed to any customer**. Audit rule for any management plane with an agent protocol: enumerate operations from the WSDL/XSD, replay each one with no session, and build a per-operation auth matrix. Service-level "the login page has auth" says nothing about operation-level checks.
- **Machine identity that is an identifier is not identity.** The predictable-credential finding (129272) is the appliance-enrollment leg of a class the wiki keeps meeting (Sept 16 hardcoded update keys, Oct 9 Nginx UI node secret): when a component authenticates with a derivable value (appliance ID, node ID, hostname), the token mint is an unauthenticated API. Recon: ask what an agent needs to *register*, and test whether the registration/token endpoint validates anything the attacker doesn't already know.
- **Cross-customer blast radius is the MSP-specific multiplier.** One N-central serves many tenants; four advisories explicitly say "belonging to other customers." On an MSP engagement, single-tenant authorization passes are not enough: provision two lab tenants and assert tenant-A-to-tenant-B reads/writes on every collection endpoint and SOAP operation.
- **The update channel is a write target, not a read-only feed.** 129286 puts file-write-outside-download-dir plus service-account code execution into the software-update metadata path. Combined with 129285 (appliance-to-appliance XMPP forgery), poisoning one appliance's view of metadata propagates. This is the same update-source-as-attack-surface genealogy as the Aug 3 Report One updater (update *source* re-pointed by an unauthenticated write): whoever controls metadata controls every agent that consumes it.
- **Defense-evasion primitives are findings, not footnotes.** Unauthenticated `MaintActionGet` lets an attacker **cancel pending maintenance actions** (silently blocking patch/reboot windows), and `remoteControlMSPAStartEndTimeSubmit` rewrites remote-control **audit entries**. When blue team tooling depends on the appliance's scheduling and logging, tampering with those is a campaign-enabling capability worth reporting in its own right.
- **Two config-to-root legs, one authz-tier inversion.** The Audit Export control-character injection (product admin to root) is the classic config-file-newline sink; the test-email argument injection proves the third rule of mail-command sinks (no CSRF, no permission check, option characters live). The view-permission-writes-execution-config leg (129281) is the read-vs-write verb drift we track on the Sept 21 precedence page: check the *verb* semantics of every permission constant, view-gated handlers that write are self-evidently wrong.
- **Password testing via unauthenticated SOAP = unbounded spray oracle.** 129280 includes an operation that tests user account passwords; that is a credential-attack channel with no lockout context, on an appliance that holds fleet admin credentials.

## Validation workflow (authorized scope only)

1. **WSDL inventory first.** Pull the WSDL for every `ServerUI`, `ServerUI2`, `ServerII2`, `ServerMMS2`, and `Maint*` service family from the lab appliance (try the same discovery paths the SOAP console uses). Parse operation names into a matrix; do not sample.
2. **No-session replay matrix.** For each operation, send the minimal synthetic call with no session cookie/token from an unauthenticated client. Record per-operation: HTTP/SOAP fault class, response shape, side effects on synthetic tenant data. Evidence = the auth matrix table (operation x required-vs-enforced). Only operations that *return or mutate* your synthetic rows count; stop at the decision table.
3. **Appliance token forgery (lab).** Register two synthetic appliances in a lab instance, capture how appliance IDs are issued (sequence length, entropy, time-derivation), then request tokens from a third unregistered identity in a scratch tenant. Prove the token-mint accepts identifier-only claims against a synthetic appliance you created. Never impersonate an appliance that exists in a real tenant.
4. **Update-metadata containment (lab only).** With an owner-approved lab appliance, stand up your own metadata endpoint serving a manifest with (a) a `../` download path, (b) a loopback URL, and (c) a version string outside the accepted grammar. Evidence: resolved write-path table and reject/accept per shape. Never deliver a manifest to a live appliance and never let a real agent pool consume it.
5. **SSRF battery with owned callbacks.** Point Report Manager/Data Export targets at your own canary hosts first; record request-arrival evidence (headers, source IP from the appliance). Loopback probing only where the engagement rules allow port-level checks.
6. **XXE with owned external entities.** For repository files and custom service import, use parameter-entity canaries to an owned HTTP callback and a synthetic readable canary file placed beside the service account's expected read set. Capture the callback/request, not customer files.
7. **Tenancy parity.** With two lab tenants (A, B), every read/write from step 2 must be re-run cross-tenant; a same-tenant pass proves nothing about scope checks.
8. Report decision tables and resolved-path evidence. Do not claim fleet compromise, real-agent message delivery, or production password testing without lab end-to-end proof under explicit authorization.

## Reporting checklist

- Name the boundary class per leg: machine-identity forgeability, operation-level auth absence, cross-tenant scope drift, update-metadata containment failure, config-to-root injection, audit-integrity tampering.
- Include the auth matrix and the appliance-ID entropy observation; those are the reproducible artifacts.
- Fingerprint the build first: anything below 2026.4.1 HF3 is in scope for this wave; record the exact build, and cross-reference the two prior N-central KEVs when prioritizing.
