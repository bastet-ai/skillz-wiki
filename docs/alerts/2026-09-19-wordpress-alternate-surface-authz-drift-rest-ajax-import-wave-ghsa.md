# WordPress alternate-surface authorization drift wave (Sept 19 09:32Z)

Source: hourly offensive-security scan of GitHub Security Advisories, 2026-09-19 (wave published 2026-09-19T09:32Z, WPScan/WPScan-rp style descriptions).

The recurring shape: **the primary UI enforces authorization; the alternate surface for the same object (REST route, AJAX action, front-end form handler, import/export job, social-login resolver) enforces nothing — or enforces a different thing.** Multiple records this wave also show *capability-vs-intent* drift: a delegated plugin-specific permission silently carries user-management or object-ownership power the grantor never intended.

## Why this is worth an operator page

- **Enumerate every surface, then diff authorization.** For one object type in a plugin (settings, posts, conversations, imports, forms), list transports: admin UI, AJAX actions (`wp_ajax_*`, both priv and nopriv), REST routes (`register_rest_route` — check each `permission_callback`), front-end form handlers, cron/import jobs. Run the same state-changing operation via each transport as the lowest-privilege principal. Botiga Pro, Master Blocks, and Mailchimp-for-WooCommerce are all "primary UI gates, REST route doesn't."
- **Delegated capability ≠ implied capability (the import/export deputy).** WP Import Export Lite shows the audit rule: when a plugin defines its own permission ("can run imports"), enumerate what objects the import format can *create or modify* (users, roles, passwords) and check the plugin re-validates each against **core** caps (`create_users`, `promote_users`, `edit_user`). Any export→import pair (Ai1wm on the July 28 page is the same family) gets tested for the deputy jump: delegate-permission holder → admin creation.
- **Conversation/session IDs in unauthenticated actions are IDOR candidates by default.** The AI booking-assistant item is the WordPress instance of the API-IDOR sweep already applied to plugins — the novelty is *bidirectional*: read AND inject into a live in-progress session, i.e., prompt-injection-into-another-user's-AI-agent as a bug class on scheduling/chat widgets. Sweep any `action=` handler taking an ID with no nonce/ownership tie.
- **Email assertion in social login = ATO oracle.** UsersWP's rule generalizes to every WordPress social-login plugin in scope: after provider auth, does the app **trust the provider-reported email** to resolve an existing account without an ownership challenge? Test in a lab with your own accounts on two providers pointed at a staging install — register the victim-lab-user's email on your provider account and attempt login. Never test against a third-party account.
- **Type-normalization differentials between authz check and sink.** Custom Field Template: the gate sees `(int)$id`, the query sees the string. On any parameter feeding both a `current_user_can(...)` call and a query, probe with values whose integer cast and string form differ (`1 OR ...`, padded/whitespace forms) — same class as the WordPress-core casting items on the Sept 18 core page.
- **Handler-config as exploit amplifier.** The CF7-addon upload becomes RCE only because Debian/Ubuntu Apache maps `.phar` to PHP. Operator rule: predictable-path arbitrary-extension uploads are always a same-origin hosting primitive; the RCE claim requires proving the **target's** handler mapping (request the stored `.phar`/`.phtml` back and observe parse vs serve behavior with an inert file).
- **Deferred-execution callbacks.** JetFormBuilder: a *privileged* config action (setting a validation callback) is executed later by an *unauthenticated* form submit. When auditing form platforms, treat any "admin configures a callable" feature as a two-stage primitive: chainable with any social-engineering or stored-config vector, and its blast radius fires at attacker-chosen time.

## Validation workflow (authorized scope only)

!!! warning "Lab installs, disposable objects"
    Disposable WordPress installs with the vulnerable plugin versions, synthetic users/roles, lab provider accounts for social-login tests, inert `.phar`/`.php` marker files (no shell code), and synthetic posts/conversations. Never overwrite real user credentials, never run credential-bearing REST dumps against production.

1. **Transport diff:** for each plugin surface discovered, replay a state-changing operation as (a) anonymous, (b) Subscriber, (c) owner-user. Evidence: verdict table transport × role × result. Positive controls on own objects.
2. **Import deputy test:** with a delegated-import-permission lab role, import a synthetic XML/CSV containing an admin user creation + a password change on a *second lab admin* account you own. Record success + fixed-version behavior. Delete synthetic users after.
3. **Conversation IDOR:** two lab browsers, two synthetic conversations; browser B replays A's conversation-ID actions for read + inject. Evidence: message visible/injected in A's session with synthetic text only.
4. **Social-login ownership:** staging install + two provider accounts you control; assert lab-user-B's email from provider account A; record login verdict.
5. **Cast-differential probe:** submit `<numeric> <sql-canary>` variants of any ID parameter paired with an authz check; compare authz verdict vs query behavior via benign time/error-free boolean canaries on your own rows.
6. **Upload handler test:** upload inert marker with `.phar`/`.phtml`/`.php.jpg` variants to predictable-path uploaders; record stored path, served-vs-parsed behavior (marker prints nothing; parse is detectable by response-type/no-exec), and delete immediately.

## Reporting checklist

- transport (AJAX action name / REST namespace+route / front-end form), auth context, `permission_callback`/`current_user_can` presence (absent vs wrong-cap vs wrong-target);
- for deputy findings: the delegated cap name, the implied core caps crossed, and the created/modified synthetic object IDs;
- for IDOR: both directions tested (read/inject or read/write), ID source (visible in UI, enumerable), and nonce presence;
- for uploads: stored path pattern, extension accepted, target handler mapping evidence (served vs parsed), removal confirmation;
- for social-login ATO: which provider, whether email-verified flag was set by provider, and the resolve-by-email code path if readable;
- bounded impact language: arbitrary-option write ≠ RCE; same-origin file host ≠ code execution until handler parse is demonstrated; shortcode execution ≠ code execution without a dangerous registered handler.

### New durable probes

- **Payment-integrity: verify the legitimacy tuple, not just legitimacy.** The IPN item generalizes far beyond PayPal: any webhook/notification flow should be tested for *four* separable checks — signature/genuine-transaction, **environment** (sandbox vs live), **recipient merchant/account identity**, and **amount/currency/order binding**. Bug-hunt move: complete a real $0/sandbox transaction against your own lab store with the plugin pointed at live mode and observe whether the order completes. When sandbox credentials are trivially obtainable (they are), the "genuine payment" precondition collapses.
- **One-pass strip filters are defeated by nesting.** Where a sanitizer removes a token pattern once (not to a fixpoint), reassembly recreates the token. Test every "delimiters are removed" claim with embedded/overlapping spellings before concluding the shortcode/XSS surface is closed. Sibling of the sanitize-then-decode differential already on this page — same ordering-class bug, different transform.
- **Sibling-leg gating asymmetry again.** To Do List Member's import leg has neither authz nor nonce while the rest of the plugin presumably does; this is the ScadaBR pattern from the same wave (its `/export_project.htm` `createExportJSON` was left unauthenticated while the matching import path already called `Permissions.ensureAdmin()`, [GHSA-w3gv-q645-g39f](https://github.com/advisories/GHSA-w3gv-q645-g39f) / CVE-2026-94148): **when you find one gated action, immediately test its mirror** (import↔export, upload↔download, create↔import). Export endpoints disclosing project/config content are the classic forgotten sibling.
- **Cart-price trust is order-integrity RCE-adjacent logic.** Client-supplied unit/add-on prices accepted without server-side recompute remain a high-signal, low-noise ecom probe: one replayed cart request with `price=0` answers it.
- **"Token protecting uploads" is only a control if issuance is gated.** Web to Print hands its upload token to any visitor — treat every "capability token" as public material until you prove the issuance endpoint itself requires authorization. Combined with zero file validation this is straight unauth upload→RCE; keep the handler-parse proof standard from the CF7-addon item above.

### Bounded validation

Lab installs of the named plugin versions; your own PayPal sandbox account for the environment-confusion test (never production merchant credentials); inert marker files with `.php`/`.phar` variants for the upload leg; nested-delimiter canary strings rendered to a page you own; cart replays against a lab store with synthetic products. Evidence = order-status transitions, rendered-marker presence, fetched-term IDs, stored-file paths; never real donor data or live payment material.

### New durable probes

- **Render-vs-process authorization parity.** Meta Box checks edit permission when *displaying* a form but not when *processing* it. Treat every render/submit handler pair as two independent gates: find the capability check in the render path, then call the process endpoint directly without ever rendering. Sweep `process|submit|handle|save` routines paired with any checked `render|display` routine across all form-capable plugins on the target.
- **Caller-target override parameters.** A form bound to a target object must re-verify the submitter's authority over *that object*, not just over the form. Any `..._object_id`, `post_id`, `target_id`, `entity_id` GET/POST parameter that selects what gets written is a horizontal-to-vertical pivot: swap your own ID for a target page's ID and watch whether the write follows.
- **Injected content is later parsed as trusted configuration.** On WordPress, post content is a config language (shortcodes carry `role=`, `auto_login=`, prices, callbacks). Once you hold an arbitrary content-write primitive — however low-severity it looks standalone — enumerate registered shortcodes for privilege-bearing or fetching attributes, because the write + config-parser pair chains to admin. Report arbitrary-content-write findings with the concrete downstream shortcode-attribute chain, not as "content overwrite."
- **Options-update endpoints are privilege-escalation routes.** Any import/settings-save AJAX that reaches `update_option()` with only a nonce present but no capability check is a two-request admin chain (`default_role` + `users_can_register`). Grep plugin source for option-name arrays fed to settings-import handlers and test each action at the lowest authenticated role with a valid nonce (public pages often mint nonces for anyone).
- **Configuration posture is part of the exploitability proof.** Give Tributes is the third consecutive same-week exemplar (after Dancer2's `static_handler: 0` precondition and NivoCart's chunk-count asymmetry): sibling code paths carry the sanitizers, and a settings toggle decides which path runs your input. When probing deserialization/upload/shortcode sinks, enumerate every plugin option combination that changes the code path before declaring the sink unreachable — and record which toggle state you proved in the report.
- **POI without a known POP chain is a conditional finding.** Keep object-injection reports as chain-conditional: impact depends on third-party plugins/themes present on the specific target. Validate by proving deserialization occurs (timing/PHP-error/state side effect on an inert class), then state the chain precondition explicitly rather than inflating severity.

Evidence = `post_content` diffs, option-table deltas, new user rows with role, rendered marker presence; never live donation data or production option tables.

### New durable probes

- **The admin review UI is an XSS sink; the admin export is a deserialization sink.** Ninja Forms turns every public form field into a latent admin-session payload (and a latent `unserialize()` input on CSV export). Bug-hunt rule: on any form/submission platform, submit inert HTML-structural canaries (`<img src=x>`, `"><svg`) to every non-sanitized field, then check the admin viewer *and the CSV/JSON export* render of your own submission. The admin-origin execution claim needs the viewer URL and the admin-open event proven, not assumed.
- **Integration-credential parameters are options with extra blast radius.** Stripe keys, Pixabay/Unsplash/Pixels/OpenAI keys, success/cancel URLs appear in payment/API settings endpoints that were built as ordinary settings writers. Sweep every AJAX/REST action whose parameter names match `[a-z]+_api|api_key|publishable_key|secret_key|webhook` and attempt write/delete as the lowest-privileged principal (unauthenticated here for Handily/Image Buzz/PixelPlay). Payment-redirect (attacker Stripe key) beats DoS (deleted key) as a report.
- **`admin_init`-hooked handlers are authenticated-user attack surface.** `admin_init` fires for Subscribers hitting any `/wp-admin/` page. When auditing, grep for `add_action('admin_init'` and read every callback for state writes without `current_user_can()` — WPUserManager's Stripe-connect writer is the exemplar.
- **Token-vs-target binding on recovery endpoints.** A recovery token validated only for signature lets the *identifier parameter* select the victim. On any password-reset/recovery flow, obtain a token for your own account, then replay it with the user-ID parameter swapped — the check you're testing is "is this token *for* that user," which is distinct from "is this token valid." Fourth sibling of the token-link authority family (Origin-header/Host-header/origin-parameter waves).
- **Deferred-validator two-step writes.** CTX Feed: persistence and consumption are two REST calls and only the first is validated. Where a settings-save endpoint stores a path/URL/ID and a *different* action later consumes it, test the pair: store your own marker payload via call 1 (always your own data), trigger via call 2, and observe whether call 2 revalidates. Same pattern as the config-write ladders page's ZLMediaKit item, WordPress-shaped; the extension whitelist on the delete leg is itself recon (it tells you which files the sink will touch).
- **Numeric-cast validators keep the string tail.** `(float)`-validated parameters accept `1<img …>` because the cast succeeds on the prefix while the original string persists. Any "validated as number/float/int" parameter should be probed with numeric-prefixed markup; compare the stored bytes against the cast value.
- **Serialized storage defeats tag-scanning sanitizers.** `wp_kses`-style filters tokenize real HTML; payloads hidden inside serialized/json-encoded values sail through and unescape later. On page builders and settings blobs, submit payloads in encoded/serialized shapes and check the *render* leg independently of the save leg.
- **Boolean-precedence guards can be dead code.** An authorization `if` with mixed `&&`/`||` may never trigger. Never conclude a guard works from its presence — always run the negative control (role that should be denied, own object, then foreign object).
- **Check the children, not just the parent.** Nested-ID payloads (Tutor LMS) cross object ownership whenever only the outermost ID is authorization-checked. On any tree-shaped save endpoint (course→topic→quiz→question, order→item→addon), submit your parent's ID with a foreign child ID inside the payload.
- **Imported third-party content is an unauthenticated attacker channel.** Yelp reviews, feeds, oEmbed, media metadata: content ingested from public platforms often bypasses the site's own input controls because the *site owner* clicked "download." Treat every platform-ingest feature as unauth stored-content injection into the site's renderers.

- Durable axes: (1) **collection-level vs object-level capability checks** — `edit_posts` ("may edit posts of this type") is not `edit_post` ("may edit *this* post"); any authorization code that only references the `cap->edit_posts`-shaped properties is the shape of this bug. (2) **Sibling-resolver parity diff**: whenever a GraphQL API exposes create/update/delete on the same object, diff their authorization code — WPGraphQL's create was correct and update was not; audit *both* directions (a check present in one resolver proves the semantic requirement exists, so its absence in the sibling is a bug, not a design choice). (3) **REST-vs-GraphQL parity battery**: on any WordPress site with GraphQL enabled, run every capability-sensitive operation twice — REST `wp/v2` and GraphQL mutation — with a Contributor/Subscriber token; a REST 403 + GraphQL 200 differential *is* the finding, and the differential harness doubles as your negative control (same input, two routers, two verdicts).
