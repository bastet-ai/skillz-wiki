# XOneManager wave (6 GHSAs): a read-only member publishes updates to devices

Sources: coordinated XOneManager 3.8.3.0 advisory set published 2026-11-20T12:31Z: [GHSA-xw34-92vg-8vj9](https://github.com/advisories/GHSA-xw34-92vg-8vj9) (critical, `tablesData` SQL), [GHSA-6gvj-h93p-38c2](https://github.com/advisories/GHSA-6gvj-h93p-38c2) (critical, update publication bypass), [GHSA-vqj3-qpvp-vhh9](https://github.com/advisories/GHSA-vqj3-qpvp-vhh9) (high, project creation bypass), [GHSA-mx6f-4r6h-rwh8](https://github.com/advisories/GHSA-mx6f-4r6h-rwh8) (high, user-controlled database key), [GHSA-jrmh-r8q2-9xhf](https://github.com/advisories/GHSA-jrmh-r8q2-9xhf) (medium, `admusers` authorization omission), [GHSA-5m9w-9wmv-xh59](https://github.com/advisories/GHSA-5m9w-9wmv-xh59) (medium, `users` POST authorization omission).

**Wave in one line:** XOneManager 3.8.3.0, a device-management console exposing a `/xmanagercore/api/services/` JSON-RPC-style surface, checked *neither* role nor object ownership on six operations, so an authenticated project member with read-only access could publish crafted software updates to managed devices, run SQL as the service account against databases outside their project (including the authentication database), and reach user-administration POSTs.

!!! warning "Authorized scope only"
    Validate only in a lab XOneManager instance you own with disposable projects, users, and managed-device simulators. The update-publication leg writes real firmware/update distribution state for the managed fleet; never exercise it against production devices. SQL probing should be limited to synthetic canary tables and existence/differential evidence, not reading authentication database contents out of a live deployment.

## Why this is worth an operator page

This is a management-console authorization-collapse wave: every defect is the same meta-shape (the server processes the operation without verifying the permission the UI implies exists), and the fleet-update publication leg turns the lowest-role project token into a supply-chain primitive against every managed device. Treat device-management consoles as credential-to-everything pivots, the same doctrine as the Nov 18 ManageEngine DDI Central fold on the Sept 21 management-plane page.

- **Update publication is a write path that skipped its gate ([GHSA-6gvj-h93p-38c2](https://github.com/advisories/GHSA-6gvj-h93p-38c2), critical).** The server accepted the initial publication requests from an authenticated *read-only* project member with no publication-permission verification; completing the workflow distributes modified update content to managed devices. Rules: (1) **enumerate the update/rollout/publish endpoint family separately from CRUD**, the operations that touch the fleet are often guarded (or unguarded) in their own code path; (2) read-only is a UI concept, so the read-only member token is the correct first credential to point at *every* POST/PUT you can enumerate from the admin console; (3) report framing: this is fleet compromise with integrity loss, one low-priv account versus every managed device.
- **A `filter` parameter that becomes SQL under the service account ([GHSA-xw34-92vg-8vj9](https://github.com/advisories/GHSA-xw34-92vg-8vj9), critical).** The `tablesData` operation of `POST /xmanagercore/api/services/` executes queries built from a caller-supplied `filter` without verifying execution permission, and the queries run with the *service account's* database permissions; testers queried databases outside their own project including the authentication database. Rules: (1) any report/table/grid endpoint with a free-form filter, sort, or expression parameter is a SQL-injection candidate *and* a privilege oracle at once: the identity that matters is the database user, not your login, so cross-database probing is the escalation proof; (2) when grid endpoints return service-account results, the confused-deputy framing (your token, their privileges) is the report lead; (3) the authentication-database reachability means credential-hash extraction and the local auth bypass chain: enumerate what the reachable databases contain before choosing impact claims.
- **Database selection by user-controlled key ([GHSA-mx6f-4r6h-rwh8](https://github.com/advisories/GHSA-mx6f-4r6h-rwh8), high) plus unguarded project creation ([GHSA-vqj3-qpvp-vhh9](https://github.com/advisories/GHSA-vqj3-qpvp-vhh9), high).** `ConvertBDToProject` picked the backing database from a caller-supplied `databasename` with no permission check, letting a basic user link their project to any database on the server and *enumerate existing databases from API responses*; separately, the same operation was reachable without the administrative role, so any basic user could create a project and execute SQL on its linked database. Rules: (1) the user-controlled-key authorization-target fallback (the key selects a resource the caller should not be able to name) is the same family as the Sept 19 WP alternate-surface and the June Keycloak `databasename`-class checks: replay every operation with a sibling/foreign key and diff response shapes; (2) **differential error text on an unguarded key-selection parameter is a free inventory oracle**; "database not found" vs "permission denied" vs success enumerates the whole instance; (3) unguarded *create* operations matter even when the entity seems benign, because creating the object often hands you a legitimate-looking anchor for SQL or config writes elsewhere in the same feature.
- **User-administration POSTs with no authorization check ([GHSA-jrmh-r8q2-9xhf](https://github.com/advisories/GHSA-jrmh-r8q2-9xhf), [GHSA-5m9w-9wmv-xh59](https://github.com/advisories/GHSA-5m9w-9wmv-xh59), medium).** `POST /xmanagercore/api/services/` accepted `admusers` and `users` operations without authorization verification. Rule: for JSON-RPC-style single-endpoint surfaces (one URL, operation name in body), authorization is implemented per-operation and is exactly where implementers forget; **build the operation-name inventory from the JS bundle or Swagger and replay every operation with the lowest-role token**, method-route enumeration finds nothing here because there is only one route. The Oct 7 Backstage DWR/legacy-endpoint rule (enumerate non-canonical endpoint frameworks separately) extends to single-endpoint RPC envelopes.

## Replayable validation sequence (lab)

1. Lab XOneManager 3.8.3.0 with a disposable project, a Read Only project member account, and a second synthetic project owned by another lab user as the foreign-target source.
2. Extract the operation inventory: pull the console JS bundle, grep for `xmanagercore/api/services` call sites and operation-name strings (`tablesData`, `ConvertBDToProject`, `admusers`, `users`, publication methods).
3. Decision table: every operation x {read-only member token, standard member token, non-member token}; record 200-vs-401/403 per cell. Any admin/fleet operation returning 200 for the read-only token is the finding.
4. For `tablesData`, prove the boundary with synthetic canaries only: a `filter` that references a second lab database you created, and time/error differentials; do not pull authentication-table rows from any deployment with real users.
5. For `ConvertBDToProject`, use canary database names to map the differential response shapes (not-found vs linked) without touching real project databases.
6. For the publication leg, target only simulator devices you control; capture the device-side update source change as the impact proof, then abort.
7. All version fields in the GHSAs were empty except the 3.8.3.0 statements in the summaries; fingerprint the console build (login page hash, `/xmanagercore/` banner) before claiming coverage.
