# MCP gateways, session stores, clients, and browser bridges: the trust lives outside the tool call

Source: GitHub Security Advisory waves published 2026-09-24 through 2026-09-30 (cross-checked against vendor text). Related existing pages: [Sept 15 MCP DNS-rebinding/alternate-auth page](2026-09-15-mcp-dns-rebinding-alternate-auth-path-and-sandbox-boundaries-ghsa.md), [Sept 22 mcp-atlassian server-side-credential deputy page](2026-09-22-mcp-atlassian-server-side-credential-deputy-cluster-ghsa.md), [Aug 6 agent tool-policy/file-fetch page](2026-08-06-agent-tool-policy-file-fetch-boundaries-ghsa.md), [Aug 18 editor-extension webview supply-chain page](../methodology/editor-extension-webview-file-write-boundary-testing.md).

This cluster is durable because every entry attacks a layer the tool-call authorization model never covers: **session identity, client-side trust of servers, browser-origin gates on local bridges, and the agent's own prompt channel**. One rule covers the batch: *the MCP protocol has more actors than "server checks tool call" — audit each actor's trust separately.*

## Durable axes

1. **Sessions are credentials — audit the key, not the login.** A gateway that authorizes endpoints but dispatches sessions by a bare client-supplied ID has no session authorization at all. Proofs: forge/replay a session id between two disposable tenants; check `/health`, `/sessions`, `/stats` for unauthenticated ID disclosure first.
2. **The server→client direction of MCP is an unauthenticated input channel.** OAuth metadata URLs, `WWW-Authenticate` fields, and server-chosen URLs/paths all cross into the client's fetch/file/exec stacks. Threat-model hostile servers explicitly — connect from a network-monitoring VM with a canary file tree.
3. **Browser-origin gates on local bridges are the weakest link** (equality checks, CORS misconfig, reflected ACAO). DNS rebinding with TTL-0 A→127.0.0.1 defeats Origin==Host; test bridges from an owned rebinding domain in a real browser.
4. **Agents that ingest untrusted text into chat templates must neutralize structural tokens.** `<|im_start|>`-style literals surviving into tokenizer input = role forgery at CVSS 10. This applies to every recon-crawl→LLM pipeline, including offensive tooling you operate.
5. **Debug/inspector/health routes ship to production** and carry more privilege than the tool surface. Enumerate them before testing a single tool.
6. **Documented quickstarts are the default deployment.** `0.0.0.0` binds, auth-off examples, and `docker.sock` mounts in READMEs are the fleet posture; fingerprint and verify, and treat docs-only "fixes" as unpatched.
7. **Prefix allowlists without boundary anchors fail one directory over.** Regex `^/allowed` and `startsWith(root)` both admit the sibling. One canonical test tuple per guard: `<root>-canary` / `<allowed>2`.

## Validation boundaries

Use disposable MCP deployments, synthetic tenant users, and marker rows/sessions only. Drive rebinding and bridge tests from owned domains and your own browser profile. Never replay real session IDs or tokens observed on shared infrastructure beyond a single authorized read-decision check; never invoke host Docker controls outside a lab VM; plant prompt-injection canaries only in targets you own or that authorize it. No live OAuth credentials, tenant data, or production gateway probing in wiki evidence.

## October 1 21:3xZ follow-up: DeepTutor shell tool — the agent's own ExecTool is the RCE route (folded)

**DeepTutor v1.4.0** ([GHSA-23c2-f3h2-xmcw](https://github.com/advisories/GHSA-23c2-f3h2-xmcw), 9.8): command execution reachable through `/tutorbot/agent/tools/shell.py:ExecTool.execute` — the agent framework ships a *shell tool* and the advisory's sink is that tool's execute path, reached through the agent's normal conversation/tool-call channel.

This is the wave's invariant landing on a consumer-facing tutor product instead of a gateway: once a product embeds an agent with a shell-capable tool, **the prompt channel *is* the command channel** — no separate exploit primitive is needed once the model can be steered (direct input, or any content the agent ingests). Triage fingerprint for any agent-product deployment: enumerate its tool registry (`tools/`, `agent/tools/`, MCP server listings) and record which tools exist — `shell`/`exec`/`python_exec`/`fs_write` presence is the risk ceiling, independent of the product's marketing surface. ## October 2 follow-up: the DeepTutor wave completes the picture — tool layer, ID space, and MCP output_path

The Oct 1 DeepTutor ExecTool item was one advisory; the Oct 2 batch (CVE-2026-51876/51878/51879/51880/51881) completes the sweep of the same product and sharpens three rules:

- **The tool layer is reachable through the WebSocket channel, not just HTTP** (CVE-2026-51881 ExecTool shell via live tutorbot WebSocket; CVE-2026-51880 `EditFileTool` writes absolute paths outside the bot workspace). When you fingerprint an agent product, enumerate its *transport surface* too — a WebSocket "live tutorbot" interface that reaches the same `*.execute()` tool sinks as the HTTP API is a second, usually less-audited entry point (no CSRF, different auth middleware, often no rate limiting).
- **IDOR across every agent object class**: `session_id` reuse to regenerate another user's turn (51878), enumerable `bot_id` to overwrite another bot's whitelisted control files over HTTP (51879), publicly exposed `book_id` to overwrite persisted metadata via confirm-proposal (51876). Agent apps carry a *menagerie* of object IDs (session, bot, book, conversation, workspace); the authz gate is per-object-class and drifts per class. Run the cross-tenant ID replay per class, not per endpoint.
- **MCP server tool parameters are file-write sinks with a prompt-injection driver**: [GHSA-xpvr-6r3p-gm34](https://github.com/advisories/GHSA-xpvr-6r3p-gm34) / CVE-2025-71427, Office-PowerPoint-MCP-Server ≤ 2.0.7 — `save_presentation`/`open_presentation`/`manage_image` accept absolute paths and `../` in `output_path`, so prompt-injecting an agent that holds this server turns "make me a deck" into overwrite-any-writable-file / read-external-file. Audit rule for every MCP server in your bundle or target's bundle: grep tool schemas for path-ish parameters (`path`, `output_path`, `filename`, `file_path`) and test whether the server anchors them to a root *server-side*. The model is not a security boundary; the tool implementation must be.

Validation: owned agent deployments, marker files inside disposable roots, two disposable tenant accounts for the ID-replay matrix, inert MCP tool invocations that only write marker paths.

## October 15 follow-up: IntentKit and MoviePilot — the advertised toolset is not the executable toolset, and the approval flag is a model-settable parameter

Two advisories from the Oct 15 03:36Z wave close two gaps in the same agent-tool gate pattern: *which tools may run*, and *who may say "yes" to a dangerous one*.

**IntentKit ≤2.6.3 — executor validates against the full registry, not the per-request advertisement ([GHSA-6qqv-mhm9-qrfj / CVE-2026-76066](https://github.com/advisories/GHSA-6qqv-mhm9-qrfj), high).** A `ToolBindingMiddleware` narrows the tool list advertised per request/context (WEB, API, TWITTER, TELEGRAM), but the executor validates incoming tool calls against the **full tool registry**. Supplying the exact name of a *de-advertised* owner-only tool — wallet transfer, posting, memory-write, call-agent — executes it with no human-in-the-loop approval gate, reachable by unauthenticated/public callers via indirect prompt injection or by replaying checkpoint/history data on a reused thread.

**MoviePilot ≤3.1.5 — prompt-injected content sets its own approval flag ([GHSA-f3rc-mp36-mqvp / CVE-2026-77931](https://github.com/advisories/GHSA-f3rc-mp36-mqvp), high).** Untrusted content entering `browse_webpage`, `search_web`, and torrent-metadata parsers can carry instructions that steer the agent into calling `execute_command` with **`confirm_dangerous` set to true** — a tool *parameter*, so the injected content supplies the confirmation the deny-list check (`validate_command_safety`) expected to be human-controlled. Execution lands in `asyncio.create_subprocess_shell` under the admin session's `is_admin` context → host RCE.

Operator rules:

1. **De-advertised ≠ disabled.** In any agent framework that filters `tools/list` per context, enumerate the full registry from source/config (`tools/`, registry dicts, middleware fixtures) and probe the *execution* endpoint with the exact de-advertised names. Advertisement narrowing and execution validation are two code paths; test each independently. This is the tool-plane twin of the disabled-setting-at-router rule — a UI-side filter that the executor never rechecks.
2. **Approval flags as tool arguments are theater.** Grep every dangerous tool schema for confirm/approve/skip-safety booleans (`confirm_dangerous`, `force`, `confirmed`). If the model composes the arguments, prompt-injected content can set them. A real gate renders approval *outside* the tool call (server-side interrupt the model cannot emit). Reproduce with an owned lab agent fed a page containing an inert marker-command instruction; prove invocation reaches a marker file, never a real payload.
3. **History/checkpoint replay is a second injection channel.** IntentKit's bypass also fired by replaying persisted checkpoint/thread data — retained conversation state re-enters the executor under the *original* (higher) context. Sweep persisted-state resume endpoints separately from live input channels.
4. **Deny-list on the command string is layer-mixing bait.** `validate_command_safety` inspecting the command text while the *confirmation* rides as a parameter means both checks trust model-supplied data. When auditing agent stacks, chart who controls each input to a dangerous tool: model, injected content, or server.

## October 19 follow-up: Google Agent Mesh (SAM) — the side-door ingress has no auth, and "authenticated" defaults to owning everything

A two-critical advisory wave against **Google OSS Agent Mesh (SAM)** (alpha line, fixed 0.1.0-alpha.3 / alpha.9) delivers two clean transport/enrollment-plane primitives for any agent mesh or MCP gateway deployment.

**Parallel ingress route skips the auth middleware entirely ([GHSA-vc9x-qg3j-cxg6 / CVE-2026-102503](https://github.com/advisories/GHSA-vc9x-qg3j-cxg6), critical, 0.1.0-alpha.1–alpha.2).** SAM's MCP protocol stream handler enforces `WithBiscuitAuth` + `Authorize` checks — but `StartIngressServer` registers a **`/libp2p-http` ingress** that routes requests *directly to backend service handlers* with no Biscuit token verification and no mesh enrollment check. An unauthenticated remote libp2p peer invokes arbitrary registered backends: command/stdio-backed MCP servers, A2A, inference endpoints. The auth gate and the attack path are two different listeners reaching the same handler table.

**Self-enrollment + wildcard default policy = hand the mesh to the internet ([GHSA-qx8v-pq9p-7g7v / CVE-2026-103091](https://github.com/advisories/GHSA-qx8v-pq9p-7g7v), critical, through alpha.8).** Three composed defects: `GET /info` publicly discloses the OIDC configuration; `POST /register` **auto-enrolls any holder of a valid OIDC token** with no claim filtering and no ban checks; and the default policy binds `sam:system:authenticated` to **wildcard services and targets**. Attack chain: read `/info` unauthenticated → obtain any token the configured issuer will mint (your own free tenant seat) → `POST /register` → full read/write/execute across every connected MCP backend node. The alpha.9 fix enforces a fail-closed default policy, explicit policy-binding requirements at enrollment, and ban checks — i.e., all three legs were genuinely absent.

Operator rules:

1. **Enumerate every listener that reaches the tool handlers, then test each one's auth independently.** The authenticated MCP transport proves nothing about a sibling libp2p/HTTP/gRPC/WebSocket ingress registered against the same backend table. Fingerprint: in source or via route/protocol probing, map all `Start*Server`/`Handle*` registration sites and run the unauthenticated tool-invocation battery against each. This is the STOMP/WS transport-parity rule restated at the mesh plane — same class as Gitea REST-vs-MCP entry-point parity and PraisonAI's SSE-vs-HTTP tool transports. libp2p adds a twist: the "client" is a *peer*, not a browser, so CORS/origin thinking doesn't apply — just dial it.
2. **`GET /info`-style config disclosure + open `POST /register` + `authenticated → *` default policy is a complete unauth-to-tool-RCE chain with zero bugs.** Audit any agent mesh/OIDC-gateway product with three unauthenticated probes: (a) does an unauthenticated endpoint leak the OIDC issuer/config? (b) does the enrollment/register endpoint accept any issuer-valid token, or does it filter claims (tenant, audience, allowlist) and check revocation/ban? (c) what capabilities does the bare `authenticated` principal hold — grep the default policy for wildcard service/target bindings. Any green answer is the finding; the fix-release diff (fail-closed defaults) tells you which leg mattered.
3. **Auto-enrollment is a standing-access factory.** Ban/deletion enforcement only matters if enrollment re-checks it; check-then-gate drift here is the enrollment-path twin of the auth-cache revocation-free side channel (pyLoad) and stale role refresh (SmarterMail) — identity decisions made once and cached past the lifecycle event that should have revoked them.
4. **Alpha-version agent meshes are being deployed.** The product is 0.1.0-alpha; fingerprint SAM/agent-mesh deployments by libp2p banner noise, `/libp2p-http`, `/info`, `/register` routes, and Biscuit-token naming, and run the chain on any you own or are authorized to test.

Validation boundaries: disposable mesh deployments only — your own OIDC tenant for the enrollment leg, canary MCP backend tools that record invocations, and synthetic capability tokens. Never register against a third-party mesh, never invoke real tenant-connected backends, and never collect live Biscuit/OIDC tokens observed on shared infrastructure.

Tracked from the same 03:31Z wave, no publish: GeoWebServer.exe default-port pair CVE-2026-108983/108984 (zero-detail, single-sentence description — revisit if detail lands), BIRD IPv6 FlowSpec nonzero-offset validation bypass CVE-2026-112112 (RFC 8956 §5 validate-reconstructed-prefix vs original-component differential; requires established BGP peer, routing-infra-only), openGauss `HllObjectUnpack()` lenTotal-vs-lenUsed heap overflow CVE-2026-111441 (authenticated SQL surface, memory-safety class), cal.com webhook `createWebhookProcedure` id-argument authz bypass CVE-2026-112043 (IDOR class), dotnet eShop Catalog API improper auth CVE-2026-112044 (demo app), plus the routine vuldb thin singles (diem ×9, iWebShop ×5, light0011 cms ×4) and rejected/re-listing batch.

## October 19 follow-up: Envoy AI Gateway MCP proxy — the anti-hijacking subject is embedded in the session ID and then thrown away at resume ([GHSA-953h-535j-jg2v](https://github.com/advisories/GHSA-953h-535j-jg2v), medium, plus default Helm seed)

Envoy AI Gateway's MCP proxy encodes the authenticated caller's JWT `sub` **inside** the encrypted `Mcp-Session-Id` blob (`{routeName}@{subject}@{backends}`, salt‖nonce‖AES-GCM ciphertext) precisely per the MCP spec's session-hijacking guidance — then `sessionFromID()` at all three resume paths (GET/POST/DELETE) parses the blob and **discards the subject without ever comparing it to the current request's authenticated caller**. The `extractSubject()` helper is called exactly once, at session creation. Session resume = possession of a decryptable blob, so any user holding another user's session ID (or forging one outright, because the official Helm chart and both binaries default `sessionEncryption.seed` to the literal publicly-known `"default-insecure-seed"` with a fixed PBKDF2 iteration count) resumes that user's backend MCP sessions and invokes `tools/call`/`resources/read` in the victim's already-initialized context.

Operator reading:

- **"Embedded for security purposes but not needed during parsing" is the finding.** When a credential blob carries an identity discriminator, grep for every consumer of the field: creation-site-embed + resume-site-discard is a two-minute source audit on any session-store implementation (MCP gateways, OAuth state, capability tokens). The comment literally documents the defect.
- **Default-seed crypto turns "obtain a session ID" into "forge one for an arbitrary subject."** Same shipped-known-secret class as the Gravitee/vlife default JWT secrets — for any product whose Helm chart/values.yaml or `main.go` flag default is a literal seed/secret, derive the key from the public default in a lab and prove you can mint a valid blob for a synthetic subject. That proof needs no victim at all.
- Probe shape for MCP gateways generally: mint session as tenant A, replay the ID under tenant B's token across all three resume verbs (SSE GET, POST, DELETE), and separately check whether the encryption key material has a public default. Route-class parity applies too — compare REST vs MCP entry points on the same backend binding.

Validation boundaries: own gateway deployment with two synthetic JWT subjects and a recording mock MCP backend only; never replay session IDs observed on shared infrastructure, never derive keys against live multi-tenant gateways.

## October 20 follow-up: IBM ContextForge MCP Gateway — the OAuth `token_url` is a full-read SSRF because the page's guard-parity rule again (6f4r/CVE-2026-8355, 0.1.0–1.0.5)

ContextForge's gateway registration applies SSRF protections to `gateway.url` but **not to `oauth_config.token_url`**: an authenticated user with gateway-creation rights registers an OAuth client-credentials gateway pointed at any internal service, cloud metadata endpoint (IMDSv1, GCP, Azure), or localhost port — the server immediately issues an attacker-shapeable **HTTP POST with form-encoded credentials in the body**, and when the response fails OAuth parsing, **up to 256 characters of the response body are reflected in the HTTP 502 error message**. Guard-on-one-field-not-its-companion, plus an error-text read-back channel: this is the guard-coverage-diff rule this wiki keeps re-listing, now on the MCP-gateway plane.

- Operator reading: when a product validates one URL field, enumerate **every** other field whose value ends up in a fetch — config-URL siblings (`token_url`, `jwks_uri`, `discovery_url`, `webhook_url`, `callback_url`) are the classic misses (OpenAM `jwks_uri` June 22, Mattermost LDAP/AD Test-Connection Oct 16, Conductor `specUrl` Oct 13). The partial-body-reflection-in-error detail is the read-back tell: score 502/400 bodies for reflection before concluding blind.
- POST-with-credentials-to-arbitrary-destination also crosses into request-forging against localhost-only admin panels that accept POST — pair with the loopback control-plane pages (July 8) when assessing multi-tenant gateway deployments. Prove with owned callbacks and synthetic internal marker services in a lab instance only; never target cloud metadata on shared infrastructure.

## October 26 18:3xZ follow-up: MoviePilot — injected content self-approves its own shell tool by setting `confirm_dangerous=true`, and the denylist sits behind the flag (CVE-2026-77931 / [GHSA-f3rc-mp36-mqvp](https://github.com/advisories/GHSA-f3rc-mp36-mqvp), high, ≤3.1.5)

Untrusted content entering through `browse_webpage`, `search_web`, and torrent-metadata parsers steers the model to invoke `ExecuteCommandTool` with **`confirm_dangerous` set to true**, which bypasses the `validate_command_safety` denylist and lands in `asyncio.create_subprocess_shell` under the admin session's `is_admin` context → RCE on the host.

Durable axes for every agent-platform hunt:

- **A tool parameter can carry the confirmation the safety layer expects from the human.** If the confirmation flag lives in the tool's *argument schema* (model-supplied) instead of out-of-band UI state, prompt injection sets it. Audit predicate: grep the tool schema for `confirm`, `dangerous`, `force`, `skip_check`, `approved` fields — any safety decision readable from the same object the model authors is decorative. The approval must be a *second channel* (human click, separate API call with session proof), never a field in the payload the guarded action already accepts.
- **Denylist-gated sinks inherit the gate's bypass:** `validate_command_safety` ran *after* the flag check, so one injected boolean skipped it entirely. Build the decision table per dangerous tool: (flag=false, benign cmd) / (flag=false, denylisted cmd) / (flag=true, benign) / (flag=true, denylisted) — the (true, denylisted) cell is the finding.
- **Content-intake = injection-intake parity sweep:** enumerate every path where third-party bytes reach the context (webpages, search results, torrent/magnet metadata, subtitles, filenames) and pair each with the tool inventory reachable from that context; the host-RCE chain here needed no tool bug at all — only content → model → self-approved command.
- Validation boundary: lab MoviePilot instance, prove with a marker command in the container (`id > /tmp/canary`), never against shared/private trackers or third-party instances.
