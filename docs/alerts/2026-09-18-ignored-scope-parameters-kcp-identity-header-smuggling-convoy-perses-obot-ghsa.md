# Scope parameters that are accepted but never enforced: kcp identity-header smuggling, Convoy list-vs-get IDOR, Perses query-param tenancy, Moquette Will-path ACL gap, and Obot OAuth audience confusion

Source: hourly offensive-security scan of GitHub Security Advisories, 2026-09-18 (waves published 2026-09-18T17:15Z–17:59Z).

One theme ties the durable records: **the authorization layer and the data layer disagree about what scopes the request.** A URL path parameter that gates the permission check is dropped before the query runs; a query parameter silently overrides the path scope; a protocol side-channel (MQTT Will, proxy identity header) reaches a sink the main path guards; an HTTP method collapses onto the wrong action; a signed digest field is never re-verified. Each is a separate, immediately testable audit axis.

## Why this is worth an operator page

- **Identity headers over an "internal" mTLS leg are only as trusted as the proxy's strip behavior.** kcp's shard trusts `X-Remote-*` because it only accepts the front-proxy connection — but the front-proxy appended instead of replaced. Sweep every reverse-proxy/aggregation hop on a target: send your own `X-Remote-User`, `X-Remote-Group`, `X-Forwarded-User`, `X-Auth-Subject` style headers and diff the downstream verdict. This is the header twin of Sept 18's Nextcloud request-URI-identity drift and the classic `X-Forwarded-For` identity steering.
- **Compare list vs single-item authorization, always.** Convoy's list endpoint scoped by project; the get-by-ID endpoint's service function took the project ID and dropped it before SQL. For every collection you can list, fetch one foreign-tenant item by ID through the same route pattern and diff. A parameter present in the handler signature but absent from the query is grep-able in any open-source target (`FindSourceByID(ctx, project.UID, sourceID)` → `WHERE s.id = $1`).
- **Query parameters that shadow path scope are tenant-isolation holes.** Perses authorized the `{projectID}` in the URL and then let `?project=` re-point the lookup. For every path-scoped collection route, append the common scope words as query params (`project`, `namespace`, `tenant`, `org`, `group`, `scope`) and diff result sets against the path value.
- **Validation asymmetry between write and read paths leaks paths and rows.** Perses validated the project string on Create/Update bodies but not list queries — traversal landed in the read path. When you find a validated input on POST, immediately test the *same field* on GET/list/search endpoints.
- **Confused-deputy decrypt: authorize the wrapper, then name the secret.** If any endpoint that authorizes scope A will resolve/decrypt/attach an object from scope B named in your body, you own a secret oracle. Enumerate endpoints where a body field names a credential/secret/config object and check the response path returns the plaintext (datasource "connectivity check" features are favorite hosts for this).
- **Protocol side-channels re-implement publish.** The broker checks ACLs on client PUBLISH but not on the Will it publishes *itself* after an abrupt disconnect. For any broker (MQTT/Kafka hooks/webhooks/AMQP), list every way a message reaches subscribers (direct publish, Will/LWT, retained messages, delayed/queued redelivery, system events) and diff which paths hit the authorization call.
- **Signed-digest fields that the server never recomputes are signature bypasses with extra steps.** AnyCable's `body_md5` was in the HMAC string but never compared against the body. When an API signature scheme includes a body digest, hash a different body yourself and replay; also test `auth_timestamp` staleness independently.
- **Method-to-action mapping collapse.** zot turned DELETE into "push" and skipped the fine-grained authorizer for bearer tokens. When a token has narrow scopes, replay it against every HTTP method on the same route — especially destructive verbs — and check whether a *different* authorization middleware applies per auth mechanism (bearer vs basic).
- **OAuth audience confusion via dynamic client registration.** Unauthenticated DCR + unrestricted redirect + no consent + a token carrying the resource-server's *authorization groups* + issuer-checked-but-audience-ignored = one-click token theft. On any OAuth-capable platform with DCR enabled: register a client with your own redirect, craft the authorize URL, check whether a consent screen actually renders, and (with your own second lab account) inspect which claims/groups the minted token carries vs its `aud`, then test it against the general API, not just the MCP endpoint.
- **Reflected-error SSRF beats blind SSRF.** Obot's metadata-sync SSRF returns the fetched body inside error messages and fires automatically on reconcile. When registering attacker-controlled URLs into any platform (MCP servers, webhooks, OAuth issuers, remote configs), test whether platform-generated error text echoes upstream response bytes.
- **Default-allow authorizers are denylists of protected routes.** Obot's second advisory: the authorizer enumerated known-protected prefixes and allowed everything else; every new top-level mount is anonymous until someone remembers to add it. Enumerate top-level route prefixes on authed products and re-check 401-vs-200 on each — especially mounts added recently.

## Validation workflow (authorized scope only)

!!! warning "Disposable tenants and synthetic objects only"
    Build two disposable projects/workspaces/tenants with a canary credential object in the victim tenant and prove cross-tenant read with a *synthetic* broker password or canary secret. For header smuggling, forge identity headers only against lab front-proxies you own and record authorization verdicts — never assert `system:masters` against shared infrastructure. For OAuth proofs use two of your own lab accounts and an owned redirect domain; revoke tokens immediately. For MQTT, run a lab broker with fake ACL topics; never Will-publish into production topics.

1. **List-vs-get IDOR sweep.** For every collection route: enumerate as user A in tenant A, then fetch one foreign item ID via the single-item route from tenant B; diff status + body. Grep open-source targets for service functions that take a scope/tenant parameter and never reference it in the query.
2. **Query-shadow probe.** For every path-scoped collection, append `?project=`, `?namespace=`, `?tenant=`, `?org=` pointing at a foreign scope; compare payloads against the path-scoped positive control.
3. **Read-path validation probe.** Take any input the API rejects as malformed/invalid on POST and send it raw on GET/list/search; watch for traversal artifacts (`../` list results, path echoes, 500s with path fragments).
4. **Broker side-channel matrix (MQTT labs).** Per ACL policy: direct PUBLISH verdict, Will-message verdict (CONNECT with restricted Will topic + TCP RST), retained-message verdict, subscription verdict. Moquette proved the Will leg is the one implementers forget.
5. **Method/scope replay.** With a narrowly scoped bearer token, replay DELETE/PUT/PATCH against routes where the token scope should deny, and compare bearer vs basic-auth verdicts on the same route.
6. **Digest-replay test.** Capture any signed request with a body-digest parameter; resend the same query string with a mutated body; also resend with an old `auth_timestamp`.
7. **Front-proxy header strip check.** Send forged `X-Remote-*`/identity headers through each proxy hop chain in scope and diff downstream identity-derived decisions (lab targets only).
8. **DCR/audience audit (owned accounts).** Register a DCR client, walk the authorize flow with a second lab account, record consent-screen presence, decode the minted token's groups/aud, and test the token against the general API surface.

## Reporting checklist

- State the exact scope parameter that was ignored (path vs query vs service-layer argument) and show the positive control (same request, in-scope object) beside the cross-tenant result.
- For credential leakage, quote only the canary value and name the JSON field; never paste live broker passwords.
- For header smuggling, include the proxy hop diagram and the raw request/response verdict table.
- For races (Paymenter-style), report concurrency count, observed N× credit delta, and whether idempotency keys exist.
- Version/commit pin each verdict (Convoy has **no patch** as of v26.6.2 — mark as disclosure-pending).

## September 23 follow-up: share-link **minting** skips the ownership check the read path enforces (Photoview)

- **Photoview through 2.4.0 `shareAlbum` GraphQL mutation authorization bypass** (CVE-2026-96271, [GHSA-r72q-r5vm-p79c](https://github.com/advisories/GHSA-r72q-r5vm-p79c), high): any authenticated user supplies an **arbitrary album ID** to the share-link mutation and receives a working share token for a **victim-owned** album — photos and sub-albums exposed to anyone with the link, and the attacker **retains indefinite control over the token's settings** (expiry/password) because they minted it. The read path checks ownership; the *link-creation* path checks only "is authenticated."
- Durable axis, sibling of the list-vs-get drift above: **token/share/invite minting endpoints are authorization sinks independent of the read endpoint they gate.** The share feature is commonly a separate resolver written later, with only a login gate. Sweep rule: for every object type with a share/public-link capability, enumerate the *mutation* that creates the link and replay it with foreign object IDs from your second lab account — a 200 with a usable token is the finding even if every read route tests clean. Two extra report dimensions unique to this class: the minted link survives the victim revoking *their own* shares (attacker-controlled token settings), and the exposure audience is "anyone with the link," so severity includes unauthenticated third parties, not just the attacker.
- Validation stays two-account: disposable user B mints a share for user A's album containing one canary photo, fetch the public link anonymously, record album ID field name, token TTL, and which settings the minter can still change. Never mint links against real instances' shared content beyond an owned canary album.

## September 23 evening follow-up: Moquette pattern-ACL **wildcard injection** — your identity string is a glob (CVE-2026-85724 / GHSA-5f42-97gr-vfhq, CVSS 9.6)

- **Moquette pattern-based ACL cross-tenant bypass** ([GHSA-5f42-97gr-vfhq](https://github.com/advisories/GHSA-5f42-97gr-vfhq), critical): multi-tenant MQTT deployments use pattern ACL rules like `sensor/%c/#` (per-client topic trees). `AuthorizationsCollector.canDoOperation` substitutes clientId/username **raw** into the pattern and then wildcard-matches it, and the clientId is never validated for MQTT wildcard characters (`+`, `#`) at CONNECT. A client that connects with clientId `+` turns `sensor/%c/#` into `sensor/+/#` — **cross-tenant read and write on every sibling tenant's topic tree from one CONNECT field**. Same advisory also ships a broker-wide DoS (the `SessionEventLoop` catches only `InterruptedException` and is never restarted, so any uncaught exception — malformed `$share/` SUBSCRIBE, deep topic nesting, ACL NPE — wedges all co-located clients) and a durable-session cross-session corruption bug.
- Durable axis, generalized beyond MQTT: **when an authorization policy interpolates an identity string into a pattern/glob/template, the identity becomes pattern syntax — inject the metacharacters into the identity itself.** This is the same class as sudoers glob metacharacters in usernames, `sudo -U#` runas-list wildcards, AWS `:${aws:username}` policy-variable interpolation, nginx `map`/rewrite matches on URI fragments, and every "per-user home/folder/topic path" ACL. Sweep rule: wherever a policy engine documents `%c`/`%u`/`{user}`/`${username}`-style substitution into a wildcard-matched path, connect/register/provision with an identity composed of that engine's metacharacters (`+`, `#`, `*`, `?`, `{}`, `..`) and diff the resulting authorization scope. The precondition (pattern ACL configured) is itself recon-visible — multi-tenant topic-naming conventions in docs/clients tell you the pattern shape before you ever connect.
- Validation boundary: lab broker only, your own two disposable clientIds (`normal` vs `+`), synthetic sensor payload markers on tenant A and B topics; never inject wildcards into a production broker's live client namespace (the bypass also grants *write*, so a stray publish is data corruption for other tenants).
- Moquette is now a two-advisory product on this page (Will-path ACL skip CVE-2026-85058 above, pattern-wildcard injection here): broker ACL audits should enumerate **every leg that moves a message or matches a policy** — direct PUBLISH, Will, retained, subscribe, pattern substitution — and check the guard on each; the implementers consistently forget the asynchronous legs.

## October 6 follow-up: External Secrets Operator webhook generator clears its own label-enforcement flag at init (GHSA-q7hv-xx6h-q2x8 / CVE-2026-26287, 7.1)

A pure initialization-order bug with a tenant-isolation payload: the `webhook` generator sets `EnforceLabels` and then a later init step **overwrites it back to false**, so the provider-side check "referenced secret must carry `external-secrets.io/type=webhook`" is silently skipped. A user with permission to create `Webhook` generators can point one at **any** Secret in reach (never labelled for webhook use) and have the controller fetch-and-forward it to a URL in the generator spec — secret exfiltration across the label boundary the platform believes is enforcing tenancy.

Operator value on Kubernetes engagements:

- This is the page's central invariant ("the enforcement layer and the data layer disagree about scope") in its most mechanical form: the scope predicate existed, was correctly written, and was **destroyed by assignment order in the constructor**. Code-audit fingerprint when you have source: grep for `Enforce`/`Required`-style boolean flags and diff set-ordering inside `New()`/`SetupWithManager()`/reconcile-init paths — a `flag = true` followed by a struct copy or defaulting pass (`if s.Field == zero { s.Field = default }`) that resets it is the bug shape. Webhook-admission bypass without touching the admission layer at all.
- Black-box probe (authorized clusters only, RBAC-scoped): with a lowest-tier principal that can create `generators.external-secrets.io/v1alpha1 Webhook`, reference a canary Secret **without** the label. Success = the label predicate is not running; the exfil proof is your own owned-listener URL receiving the canary value — never a real secret. Two-tenant decision table: labelled vs unlabelled target Secret × your principal vs control principal.
- Generalize to any controller/operator CRD that gates resource references by label/annotation: the reference-target label check is a first-class authz surface. Test create-leg with an *unlabelled* target before assuming the admission policy or controller-side check fires — same add-leg-missing-update-leg's-guard genealogy as the Oct 3 Groundhogg upsert leg.

## October 7 21:3xZ follow-up: OpenStack Zaqar WebSocket transport never binds the authenticated project to subsequent requests (CVE-2026-107363 / [GHSA-hc4w-8h6h-frmg](https://github.com/advisories/GHSA-hc4w-8h6h-frmg), medium, fixed 23.0.1)

The page's invariant on a *stateful* transport: Zaqar authenticates the Keystone token at WebSocket connect, then **fails to bind the project identifier in subsequent requests to the authenticated project** — any client holding a valid token for project A substitutes project B's UUID in in-protocol messages and enumerates, inspects, creates, or deletes B's queues. ## October 8 09:31Z follow-up: Apache DolphinScheduler authorization wave — the scope parameter is checked, the resource is not, and "unauth-" is a route-family fingerprint (7 GHSAs, fixed 3.4.3)

A coordinated DolphinScheduler wave (CVE-2026-66082/66084/66087, CVE-2026-71183/71895/71896; all fixed 3.4.3) restates this page's core invariant across an entire scheduler API with three sharper operator rules.

- **"Authorized on *some* project" is the only precondition — supplied-scope-vs-owned-scope confusion.** The schedule online/offline **and** workflow-definition release legs ([CVE-2026-66082 / GHSA-r995-5488-jh52](https://github.com/advisories/GHSA-r995-5488-jh52)), task-definition modify ([CVE-2026-66084 / GHSA-26vh-p5jc-q2mg](https://github.com/advisories/GHSA-26vh-p5jc-q2mg)), and task-instance stop/savepoint ([CVE-2026-66087 / GHSA-8x8j-rj29-7qph](https://github.com/advisories/GHSA-8x8j-rj29-7qph)) all check permissions against the **`{projectCode}` you supply**, then act on a resource ID from *any* project — the handler never verifies the target belongs to the scope it authorized. - **Admin-shaped config endpoints behind non-admin auth are standing cluster-credential oracles.** [CVE-2026-71895 / GHSA-vpj2-fvw3-8jgc](https://github.com/advisories/GHSA-vpj2-fvw3-8jgc): 3.2.0–3.4.2 let **any authenticated non-admin** retrieve the Kubernetes **kubeconfig** intended for admin-managed cluster config — bearer tokens/client certs that authenticate *directly to the Kubernetes API*, outside the product's own RBAC.
