# Splunk Enterprise wave: unauthenticated Patroni sidecar RCE

**Wave in one line:** unauthenticated Patroni sidecar RCE, search-job tenancy collapse, Secure Gateway signing oracles, and raw-config capability misses

Source: hourly offensive-security scan of GitHub Security Advisories, 2026-10-07 (wave published 2026-10-07T21:33Z, CVE-2026-76264 through CVE-2026-76286).

One theme ties the batch: **Splunk's REST surface is not one authorization plane.** Search-head-cluster sidecars expose their own unauthenticated APIs; job/resource tenancy is enforced per-route and the tenancy check is the route most often forgotten; capability checks live in the UI-facing handlers while raw configuration endpoints write the same files; and helper apps (Secure Gateway, Observability, MCP Server) attach privileged server-side actions (signing, outbound fetch, token-bearing requests) to weakly-gated endpoints. Every leg is individually testable in an authorized Splunk engagement.

## Why this is worth an operator page

- **The sidecar lineage is now two-for-two.** June's KEV was the PostgreSQL sidecar performing unauthenticated file operations; this wave is the **Patroni REST API performing unauthenticated OS command execution** on search head cluster members. The durable rule from the June 18 page — inventory embedded sidecar services separately from the main management plane — now has a concrete second instance and a stronger effect class (RCE, not file create/truncate). Recon on any Splunk SHC: enumerate listener ports beside 8089/8000, fingerprint Patroni (`/patroni`-style REST surfaces, cluster config endpoints), and test config-operation routes **with no Authorization header** before touching splunkd auth. The version-band asymmetry (10.0.x/9.4.x unaffected because of topology, not patching) means the deployment shape is the fingerprint, not just the version string.
- **Job-ID tenancy is a query-text and results oracle.** Two routes, one missing ownership predicate: fetch-by-ID returned everything, listing leaked query text. On any authorized Splunk assessment, run the two-principal harness: user B runs a distinctive synthetic search, user A (no admin/power) walks the search/jobs REST family with B's sid and diffs what is returned. Splunk query text routinely contains hostnames, app names, and field structures that are themselves recon gold, and preview results mean **live** data reads. Generalizes to every "async job" REST API (transcoding, ML training, report generation): enumerate the job read surface — status, results, preview, artifacts, logs — and check ownership per-verb, not per-family.
- **Capability checks in UI handlers, raw config endpoints without them.** The scripted-lookup leg is the classic Splunk privilege path (scripted lookups execute OS commands) reached through the **raw transforms configuration write path**, which skips the external-lookup capability check. Rule: for any product with both a modeled UI/API surface and a raw config read/write surface (`/services/-/configs/...`-style endpoints), diff the capability gates per surface. The raw path is the one that writes the file the feature actually reads.
- **Signing oracles are confused deputies with report-worthy impact.** Two separate Secure Gateway legs (missing per-request authorization check + endpoints processing before enforcement) let a low-privilege user have the gateway **sign attacker-controlled payloads**. On any appliance/gateway that holds a signing key or client cert, enumerate endpoints that return signatures/attestations/signed tokens and test: does the request bind *who* may request a signature over *what*? Same decision-table probe as the Oct 6 Payload join-filter oracle family: same payload, different principal, diff the acceptance.
- **Trusted notification plumbing is writable.** The KV-store leg lets non-admins write the alert/mobile-recipient collections that later workflows consume — injection into the channel humans trust. Sweep App KV Store collections (`/services/-/ns/-/collections/...`) with a lowest-tier principal for any app-owned collection backing alerts, subscriptions, or dashboards; writes to another app's collection are the finding, regardless of CVSS label.
- **Normalization-before-authorization, again.** `collect` skips whitespace normalization on the index name before applying the role's index-access restriction — the ACL and the writer disagree about the string's shape. Feed leading/trailing whitespace, tab/newline spellings, and case variants into any name-shaped input that gates an access decision (indexes, buckets, tenants, paths).
- **MCP custom-tool configs are token-bearing exfil sinks.** The MCP Server leg is the config-plane twin of every "confused-deputy fetch" on this wiki: the tool **definition** (URL) is authored by one user, executed with another user's bearer token. Wherever MCP/custom tools are shared in an org, audit who can write tool configs separately from who can execute them; a custom API tool whose URL you control captures the runner's platform token verbatim. Two-principal lab proof: attacker-authored tool config → owned listener → victim-role execution → token received.
- **Maintainer scripts are root-time consumers of low-trust content.** The LPE leg is same-family as the OpenLiteSpeed updater lesson on the [Sept 23 updater page](2026-09-23-document-viewer-and-desktop-update-surface-cluster-ghsa.md): a root-privileged upgrade step trusts installation content owned/writable by a lower-trust account. On Linux engagements with local footholds, read the installed package's pre/post scripts (`rpm -q --scripts`, `dpkg-deb -f ... maintainer scripts`) before the next upgrade window and diff which paths the script touches as root that the service account can modify.

## Validation workflow (authorized scope only)

1. **Fingerprint topology first**: search head cluster or standalone; Enterprise version; Secure Gateway and Observability app install + version; MCP Server presence. The affected bands differ per leg (Patroni/SPL2/o11y legs are 10.4.x- or 10.2.x-specific).
2. **Sidecar enumeration** (approved scope): enumerate listeners adjacent to splunkd; identify Patroni-style management APIs; capture route-level authentication behavior **unauthenticated** — status/auth-challenge responses only, no configuration mutation.
3. **Tenancy harness**: two disposable non-admin principals; principal B runs a synthetic search with a unique marker string; principal A requests B's sid through every search-job verb (status, results, preview, listing). Positive = marker appears cross-principal. Capture sid-redacted evidence.
4. **Raw-config vs modeled-config parity**: with principal A, attempt one **read-only** probe of raw transforms configuration endpoints, and — lab only, with rollback — one benign scripted-lookup definition write. Delete immediately; never point a lookup at a real command outside a lab canary script.
5. **Signing oracle probe** (lab): request a signature over a synthetic marker payload as the low-tier principal; store the response; verify offline that it validates. Never use captured signatures against third parties.
6. **KV-store write probe** (lab): create/modify a row in a test collection with a marker; delete; check no alert workflow consumed it.
7. Negative controls: fixed-version instance, standalone (non-SHC) instance for the Patroni leg, and a principal with genuinely no capabilities for the tenancy legs.

## Evidence to capture

- Version + install inventory (apps, sidecars, topology) per leg.
- Redacted request/response pairs showing the missing authz decision (principal role, route, outcome) — never full search results from real users.
- For lab proofs: marker values, principal pairs, decision tables (capability × route × outcome), immediate-cleanup confirmation.
- Version-band confirmation per leg (several legs do not apply to 9.4.x/10.0.x).

## Reporting heuristic

Strong titles:

> Unauthenticated Patroni REST API on search head cluster member permits OS command execution (CVE-2026-76268)

> Search job REST endpoints return other users' queries and results to any authenticated user

Frame each leg as the crossed boundary (principal class → protected resource/authority), cite the fixed band, and keep impact claims inside what was actually proven — the signing oracle is a signing oracle unless you independently demonstrate a downstream consumer that trusts the signature.

### New durable rules from wave 2

- **A credential derivable from an observable is the observable's privilege.** CVE-2026-76298: sidecar superuser password = f(search-head-cluster identifier), and the identifier appears in logs readable by non-privileged users. On any clustered product: enumerate identifiers/IDs visible to the lowest principal (job logs, status pages, error strings), then grep docs/configs for anything **derived** from them (passwords, keys, node names, JWT secrets). Two-principal probe: reader-principal extracts the identifier → attempt derived-credential auth to every sidecar/replication listener. The sidecar lineage (June 18 file ops → Patroni unauth RCE → derived-password RCE) means every Splunk SHC engagement should inventory adjacent listeners **and** their credential-derivation inputs.
- **Enforcement-path asymmetry: the async engine skips the sync engine's guards.** SPL risky-command safeguards applied interactively but never by the scheduler. For every product with interactive + scheduled/background/replayed execution paths (cron runners, job queues, import pipelines, MCP auto-run), run the same risky-action battery down each path and diff. A capability that only grants scheduling is a full-capability grant if the scheduler has no guard layer.
- **Filter-before-projection = inference oracle on protected fields.** SOAR applied REST query filters to user records before hiding sensitive fields — equality/range probes infer password hashes and auth tokens character-by-character even though values never render. Same lineage as the Oct 20 Apostrophe search-builder leg (`search`/`sort` builders running ahead of `publicApiProjection`). Standing probe on every list endpoint: attach filters naming secret-shaped fields (`*hash*`, `*token*`, `*secret*`, `*key*`) and watch 200-vs-400 / true-vs-false response differentials.
- **Operation ordering is a boundary: decrypt-before-authenticate.** Submit stolen/historical encrypted credential blobs to an endpoint that decrypts before deciding who you are. Grep auth flows for crypto calls sequenced before the authz decision; any prior-epoch ciphertext leak becomes a live decrypt oracle.
- **Destination-target authorization on move/rename/copy verbs.** Wave 1 found move-without-ownership; wave 2 shows source-permission-checked, destination-app-unchecked (and reverse: edit objects inside apps you can't read). Every move/rename/copy/restore verb needs both endpoints authorized separately — run the destination-app battery with a principal confined to one app.
- **Config formats that evaluate expressions are SSTI with extra steps.** The Manager XML leg: a legitimate admin config surface whose parser evaluates user expressions. Wherever a product lets low-mid roles author XML/YAML/JSON configs, probe for expression syntax (`$expr$`, `eval`, SpEL, OGNL, JEXL, template markers) in values the UI never intends to evaluate.
- **Export/download routes are the forgotten gate siblings.** App archive and compose-file downloads skipped the permission the browse/edit routes enforce. Enumerate every export/download/backup/dump route per resource family as its own authz test — wave-1's `disableDuplicate`-at-router and Oct 6 Payload read-verb rules generalized.

### Wave-2 validation additions

1. **Derived-credential probe (lab/approved scope)**: as a non-power principal, capture your own synthetic search job's log output; diff which cluster/topology identifiers appear; test derived-password auth against adjacent sidecar listeners **in a lab SHC only** — never against production sidecars.
2. **Scheduler-path guard diff**: with a `schedule_search`-only principal, schedule a harmless marker SPL command that the interactive path blocks; compare accept/reject per path. Delete the schedule immediately; no risky commands on shared instances.
3. **Filter-inference harness**: with a low-tier SOAR principal, run equality filters against your own synthetic user's hash/token columns; a filter-matching-true response proves the pre-projection application. Use only disposable accounts.
4. **Decrypt-order probe**: submit a known-lab-generated encrypted Basic value to the REST auth path on a lab instance and observe whether decryption happens pre-auth (timing/error-shape differential). Never replay real credential exports.
5. **Destination-app battery**: move one disposable field-extraction to an app the principal cannot read; verify rejection. Revert immediately.
