# Postgres Enterprise Manager wave (9 GHSAs): one owned monitored host roots every database it watches

**Wave in one line:** The PEM 10.6.1 release fixed nine boundaries, and the crown legs invert the usual direction: a single compromised *monitored host* (and therefore its PEM agent certificate) lets you create SQL and shell jobs on every other agent including the PEM server itself, read and write files on the PEM server as the `postgres` OS user including the CA key used to mint those agent certificates, so one edge foothold in a monitored fleet becomes superuser SQL across every database the platform watches.

Sources: nine PEM advisories published 2026-11-20T15:31Z, all fixed in Postgres Enterprise Manager 10.6.1, empty GHSA CVSS/package fields (vendor-advisory band fingerprinting per the Oct 14 NGINX precedent): [GHSA-j42g-7277-7599](https://github.com/advisories/GHSA-j42g-7277-7599) / CVE-2026-132659 (agent RLS), [GHSA-mff5-m274-g5ww](https://github.com/advisories/GHSA-mff5-m274-g5ww) / CVE-2026-132658 (agent file roles), [GHSA-3p3c-5pxp-xrr7](https://github.com/advisories/GHSA-3p3c-5pxp-xrr7) / CVE-2026-132660 (SECURITY DEFINER search_path), [GHSA-2779-4w9v-fwg4](https://github.com/advisories/GHSA-2779-4w9v-fwg4) / CVE-2026-132664 (shared encryption key), [GHSA-fc5h-w9ph-v64j](https://github.com/advisories/GHSA-fc5h-w9ph-v64j) / CVE-2026-132662 (SQL Profiler path escape), [GHSA-vvh5-f7wx-5mrm](https://github.com/advisories/GHSA-vvh5-f7wx-5mrm) / CVE-2026-132663 (file:// webhook read-back), [GHSA-96wp-998m-8v6p](https://github.com/advisories/GHSA-96wp-998m-8v6p) / CVE-2026-132661 (MFA route bypass), [GHSA-2j27-r4hr-qrcc](https://github.com/advisories/GHSA-2j27-r4hr-qrcc) / CVE-2026-132665 (cross-team job deploy), [GHSA-v5cx-gxvh-mfq6](https://github.com/advisories/GHSA-v5cx-gxvh-mfq6) / CVE-2026-132668 (webhook confused deputy).

!!! warning "Lab instances and synthetic credentials only"
    Run every probe against a disposable PEM you control: a lab PEM server, synthetic monitored hosts, synthetic agent certificates, marker files outside any real config path. Never touch a customer's monitored fleet, never read a live `pgpass`/agent certificate, never issue certificates from a real PEM CA. The agent-side legs prove with your own lab-host agent identity only.

## Why this is worth an operator page

PEM is the classic management-plane hub: one central database that holds credentials and job authority for *every* monitored Postgres server in the estate. The two agent legs show that the agent trust boundary (a per-host certificate) was the only thing between "I own one low-value monitored box" and "I own the whole estate," which is the fleet-management-plane pattern to hunt in every monitoring/backup/DBA tool, not just PEM.

- **One agent certificate = fleet job authority (the crown leg).** The RLS policies on `pem.job`/`pem.jobstep` that scope agents did **not** limit an agent to its own jobs: control one monitored host, use its agent certificate, and create/modify/delete jobs for every other agent, including the PEM server's own agent. Jobs run SQL steps with the monitored server's database credentials and shell steps where batch jobs are enabled, so one host compromise chains to superuser SQL everywhere plus OS execution on the hub. Rules: (1) **enumerate what a device/agent credential can *write*, not just report**; (2) when a platform has agent-initiated job/task channels, probe the RLS/tenancy predicate with a valid low-value agent identity against another agent's job namespace (create-with-foreign-agent-id is the probe); (3) hub-and-spoke monitoring tools are the highest-value lateral hop after any edge foothold: agent channels are always bidirectional in practice, so treat "telemetry upload" endpoints as remote-code surfaces at the hub.
- **The CA key is readable from the credential it issues.** The `pem_agent` role every agent login inherits held `pg_read_server_files`/`pg_write_server_files` on the PEM backend, so an agent-side foothold reads files as the `postgres` OS user, including the **PEM certificate authority key**, letting the attacker mint certificates for arbitrary agents and impersonate any host permanently. Generalized rule: in any mTLS fleet, ask what the *lowest* device identity can read on the hub, because CA signing material reachable via an issued credential converts every past and future authentication decision into attacker-controlled state. Companion grep on any hub product: enumerate role memberships of the service accounts that *device* logins inherit (`pg_read_server_files` is membership-writable, grep it as a role-inheritance check).
- **SECURITY DEFINER without a fixed `search_path` = unprivileged-to-superuser SQL, with a version-conditional exploitability split.** Several `pem` schema functions ran as superuser with the caller-controllable search path; any PEM user able to connect can shadow referenced objects via **temp objects on every supported PostgreSQL version**, while `public`-schema shadowing additionally works on 14 backends and 14-upgraded backends. This is the same search-path family as the Nov 12 PostgreSQL wave's security-restricted-path hijack leg and the Aurora wrapper precedent on the June 15 page; the operator additions: (1) temp-schema shadowing means the public-schema lockdown (PostgreSQL 15+ default) is *not* a fix, so test `pg_temp` shadowing even on modern servers; (2) fingerprint the backend major version and the upgrade lineage (`public` privileges survive upgrades from 14), because exploitability of the same function differs by that history. Audit one-liner: `SELECT p.proname, r.rolsuper FROM pg_proc p JOIN pg_roles r ON r.oid=p.proowner WHERE p.prosecdef AND r.rolsuper` against any product database schema, then probe each hit for shadowable references.
- **Encryption at rest with an install-invariant key is plaintext at rest.** Any PEM user could read the encrypted server-connection passwords PEM agents use (including the stored PEM backend superuser password), and unless an admin configured a custom key the encryption key is identical across every PEM installation, so the ciphertext decrypts anywhere. Rules: (1) credential stores in management hubs deserve a **key-provenance question** (`is this key derived from the install, the product, or an admin secret?`) before treating ciphertext as protected; product-default keys mean your lab install decrypts production-shaped ciphertext offline; (2) the *read* endpoint being permissionless is often the whole finding even while the crypto looks fine: enumerate every table/view/API that serializes stored credentials, even masked-looking ones.
- **Two file-confinement breaks with different gates.** The SQL Profiler save/load kept the *caller-supplied filename* outside the user's storage directory, letting a `pem_comp_sqlprofiler`-role user read arbitrary JSON files and overwrite anything the web-server account can write (overwriting the web app's own config database = console kill for all users); and alert webhooks accepted `file://` URLs, so a `pem_config_alert`-role user had the **root-running agent on the PEM server** read a local file and deposit its contents into a webhook error record readable by any PEM user. Rules: (1) the classic validate-at-one-endpoint-vs-consume-at-another pair for filename parameters, enumerate read AND write modes separately, config-database overwrite as a denial-and-integrity proof shape; (2) the `file://` webhook is the read-back-channel SSRF pattern from the July 30 FireFighter leg: *any* server-side fetcher whose errors/contents persist into a user-visible record is an arbitrary-file-read primitive, and the role names in the advisories (`pem_config_alert`, `pem_comp_sqlprofiler`, `pem_manage_schedule_task`) are your low-privilege test identities, so **map product roles to capability verbs first** and re-run the URL-scheme battery (`file://`, `gopher://`, redirect chains) on each alert/webhook config surface.
- **MFA enforced at the UI flow, not at the routes.** A user with an enrolled second factor could skip it entirely by calling PEM pages/APIs directly, the pgAdmin 4 CVE-2024-4215 sibling. Standing rule: for every MFA-gated admin app, enumerate the underlying API route family and replay a valid single-factor session against raw routes; MFA state that lives only in the web-flow's session flags never covers direct API access, and management-plane APIs are usually documented, which makes enumeration free.
- **Cross-team deploy + webhook confused deputy (the low-severity legs worth keeping).** `pem.deploy_job_template()` skipped per-target access checks, so a schedule-task-role user could deploy SQL/shell job steps onto *other teams'* agents (tenancy check absent from the bulk/deploy variant of a checked single-deploy path, the sibling-parameter rule); and `pem.send_webhook()` ran elevated and queued payloads to any configured webhook, delivering them **with that webhook's stored headers, OAuth token, or client certificate**, letting any PEM user forge notifications to endpoints they cannot authenticate to. Rules: (1) bulk/deploy/import variants of a permission-checked operation are the drift candidates, test the multi-target variant separately; (2) **stored-credential relay** is its own boundary class: any "send a message" API that attaches *someone else's* stored credential is a confused deputy, probe by pointing your payload at an endpoint where only the stored credential has access (your owned callback records who really authenticated).

## Replayable validation sequence (lab)

1. Disposable PEM 10.6.0 backend plus two synthetic monitored hosts (HOST-A attacker-owned, HOST-B victim) and two synthetic PEM users (low-priv `pem_user`, role-holders per leg); marker tables/files only.
2. **Agent RLS leg:** with HOST-A's agent credentials, attempt to create/modify a job bound to HOST-B's agent id; the create succeeding is the fleet-RCE claim.
3. **search_path leg:** as the low-priv user, create a temp-schema shadow object named like a referenced helper table, call the target SECURITY DEFINER function, prove execution via a marker insert into your scratch table as the definer role.
4. **Credential-read leg:** SELECT the agent-connection password columns as the low-priv user; store ciphertext, confirm a *fresh separate* PEM install decrypts it with its default key (offline, lab files only).
5. **Webhook read-back leg:** configure a lab alert webhook URL `file:///etc/passwd`-class marker (a synthetic canary file you own), trigger the alert, read the webhook error record as the low-priv user. Never read real config files.
6. **MFA route leg:** enroll MFA, authenticate single-factor via the API path or replay the flow's pre-MFA session, call a post-MFA-gated API route directly; record the route matrix.
7. **Confused-deputy leg:** configure a webhook with a stored bearer token to an owned callback, call `send_webhook()` as the low-priv user, confirm the callback logs the *stored* token on your payload.
8. Redact every credential, certificate, and password column value from evidence; hash ciphertext where content is unnecessary; record the lab image digest so each leg is replayable.
