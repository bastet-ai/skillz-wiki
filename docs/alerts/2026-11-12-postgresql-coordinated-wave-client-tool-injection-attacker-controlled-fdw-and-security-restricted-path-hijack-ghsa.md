# PostgreSQL wave (52 GHSAs): attacker-controlled foreign server gets RCE on the database host

**Wave in one line:** The November 12 coordinated PostgreSQL release (fixed 18.7 / 17.12 / 16.16 / 15.20 / 14.25) ships 52 advisories, and the operator-relevant cores are four legs that turn a *foreign* server, a *dump file*, a *low-priv CREATE grant*, or a *pg_temp schema* into code execution, plus the RLS/DROP OWNED and security_barrier bypass pair that every app pentest against a Postgres back end should re-run.

All 52 advisories landed at 2026-11-12T15:31-15:32Z with empty GHSA CVSS fields (vendor-advisory band fingerprinting per the Oct 14 NGINX precedent); band details are in each description. The memory-safety majority (type-confusion via `ALTER ... SET DATA TYPE`, plperl/plpgsql/pltcl UAFs, tsvector overflows, tuple-size wraparound) is the tracked memory-safety class and is not published standalone. The legs below are durable because they cross a trust boundary an attacker who is *not* the DBA can reach, or they invert the direction of a well-known attack.

!!! warning "Lab instances and disposable data only"
    Every probe here runs against a disposable PostgreSQL you own, with synthetic roles, synthetic extensions, and marker tables. The client-tool legs require running `pg_dump`/`pg_restore`/`vacuumdb`/`psql` against hostile inputs, so run them in a throwaway container as a non-privileged user. Never point a customer's server at your foreign-data-wrapper listener or restore untrusted dumps outside the container.

## 1. A malicious foreign server is a remote attacker against the database host

- **Heap overflow in foreign batch inserts** ([GHSA-gqm6-3wfg-52x5 / CVE-2026-120149](https://github.com/advisories/GHSA-gqm6-3wfg-52x5), high): a foreign server that *reports more inserted rows than the batch supplied* overflows a heap buffer on the local side, giving code execution as the OS user running the database. The vendor notes `postgres_fdw` can legitimately hit the count mismatch when a remote rule expands an INSERT, so the local side treats the remote's row count as trusted bookkeeping.
- **Reverse-direction deserialization**: this inverts the standard FDW attack. Normally the pentester controls the local server and pokes a configured foreign one. Here the *foreign* endpoint is the attacker-controlled input channel: row counts, and by adjacency the dblink type-conversion reentry UAF ([GHSA-63j6-rm8q-mhqx / CVE-2026-120147](https://github.com/advisories/GHSA-63j6-rm8q-mhqx), type-conversion code re-enters dblink and closes a connection whose results an outer call is reading).
- **Compromised-publisher leg**: logical replication lets a **compromised publisher** execute code as the OS user running a superuser-owned subscription by naming a system catalog as a replication target ([GHSA-j3p3-grqw-h5vf / CVE-2026-120145](https://github.com/advisories/GHSA-j3p3-grqw-h5vf), high, superuser-owned subscriptions only).
- Validation workflow (authorized lab): stand up a synthetic FDW listener that speaks enough of the protocol to accept a batch and lie about the returned row count; run `INSERT INTO foreign_table ...` from a lab subscriber and watch for subscriber-backend crash. Same-shape probe battery for any product embedding a foreign-data client (postgres_fdw, dblink, oracles_fdw, pg_mssql_server-adjacent wrappers): treat every server-supplied count/length/ordinal in the wire contract as attacker-controlled even when the *connection* was configured by an admin.
- Reporting angle: the trust boundary is **operator config (a trusted foreign server entry) does not make the peer trusted at runtime**. This is the FDW sibling of the "remote listing entries steer endpoint operations" rule from the Camel page: server-controlled input crossing into client-side bookkeeping.

## 2. The dump/restore toolchain is an attack surface, not just a data plane

- **restore.sql predictable restriction key** ([GHSA-3cj4-r426-m55g / CVE-2026-116330](https://github.com/advisories/GHSA-3cj4-r426-m55g), high): a **compromised origin server** puts untrusted content into the undocumented `restore.sql` inside a `pg_dump --format=tar` archive, and the *predictable restriction key* means the client-side `psql` executes it; RCE as the OS account running psql. Explicitly a gap in the fix for CVE-2025-8714, incomplete-fix genealogy to fingerprint.
- **pg_restore archive-provider code execution** ([GHSA-mhqh-c375-96c6 / CVE-2026-116314](https://github.com/advisories/GHSA-mhqh-c375-96c6), high): a crafted non-plain archive yields code execution **in the pg_restore process itself**, the advisory drawing the line the community routinely blurs: crafted archive data legitimately confers arbitrary SQL at the restore destination, not arbitrary code in the client OS process.
- **pg_dump SQLi via constraint quoting** ([GHSA-6vgg-f58c-3v5x / CVE-2026-116318](https://github.com/advisories/GHSA-6vgg-f58c-3v5x), high, 18.x): an inherited column whose child-local not-null constraint name requires quoting injects SQL executed as the *restoring* user. Same shape as **reindexdb** `--jobs --index` parallel catalog query injection via a crafted index name ([GHSA-qq3m-7qq2-628h / CVE-2026-116325](https://github.com/advisories/GHSA-qq3m-7qq2-628h)) and **vacuumdb** `--missing-stats-only` operator shadowing ([GHSA-64m9-jq4j-66v4 / CVE-2026-116313](https://github.com/advisories/GHSA-64m9-jq4j-66v4), where the pg_upgrade docs themselves recommend the affected invocation).
- Durable rules:
  1. **Object names are code in the toolchain.** Any identifier you can create (constraint, index, table) is re-embedded into SQL that a *higher-privileged* maintenance user will run hours later. Deferred-execution SQLi family: object-creator privilege, restorer/DBA execution.
  2. **Operator-path search-path hijack**: vacuumdb's catalog query resolves operators unqualified, so a created `pg_temp` operator shadows theirs. Grep the same flaw in every client tool that runs catalog SQL: `pg_dump`, `pg_upgrade` scripts, backup agents, ORM migration runners.
  3. **Dump-consumption pipeline test (authorized)**: if a target ingests dumps/archives from customer servers, feed it a tar-format archive from a compromised-origin stand-in in a container and instrument for psql-side execution; also diff "restores cleanly" against "restores in a sandbox" since the restore.sql executes during plain restores.
- `sslkeylogfile` arbitrary-file-append via `dblink`/`CREATE SUBSCRIPTION` connection parameters ([GHSA-qr4r-2rhh-hpj4 / CVE-2026-14661](https://github.com/advisories/GHSA-qr4r-2rhh-hpj4), high) is the connection-string-as-file-primitive leg: NSS-keylog-format appends to a user-chosen path (no arbitrary bytes), persistent DoS when the target is a config file. Connection-string parameters deserve the same file-path audit as any URL field (July 30 URL-policy page family).

## 3. Database-level CREATE is bootstrap-superuser RCE on trusted extensions

- **CREATE EXTENSION search-path hijack** ([GHSA-pm32-vprj-4hwf / CVE-2026-6467](https://github.com/advisories/GHSA-pm32-vprj-4hwf), high): via `ALTER SCHEMA ... RENAME` or `CREATE EXTENSION ... SCHEMA "$user"`, a trusted-extension script *locates the wrong object* and executes attacker SQL as the bootstrap superuser. Requires only database-level CREATE privilege.
- **Extension-script substitution injection** ([GHSA-w429-xmhm-p6jc / CVE-2026-120153](https://github.com/advisories/GHSA-w429-xmhm-p6jc), high): a schema or owner name containing newlines/special substrings injects into `@extschema@`-style substitutions in a **non-bundled extension's** script, again code as the bootstrap superuser; explicitly the CVE-2023-39417 genealogy with a new precondition.
- **pg_temp type hijack of security-restricted operations** ([GHSA-vhhp-qrj9-rf8m / CVE-2026-116316](https://github.com/advisories/GHSA-vhhp-qrj9-rf8m), high): create a domain/enum/range type in `pg_temp`, then wait for a victim session running a security-restricted operation to write an unqualified type name (`SELECT '1'::bigint` shape), and your type's casts/functions run as the operation's caller. Advisory notes autovacuum avoids unqualified casts, so hunt the *other* scheduled/daemon sessions (maintenance jobs, app cron roles, pgAgent, backup tooling).
- Operator checklist on any Postgres-backed app or platform (the "can I escalate through the database itself" audit):
  1. Enumerate installed and *installable* extensions (`SELECT * FROM pg_available_extensions`), flagging non-bundled ones with `@extschema@`/`@extowner@` substitutions in their scripts, then test CREATE EXTENSION as the lowest privileged role that holds database CREATE.
  2. Test the search-path legs: `CREATE EXTENSION <trusted> SCHEMA "$user"` under a role owning a schema named after itself, and rename-schema variants; a trusted script touching your objects = the finding.
  3. Plant `pg_temp` domain/enum/range types shadowing common casts; instrument which daemon/maintenance sessions consume them (logged statements + synthetic functions writing marker rows in your own lab).
  - Rules: **trusted extension = trusted code run through untrusted name resolution**; search-path resolution order is an authorization decision, and `$user`/pg_temp are user-writable rungs on it. Same family as the Aurora wrapper search-path privilege leg (June wave) but executed by PostgreSQL core itself.

## 4. The two privilege-model bypasses worth re-running on every app assessment

- **DROP OWNED escapes row-level security** ([GHSA-c93m-7254-wq8r / CVE-2026-116311](https://github.com/advisories/GHSA-c93m-7254-wq8r), medium): a role can `DROP OWNED` to remove *itself* from restrictive RLS policies, then read/modify rows the policy denied. Multi-tenant apps that lean on RLS as the tenant boundary while roles own schema objects have a same-connection policy-removal path. Adjacent: `REASSIGN OWNED` lets a role granted INHERIT but not SET transfer objects to the granted role and reassign database ownership without CREATEDB ([GHSA-v5xq-4x8p-53j2 / CVE-2026-120146](https://github.com/advisories/GHSA-v5xq-4x8p-53j2)), where the equivalent `ALTER ... OWNER` is blocked, utility-command vs DDL-command authorization parity.
- **security_barrier view leak via leaky function** ([GHSA-w7w5-rq5g-wxfw / CVE-2026-116327](https://github.com/advisories/GHSA-w7w5-rq5g-wxfw), medium): apply a leaky function to a CASE test value or an indirect parameter to infer values the barrier view hides; the barrier's predicate-ordering guarantee is defeated through expression evaluation order.
- **INSERT ... ON CONFLICT breaks view WHERE and RLS both**: iterated `INSERT ... ON CONFLICT DO UPDATE` through an auto-updatable view bypasses the view's WHERE condition and reads *and writes* every base-table row ([GHSA-wrm7-crvq-vpv9 / CVE-2026-16237](https://github.com/advisories/GHSA-wrm7-crvq-vpv9)); the RLS variant reads every row despite policies ([GHSA-9pxp-38rf-5pgv / CVE-2026-120154](https://github.com/advisories/GHSA-9pxp-38rf-5pgv)). Both are read-oracles-with-a-write-primitive: the iterated upsert is also a row-existence probe. MERGE transition-table state confusion (wrong AFTER trigger row on partitioned insert-then-update, [GHSA-xqm8-qxc4-qxc9 / CVE-2026-116312](https://github.com/advisories/GHSA-xqm8-qxc4-qxc9)) completes the "auditing triggers lie" set: audit triggers on MERGE/partitioned tables cannot be trusted as an integrity record.
- Assessment pattern: on a Postgres back end, always ask *which* enforcement layer the app trusts (RLS, view WITH CHECK, security_barrier, trigger auditing, column grants) and attack **that layer's utility-command interactions**, not just the query text. These five legs are the November 2026 vocabulary for that question, and all predate 18.7: run the battery against *current* versions first, then fingerprint minor versions from behavior differences (e.g. ON CONFLICT-on-view works or doesn't).

## Reporting notes

- For the client-tool legs, state which tool version executes attacker content, which OS user runs it, and whether the trigger requires restoring from a hostile origin (pg_dump/restore.sql) vs merely *naming* objects (pg_dump/reindexdb/vacuumdb SQLi). Quote the pg_restore SQL-vs-code line, it pre-empts the "restores execute SQL by design" dismissal.
- For the FDW legs, the finding is a **pre-auth-to-DB-host primitive against the connecting server** from the peer side, prove crash or marker-write in a disposable subscriber, no production FDW configs touched.
- For RLS/view bypasses, prove read or write of one marker row that policy denies, from a role that legitimately holds only view INSERT+UPDATE; report the enforcement-layer name the app relies on.
