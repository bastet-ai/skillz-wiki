# AI serving and RAG platform wave — unauthenticated KV-cache data plane, tenant-blind secondary routes, and validate-endpoint code sinks

Source: GitHub Security Advisory wave published 2026-10-02 00:31Z (Mooncake, RAGFlow, Langflow, Langchain-Chatchat, Devika). Related existing pages: [Oct 1 MCP trust-layers cluster](2026-10-01-mcp-gateway-session-client-browser-bridge-and-agent-prompt-injection-cluster-ghsa.md), [Sept 16 vLLM route-guard parity page](2026-09-16-rmcp-oauth-resource-spoofing-mdc-sanitizer-gaps-and-vllm-route-guard-parity-ghsa.md), [Aug 26 DB-GPT upload-route page](2026-08-26-db-gpt-skill-upload-path-write-boundary-ghsa.md), [May 21 Fission/MLflow/Langflow SSRF page](2026-05-21-fission-mlflow-langflow-ssrf-crabbox-boundary-batch-ghsa-kev.md).

One rule covers the wave: **the AI stack's internal plumbing (transfer engines, metadata services, per-app API registries, "validate" endpoints) was designed inside a flat trust zone and never got the authz layer the UI routes got.** Fingerprint a deployment by its unauthenticated internal ports and secondary route families before touching the login form.

## Durable axes

1. **Inference-cluster internal protocols are pre-auth by design — and they carry model secrets.** Disaggregated serving (Mooncake and friends) moves KV cache over TCP with no authentication on either the data port or the metadata service. From any network position that reaches those ports (a compromised pod, a tenant VM, a flat VPC), you get (a) a process-memory read primitive over the transfer opcodes and (b) a descriptor-poisoning primitive that redirects *other nodes'* transfers to you. Sweep AI infra for non-HTTP listeners first: transfer-engine data ports, metadata/RPC bootstrap services, RDMA/TCP rendezvous endpoints. Evidence value here is prompt/secret disclosure from synthetic sessions only.
2. **Poison the control plane instead of touching the data plane.** Writing one metadata key (`tcp_data_port`, `rpc_meta`) is quieter and scales better than exploiting a memory bug: the cluster delivers victim traffic to your listener. For any unauthenticated KV/metadata service, dump the schema and grep the values for host:port fields consumed by other components.
3. **Per-app route registries drift independently in RAG platforms.** RAGFlow ships separate Flask-style apps (`main`, `kb_app`, `connector_app`, `evaluation_app`); authz middleware applied to one does not cover the others. On source-available deployments, enumerate every `*_app.py`/router module and build the authorization matrix per module; on closed deployments, probe feature-sidecar families (evaluation, connector, mindmap, preview, temp upload) with two disposable tenants and cross-referenced IDs.
4. **Caller-selected identifiers on data-access routes are the standing IDOR oracle.** `doc_id`, `dataset_id`, `session_id`, `bot_id`, `book_id` — enumerate ID-bearing params on every read *and* write route and replay tenant B's ID under tenant A's token. RAGFlow's six-GHSA spread is what a full sweep of one product looks like: the fix list is the route list.
5. **"Validate" endpoints in low-code AI builders execute.** Langflow's `/validate/code` compiles/execs submitted Python server-side. Authenticated ≠ authorized: map what a minimal-privilege account can make the server run, with inert marker statements in a lab instance.
6. **Compatibility shims and temp routes are unfixed siblings of fixed routes.** `/v1/files` (OpenAI-compat), `upload_temp_docs`, KB-creation name fields — the filename/path sanitizer applied to the primary upload is re-implemented (or absent) on each alternate surface. Grep the codebase for every parameter that reaches `open(...,'w')`/`os.path.join`, per the fixed-handler-is-the-map rule.

## Validation boundaries

Mooncake checks belong in a lab inference cluster with synthetic prompts and marker payloads — never against shared serving nodes, and never read real KV caches or other tenants' prompts. RAG-platform IDOR proofs use two disposable tenants, synthetic documents/datasets, and cross-read checks only; Langflow code-execution proofs use inert marker statements in disposable flows on owned instances. Chatchat/Devika/KB-name traversal proofs write marker files only inside disposable roots. No production tenant data, real model outputs, or customer embeddings in wiki/report evidence.

## October 2 19:31Z follow-up: Trigger.dev control-plane SSRF + loader-vs-action authz parity

- **Trigger.dev webhook alert channel = signed SSRF proxy from any org member** ([GHSA-xxv7-2vv3-h682](https://github.com/advisories/GHSA-xxv7-2vv3-h682), 7.7, fixed 4.5.2): the alert-channel `url` is stored as a bare `z.string()` (not even `.url()`) and the control plane POSTs to it via raw `fetch()` with **no private-IP/link-local/metadata/redirect filtering anywhere in the webapp** — repository-wide search for an SSRF guard returns nothing. Creating the channel requires only *organization membership*, not admin. The attacker then fails a task run in their own environment and the delivery job POSTs a validly HMAC-signed payload to `http://169.254.169.254/...` or internal-only admin services. Durable axes: (1) **outbound-notification surfaces (webhooks, alert channels, integrations) are SSRF channels that ship unsanitized because they are conceived as convenience, not attack surface** — same shape as the LocalAI gallery leg above and the Faraday/9Router outbound-fetch family; (2) **the signature makes it worse, not better** — a server-originated, validly-signed request is indistinguishable from legitimate platform traffic to the receiving internal service, so perimeter allowlisting of the platform's egress does not stop it; (3) blind-SSRF oracle still applies: response body isn't returned, but status/latency/error deltas in delivery logs/state give a probe channel. Bug-hunt pattern: on any SaaS with user-configurable webhook/callback URLs, check whether the *creation* route's schema constraint matches the *delivery* sink's checks, and whether the lowest membership tier (not admin) can create the channel.
- **Trigger.dev run-replay cross-tenant environment injection** ([GHSA-qxpp-qjg8-x4jv](https://github.com/advisories/GHSA-qxpp-qjg8-x4jv), 7.1, fixed 4.5.2): the replay *action* member-scopes the source run correctly, but takes the target `environmentId` verbatim from the form body; the lookup (`findEnvironmentById`) filters by `id` only — no org/project/membership predicate — and the downstream task service trusts the resolved environment blindly. The replay *loader* constrains the environment picker to the run's own project, but the action never re-imposes it. This is the crisp **loader-vs-action parity drift**: UI-gated constraints are not server-side controls; the picker's WHERE clause living in a different module than the submit handler is the audit predicate. Sweep every mutation route whose GET/loader scopes a selector and ask whether the POST repeats the scope. Impact shape: authenticated user injects task runs into another tenant's environment (including production), burning their queue concurrency/compute and poisoning run history — cross-tenant *write* that needs only a target CUID plus a task identifier that exists there. Proof pattern: two disposable orgs, one owned run, victim environment id from the second org; assert run creation lands in the victim environment, then delete the marker runs.
- Shared fingerprint note: Trigger.dev is the async-jobs/agent-task control plane under a growing slice of AI products; where a deployment self-hosts the webapp, both legs (alert-channel SSRF, replay environment drift) apply at `<4.5.2` with the same low privilege floor — org membership.

## October 27 follow-up: Agno `FunctionCall.field_type` eval'd during tool-call hydration — the serialized tool-call envelope is itself an exec sink ([CVE-2026-35002](https://github.com/advisories/GHSA-m4w4-3r8h-jw98), critical 9.8/9.3, agno <2.3.24)

Agno's model-execution path passed the `field_type` string from a `FunctionCall` input field straight into Python `eval()` — arbitrary code execution for anyone who can influence a FunctionCall record reaching the process. The advisory names the three realistic sources: API request bodies, web UI, and **untrusted tool/model output** — i.e., a hostile tool or a prompt-injected model response can author the FunctionCall JSON that the framework hydrates. Fix (commit `cbf67552`, PR #5912) replaced `eval()` with a fixed `type_mapping` dict lookup plus validation that `field_type` is a known key or already-resolved `type`.

Durable rules extending this page's agent-boundary set:

- **Enumerate string-typed fields inside serialized tool-call/function-call envelopes as candidate code sinks.** Framework hydration metadata (`field_type`, `class`, `callable`, `import_path`) is routinely model- or tool-writable yet processed by framework code, not app code — the deserialization leg sits *behind* every guard attached to tool invocation. This is the tool-call twin of the page's model-output-to-code legs (`code_revision`→`trust_remote_code` vLLM, Langflow LLM-to-`eval`): the sink is reached through the *plumbing* format, not a feature endpoint.
- **Fingerprint pattern:** grep agent frameworks for `eval(`/`importlib`/`getattr` applied to fields parsed from LLM/tool JSON. Dict-lookup fixes (`type_mapping`) are the tell of where the eval used to be — fix diffs are the map for older deployed versions (<2.3.24 here; 2.6.x current).
- **Proof boundary:** inert marker only (e.g., `field_type` selecting `os.getpid`-style observable or a `__import__` of a canary module) against a lab Agno instance with synthetic FunctionCall input; never run this against deployments holding live provider credentials. Duplicate marker GHSA-77rh-m34w-rv36 (withdrawn) — do not treat as second finding.

## October 27 16:1xZ follow-up: Flexible GraphRAG — ingest-document content is Cypher injection input; broken `_escape()` = full graph wipe ([CVE-2026-114510 / GHSA-vqrg-773h-4wxc](https://github.com/advisories/GHSA-vqrg-773h-4wxc), high)

The FalkorDB adapter's `_escape()` string-escaper is broken, so entity/relation strings extracted from **ingested documents** interpolate raw into Cypher: a document whose text is crafted (quoted-string breakout into `DETACH DELETE` or stacked statements) wipes or rewrites the whole graph from pure content input — no account, no console. Second FalkorDB-adjacent injection wave this month (Sept 21 Bolt wave on the precedence page was the first).

Operator rules for any RAG/graph pipeline:

1. **Ingested content is a query-language input channel.** Every field the extractor carries from document text into node/relationship properties crosses a string-construction boundary; test with quote/escape breakout canaries (`'`, `\`, backtick, `$`-param names) inside otherwise innocuous documents, then diff intended vs executed Cypher via the graph's query log where readable.
2. **Sweep the graph-DB adapter matrix, not the framework:** Cypher (Neo4j/FalkorDB/Aurora), Gremlin, SPARQL, and GQL each ship per-adapter escapers; one adapter's `_escape()` being wrong doesn't stop the framework's docs advertising multi-backend support. Name-the-backend before testing — the vulnerable sink lives in the adapter, not the RAG core.
3. **Impact framing:** graph wipe/rewrite is integrity destruction from an input path users believe is passive; in reports, pair the injection proof with a benign marker node (property write) before demonstrating any destructive leg, and never run the wipe leg against shared graphs.

## October 27 17:1xZ follow-up: Hydra legacy `instantiate()` blacklist omits `yaml.unsafe_load` — model-bundled config executes code through a deny-list gap ([GHSA-wf6j-7hvr-gr93](https://github.com/advisories/GHSA-wf6j-7hvr-gr93), high, hydra-core >=1.3.6 <1.3.8, >=1.4.0.dev9 <1.4.0rc3)

Hydra's *legacy* target blacklist (the pre-whitelist defense-in-depth path) never listed PyYAML's unsafe loading surfaces, so an app that passes attacker-controlled `target` + arguments to `instantiate()` executes code via `target: yaml.unsafe_load` pointed at a config-controlled YAML stream carrying Python object-construction tags. The advisory's named realistic exposure is the model-supply-chain one: a third-party model bundle (e.g. Hugging Face) ships attacker-controlled config metadata that victim loader code feeds to legacy Hydra instantiation.

Operator rules for AI/model-loading pipelines (extends this page's model-metadata-to-code legs):

- **Deny-list gaps are enumerable in one sitting.** Where a framework gates dynamic instantiation by *blacklisting* known-dangerous targets, enumerate the whole loader surface, not the famous entries: `yaml.unsafe_load`, `yaml.unsafe_load_all`, `OmegaConf.load` + unsafe resolvers, `pickle.loads`, `marshal.loads`, `eval`/`exec` builtins, `builtins.__import__`, `subprocess.Popen`, `os.system`. The blacklist tell is a module-level constant of target strings — grep for it, diff it against the language's actual dangerous-callable inventory. This page's vm2 `DANGEROUS_BUILTINS`-omits-child_process leg is the same membership-audit rule.
- **Version-band nuance is a fingerprint:** 1.3.x affected on its blacklist path, 1.4 affected only on the deprecated no-whitelist legacy path (1.4's trusted whitelist is not bypassed) — probe which instantiation API the loader app actually calls before dismissing "patched" 1.4.x apps that still use the legacy call.
- **Model-artifact recon checklist stays the same shape as the vLLM `code_revision` leg:** config/metadata files inside model repos are code inputs when the loader instantiates from them; inspect downloaded bundles for `_target_`/`target:` keys pointing at loader/serialization functions before loading in any shared environment.
- Proof boundary: lab loader, disposable YAML payload with `yaml.unsafe_load` + an inert object-construction tag (marker write), never against shared inference workers.
