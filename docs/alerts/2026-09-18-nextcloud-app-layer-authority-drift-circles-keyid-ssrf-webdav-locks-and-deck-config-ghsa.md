# Nextcloud app-layer authority drift: Circles keyId blind SSRF, WebDAV absolute-path locks, viewer-config leaks, and optional-guard fail-opens

Source: hourly offensive-security scan of GitHub Security Advisories, 2026-09-18 (unreviewed wave published 2026-09-18T03:30Z).

One theme ties the durable records: **bundled/first-party apps reimplement the platform's security machinery and drift from it.** Nextcloud core ships SSRF protections, per-user path confinement, and per-board/per-file authorization — but Circles opts its key-fetch out of the SSRF guard, the DAV plugin resolves identity from the request URI instead of the session, Deck's config API skips the board-ownership check every sibling route performs, Photos builds an owner's album listing from the *viewer's* folder config, and Approval's freshness check only runs when the caller volunteers the parameter. Each is a separate audit axis that generalizes far beyond Nextcloud.

## Why this is worth an operator page

- **App-level fetch paths routinely opt out of the platform's SSRF guard.** Circles needed an outbound key fetch and whitelisted local/private ranges for it, silently defeating core protections on two unauthenticated `POST` endpoints. Audit rule on any framework with a central SSRF helper: enumerate outbound HTTP calls and check each one *calls* the helper; explicit "local addresses allowed" exceptions on a request whose URL (or a fragment of it, like a keyId) is attacker-controlled are top-tier blind-SSRF candidates. Pair with the Sept 17 Nuxt OG Image outer-status oracle pattern — a blind endpoint like this still yields an internal reachability oracle from response/error differentials.
- **Alternate protocol surfaces re-resolve identity from the request, not the session.** The WebDAV lock handlers trusted the absolute URI path to identify the file owner context. Same axis as the July 28 wp-admin public-namespace triad and the Sept 17 Keycloak versioned-route family: REST, WebDAV, OCS, and app-specific endpoints over the same object store each re-implement authorization, and the copy drifts. Decision-table probe: for every object-scoped action on the primary API, run the equivalent on each alternate protocol surface as a *different* low-privilege user and compare verdicts. Bonus: a lock token returned to a non-owner converts a write-availability bug into lock-management takeover.
- **Config/setting endpoints are the least-audited sibling of resource CRUD.** Deck's card/board CRUD checks permissions; the *config* key on the same board checks nothing. When enumerating any resource API, list the auxiliary sub-resources (config, settings, labels, favorites, activity, comments) and test ownership on each — they were usually added later by a different commit author.
- **Wrong-principal configuration application is a metadata oracle.** Photos answered "which of the owner's files match this filter?" using the *viewer's* source-folder scope. Wherever a shared, saved, or templated artifact is *evaluated* (not stored) at read time, ask whose configuration the evaluator injects. A share normally considered read-scoped becomes a targeted enumeration primitive against the owner's tree.
- **"Optional security parameter" is fail-open.** Approval's etag check ran only if the client *sent* the etag. Any control gated on the presence of a request field — nonces, confirmation tokens, dry-run flags, checksums, version guards, second factors — must be tested with the field **absent**, not just forged. This is the parameter-omission twin of the null==null Sept 5 AVideo MFA bypass.

## Validation workflow (authorized scope only)

!!! warning "Two disposable accounts, owned callbacks"
    Use a lab Nextcloud instance (or explicitly authorized target) with two synthetic users, synthetic files/albums/boards, and owned no-content callbacks. Never lock or modify real users' files, never enumerate real owners' trees, never probe internal services outside the authorized scope, and never intercept or replay a real approval flow.

1. **Circles-class keyId SSRF:** as an unauthenticated caller, `POST /apps/circles/event/` with a `keyId` pointing at an owned callback; record the outbound GET (User-Agent, source IP, whether it follows redirects). Then, only within authorized scope, a private-range canary to confirm the local-address allowance; capture reachability booleans via timing/error differentials plus the outer response — no response-body claims. Positive: server-side GET to attacker-selected URL fires before any trust establishment (error text often confirms parse-then-fetch ordering).
2. **WebDAV lock decision table:** users A and B, one marker file each. B sends `LOCK`/`UNLOCK` against A's absolute DAV path; then attempt lock-listing to see if A's token is disclosed. Evidence: lock state change on A's file + token value presence in B's response (redact in reports). Negative control: same op against B's own file.
3. **Deck config sibling-audit:** user B `PUT`s a synthetic config key on user A's board ID while B's board-list shows no such board. Positive: 2xx and key readable by A; compare against card-create on the same board (expected 403) to prove the drift is sub-resource-specific.
4. **Photos viewer-config oracle:** owner seeds two folders, shares one filter-based smart album with the viewer; viewer sets `photosSourceFolders` to include the unshared folder and reads the album. Evidence: presence-only — filename/ID of the owner's unshared marker appears. Never harvest beyond seeded markers.
5. **Optional-parameter omission:** in the lab Approval flow, approve with a stale/omitted `etag` and record whether the decision is accepted. This is a decision-table test (send/stale/omit × accept/reject), never a MITM of a real approval.
6. **Delegated-admin REST parity:** provision a Workspace-delegated admin scoped to folder X; exercise folder Y over REST and over the UI. Positive: REST accepts, UI rejects — the entry-point drift table is the deliverable.

Reporting heuristic: title by the drifted control — **"core SSRF guard bypassed by app-level keyId fetch"**, **"DAV path resolved without session-owner check"**, **"board-config sub-resource skips ownership"**, **"album evaluated with viewer's folder scope"**, **"freshness check skipped when parameter omitted"** — and always include the primary-surface vs alternate-surface verdict table. These are unreviewed mirrors: confirm exact app versions and endpoint behavior against the linked advisories and the instance itself before reporting.
