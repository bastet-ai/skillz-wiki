# Identity-provider authority boundaries: ZITADEL token exchange, Keycloak stale link proof, Nezha Host-injected redirect (3 GHSAs)

Source: hourly offensive-security scan of GitHub Security Advisories on 2026-09-16 (reviewed wave published 2026-09-15/16).

Three identity-boundary records that share one operator lesson: **an identity provider's authority decision is only as strong as the weakest binding in the flow — exchanged-token provenance, link-proof lifecycle, or the value the server uses to build the redirect target.**

## Why this is worth an operator page

- **Token exchange is the newest large IdP attack surface and it is consistently under-tested.** RFC 8693 exchanges cross application boundaries inside one IdP; if the server skips "does this subject token belong to this client?" and "are requested scopes ⊆ original scopes?", the entire per-app role model collapses to "hold any token." Any ZITADEL/Auth0-style deployment with token exchange enabled deserves a dedicated exchange matrix, not a spot check.
- **Proof lifecycle bugs are quiet and persistent.** The Keycloak record is not a bypass of the confirmation step — the confirmation worked. The finding is that the *receipt* outlived its purpose, and the product also fails to revoke it when the user explicitly unlinks. Identity proofs must be single-use *and* revoked when the relationship they authorized is dissolved. This is a reusable check on any "confirm in another device/browser" flow (SSO link, device pairing, passkey enrollment).
- **Fix regressions hide behind new optional config.** The Nezha record is a previously-fixed Host-injection that returns whenever a newly added setting defaults to empty. When a product ships a fix that is gated on configuration, the empty/unconfigured state is the first thing to re-test — upgrade paths and defaults frequently land in the regressed state.

## Validation workflows (authorized scope only)

!!! warning "Disposable IdPs, synthetic clients, synthetic users only"
    Run every proof against a lab IdP you own with throwaway realms/organizations, fake client credentials, and canary users. Never exchange real user tokens, never target a production IdP, and never collect real authorization codes or tokens in report evidence.

### 1. ZITADEL-style token-exchange matrix

Preconditions: lab IdP with token exchange enabled, one low-privilege client/app (A) you can authenticate as, one high-privilege target app (B) with an administrative role assignable to a canary user, and two canary users (low, high).

1. Mint a low-privilege access token for app A (client credentials or a disposable low-role user).
2. Send a token-exchange request with `subject_token` = A's token, `audience` = app B, and `scope` requesting B's highest available role/scope.
3. Record the decision table: token accepted/rejected, returned token's app audience, returned roles/scopes, and whether requested scopes exceeding the subject token's scopes are honored.
4. Cross-product variants: submit app B's own token from client A (token/client mismatch), submit a token from an unrelated app C, submit with a public client (no secret), and request scopes beyond the subject token's grants.
5. Positive: a low-privilege token yields a B-audience token with administrative roles, or out-of-scope requests honored. Confirm the negative on the patched build (4.15.3+), then delete all minted tokens and canary grants.

Report the exchange as a **provenance + scope-containment** failure with the exact grant type, request parameters (token labels only), and the role/scope delta between subject and issued token.

### 2. Link-proof lifecycle check (Keycloak-style first-broker-login)

Preconditions: lab realm with identity brokering, a fake external IdP you control, two disposable browsers/profiles (victim + attacker), and a canary victim account.

1. Drive the normal flow: victim initiates login via the external IdP, confirms account linking from the second browser, capture the temporary proof's lifetime and binding.
2. After the link succeeds, **replay the proof** from the attacker-controlled external identity — the check is whether the still-stored proof lets the attacker's identity re-establish (or re-bind) the link without victim confirmation.
3. Add the removal path: victim manually unlinks, then the attacker replays the same proof again. A leftover proof that re-links after explicit removal is the durable finding.
4. Record: proof creation trigger, TTL, subject binding, whether link success clears it, whether manual unlink clears it, and the re-link decision. Use a harmless canary attribute (e.g., a marker email on the fake IdP), never real identities.

### 3. Host-header redirect regression check (Nezha-style)

Generalize the check to any self-hosted app that builds an OAuth2 `redirect_uri` at login-start time:

1. Enumerate the app's configuration surface and find settings that changed in recent releases; note every newly-optional setting whose **empty/default state** selects a different code path.
2. Start an OAuth login with a forged `Host` header (point it at an owned no-content observer) and capture the exact `redirect_uri` sent to the IdP in the outbound request — compare against the configured install/dashboard host.
3. Repeat with the setting populated (control) and empty (suspected regression). The positive is `redirect_uri` host following the request header in the empty/default state on a build that supposedly fixed the original advisory.
4. Prove only destination control at the IdP request boundary with an owned observer; never complete a real code exchange with a victim authorization code.

## Reporting heuristics

- For token exchange, report the **two missing checks separately**: token↔client provenance and scope containment. They can be fixed independently.
- For proof-lifecycle bugs, state explicitly which lifecycle event failed to revoke the proof (link success, link removal) — that is the boundary, not "account linking is insecure."
- For config-gated regressions, cite the original advisory being regressed, the exact setting whose empty state restores the vulnerable path, and the version. Empty-default regressions are frequently absent from vendor fix notes.
- Keep evidence to parameter tables and token/proof labels; never include live tokens, authorization codes, or real IdP metadata.

## October 4 follow-up: ZITADEL Login V1/V2 account-takeover cluster — the identify-only session as a privileged foothold (10 GHSAs)

Source: GitHub advisories published 2026-10-04 15:30Z (fixed 3.4.14/3.4.15 and 4.16.2/4.17.1/4.17.3). Ten legs, four rated critical, all inside the hosted Login UIs. The cluster generalizes this page's core claim: **the weakest binding in an IdP flow is usually a state the flow treats as "in progress" but the handlers treat as authenticated.**

- **Identity binding without a factor or permission** ([GHSA-98x8-wvr5-pxqj](https://github.com/advisories/GHSA-98x8-wvr5-pxqj), CVE-2026-105207, 9.8): user↔external-IdP links are created without verifying a primary factor or the caller's permission — including on identify-only Login V2 sessions and via User Service V2 `AddIDPLink`. Unauthenticated attacker knowing a login name binds **their own** IdP identity to the **victim's** account, then signs in as the victim. Direct sibling of the Keycloak stale-link-proof leg above: that one abused a leftover link receipt; this one never required the receipt at all.
- **Authenticator enrollment on identify-only sessions** ([GHSA-4727-2r9w-rpch](https://github.com/advisories/GHSA-4727-2r9w-rpch), CVE-2026-105212, 7.5): passkey/authenticator enrollment accepted on identify-only login sessions **before any primary factor is verified** — knowing a login name is enough to register an attacker authenticator and log in, bypassing password and MFA.
- **Second-factor enrollment/initialization handlers act pre-primary-factor** ([GHSA-j55w-p4wc-frwh](https://github.com/advisories/GHSA-j55w-p4wc-frwh), CVE-2026-105210, 8.2): Login V1 TOTP / OTP-SMS / OTP-Email / U2F enrollment handlers act on the identify-only session; attacker-controlled factors enroll, the verified phone number gets overwritten, and discrepant errors yield user enumeration.
- **OTP codes returned in server-action responses** ([GHSA-mq63-7hcv-jfrc](https://github.com/advisories/GHSA-mq63-7hcv-jfrc), CVE-2026-105211, 8.1 critical): the `returnCode` delivery type echoes OTP-Email/OTP-SMS codes back in the HTTP response — an attacker who knows the login name reads both codes from the server action and walks out with an MFA-authenticated session, including admin accounts. Delivery-channel abstraction where one mode returns the secret to the requester.
- **Account squatting on unverified external identity** ([GHSA-639g-x9rp-hw3x](https://github.com/advisories/GHSA-639g-x9rp-hw3x), CVE-2026-105215, 9.1): the "external account not found" registration endpoint trusts client-supplied `IDPConfigID` + `ExternalUserID` with **no completed IdP callback** — pre-create an account bound to the victim's external IdP identity; the victim's later genuine IdP login lands in the attacker-seeded account. Reverse-direction account-linking squat: the link is asserted, not proven.
- **Org header scoped to caller, not target** ([GHSA-hcch-574x-xrm8](https://github.com/advisories/GHSA-hcch-574x-xrm8), CVE-2026-105209, 9.6 critical): passkey/passwordless enrollment-code issuance checks only the `x-zitadel-orgid` header (the caller's org), not the target user's org — user-write permission in org A buys an enrollment code for a user in org B on the same instance. Same class as the OpenAM session-verb legs: authorize against the **target object's** scope, never the request envelope's.
- **Cross-org read authorization keyed on caller's org** ([GHSA-pmw5-r3fq-5gm7](https://github.com/advisories/GHSA-pmw5-r3fq-5gm7), CVE-2026-105206): User Service verifies `user.read` against the caller's org instead of the target user's org — org-scoped readers enumerate other orgs' registered authentication-method types via `GET /v2/users/{userId}/authentication_methods`. Enumeration oracle feeding the enrollment legs above.
- **Malleable unauthenticated intent tokens + timing race** ([GHSA-xv85-7fx2-46j9](https://github.com/advisories/GHSA-xv85-7fx2-46j9), CVE-2026-105208, 7.7): IdP intent tokens are encrypted but unauthenticated and malleable; tamper your own token to be accepted for another user's in-flight external-login intent, predict the intent identifier, win the race on `/v2/idp_intents` or `/v2/sessions`, steal the victim's IdP tokens or hijack the session. Unauthenticated-ciphertext pattern/state handoffs are bearer credentials.
- **Tenant lifecycle state not rechecked at auth** ([GHSA-3fc9-77fj-j3c7](https://github.com/advisories/GHSA-3fc9-77fj-j3c7), CVE-2026-105213, 8.2): Login V2 checks only the individual user's status, never the organization's inactive state — users of a deactivated org keep signing in, minting sessions, and refreshing tokens. Disabled-tenant recheck axis, sibling of the Keycloak disabled-client recheck rule.
- **Domain-verification SSRF via bare default client** ([GHSA-66r9-3738-gxmw](https://github.com/advisories/GHSA-66r9-3738-gxmw), CVE-2026-105214): organization domain HTTP verification fetches the challenge with Go's default `http.Get` instead of the project's protected (SSRF-guarded) client — register a domain that redirects to loopback/internal/metadata to port-scan the internal network. Exact hardened-sibling-grep axis promoted the same day on the Gitea OIDC picture-claim leg: when a repo has a guarded HTTP client, grep for `http.Get`/`http.DefaultClient` call sites; each one is a bypass candidate.

### Replayable checks (lab IdP only)

1. **Session-state gating matrix.** Enumerate every Login UI handler and classify which session state it requires: pre-identify, identify-only, primary-verified, second-factor-verified. Any enroll/link/enrollment-code/phone-update handler reachable at identify-only is a finding — that sweep alone would have caught four of the ten legs.
2. **Delivery-mode decision table.** For every OTP/email/SMS delivery abstraction, request each delivery mode and diff responses; a mode that returns the code to the requester (or its hash/length) is a transport leak independent of channel security.
3. **Target-scope audit on multi-tenant verbs.** For every org-header/org-param-carrying write (enrollment code, role grant, session action), supply a target object ID belonging to a second lab org and check whether authorization consults the target's org; also query the read sibling (`authentication_methods`) as the low-priv caller.
4. **Tenant-deactivation probe.** Deactivate a lab org, then replay a valid login, an existing session, and a refresh-token exchange; any success is the lifecycle-recheck miss.
5. **Intent/handoff token tamper test.** For any short-lived cross-request token (login intent, pairing, password-reset), flip user/tenant-bound fields in the ciphertext **without recomputing** and check acceptance for a second user's flow; pair with identifier-predictability measurement.
6. **Protected-client grep.** `grep -R "http.Get\|http.DefaultClient"` in any product that ships an SSRF-guarded HTTP client; verify each bare call site against untrusted URLs (domain verification, webhooks, avatars, `jwks_uri`).

Report shape for this cluster: per-leg, name the missing gate precisely ("enrollment acts on identify-only session", "authz keyed on caller org not target org", "org state not rechecked at mint") — the vendor fixed ten distinct gates in four releases, so consolidated "IdP ATO" framing undersells each independently patchable boundary.

## October 5 follow-up: Keycloak registration attributes, pre-validation cert fetch, and session-note token bleed (3 GHSAs)

Source: GitHub advisories published 2026-10-05 06:30Z. Three more Keycloak legs, one per flow stage — client registration, certificate authentication, and token issuance — each breaking a different binding in the same "trusted IdP config object" assumption.

- **Open-introspection client via unfiltered registration attributes** ([GHSA-q5jp-7g4g-ch69](https://github.com/advisories/GHSA-q5jp-7g4g-ch69), CVE-2026-105306, 6.5): Dynamic Client Registration copies attacker-supplied client attributes onto the new client without filtering security-sensitive ones, so a client registered with a valid Initial Access Token can carry an attribute set that **bypasses audience checks during token introspection** — the registered client then reads roles, identity claims, and session details out of access tokens minted for *other* applications in the realm. Durable axes: (1) client-attribute round-trip — in any OAuth AS, register a client echoing every writable attribute, then diff which attributes change enforcement behavior at introspection/token endpoints (registration surface and enforcement surface are routinely written by different code); (2) Initial Access Token is a *least-privilege* credential in threat models, but here one registration with it yields cross-client token reads — enumerate what a lowest-tier registration credential actually unlocks end-to-end, not just "can I register". Probe: register a canary client, request its introspection of another canary client's token, decision-table accepted/rejected + returned claims before/after toggling the attribute.
- **Blind SSRF from unvalidated certificate revocation URLs** ([GHSA-hg66-m76j-q2rm](https://github.com/advisories/GHSA-hg66-m76j-q2rm), CVE-2026-105301, 4.0): with X.509 client-certificate authentication configured for CRL Distribution Points or OCSP checking, Keycloak fetches the CRL/OCSP URL embedded in the **presented (still-untrusted) certificate** before full validation completes — a crafted cert pointing its DP/OCSP at an internal endpoint gets the IdP to make an outbound request on the attacker's behalf during the TLS/login handshake. Rule: any revocation/chain-URL fetch (CRL DP, OCSP responder, and the analogous `jwks_uri`/`scope` claim fetches on the OpenAM and July 28 pages) is a **pre-trust network sink** — the data driving the fetch originates from attacker input, so URL-grpc scheme, host, and port all deserve canary-callback testing on cert-auth-enabled realms. Proof stays blind-callback: owned observer, timing/response-shape diff, never internal-service probing.
- **Session-note mapper bleeds upstream IdP tokens into downstream tokens** ([GHSA-3xph-hcf4-hx94](https://github.com/advisories/GHSA-3xph-hcf4-hx94), CVE-2026-105302, 5.7): the User Session Note mapper copies any named session note into issued tokens with no sensitive-key filtering — a delegated administrator of one client can add a session-note mapper for the note holding a user's **federated bearer token from an external IdP**, then harvest upstream Google/Microsoft-style tokens out of tokens issued to their own managed application. Rule: protocol mappers are read primitives over the server's session store; enumerate every mapper type (claims, audience, session note, user metadata) against every session-store key you can name from the broker config, from a lowest-tier delegated-admin account. This is the identity-broker mirror of the Sept 16 IdP page's own thesis: the realm's *internal* credential bag is reachable through a *config* surface a delegated admin legitimately controls. Validation: two-client lab realm with a fake upstream IdP minting a canary federated token, add the mapper from a delegated-admin user, decode the issued token, confirm canary presence — never against real upstream providers.

Cross-refs: introspection-audit and disabled-state recheck axes already on the [June 11 Keycloak batch page](2026-06-11-kolibri-hapi-keycloak-flowise-arc-boundary-batch-ghsa.md); `jwks_uri` pre-trust fetch sibling on the [June 22 OpenAM page](2026-06-22-container-openam-xwiki-comfyui-boundaries-ghsa.md) and July 28 SSRF page; future Keycloak legs fold here or on the June 11 page per flow stage (registration/issuance here, admin-REST verb drift there).

## October 8 follow-up: Eclipse Ditto Explorer — split-authority OAuth where the config URL IS the authority ([GHSA-g8w6-jp67-cwcc / CVE-2026-107503](https://github.com/advisories/GHSA-g8w6-jp67-cwcc), high, Explorer 3.6.0–3.9.7)

A crafted `environments` link sets an attacker-controlled OIDC authority while `autoSso` is enabled. The UI then **starts a genuine login at the real identity provider** — the authorization redirect itself is legitimate — but exchanges the returned authorization code and its PKCE `code_verifier` at the **attacker-controlled token endpoint**, letting the attacker redeem the code for the victim's access *and* refresh tokens. An attacker-controlled `api_uri` variant sends the victim's bearer token or Basic credentials straight to the attacker. Because the environment config **persists**, every later visit to the UI without the crafted link repeats the theft.

Durable axes for any SPA/ops-console that takes config from the URL:

1. **Authority-split OAuth.** The classic `redirect_uri` check is the wrong gate here: the IdP is genuine, the client is genuine, only the *token-exchange endpoint* is attacker-chosen. Audit which OIDC discovery document the SPA uses and where that discovery URL came from — if `token_endpoint` can transit untrusted input (URL param, persisted storage, tenant config), the authorization code + PKCE guarantees nothing; PKCE binds code↔client, not code↔token endpoint. Probe: craft an environment link pointing discovery/token at an owned observer, complete your own login, confirm the observer receives the code + verifier; never test against real users.
2. **Persisted client-side config = durable phishing implant.** A one-click link that rewrites where the app sends tokens, surviving across sessions, converts a single phish into standing token theft — worth more on any bounty triage than the open-redirect-class it superficially resembles. Enumerate every URL/storage key that reconfigures auth endpoints; check whether any trust decision (prompt, origin check, allow-list) gates *writing* them.
3. **`autoSso`-style auto-login turns config injection into no-click-per-session token loss.** Auto-initiated auth flows remove the user step from the chain after the initial link click.

Cross-ref: the July 30 URL-policy page covers guard-coverage parity for fetch targets; this leg is its auth-flow mirror — the fetch target that matters most is the one that receives your code and tokens.

## October 8 15:3xZ follow-up: Keycloak read-only-role client-secret read + DCR update silently disabling offline-token revocation (CVE-2026-107604 / [GHSA-ch4r-x5r9-rqr3](https://github.com/advisories/GHSA-ch4r-x5r9-rqr3), 4.9 · CVE-2026-107623 / [GHSA-qxj8-968q-qm7w](https://github.com/advisories/GHSA-qxj8-968q-qm7w), 4.3)

Two more Keycloak client-management boundary legs for the IdP page:

- **Read-only view-clients role exposes the active primary secret of any confidential client** (ch4r, realm-admin scope): via the installation-provider and client-registration endpoints, an account holding only the *read* clients role retrieves client secrets that should be admin-write-gated — secret **read** verbs leaking through installation/config-export endpoints while everyone audits the **write** path. Sweep rule: for every client-management field, enumerate **which endpoint families render it** (admin REST, registration API, installation/download-format endpoints — OpenShift/OIDC client-config downloads, `keycloak.xml`, OIDC client JSON); the export family is the classic un-redacted twin. Proof: disposable realm, synthetic client, compare `view-clients`-only principal responses across all endpoint families; never touch live client secrets.
- **DCR update silently drops the backchannel-logout offline-token revocation setting** (qxj8): a response-serialization bug omits the setting from GET responses, so a standard client update (read → modify → PUT) round-trips a payload that lacks it ⇒ the setting is **silently disabled**, and offline tokens stay valid after backchannel logout. Durable operator/verification axis rather than an exploit: **GET-then-PUT read-modify-write flows silently strip any field the GET response fails to serialize** — a config-drift mechanism that's also a quiet security-control-disable path. Test any API's settings surface with a field-presence parity check (fields in PUT request vs fields in subsequent GET); the missing fields are the ones updates destroy. On the offensive side, where you legitimately control a client's DCR token, this is a revocation-defeat path worth checking post-fix.


## October 9 19:1xZ follow-up: Pingvin Share X — automatic OAuth email linking where `email_verified` is never checked (critical ATO)

[GHSA-7p7c-6qwr-q8j7](https://github.com/advisories/GHSA-7p7c-6qwr-q8j7) / CVE-2026-108157 (critical, Pingvin Share X 0.19.0–<1.22.0): `OAuthService.signUp()` **auto-links an OAuth/OIDC identity to an existing local account on matching email alone**, and `GenericOidcProvider` never checks the `email_verified` claim. An attacker registers a **victim's unverified email** on an enabled attacker-controlled (or self-hosted) OAuth provider, then uses that provider's login flow to **sign in as the victim — administrators included — while bypassing TOTP** entirely (the local second factor belongs to the password flow, not the federated one).

Durable axes for every product with "social login auto-creates/links by email":

1. **The email claim is only as trustworthy as the IdP that minted it.** The exploit is not a bug in the match logic — it's that ANY enabled provider's email claim is treated as proof of ownership. On a target with admin-configurable or self-hosted OIDC, the attack is: register attacker provider → put victim email on attacker's IdP → login. Recon: enumerate `/api/auth/*` provider list, `.well-known/openid-configuration` reachability rules, and whether non-admins can add IdP configs; the missing gate is `email_verified` AND provider-tier trust, both.
2. **Federated login silently skips the local MFA enrollment.** If account linking succeeds, the victim's TOTP is never offered — the second factor is bound to the *credential path*, not the *account*. Add to every federated-login matrix: victim has password+TOTP; attacker authenticates via linked IdP; record whether the local factor is enforced (it must be, at minimum for elevated accounts).
3. **Unverified-email registration on the attacker side is a prerequisite — verify with a disposable chain only.** Lab proof: two lab users + a self-hosted OIDC test provider you control (Keycloak/Authelia lab realm), set the attacker IdP account's email to the victim's, complete the OAuth dance, record which account the session binds to. This fixture is also the general-purpose account-linking regression harness for any product's OAuth surface (pairs with the Sept 16 Keycloak link-proof-reuse leg at the top of this page — same trust boundary, opposite defect: that one never cleared the confirmation proof, this one never asks for confirmation).

## October 9 21:1xZ follow-up: Vikunja OIDC `emailfallback` — email-only linking where the `email_verified` claim doesn't even exist in the parser (ATO)

[GHSA-xv7q-fvmc-jx96](https://github.com/advisories/GHSA-xv7q-fvmc-jx96) / CVE-2026-62367 (high, Vikunja 1.0.0–2.3.0, fixed 2.4.0): with the per-provider OIDC `emailfallback` option enabled, the callback resolves identity on `(issuer, subject)` first, and on a subject miss falls back to `WHERE issuer='local' AND email=?` against local accounts — **no `email_verified` check, no `xms_edov` (Microsoft education-disclosure-opt-out) check, no password**. ## October 13 follow-up: oauthlib library layer — JSONP revocation-endpoint JS injection and PKCE-plain timing oracle (2 GHSAs, descriptions published Oct 13)

The most-deployed Python OAuth2 server library shipped two reusable boundary patterns in one advisory pair (published late Sept, detailed technical descriptions added 2026-10-13):

- **JSONP callback reflected as executable JavaScript on the revocation endpoint** ([GHSA-hj66-6f7g-4r5v](https://github.com/advisories/GHSA-hj66-6f7g-4r5v) / CVE-2026-49264, medium, `enable_jsonp=True`): `RevocationEndpoint` wraps responses as `'{callback}({body});'` on the error path and `'{callback}();'` on success, with **zero validation** that `callback` is a legal JS identifier — the parameter is merged from query string *and* POST body, so the attacker controls the entire JavaScript returned from a same-origin OAuth endpoint. The success path is the interesting one: even a *valid* revocation request echoes the injected expression. Operator probe: on any Python-oauthlib-based AS, request `POST /oauth/revoke` with `callback=alert(1)//` (and query-string variant) and check whether the response body starts with your literal string; content-type `application/javascript`/`text/javascript` completes the stored-reflect XSS primitive for anything that scripts in the path. Fingerprint: any JSONP-capable OAuth route (revoke, token introspection, userinfo) — JSONP is a legacy-browser-era pattern still enabled on auth endpoints where nobody re-tests it, and the revocation endpoint in particular is habitually skipped in OAuth security reviews because it "just revokes tokens."
- **PKCE `plain` method compared with `==` → timing oracle on the code_verifier** ([GHSA-xpv3-w29h-x7cv](https://github.com/advisories/GHSA-xpv3-w29h-x7cv) / CVE-2026-49265, medium): `code_challenge_method_plain` short-circuits on first mismatch, so repeated `/token` submissions with the same `authorization_code` measure the common-prefix length of the verifier character by character (advisory PoC shows a statistically clean per-character latency delta). Precondition gate: the AS must accept `method=plain` — which is itself the bigger finding. Operator probe order: (1) enumerate `code_challenge_method` support at `/authorize` (a server that accepts `plain` at all is weak PKCE — RFC 9700 guidance is S256-only); (2) if plain is accepted, the token endpoint becomes a **replayable timing oracle** — high-volume repeated exchanges with prefix-growing verifiers, measuring latency to bisect each position; practical over LAN/co-tenant, marginal over internet jitter, so scope it to internal/red-team engagements; (3) also run the negative check: does the same short-circuit apply to S256 digest comparison (it shouldn't leak verifier material, but it can leak challenge-prefix matches).

Rules: (1) **library-layer advisories fan out to every product built on them** — when an AS bug lands in oauthlib/authlib/oauth2-server libs, grep your target's stack (`requirements.txt` leaks, error-page fingerprints, `/.well-known` response-header quirks) instead of waiting for product advisories; (2) JSONP-capable auth endpoints are an un-retested legacy surface — include `callback=` reflection on every OAuth route family in recon, not just search/userinfo endpoints; (3) PKCE is only as strong as its weakest accepted method *and* its comparison implementation — method enumeration is a five-request check that gates the entire timing class.

Pre-fix `SessionResource.create()` (the unauthenticated `POST /api/session` login handler) shape:

## October 21 21:4xZ follow-up: Keycloak — required-action *ordering* is the MFA enforcement gate; a locale prompt scheduled before Configure OTP skips enrollment ([GHSA-52qh-rwj9-2j89](https://github.com/advisories/GHSA-52qh-rwj9-2j89) / CVE-2026-114438, medium)

- **Signed gateway token embeds *additional destinations* that the enforcement point trusts** (prr7): token generation for Devolutions Gateway accepts wildcard destination additions, and the gateway enforces Network Access Rules against the token's embedded destination list rather than server-side policy — a non-admin signs denied hosts into their own token and reaches them. Rule: when a policy engine's decision input is a *client-carried signed artifact*, ask who authored the fields inside the signature — signature integrity is not content authorization. Sweep every token/cert/SAML-attribute writer for user-influenced destination/scope/host arrays before trusting the enforcing gateway's allowlist.
- **PAM AD computer-import endpoint has no authorization check** (qmr2): an authenticated non-admin with a PAM license creates PAM sub-providers under *existing* AD providers via a crafted import request — a bulk-import convenience route outside the admin gate its CRUD siblings sit behind. The route-family enumeration rule again: import/bulk/sync verbs are chronically missing the parent-resource permission check; probe import endpoints with a lowest-priv licensed account and a synthetic target.
- Validation boundary: lab Devolutions Server, two disposable accounts (one delegated-view, one non-admin with PAM license), synthetic vault entries and a test AD fixture; never touch a production vault, real MFA seeds, or live gateway destinations.

## October 27 follow-up: Psono Server five-leg wave — a secret vault leaks its own boundaries: transfer-direction binding, URL_PREFIX authz fail-open, device-code scope uplift, Duo-host SSRF oracle, and unconsumed WebAuthn challenges (CE & EE, ≤7.2.3; [GHSA-jg7j-q6m4-7gq5](https://github.com/advisories/GHSA-jg7j-q6m4-7gq5), [GHSA-4hh2-mhpm-69h3](https://github.com/advisories/GHSA-4hh2-mhpm-69h3), [GHSA-897w-6p63-7p9g](https://github.com/advisories/GHSA-897w-6p63-7p9g), [GHSA-q3ph-3gv2-g5wq](https://github.com/advisories/GHSA-q3ph-3gv2-g5wq), [GHSA-3gq2-hx4p-69qc](https://github.com/advisories/GHSA-3gq2-hx4p-69qc))

A five-advisory coordinated wave on self-hosted password manager Psono (all ≤7.2.3) lands on this page's crown-jewel rule — a credential vault is an IdP-adjacent authority system, and its own auth layer carries the same defect classes this page collects. Each leg generalizes past Psono:

- **Credentials carry capability but not direction** (jg7j, CVE-2026-117469): a file-transfer credential minted for *download* is accepted at the *upload* endpoint — read-only access to a file lets a user present the download transfer to upload, obtaining a signed upload URL for an attacker-selected object key and appending chunks to the owner's file. The authorization gate checked "valid transfer credential," never "transfer issued for *this* operation." Rule: for every single-use/signed credential (presigned URL, transfer token, one-time ticket), probe the **inverse operation** of the one it was issued for — sign-for-read → replay-at-write, sign-for-export → replay-at-import. Grep fingerprint: endpoints that consume a shared token type and branch on a client-supplied `method`/`direction` field instead of a server-recorded issuance intent. Validation: two disposable vault users, append a synthetic marker chunk to your *other* user's file only.
- **Deployment-prefix config silently breaks a hard-coded path comparison → scope swap** (4hh2, CVE-2026-117472): the bulk-secret-read endpoint compared the request path against a hard-coded *unprefixed* string; under a `URL_PREFIX` deployment the comparison never matched and the POST fell through to **write-scope** authorization instead of read — a read-disabled, write-enabled API key retrieves encrypted secret data + nonces through the prefixed endpoint. Rule: authorization logic that string-compares request paths is **configuration-sensitive**; replay the same verb/scope battery under every documented URL-prefix/mount-point shape (`/`, `/psono/`, reverse-proxy subpaths) with a deliberately *scope-skewed* API key (read-off/write-on and vice versa). Default-config-only testing misses this entire class — fingerprint it by grepping permission classes for literal path strings rather than route names.
- **Device-code flow grants the *poller's* session, not the requester's scope** (897w, CVE-2026-117468): claiming a device code never enforced the session's token write scope, so a restricted API-key-derived session could claim an attacker-supplied device code and receive a **full read-write session valid up to 365 days** — scope and lifetime restrictions of the originating token left behind. This is the device-flow mirror of the CIBA per-client gating leg above: the *grant itself* is a privilege-uplift primitive, and the check must live at the claim step. Battery on any product with device-code/OOB/pairing flows: (1) authenticate with the lowest-scope credential you can mint, (2) start a device-code flow yourself, (3) claim/complete it from the restricted session; a token whose scopes/lifetime exceed the claimant's is the finding. 365-day uplift from a scoped key is report-grade on any secret vault.
- **Third-party integration host fields are SSRF inputs** (q3ph, CVE-2026-117471): personal Duo device configuration accepted a user-controlled *host*, passed to the Duo client with no allowlist/timeout — authenticated server-side HTTPS connections on port 443 with distinguishable failure modes = internal DNS + service-reachability oracle (TLS validation still applies; unresponsive targets pin a worker). Known shape, new instance class: any "bring your own endpoint" integration field (webhook URL, IdP host, SMTP host, marketplace API base) deserves an owned-callback reachability probe even when the client library looks hardened — and record the worker-occupancy side effect as a bounded DoS note, not a separate finding.
- **WebAuthn challenges must be single-use server-side state** (3gq2, CVE-2026-117470): the stored challenge was not consumed after successful assertion verification, so a captured valid assertion replays across *separate* login tokens for the same user — password + one captured assertion = persistent second-factor bypass. Pair with the miniOrange pending-passkey leg above: that one was *enrollment* during a pending login; this one is *assertion replay* — the full WebAuthn battery on this page now covers register-mid-login, assert-replay, and challenge-lifetime. Probe: complete a WebAuthn login on a disposable lab account, capture the assertion, start a fresh login-token and replay the captured assertion without the authenticator; success = MFA bypass. Report severity assumes password-theft composition.
- Validation boundary: lab Psono CE with disposable accounts/objects, your own Duo-callback-style owned endpoints, and only synthetic vault items; never target hosted deployments or replay assertions captured from anyone else's session.
