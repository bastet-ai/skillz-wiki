# Nginx UI wave (7 GHSAs): the node secret is a master credential

**Wave in one line:** the node secret is a master credential, the 2FA UI flag is not the login enforcement, and the fix missed the parallel router

**Signal:** GitHub Security Advisories published a coordinated seven-advisory wave against [0xJacky/nginx-ui](https://github.com/0xJacky/nginx-ui) (CVE-2026-107807 through CVE-2026-107813) at **2026-10-09T17:07–17:08Z**, all fixed in late-July 2026 builds (pseudo-versions `1.9.10-0.20260728*`). Nginx UI is a widely deployed web management panel sitting directly in front of the reverse proxy that fronts everything else — its own compromise is an engagement-level pivot. The wave is a textbook cluster of reusable axes: a machine-to-machine shared secret that upgrades to a superuser identity, a capability flag that says "2FA on" while the enforcement code checks a different flag, a security fix applied to every router except its physically separate sibling, an archive restore that materializes files before it consults the restore flags, and a self-upgrade whose only integrity check is a digest fetched from the same endpoint as the binary.

## Why this is durable operator value

1. **Machine-to-machine secrets are authorization state, and "upgrade-to-superuser" middleware is the highest-value gate to hunt.** The node secret did not just authenticate a peer — it *replaced the identity* with `initUser` and skipped user auth entirely. On any clustered tool (Consul-style gossip, HA pairs, load-balancer sync, backup agents), enumerate the shared-credential surface and ask what identity a correct credential yields. Two independent legs here reach the same credential: an API field that should have been redacted (`json:"token"`, no per-endpoint redaction) and a transport convenience (header → query fallback). **Credential-in-query is a permanent leak** — grep any auth middleware for `Query()`/`url.Values` fallbacks.
2. **Capability-flag vs enforcement-point drift.** The UI, the DB column, and the policy function all said "2FA enabled" (`Enabled2FA`), but the login handler branched on a *different* predicate (`EnabledOTP`). Rule for every MFA-capable product: enumerate every factor type, then diff what the status endpoint reports against what each login/step-up route actually requires — test a passkey-only and a TOTP-only account against password-only login. Same genealogy as the permission-vs-scope drift families already on the Sept 21 auth-precedence page.
3. **Fix drift across sibling routers — a concrete incomplete-fix differential.** The patched middleware was applied per-router; the cluster package was a separate registration site and was missed. After any published advisory + fix, enumerate *all* router/controller registration sites for the same op class and re-test the old advisory's behavior there (this advisory literally names the fixed sibling vs the missed one — vendor fix commits are attack maps). Nginx UI also ships the MCP sensitive-tool list as part of the fix — tool-name lists and router lists drift independently.
4. **Extract-before-decide restore + "confined" symlink allow-lists.** The restore decided *what to apply* after already materializing *everything*; the symlink guard checked only the link *target* prefix, then later entries wrote *through* it. Hunt pattern for every import/restore/agent feature: (a) does the extractor write before the flags/plan are evaluated? (b) does the containment check apply to the link itself or the final resolved path? Absolute symlinks under an allow-listed prefix are a classic double-link primitive.
5. **Same-origin digest ≠ integrity (fourth independent week of update-channel trust).** Binary + checksum from one endpoint = the check verifies the fetch, not the publisher. Grep upgraders for `digest`/`checksum` fetches sharing a base URL with the payload, no signature site; note `github_proxy` accepting `http://` = cleartext supply leg. Pairs with the Sept 16 hardcoded-update-key axis below and the ongoing same-origin-update theme.
6. **Bearer-token-in-cookie is ambient authority.** A cookie fallback on an API middleware silently converts a token API into a CSRF-able one for the browser threat model. On any SPA+API panel: check `document.cookie` for JWTs, then drive one cross-site state-changing POST from an attacker page with no token knowledge.

## Replayable validation boundaries (lab/authorized scope only)

- **Node credential ladder (two disposable nodes, lab cluster only):** create a low-privilege user → `GET /api/nodes` → check for a `token` field in the JSON (redaction-or-not is the finding, stop before use on any live system). In the lab, replay that value as `X-Node-Secret` against the peer node's API and record the resulting identity. Query-parameter leg: send `?node_secret=<value>` to a benign endpoint and confirm whether it authenticates (and whether it lands in your own access logs — log exposure is provable on your instance alone).
- **2FA enforcement parity matrix:** provision passkey-only, TOTP-only, and both-factor lab accounts; attempt password-only `POST /api/login` for each; evidence = decision table (factor config → login outcome → `enabled_2fa` value reported). Harmless session; no account takeover claims.
- **Step-up coverage sweep:** for a fixed advisory that added step-up middleware, list every sensitive mutation route (node CRUD, reload/restart, cert issuance, backup restore) and re-test each with a long-lived JWT and no fresh secure session. Route-decision table per router group is the deliverable.
- **Restore-symlink probe (own instance only):** build a backup archive with an absolute symlink into a *scratch* directory outside the intended restore root plus a regular marker entry; restore with all restore flags disabled; evidence = whether the marker materialized outside the staging root. Never target live nginx config paths — use a lab nginx-ui instance and scratch targets you own.
- **Upgrade-integrity posture (passive + own-instance):** read the upgrade code path for signature verification vs digest-equality; confirm whether the proxy/base-URL setting accepts `http://`. Proof-of-impact requires an owned mirror serving a synthetic binary — never intercept a live customer upgrade channel.
- **Cookie-ambient CSRF:** from a controlled attacker page, fire one reversible state-changing request (e.g. toggle a benign lab setting) with no explicit token; browser-sent cookie authenticity is the finding.

Durable operator rules from this batch:

1. **A validator that parses a different grammar than the engine is not a validator.** The denylist scanner spoke line-per-directive; nginx speaks `;`-per-directive. For any config-validation/upload-sanitization control: (a) enumerate the target engine's full statement-separator vocabulary (`;`, braces, `\n`, quoted-string continuation) and craft same-line/continuation variants of the first blocked token; (b) check the denylist against *indirection primitives* — a missing `include` makes any directive denylist void; (c) fingerprint the Docker image for available module surfaces (`find / -name 'ngx_http_js_module.so'` in a lab container; on engagements, module presence is what turns directive-injection into RCE and it differs between packaged and official images).
2. **Enumerate every write path to the same sink and diff the guards** — the REST add path validated, the MCP modify validated, the MCP add never did, and the hardening commit itself is the map of which siblings got the patch (`git log` for the validator-introducing commit, then `git show --name-only` to list the untouched siblings). Generalizes the incomplete-fix rule from *router families* to *call-site families*, and adds the MCP-specific axis: **MCP tool surfaces mount under their own middleware and frequently skip the HTTP path's step-up/validation gates** — on any product exposing MCP, re-run the guarded-verb battery through `/mcp`+`/mcp_message` with a JWT only (cf. the vc32 step-up leg). Agent-driven MCP use means a prompt-injected agent is an authenticated attacker with your token.
3. **2FA enrollment is a credential write and must require proof-of-possession of the existing credential.** The validation bug pattern here is the *tautology check*: endpoint accepts secret+code from the same request and validates the code against the supplied secret. Sweep every MFA/passkey/webauthn enrollment endpoint on any product: valid JWT, no password re-prompt, attacker-generated secret → enrolled? Then test the lifecycle claim (does password rotation clear an attacker-bound factor? Here: no). Passkey registration with no already-enrolled guard = persistent multi-key implant.
4. **Revocation code must enumerate credential shapes.** Grep the revocation/invalidate function for field predicates (`!= ""`, `!= nil`, status enums) and diff against every issuance function's populated-field shape. Test shape: issue each token type → revoke/disable → re-enable → replay *each* token class (long JWT, short token, WS token, API key) against each accepting transport. DB-row-deleted ≠ cache-invalidated; the cache is the enforcement point.
5. **Validated-container ≠ validated-final-path** (third sighting this month, with the Sept 19 upload write-target and Oct 14 backup-restore legs): `storage_path` confined, appended attacker `name` unfiltered. Probe every path-with-name API by putting `/`, `\`, and `..` in the *name/label/title* field even when the path field itself is validated — the join is where the boundary dies.
6. **Two SSO implementations in one codebase = test the old one.** Casdoor path shipped constant `state` while the sibling OIDC handler did it right. When a product supports multiple identity providers, run the full OAuth/CSRF battery per provider — shared `state`/missing PKCE lives in whichever handler was written first.

Lab validation (owned instance only): same-line battery against any config validator (`;`, `{}`, `\r\n`, trailing-space variants of the first blocked directive); REST-vs-MCP guard decision table per sensitive verb (accept/reject per path × per factor state); enrollment-without-reprompt probe using a TOTP secret you generated yourself; revocation matrix (token class × transport × disable/re-enable); login-CSRF check = compare the `state` value across two fresh logins (identical constant = finding, no victim browser needed).
