# Payment-gateway webhook branch integrity and client-trusted amount state (Sept 23 WP/WC cluster)

Source: hourly offensive-security scan, 2026-09-23. GitHub advisories [GHSA-wv8r-wv6j-wh9g](https://github.com/advisories/GHSA-wv8r-wv6j-wh9g) / [CVE-2026-93511](https://nvd.nist.gov/vuln/detail/CVE-2026-93511) (Premium Packages), [GHSA-7x4m-8ff6-56c9](https://github.com/advisories/GHSA-7x4m-8ff6-56c9) / [CVE-2026-87979](https://nvd.nist.gov/vuln/detail/CVE-2026-87979) + [GHSA-pgxh-7vg6-g5g2](https://github.com/advisories/GHSA-pgxh-7vg6-g5g2) / [CVE-2026-87981](https://nvd.nist.gov/vuln/detail/CVE-2026-87981) (Paymob for WooCommerce), [GHSA-68x3-xpqw-vw3q](https://github.com/advisories/GHSA-68x3-xpqw-vw3q) / [CVE-2026-80342](https://nvd.nist.gov/vuln/detail/CVE-2026-80342) (Payment Plugins for PayPal WooCommerce), [GHSA-h7x3-7cw4-64m2](https://github.com/advisories/GHSA-h7x3-7cw4-64m2) / [CVE-2026-77765](https://nvd.nist.gov/vuln/detail/CVE-2026-77765) (Better Payment), [GHSA-8v3j-283x-6xf7](https://github.com/advisories/GHSA-8v3j-283x-6xf7) / [CVE-2026-93510](https://nvd.nist.gov/vuln/detail/CVE-2026-93510) (Points and Rewards for WooCommerce).

Five money-handling WordPress/WooCommerce plugins failed the same way in one publication window: the gateway's *cryptographic* or *server-side* integrity control exists, but it is applied per-branch, per-state, or not at all — and the skipped branch is the exploitable one. This generalizes the Sept 22 ZenHive challenge-binding rule (verifier state vs dedup state) to the payment-gateway integration layer, and it is a coherent audit checklist for any WooCommerce payment extension or webhook-consuming SaaS.

## Durable axes

1. **Webhook signature verification is per-branch coverage, not a global property.** Paymob proves a single webhook handler can verify signatures on the payment branch and skip it on the card-token branch; Premium Packages proves the whole handler can skip it. Audit rule: for every webhook consumer, enumerate the *event-type/branch* dispatch table (payment, cancellation, refund, card-token, subscription, dispute) and test **each branch independently** with a forged, correctly-shaped-but-unsigned payload. A signed branch returning 401 on tamper tells you nothing about the sibling branch. This is the per-tool/per-auth-branch coverage-drift class (mcp-atlassian unhooked-session legs, Sept 22) wearing a payments costume.
2. **Conditional integrity checks: probe the skip-condition.** Payment Plugins' ownership check runs only for already-completed PayPal orders — every `if (state == X) verify()` pattern hides an unverified non-X path. For any cross-object binding (order↔order, intent↔cart, voucher↔purchase), enumerate the state machine's states and run the foreign-object-id submission in **each state**; the approved-uncaptured window is exactly the state a developer assumes "can't happen yet." Funded-but-uncaptured payment instruments are a reusable capture primitive when the binding check defers to completion.
3. **Amounts, rewards, and credit are server-derived or they are attacker-derived.** Better Payment (amount), Points and Rewards (claimed reward + caller identity) both trust the client number. Sweep every checkout/claim/redeem endpoint with a modified amount/value parameter and diff the recorded ledger against the server-side expected value; the float-cast/numeric-validator gap (Sept 22) is the input-shape sibling — here the validator is *absent*, not weak.
4. **Identifiers become credentials when verification is absent.** Premium Packages' exploitability precondition is "knows the transaction id." Transaction ids, order keys, invoice numbers, and intent ids appear in confirmation pages, emails, REST responses, and are often sequential. Treat every opaque id used at an unverified endpoint as an enumerable credential: harvest your own ids first, measure their structure (sequential? date-prefixed? hash?), and report the structure — sequential ids convert a signature-missing bug from targeted to fleet-scale.
5. **Payment config planes inherit the plugin's weak auth posture.** Paymob's contributor-reachable gateway-config wipe is the third-plus instance (after WP User Manager Stripe connect, Handily, Image Buzz/PixelPlay on Sept 22) that gateway credentials are just options rows. The sweep is canonical: parameter names `[a-z]+_api|api_key|secret_key|client_key|server_key|webhook` × lowest authenticated principal × write/delete verbs.

## Validation workflow (authorized scope only)

!!! warning "Lab stores, gateway sandbox/test accounts, synthetic money"

    Run every leg on a WooCommerce lab install with **gateway sandbox/test-mode accounts you own**. Never probe a production gateway webhook with forged signatures (that is an attack, and gateway providers log it), never use real transaction ids or real buyer instruments, and never submit foreign order/intent ids outside your own lab tenant.

1. **Branch coverage matrix (webhook consumers):** on the lab store, complete one real sandbox transaction; capture the webhook payload shape. For each event-type branch, resend the payload (a) untampered, (b) amount/status tampered without signature, (c) tampered with an invalid signature. Record per-branch accept/reject — a single accepting branch is the finding. Evidence = order/subscription state transitions in your lab DB caused by (b).
2. **Cross-order capture proof:** two lab buyer accounts, sandbox PayPal. Buyer A approves (does not capture) an order. On Buyer B's lab checkout, replay A's PayPal order id in the payment-request parameter. Vulnerable evidence: A's authorization is captured and B's order marked paid while A's cart shows captured. Immediately refund/void in sandbox and record ids.
3. **Amount re-derivation:** add a fixed-price lab product; submit the payment request with the amount parameter rewritten to 1 (or the currency minimum). Evidence = captured sandbox charge amount vs catalog price diff.
4. **Reward-claim sweep:** call the claim/redeem handler directly (bypass the UI) with arbitrary reward values and from a second lab user; ledger diff is the evidence. Test the handler with the UI-gating precondition (wheel spin state) absent — call-time identity checks are what you're proving missing.
5. **Config-plane check:** as a Subscriber/Contributor lab user, attempt the plugin's admin AJAX config actions (delete/update gateway keys) with your own synthetic test keys as the payload. Positive/negative pair: contributor write accepted vs admin-only control.

## Reporting heuristics

- Lead with the money movement, not the missing check: "attacker captures another buyer's authorized funds" (80342) and "unauthenticated forged payment confirmation for any known transaction id" (93511) are the headline sentences; "missing signature verification" is the root cause line.
- State the precondition honestly: signature-missing bugs need a transaction id (report its structure and enumerability); cross-order capture needs the approved-uncaptured window (report the provider state you exploited).
- Report branch coverage explicitly: attach the per-event-type accept/reject table — it both proves the finding and tells the vendor which branches were unverified, which prevents an incomplete-fix repeat (the Directorist/CVE-2023-1889 pattern in this same wave).
- Keep sandbox evidence: order ids, ledger diffs, state-transition logs. Redact gateway account ids and buyer emails even for synthetic buyers.
