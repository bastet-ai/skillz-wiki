# NocoDB wave (27 GHSAs): empty admin password lets the first signup take super admin

**Published:** 2026-11-13 12:31Z, one coordinated NocoDB release (CVE-2026-126267 through CVE-2026-126293), fixed across the 2026.04.4 to 2026.09.1 band depending on leg. GHSA package/version fields are **empty** across the wave, the vendor-advisory band-fingerprinting pattern. None of these CVEs are in KEV as of catalog 2026.11.10 = head-start window for lab validation.

**Wave in one line:** an Airtable-clone audit campaign that reads as one permission-model review: **a scope field the server never stores or checks, a bootstrap that silently skips when its password env var is empty, read handlers that mask the password but not the TLS private key, and legacy compatibility parameters that walk around the modern sanitizer.**

**Audience:** bug hunters working low-code/no-code platforms (NocoDB, Baserow, Teable, APITable share this architecture), pentesters on self-hosted internal tools in Docker, and anyone auditing token-scoping or credential-masking code.

!!! warning "Authorized validation only"
    Run a disposable NocoDB Docker instance with synthetic bases, your own second accounts, and redacted connection canaries. Prove bootstrap races on a fresh volume only, never on a shared instance. Use your own external database as the "data source" so the leaked material is synthetic. Do not enumerate real bases, read production data-source credentials, or trigger bulk-write DoS legs against shared deployments.

## Why this cluster is one audit axis

NocoDB is the archetypal "spreadsheet over Postgres/MySQL with share links, API tokens, and OAuth clients." Twenty-seven boundary bugs published in one sitting means the maintainers (or one researcher) walked the whole authz surface at once. Every leg maps to one of six recurring questions you can ask of any similar platform:

1. When the config says "scoped," does the server persist and verify the scope at request time?
2. When first-run bootstrap can fail silently, who owns the empty instance?
3. Which fields does the read handler actually mask, and which does it return raw?
4. Do legacy compatibility parameters re-enter the query path that the modern filter layer sanitizes?
5. Which feature-flag network exemptions does a second feature inherit?
6. Where does a token get rotated without an atomicity or row-count check?

## The crown legs

- **Empty admin password env var skips super-admin bootstrap; public signup takes the crown** ([GHSA-gfhh-22w3-3gcg / CVE-2026-126273](https://github.com/advisories/GHSA-gfhh-22w3-3gcg), critical, < 2026.09.0): `initAdminFromEnv.ts` silently skips the admin bootstrap when the admin password environment variable is empty (a common Docker-compose shape where `NC_ADMIN_PASSWORD` was never set), and the **public signup endpoint runs first**, so the first unauthenticated visitor to register on a fresh instance receives Creator **and Super Admin** roles. Durable rules: (1) on any self-hosted app, `/api/auth/user/signup` on a fresh container is a race you can win with a curl; fingerprint deployments where bootstrap is conditional on an env var having a value, the failure mode should be loud or fail-closed, not silent-skip; (2) test the {instance-state, signup-state} matrix: fresh volume no env set, fresh volume env set but user deleted, initialized instance, and record which cell grants elevated roles; (3) the same first-register-takes-admin shape has appeared in Payload (97rh first-register RCE, Oct 6 page) and Frappe Cloud (multi-email OTP broadcast, Oct 8 note) = **first-run lifecycle is a standing probe family for self-hosted tools**, not a one-off.
- **Base-scoped API tokens are account-wide credentials because `base_id` is never stored or checked** ([GHSA-fhqx-7jhc-mgh3 / CVE-2026-126283](https://github.com/advisories/GHSA-fhqx-7jhc-mgh3), high, < 2026.08.0): the token-creation UI offers a per-base scope, but the backend never persists the `base_id` and never compares it on request. A leaked "single base" token reads, writes, and deletes on **every base the owner belongs to, including bases joined later** (live scoping, not snapshot). Operator rule: for every scope/purpose/team field in a token/API-key issuance form, mint a minimally-scoped credential and use it against the **out-of-scope sibling**; a scope the server drops at issuance or never re-reads at verification is decoration. This is the same "scope claim vs scope enforcement" gap as Zaqar's WebSocket connect-time scope-binding loss (Sept 18 ignored-scope page) and the traQ empty-scope silent-auth widening (Nov 10 IdP page): always ask whether the scope string survives into storage and the request path, or dies in the UI.
- **Revoked users regain Creator access through the legacy role system** ([GHSA-gmp9-rjm3-p4wx / CVE-2026-126282](https://github.com/advisories/GHSA-gmp9-rjm3-p4wx), high, 2026.04.0-< 2026.08.0): updating a user's **legacy organization role** rewrites their **default-workspace** role (`org-users.service.ts`), so a user whose workspace access was revoked can self-service Creator-level read/write/schema rights across all default-workspace bases with their still-valid session token. Durable rule: every product that grew a second authorization system (org vs workspace, team vs base, legacy vs v2) must be probed for **cross-system role write paths**; enumerate mutation endpoints on the old system and watch whether the new system's grants move. Revocation tests belong on both systems: revoke in the new one, then mutate in the old one.
- **Refresh-token rotation never checks the affected-row count: captured tokens stay alive** ([GHSA-qmfq-9h33-q6xx / CVE-2026-126280](https://github.com/advisories/GHSA-qmfq-9h33-q6xx), critical, < 2026.08.0): `UserRefreshToken.ts` rotates by UPDATE without checking whether the UPDATE matched a row, so an attacker holding a captured refresh token can present it **concurrently** with the legitimate user and receive their own valid session, with no reuse event recorded. The sibling [GHSA-2g7w-6p94-6352 / CVE-2026-126287](https://github.com/advisories/GHSA-2g7w-6p94-6352) (medium, < 2026.06.2) is the same rotation on the OAuth token service, non-atomic read-then-write. Operator rules: (1) the three-property refresh-token test: reuse-after-rotation must fail, concurrent double-spend must yield at most one winner, and reuse must record an event; run all three on every auth service you touch; (2) code-level fingerprint: an `UPDATE`/`save` whose return value is discarded inside a rotation function = this bug class, worth grepping in any knex/ORM codebase you have source for. The Oct 9 SmarterMail stale-role-refresh rule (role claim never revalidated at redemption) is the same lifecycle family from the other end: **treat every token lifecycle transition as a state machine with concurrent-input probes**, not a single happy-path call.

## Credential-masking failures: the read/write echo battery

Four legs share one root: the handler returns the **stored record** where it should return a **filtered projection**.

- **Data-source read masks only the password, leaks the TLS client private key** ([GHSA-jfqq-j3g5-9vjq / CVE-2026-126271](https://github.com/advisories/GHSA-jfqq-j3g5-9vjq), high, < 2026.09.0): a base Viewer reading the base's data source gets the decrypted **client private key, client certificate, and CA**, masked fields were password-only. Direct connection to the external database bypasses every NocoDB permission. Rule: for every credential-bearing GET, diff the returned JSON keys against the stored row (or the create payload); each unmasked non-UI field is a finding. Private-key material in particular gets forgotten by password-only masks.
- **Private integration configs readable by omitting a query flag** ([GHSA-f8p8-8grw-947j / CVE-2026-126290](https://github.com/advisories/GHSA-f8p8-8grw-947j), high, < 2026.07.0): requesting another user's private integration **without** the configuration flag bypasses the ownership check entirely. The inverse of the usual flag-gated leak: here the *safest-looking* request is the unsafe one. Battery: for every detail endpoint with query flags (`?config=`, `?include=`, `?fields=`), run {flag absent, flag=true, flag=false} with an out-of-owner resource id.
- **Profile-update echo returns the raw user record: bcrypt hash, salt, and session token counter** ([GHSA-pm85-5w67-j943 / CVE-2026-126292](https://github.com/advisories/GHSA-pm85-5w67-j943), medium, < 2026.06.1): the update handler returns the stored row without the user-serialization filter. Rule: **write-echo responses need the same masking audit as read endpoints**; PATCH yourself and diff the response against the GET response, divergence is the leak. Pair with the Oct 6 Payload 238x leg (apiKey plaintext in any permitted cross-user read) = standing rule for any app with per-user secrets.
- **Public OAuth client lookup returns registration access token and secret hash** ([GHSA-p7rc-hwxx-h77q / CVE-2026-126288](https://github.com/advisories/GHSA-p7rc-hwxx-h77q), medium, < 2026.06.2): `oauth.controller.ts`'s public client-lookup route answers with the **full client record**, including the registration access token (which can modify/delete registrations) and the bcrypt client-secret hash. The "public" endpoint is the one nobody masks. Enumerate every deliberately-unauthenticated endpoint and diff its payload against the authenticated sibling.
- **copy-from integration branch decrypts other users' connection credentials** ([GHSA-5xwc-xpgh-jhhc / CVE-2026-126281](https://github.com/advisories/GHSA-5xwc-xpgh-jhhc), high, < 2026.08.0): the `copy-from` branch of integration creation decrypts the **source** integration's host/username/password without checking owner or private flag; Creator-role users enumerate integration ids and copy database credentials into an integration they own. Rule: on any resource with a copy/clone/duplicate verb, the **source object authorization is a separate check from the destination authorization**; test every copy branch with a foreign source id.

## Query-grammar and injection legs

- **Email address is SQL text: quoted local-part injects through CTE user resolution** ([GHSA-g94q-3gw8-47w2 / CVE-2026-126291](https://github.com/advisories/GHSA-g94q-3gw8-47w2), high, < 2026.06.2): `base-user.cte.utils.ts` concatenates base members' **email addresses** into the SQL resolving user/created-by/last-modified-by fields. A registered user sets their email to a quoted local part containing a single quote and executes arbitrary SQL at the moment anyone views a row they touched; blast radius includes user records, API tokens, and data-source credentials. Durable rules: (1) **profile fields are injection inputs** - email, display name, org name, and bio reach SQL, filenames, HTML, and shell contexts through *other users'* views; seed quote/control-character shapes into every profile field in two-user labs; (2) this is the second-order pattern: attacker writes at registration, sink fires on a victim's innocent read; single-user harnesses structurally miss it (the Sept 18 query-grammar page's sort-leg and Koha/MyBatis siblings are the same object-query family).
- **Legacy `where` parameter bypasses the modern filter sanitizer** ([GHSA-2phw-hmfj-7vgj / CVE-2026-126285](https://github.com/advisories/GHSA-2phw-hmfj-7vgj), high, < 2026.08.0): Viewer-role users inject single quotes into filter values concatenated by `CustomKnex.ts` through the **legacy `where` parameter**, reading other tables, schemas, view-filtered rows, and hidden columns. Rule: enumerate **deprecated/compatibility query parameters** separately from the current filter API; the sanitizer was written for the new parameter, the old one still concatenates. Grep route schemas for parameters marked legacy, deprecated, or hidden from docs.
- **CSV export formula injection** ([GHSA-h5m9-m957-rxww / CVE-2026-126289](https://github.com/advisories/GHSA-h5m9-m957-rxww), medium, < 2026.06.1): record values and column titles starting with formula characters flow into exports unneutralized; low-privileged collaborators or **unauthenticated public-form submitters** plant formulas that execute when the export is opened in a spreadsheet. Standing rule: any export-to-office feature is an injection sink where the *reader's* application is the interpreter; plant `=HYPERLINK(...)`-style inert canaries through the lowest-privilege write path available.

## XSS and client-side legs (localStorage token theft is the common impact)

NocoDB keeps its session token in localStorage, so every one of these is an account-takeover leg, and the sink choices are the interesting part:

- **Destructive-action confirmation dialog as XSS sink** ([GHSA-q33x-f753-x487 / CVE-2026-126274](https://github.com/advisories/GHSA-q33x-f753-x487), critical, < 2026.08.0): Creator users put markup in **column/table titles**; the Delete.vue confirmation renders them through unescaped innerHTML. Confirmation dialogs that echo resource names are systematically un-audited, they're "just UI", not "user content". Probe every delete/danger dialog with markup-bearing names.
- **AI field prompt tooltips** ([GHSA-9jcw-33w5-6h35 / CVE-2026-126279](https://github.com/advisories/GHSA-9jcw-33w5-6h35), high, < 2026.06.2): field references inside AI prompts render as HTML; executes when a victim opens field configuration. New feature surfaces (AI fields) ship without the sanitizer the mature surfaces have.
- **Attachment MIME parsed as `text/html;image/png`** ([GHSA-mfx6-x56r-2945 / CVE-2026-126269](https://github.com/advisories/GHSA-mfx6-x56r-2945), critical, < 2026.09.0): Editor users store that crafted MIME through the records API and the `/dltemp` signed URL serves HTML **inline**; parser disagreement on the semicolon is the bypass (the server sees the second token or first token where the browser sees `text/html`). Same validation-target-vs-write-target family as the Sept 19 Bricksforge and Oct 3 CodeIgniter4 rules; battery: semicolon-suffixed, parameter-suffixed, and quoted MIME shapes against every download route.
- **ASCII control character in the redirect scheme** ([GHSA-p6j3-gj3p-wv45 / CVE-2026-126286](https://github.com/advisories/GHSA-p6j3-gj3p-wv45), high, < 2026.08.0): an unauthenticated link with a control char inside the `ncRedirectUrl` scheme defeats the scheme check and reaches `href`/`window.location`. Add the C0-prefix battery to every scheme check (the Nov 10 Echo page's control-character redirect grammar, Vue-SPA edition).

## Infrastructure and race legs

- **Express trust proxy on unconditionally: XFF writes your audit trail** ([GHSA-4mr5-573j-wrf5 / CVE-2026-126268](https://github.com/advisories/GHSA-4mr5-573j-wrf5), medium, < 2026.08.0): unauthenticated attackers forge recorded source IPs, poisoning audit/request logs and evading the per-address public API rate limiter (the brute-force unlock of the refresh-token legs above). Standing header battery applies (Sept 15 header-route page): treat the limiter as bypassable until proven, then the TOTP/refresh brute-forces become feasible.
- **Import reuses the webhook network exemption** ([GHSA-9g8j-97vg-657m / CVE-2026-126284](https://github.com/advisories/GHSA-9g8j-97vg-657m), low, 2026.05.2-< 2026.07.0): when `NC_ALLOW_LOCAL_HOOKS`/`NC_WEBHOOK_ALLOW_PRIVATE_NETWORK` is set for webhooks, the **CSV/spreadsheet import** fetches internal URLs and returns response content to Editor-role users. Rule: **SSRF exemptions are per-product-instance features that leak between features**; if you find one operator-set network exemption, re-test every other URL-ingesting route (import, upload-by-URL, preview, webhook) under it. Pair with the Oct 27 Vvveb incomplete-SSRF-fix leg.
- **Bulk-write limit keyed on auth method** ([GHSA-mcg2-w2p8-3x95 / CVE-2026-126272](https://github.com/advisories/GHSA-mcg2-w2p8-3x95), high, < 2026.09.0): row-count limits apply to API-token requests but **session-authenticated** bulk writes are unbounded. Quota/limit checks must be tested across every authentication transport (the transport-parity rule from the Oct 2 UTMStack page, now on the rate/limit dimension).
- **Upload-by-URL trusts the remote advertised Content-Length** ([GHSA-2pc5-c4pw-6xxr / CVE-2026-126293](https://github.com/advisories/GHSA-2pc5-c4pw-6xxr), high, < 2026.06.2): size limits enforced against the server's *claimed* length, not the received bytes. Budget-charged-post-validation family (Rack hfr4 sibling): charge the budget by observation, not by declaration.
- **Reset-token race before token clear** ([GHSA-f9qx-jg46-3q7v / CVE-2026-126278](https://github.com/advisories/GHSA-f9qx-jg46-3q7v), high, < 2026.08.1): concurrent password resets win multiple changes during the slow bcrypt window, letting an attacker with a valid token overwrite the owner's new password and lock them out. Race fingerprint: any "validate token, do expensive work, clear token" sequence; fire N concurrent requests before the clear.
- **Cross-base comment IDOR** ([GHSA-wm95-jp92-x3pj / CVE-2026-126275](https://github.com/advisories/GHSA-wm95-jp92-x3pj), high, < 2026.09.0): row comments authorize on `model` + `row` ids only, so a Viewer on any base reads private comments (with author emails) from every other base, and can plant decoy tables to **spoof teammate comments** under duplicate ids. Rule: sub-objects (comments, attachments, audit rows) frequently skip the parent's authorization wrapper; enumerate `/comments|/attachments|/versions` style routes and vary the parent id with the lowest-privilege account.
- **Unauthenticated instance metadata + query amplification** ([GHSA-prxq-54q2-754w / CVE-2026-126270](https://github.com/advisories/GHSA-prxq-54q2-754w), medium, < 2026.09.1): the aggregated meta route hands anonymous callers base counts, user counts, shared/password-view counts, webhook counts, and **live per-base row counts**. Useful passive recon surface on any NocoDB target before auth; every "dashboard stats" endpoint is an unauthenticated inventory API until proven otherwise.
- **Shared-view bulk endpoints with unbounded filter arrays** ([GHSA-cj5g-7mh3-57gp / CVE-2026-126277](https://github.com/advisories/GHSA-cj5g-7mh3-57gp), high, < 2026.08.1): a shared-view UUID plus a large minimal-filter body = one DB query per entry. Shared/public surfaces get parser-budget audits too.

## Operator playbook (any Airtable-clone target)

1. Fingerprint version from the SPA bundle and check against the 2026.04-2026.09 fix bands; empty GHSA version fields mean diff the vendor release notes for band confirmation.
2. Fresh-instance check first: hit the signup endpoint on any container you're authorized to test; check role claims in the issued token.
3. Mint the minimum-scope token you're offered, then use it out of scope; run the refresh-token three-property test with a second browser profile as the "legitimate user".
4. Two-user lab: seed quote/control-char/markup shapes into email, display name, column titles, table names, AI prompts, and attachment MIMEs from user A; read everything as user B; diff read vs stored vs write-echo payloads for unmasked credential fields.
5. Enumerate legacy query parameters (`where`, `offset`, `sort`), copy/clone branches, and flag-gated detail routes with foreign ids.
6. Under any operator network exemption, re-run the SSRF battery on every URL-ingest route.
7. Validation boundary: your own external Postgres as the data source, synthetic tokens, your own second accounts, marker-only proofs; never touch a real estate's data-source credentials.
