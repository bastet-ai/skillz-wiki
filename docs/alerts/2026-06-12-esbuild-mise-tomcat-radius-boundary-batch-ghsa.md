This batch is durable because each item exposes a reusable operator boundary: build tooling that converts registry environment variables into executable native binaries, developer servers that normalize paths differently from their host OS, repository-local tool config that can approve its own trust state, TLS SNI/HTTP `Host` split-brain authentication, HTTP-version/method parsing that crosses servlet security constraints, Kubernetes controller confused-deputy deletes across tenants, and TYPO3 backend permissions crossing into SQL-capable form definitions or unauthorized record/file operations.

## What changed

- **esbuild Deno binary integrity boundary** — the Deno module fetched native binaries from `NPM_CONFIG_REGISTRY` and wrote executable files without the SHA-256 integrity checks used by the Node installer path. This is a CI, shared dev-host, and private-registry trust boundary, not a generic browser issue.
- **esbuild Windows dev-server file boundary** — the development server used POSIX-style `path.Clean()` on request paths while Windows treats backslashes as path separators, enabling traversal out of `servedir` on affected Windows hosts.
- **mise project-local trust boundary** — local `.mise.toml` settings could be loaded before trust checks, allowing repository-controlled settings such as `trusted_config_paths = ["/"]` to make that same untrusted project config appear trusted and reach hooks, tasks, templates, or `[env] _.source`. A June 22 follow-up adds a separate `.tool-versions` parser boundary where Tera template rendering, including `exec()`, ran without a trust prompt in non-paranoid mode.
- **Tomcat connector mTLS virtual-host boundary** — when client certificate authentication was enforced only at the connector, Tomcat virtual hosts with different TLS requirements could be confused by sending one host in TLS SNI and another in the HTTP `Host` header.
- **Tomcat HTTP/0.9 security-constraint boundary** — Tomcat accepted non-`GET` HTTP/0.9 request lines. In applications where a servlet security constraint allowed `HEAD` but denied `GET` for the same URI, a specification-invalid HTTP/0.9-style `HEAD /path` request could reach the `GET`-protected resource boundary.
- **Tomcat RewriteValve session identifier boundary** — RewriteValve redirects and cross-context rewrites did not consistently run through the same session URL-encoding and session-info recycling path that normal redirects use. In cookie-less or URL-rewritten session deployments, this can let an attacker-controlled session identifier survive a rewrite/redirect boundary instead of being regenerated or bound to the expected context.
- **Radius controller confused-deputy boundary** — in multi-tenant installs, a tampered `radapp.io/status` Deployment annotation could cause the controller to delete a container resource referenced under another tenant/resource group using controller privileges.
- **TYPO3 form, file-mount, and record-control follow-up wave** — late TYPO3 advisories add Form Framework extension/case bypasses that can reach SQL-capable form definitions, direct `DataHandler` writes to `form_definition`, unauthorized record moves/restores, destructive operations on file-mount roots, and a core utility open-redirect boundary.

## Operator triage

1. **Lead with preconditions.** esbuild requires Deno module execution plus registry/environment influence; the file-read variant is Windows dev-server only; mise requires a repo or working tree the tester can place files in and a shell/editor/CI path that invokes mise hooks or parsing; Tomcat mTLS testing requires connector-level client cert auth and multiple virtual hosts with different requirements; Tomcat HTTP/0.9 testing requires a security constraint that allows `HEAD` but denies `GET` on the same URI; Tomcat session-fixation testing requires RewriteValve plus URL-based session tracking, cookie-less clients, or an application flow where `jsessionid` URL rewriting is intentionally supported; Radius is strongest in multi-tenant controller topologies; TYPO3 requires backend roles, file-write, module, or table-write access.
2. **Separate proof of boundary from destructive impact.** A downloaded inert binary canary, file-read marker, hook marker, mTLS route differential, HTTP/0.9 method/constraint decision table, synthetic URL-session marker, synthetic Radius container ID, or disposable TYPO3 form definition is enough. Do not execute production payloads, read secrets, hijack live user sessions, delete real tenant resources, or create real admin accounts.
3. **Favor environment and parser-differential evidence.** Capture the exact environment variable, path separator, trust setting, SNI/Host pair, raw request line, RewriteValve rule/redirect pair, Kubernetes annotation field, or TYPO3 module/table/extension check that made the boundary fail.

## Replayable validation boundaries

### esbuild registry-to-executable validation

- Scope only CI runners, build images, or developer hosts where running the esbuild Deno module is authorized.
- Set `NPM_CONFIG_REGISTRY` to a tester-controlled local registry or HTTP callback that serves an inert tarball matching the expected package path and platform name.
- Positive proof is that the Deno installer downloads from the canary registry and writes/attempts to execute a tester-owned marker binary without an integrity mismatch.
- Keep the binary inert: print a marker, write a disposable file under a temp directory, or exit with a unique code. Do not run shell download cradles or credential access commands.
- Evidence: esbuild version, Deno invocation, redacted environment, requested registry URL, marker result, and patched `v0.28.1+` negative control.

### esbuild Windows `servedir` traversal validation

- Validate only against a local or lab Windows dev-server instance; do not expose production dev servers to the internet for testing.
- Create a harmless marker file outside `servedir`, then request a URL path containing Windows backslash traversal segments toward that marker.
- Positive proof is retrieval of the marker file and a negative control showing normal forward-slash normalization stays confined.
- Evidence should include OS, esbuild version, `servedir`, sanitized request path, marker file contents, and patched negative behavior.

### mise repository-config trust validation

- Use a disposable repository and a canary `.mise.toml`; avoid testing against developer home directories or repositories with real hooks/secrets.
- Place a local config that sets a trust-expanding setting such as `trusted_config_paths` and an inert `[env] _.source`, hook, task, or template marker.
- Trigger only a safe command path such as `mise hook-env` in a sandboxed shell and confirm whether the marker executes before explicit user trust is granted.
- Evidence: mise version, repository path, `.mise.toml` trust stanza, command used, canary marker, and patched-version behavior.

### mise `.tool-versions` Tera execution validation

- Validate only in a disposable repository and sandbox shell. Do not run this in a real developer checkout, home directory, or environment carrying live cloud, package-registry, SSH-agent, or API credentials.
- Create a `.tool-versions` file with the smallest inert Tera marker that proves template evaluation. Prefer a temp-file marker over network callbacks:

  ```text
  node 20 {{ exec(command="printf skillz-mise-canary > /tmp/skillz-mise-canary") }}
  ```

- Trigger a safe mise parse path such as `mise hook-env` or the same shell activation path the target workflow uses. Avoid package installs, build scripts, or commands that execute project code for unrelated reasons.
- Positive proof is the marker appearing before any explicit trust approval for the repository and without a `.mise.toml` trust prompt. Pair it with a patched-version negative control where possible.
- Evidence: mise version, shell integration path, `.tool-versions` contents, command used, marker file metadata, and confirmation that the repo was untrusted/non-paranoid. Redact environment output; do not demonstrate token access even if the advisory notes inherited environment exposure.

### Tomcat SNI/Host mTLS bypass validation

- Confirm a lab or customer-approved Tomcat deployment has at least two virtual hosts on the same connector: one requiring client certificates and one not, with client certificate auth enforced at the connector rather than inside the web application.
- Send one TLS SNI value for the non-client-cert host and an HTTP `Host` header for the client-cert-protected host. Use an owned route that returns a marker page, not a sensitive application endpoint.
- Positive proof is access to the protected virtual host without presenting a client certificate, paired with controls where matching SNI/Host values behave as expected.
- Evidence: Tomcat version, connector/vhost layout, SNI, `Host`, client-cert presence/absence, marker route status, and patched version negative behavior.

### Tomcat HTTP/0.9 method constraint validation

- Validate only on a lab or explicitly authorized Tomcat application where you can create or identify a harmless URI with split method constraints: `GET` denied and `HEAD` allowed. Do not use real admin, export, backup, or user-data routes as proof targets.
- First prove the intended controls with normal HTTP/1.1 requests: `GET /canary HTTP/1.1` should be rejected and `HEAD /canary HTTP/1.1` should follow the configured `HEAD` policy.
- Send a raw HTTP/0.9-style request line for the same marker URI using `HEAD /canary` with no HTTP version token. Positive proof is a response/body/status behavior that reaches the resource path despite the `GET` denial, paired with a patched Tomcat negative control.
- Capture raw bytes and parser outcomes rather than sensitive content. A synthetic route that returns a marker header/body is enough.
- Evidence: Tomcat version, connector, security-constraint snippet, URI, raw HTTP/1.1 and HTTP/0.9 request lines, response decision table, and fixed-version behavior for 9.0.113+, 10.1.50+, or 11.0.15+.

### Tomcat RewriteValve session-fixation validation

- Validate only on a lab or explicitly approved Tomcat application where you control the test account, can enable URL-based session tracking, and can place a harmless RewriteValve rule that redirects or internally rewrites between synthetic routes. Do not test against real login, admin, payment, or customer-account flows.
- Create two canary routes: one route that establishes a test session and one route behind the rewrite or redirect boundary that reports only a synthetic session marker such as `skillz-session-canary`, never usernames, cookies, roles, or application data.
- With cookies disabled, send a URL containing a tester-chosen `;jsessionid=<canary>` or follow the application-generated URL rewriting path through the RewriteValve rule. Positive proof is that the pre-fix RewriteValve path preserves or accepts the session identifier across the redirect/rewrite where the patched path either re-encodes the redirect with the expected session id, recycles cross-context session state, or rejects the attacker-supplied session boundary.
- Pair every positive result with controls: normal non-RewriteValve redirects, cookie-enabled requests, a fresh session after authentication, and a patched 9.0.106+, 10.1.42+, or 11.0.8+ build when available.
- Evidence: Tomcat version, session tracking mode, RewriteValve rule, sanitized request URL, `Location` header or internal-rewrite target, canary session-id decision table, and fixed-version behavior. Do not publish reusable victim-session fixation links.

### Radius controller annotation confused-deputy validation

- Validate only in a lab or explicitly approved multi-tenant Radius/Kubernetes environment with disposable tenants, resource groups, Deployments, and container resources.
- Create two synthetic tenants/resources and tamper only the attacker-controlled Deployment's `radapp.io/status` annotation to reference a victim canary container resource.
- Trigger the reconcile/delete flow and verify whether the controller attempts to delete the referenced canary resource.
- Stop at canary deletion/attempt evidence. Do not target production containers, shared namespaces, service accounts, or non-test resource groups.
- Evidence: Radius version, controller scope/RBAC, tenant/resource IDs, sanitized annotation JSON, controller log/API delete attempt, and recovery/cleanup.

### TYPO3 late-wave validation

- For Form Framework extension and `DataHandler` issues, use a disposable backend user and a synthetic form definition that executes only a harmless SQL canary such as creating or updating a marker row in a lab table. Do not create administrative users on production systems.
- For file-mount root operations, prove attempted rename/move/delete only against a disposable mount root in a lab; prefer observing authorization acceptance/rejection rather than performing destructive operations.
- For Recycler and record-move checks, use synthetic pages/tables and marker records where source/target permissions are intentionally split.
- For `sanitizeLocalUrl`, demonstrate only a redirect to a tester-owned URL and never use phishing pages or user-targeted links.
- Evidence should include TYPO3 version, backend role, module/table/file permission, canary object, route/API used, and patched-version negative behavior.

## Reporting heuristics

- Name the crossed trust boundary in the title: `NPM_CONFIG_REGISTRY to native binary execution`, `Windows dev-server backslash traversal`, `repo config self-trust`, `.tool-versions Tera template to shell execution`, `SNI/Host mTLS mismatch`, `HTTP/0.9 HEAD to GET-denied route`, `RewriteValve redirect to URL-session fixation`, `Deployment annotation to cross-tenant delete`, or `backend form/file permission to SQL/admin-capable action`.
- Keep impact scoped to the proven precondition. These are strong findings when the report preserves topology and role requirements instead of claiming blanket RCE, auth bypass, or tenant takeover.
- Redact environment values, client cert material, Kubernetes tokens, registry credentials, and application secrets. Canary evidence should be enough.

## June 23 mise HTTP-backend symlink update

GitHub Advisory Database added [GHSA-f94h-j2qg-fxw3](https://github.com/advisories/GHSA-f94h-j2qg-fxw3) / CVE-2026-54557 for a separate mise package-install boundary: the HTTP backend used the raw requested version path when creating the install symlink destination. That makes repository, task, or operator-supplied version strings filesystem material rather than inert package selectors.

Operator value: treat package-manager version fields as write-path inputs. This is adjacent to the existing mise repo-trust and `.tool-versions` guidance because the useful proof is not generic command execution; it is whether an untrusted project can steer mise's install/cache layout outside the expected tool directory.

Safe validation boundaries:

## September 17 flatpak-builder Git-hook build-host update

GitHub Advisory Database added [GHSA-rvpr-5p35-6vf8](https://github.com/advisories/GHSA-rvpr-5p35-6vf8) / [CVE-2026-86320](https://nvd.nist.gov/vuln/detail/CVE-2026-86320): when flatpak-builder applies patch sources with `use-git-am: true`, it runs Git without disabling hooks, so a malicious source containing a Git `post-applypatch` hook executes on the **host** as the user running flatpak-builder during the build.

Operator value: this is the repository-trust family again, reached through a build wrapper rather than a dotfile parser. The generalizable audit rule: **any tool that shells out to Git over attacker-supplied content** — `git am`, `git apply`, `git checkout`, `git merge`, archive-to-repo materializers, CI checkout actions, package patchers — executes repository-internal `.git/hooks/*` unless the caller passes `-c core.hooksPath=/dev/null`, `--no-verify`, or an equivalent. Repository content that is nominally "data" (a patch source in a manifest) becomes host code execution because the hook lives *inside* the delivered object, not in a config file the tool parses.

Safe validation boundaries:

1. Disposable checkout only: a tester-controlled source repo or module directory containing a `post-applypatch` (and `pre-applypatch`/`post-checkout` variants) hook that writes a marker under a temp directory. Run flatpak-builder with `use-git-am: true` against a minimal manifest in a throwaway build directory.
2. Evidence is hook invocation and marker creation outside the sandbox; do not run network or persistence payloads.
3. Negative controls: fixed flatpak-builder refusing to trigger the marker, plus confirming hooks do not fire when `core.hooksPath` is redirected — this distinguishes "hooks disabled by the wrapper" from "hook never reached".
4. Sweep adjacent tooling with the same harness mindset (authorized CI runners, devcontainers): grep the tool source for `git am`/`git checkout` invocations lacking hook suppression flags before probing.

Reporting heuristic: title as **flatpak-builder `use-git-am` patch source `post-applypatch` hook to host execution**; include flatpak-builder version, manifest fragment, hook name, marker path, and patched behavior. Related waves with the same shape: mise `.mise.toml`/`credential_command` self-trust above, and repository-controlled `.pdm-plugins` pre-parse execution.

## September 17 follow-up: Snowflake CLI repo-config values interpolated into multi-statement SQL

GitHub Advisory Database added [GHSA-p2xq-qfx5-xp6q](https://github.com/advisories/GHSA-p2xq-qfx5-xp6q) / [CVE-2026-92903](https://nvd.nist.gov/vuln/detail/CVE-2026-92903) (high): in Snowflake CLI prior to **3.27.0**, unsanitized user-controlled values are interpolated into SQL strings that execute as **multi-statement queries**. An attacker with write or pull-request access to a project repository whose CI/CD pipeline runs Snowflake CLI under an **elevated service-account role** — or who can supply input to CLI-wrapping automation — gets attacker-controlled SQL executed in the victim's Snowflake session and active role. Impact is bounded only by the configured role's privileges; the fix landed in 3.27.0 and **requires a manual user upgrade**, so pinned CI images lag the advisory.

Operator value: this is the repository-trust family crossing from *shell* into *query structure*. The generalizable audit rule: **for every CLI that reads project-local configuration (`.snowflake/` config, connection/project files, CLI args from repo scripts), check whether config-derived values are bound as parameters or concatenated into SQL, and whether the executor enables multi-statement mode** — multi-statement execution turns one injected fragment from a subverted statement into arbitrary follow-on statements (GRANT, data exfil, object drop) under the CI role. On bug-bounty/authorized-CI engagements: a PR you can author is the write-access precondition the advisory itself names; treat any repo that runs a DB CLI in CI as a SQL-structure injection surface and diff "value bound" vs "value interpolated" in the generated query log before executing anything.

Safe validation boundaries:

1. Disposable project repo + throwaway Snowflake account or a mocked/recorded request sink: plant a config value containing a statement separator and a second inert marker statement; trigger the CLI path in a temp directory. Evidence is the generated/recorded query text containing both statements, not execution against real data.
2. CI-context proof uses a dedicated low-impact test role; record role name and whether the injected follow-on statement was accepted (multi-statement mode on/off is the decision to capture).
3. Negative controls: fixed CLI 3.27.0 rejecting or parameterizing the same value, and confirming the vulnerable path is the repo-supplied config (not your own command line) by removing the file and re-running.

Reporting heuristic: title as **Snowflake CLI repo-controlled config value to multi-statement SQL under CI role**; include CLI version, config key, generated query fragment (redacted), execution role, and patched parameterization behavior. Same shape as the mise `credential_command` and flatpak-builder hook items above — repository content executing in whoever's context runs the tool.

## September 17 follow-up: Redocly CLI `split` traversal and cyclonedx-npm Windows `--workspace` shell injection (2 GHSAs)

[GHSA-657c-g7qc-r9j2](https://github.com/advisories/GHSA-657c-g7qc-r9j2) / [CVE-2026-63225](https://nvd.nist.gov/vuln/detail/CVE-2026-63225) (fixed `@redocly/cli` 2.33.2): an OpenAPI/AsyncAPI description can make `redocly split` write files outside the chosen output directory — component names and `x-codeSamples` `lang` values become path segments. [GHSA-q69g-4hcv-6jg4](https://github.com/advisories/GHSA-q69g-4hcv-6jg4) / [CVE-2026-71538](https://nvd.nist.gov/vuln/detail/CVE-2026-71538) (fixed `@cyclonedx/cyclonedx-npm` 6.0.0): on the Windows fallback execution path, the `--workspace` value is interpolated into a shell command without neutralization — `>`, `&`, `|` metacharacters execute with the invoking user's privileges whenever automation or a repo script passes an attacker-influenced workspace name.

Operator value: both are the developer-control family reached through **tooling that consumes untrusted spec/repo metadata on a workstation or CI runner** — the analyst who runs `redocly split` on a supplied API description is the victim, exactly like the flatpak-builder hook and mise task items above. Validation stays inert: a disposable spec with a `../marker` component name writing into a temp tree, and a workspace value containing a marker-writing command against a throwaway directory only; never write outside the disposable root or run persistence payloads.

## September 20 follow-up: Mistral Vibe executes repository `post-checkout` hooks before trust validation

[GHSA-92v2-hh9v-6vj5](https://github.com/advisories/GHSA-92v2-hh9v-6vj5) / [CVE-2026-93993](https://nvd.nist.gov/vuln/detail/CVE-2026-93993) (8.8, Mistral Vibe before 2.25.5): the **worktree creation** process runs Git hooks before the trust validation step. A supplied repository containing a crafted `post-checkout` hook executes arbitrary shell with the privileges of the user running Vibe — the "open an untrusted repo in an AI coding tool" attack becomes host code execution without any trust prompt being answered.

Operator value: this closes another leg of the flatpak-builder audit rule above — **"any tool that shells out to Git over attacker-supplied content executes repository-internal `.git/hooks/*`"** now includes `git worktree add`. Worktree creation fires `post-checkout`, and tools that clone-then-worktree (AI coding assistants, IDE workspace managers, CI checkout helpers, review bots) often invoke Git *before* their own repo-trust gate, so the trust UI is bypassed by ordering, not by a flaw in the gate itself. Audit rule for developer-workstation and agent-runner assessments: enumerate every Git subcommand the tool invokes during repository *acquisition* (clone, checkout, worktree add, submodule update, stash apply), and check whether each passes `-c core.hooksPath=/dev/null` / `--no-verify` **and** whether it runs before or after the trust decision. Validation: disposable repo with a `post-checkout` hook writing a marker under a temp directory, opened against a throwaway Vibe install; evidence is marker creation timestamped before any trust prompt interaction. Related: the agent repository-trust pages — MCP/agent tools that materialize PR-controlled repos hit the same ordering bug.

## October 1 follow-up: virtualenv activation scripts execute metacharacters from paths and prompts

[GHSA-x78j-v8h9-3j2q](https://github.com/advisories/GHSA-x78j-v8h9-3j2q) / [CVE-2026-102937](https://nvd.nist.gov/vuln/detail/CVE-2026-102937) (fixed virtualenv 21.7.12): `BatchActivator.quote()` returned its input unchanged — the only activator with no escaping — so `--prompt`, `VIRTUALENV_PROMPT`, or a config-file prompt is written raw into `@set "VAR=value"` in `activate.bat`. A prompt containing `"` closes the string early and the remainder runs as live cmd.exe syntax (`virtualenv --prompt 'x" & calc & "' venv` fires on activation). Anyone templating a prompt from untrusted input — a CI job using a branch name, a wrapper deriving the env name from user input — hands code execution to whoever activates the venv on Windows.

[GHSA-p58f-9548-mpm2](https://github.com/advisories/GHSA-p58f-9548-mpm2) / [CVE-2026-102925](https://nvd.nist.gov/vuln/detail/CVE-2026-102925) (fixed virtualenv 21.7.13): same defect class in the POSIX activators. Gate and sink speak **different path dialects**; the same advisory family as the Vite `safeModulePaths` URL-vs-fs leg and the virtualenv fish-quote grammar legs. Battery: on any allowlist-gated file read on Windows targets, probe `\`, `..\\`, `C:` drive-prefix, and UNC shapes even after a `/../`-rejecting fix is confirmed.
- Recon tie-in (standing dev-server rule): enumerate exposed Vitest/Vite ports like any service; the WS message surface is readable and *writable* pre-auth — `ws://host:port/__vitest_api__`-shaped endpoints answering without a token is the fingerprint of this family. Lab proof only: marker `.env` files, mock module that writes a temp marker, never real project secrets.

## October 23 follow-up: virtualenv fourth wave — consumer-codec defeats quote escaping, wheelhouse caches verify a different file than they store, and a CLI-disabled unsafe mode re-armed by env/config ([GHSA-394h-qwmc-48pf](https://github.com/advisories/GHSA-394h-qwmc-48pf), [494p-63j8-28p3](https://github.com/advisories/GHSA-494p-63j8-28p3), [cx28-75q4-x26q](https://github.com/advisories/GHSA-cx28-75q4-x26q), [4f8h-vr72-p32c](https://github.com/advisories/GHSA-4f8h-vr72-p32c), [fc2g-4w5p-6whm](https://github.com/advisories/GHSA-fc2g-4w5p-6whm); CVE-2026-113718/-113714/-113717/-113713/-113720)

Four waves deep (Oct 1 → Oct 21 ×2 → Oct 23) and the Anthropic OSS Scanner `ANT-2026-*` batch against virtualenv keeps finding a *new layer* each time: this one covers the consumer-side decoder, the wheel-cache pipeline, the seeder selection path, the app-data seeder's config channels, and copied-file permission provenance. All fixed 21.14.9/21.14.10.

- **Escaping must survive the *reader's* codec, not just the writer's — GBK/Big5 byte-pairing eats the backslash that protects the quote** ([GHSA-394h-qwmc-48pf / CVE-2026-113718](https://github.com/advisories/GHSA-394h-qwmc-48pf), high, <21.14.9). `activate.xsh` is written UTF-8; `quote()` used `repr()`, which keeps printable non-ASCII raw and backslash-escapes embedded quotes. Xonsh `source`s the file under `$XONSH_ENCODING`: with GBK/Big5, the UTF-8 bytes of e.g. `中` end in `0xad`, which pairs with the following `0x5c` backslash into one decoded character — the escape disappears, the quote closes early, and a `--prompt`/destination value becomes executable statements at activation. UTF-8 decoding leaves the same value inert. Rules: (1) **for every generated artifact, enumerate the decoders on the consume side and test payloads through each legacy multibyte codec (GBK, Big5, Shift-JIS, CP1252)** — lead-in/trail byte pairing silently deletes escape bytes; this is the codec-direction sibling of the Oct 21 dialect-grammar leg (same value, different grammar per dialect — now also different byte-alignment per codec); (2) fingerprint `repr()`/`shlex.quote()`-style writers feeding any script source whose read-side encoding is user-configurable; the fix (`ascii()`, PR #3432) shows the maintainers' own conclusion — output must be codec-invariant ASCII.
- **Verify-target ≠ store-target in the wheel cache: hash a path selected from pip's *textual stdout*, and rejected wheels stay in the reusable cache** ([GHSA-494p-63j8-28p3 / CVE-2026-113714](https://github.com/advisories/GHSA-494p-63j8-28p3), low but chainable, <21.14.9). `download_wheel()` downloads straight into the reusable `wheel/house`, then picks the file to digest-verify from the first `Saved ` line in pip stdout — a hostile index can forge that line via a discarded link's `data-requires-python` attribute to make verification hash a *genuine* bundled wheel while the poisoned one is cached; separately, a digest mismatch raises *after* the file already entered the cache, and later selection never re-hashes. Rules: (1) **verification that hashes a file identified by parsing human-readable tool output instead of the file actually written is theater** — same "validated path ≠ consumed path" axis as the Sept 19 upload pages and the Oct 8 temporaryFileUploads leg; (2) **failure must evict — a rejected artifact left in a reuse cache is a persisted payload**; (3) index-injected text (`data-requires-python`) is a parser channel into tool control flow. Needs a hostile `pip.conf` index — bug-bounty-relevant for enterprise mirror fleets, not default PyPI.
- **Digest verification is per-seeder-path: `--seeder pip --download` skips it entirely** ([GHSA-cx28-75q4-x26q / CVE-2026-113717](https://github.com/advisories/GHSA-cx28-75q4-x26q), low, <21.14.9). `PipInvoke` calls `get_wheel(download=False)` then lets pip consult the index, so the PyPI-digest comparison added in 21.7.12 for the default seeder never runs on this route — same option, same threat model, one leg unguarded. Rule: **when a security check is added to a pipeline, enumerate every alternate route to the same sink (seeder/backends/providers) and test the check on each** — sibling-gate drift again, and the advisory's own control/attack table is the template.
- **A mode the CLI disables is re-armed by env var or config file — and the leftover symlink path is claimable by another account** ([GHSA-4f8h-vr72-p32c / CVE-2026-113713](https://github.com/advisories/GHSA-4f8h-vr72-p32c), medium, 21.14.8–21.14.9). `--symlink-app-data` is deliberately disabled for temporary app-data, but `VIRTUALENV_SYMLINK_APP_DATA`/`virtualenv.ini` still reach the parser default and the seeder constructor accepts it without rechecking cache lifetime; cleanup deletes the temp cache, leaving the environment's `site-packages/pip` link dangling at a predictable shared-temp pathname another account can acquire before next use. Rules: (1) **safety decisions enforced only in the CLI action layer are bypassed by every other config channel (env, ini, wrapper scripts)** — the env/config fallback family from the Sept 21 precedence page, now in build tooling; (2) **dangling symlinks with attacker-claimable targets in shared temp = the symlink-slot squatting primitive**, pair with the lz4-java/Metalama lineage.
- **Cache history leaks into fresh environments: `shutil.copy` applies the cached file's mode, overriding the creator's umask** ([GHSA-fc2g-4w5p-6whm / CVE-2026-113720](https://github.com/advisories/GHSA-fc2g-4w5p-6whm), medium, <21.14.9). A cache first built under one umask yields world-writable pip files in later environments; the scanner's repro had a second uid append a line to `pip/__init__.py` that then ran as the environment owner = local privilege lateral via shared cache. Rule: **copied artifacts inherit permission history, not current intent — audit any seeder/copy pipeline where mode bits come from the source file (`copy`, `copy2`) instead of a fixed policy**; on shared build hosts, check `find <env>/site-packages -perm -o+w` as a foothold sweep.

Lineage note: virtualenv generation tally now four waves / thirteen-plus GHSAs in three weeks — a model example of the same-product re-sweep payoff when one scanner keeps drilling one package. Validation stays lab-bounded: disposable indexes in local `pip.conf`, temp-dir marker files, codec-harness `ast.literal_eval` checks; never poison a shared index or cache.

## October 27 follow-up: Mistral Vibe `git worktree add` runs repo-defined filter drivers before the trusted-folder check — the execution vector that survives hook-blocking ([GHSA-xwx6-2mm7-g8wj](https://github.com/advisories/GHSA-xwx6-2mm7-g8wj) / CVE-2026-116843, high, before 3.0.3)

Mistral's agentic CLI (Vibe) is RCE'd by an untrusted repository through a vector the repo-trust battery on this page hasn't had a row for: **git filter drivers**. A hostile repo defines a `filter.<name>.process`/`smudge`/`clean` command in its `.git/config` and marks files with the corresponding `.gitattributes` filter; when the tool runs `git worktree add` (started with `--worktree`), git applies `.gitattributes` and executes the filter command **during checkout — before the tool's trusted-folder check runs**. The agent CLI's own working-tree management is the trigger; no prompt injection, no model interaction, no user approval yet.

Operator rules:

- **Trust gates that run after a git operation are theater — enumerate the operation's mid-flight side effects.** This page's genealogy is now five tools deep (mise, Black action, virtualenv writers, aider, Mistral Vibe) and the failure mode never changed: the config/checkout step executes before the trust prompt. For any tool that clones, checks out, or worktrees attacker-repo material, the test is "what executes *during* the git invocation," not "what does the trust dialog gate?"
- **`.git/config` filter drivers are the hook-blocker's blind spot.** Security reviews of git-wrapper tooling focus on hooks and `core.sshCommand`/`core.pager`; `filter.*.process` is equally executable, is triggered automatically by `.gitattributes` at checkout/worktree-add/merge time, and is rarely on denylists. Add to the battery: hostile repo with `[filter "x"] process = <marker command>` + `* filter=x` in `.gitattributes`, exercised through clone, `worktree add`, checkout, and merge in a disposable directory.
- **AI-agent CLIs are repo-trust consumers at machine speed.** Any agent harness that materializes untrusted repositories (repro pipelines, code-review bots, "clone this repo and fix it" agents) inherits every leg on this page; fingerprint which git subcommands the harness shells out to, and drive the filter-marker repo through each one. Proof shape: marker file only, disposable repos, never against third-party checkouts or shared CI.
