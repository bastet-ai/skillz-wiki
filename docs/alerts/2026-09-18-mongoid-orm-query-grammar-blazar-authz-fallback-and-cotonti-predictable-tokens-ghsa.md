# ORM query-grammar injection and authorization-target fallback: the Mongoid cluster, OpenStack Blazar parameter-name drift, Cotonti clock-derived tokens, and Azkaban sibling-action authz gaps

Source: hourly offensive-security scan of GitHub Security Advisories, 2026-09-18/19 (waves published 2026-09-18T18:31Z, 21:32Z, and 2026-09-19T00:32Z).

Two durable themes tie the promoted records:

1. **The ORM/ODM layer parses your input as query grammar, not as data.** A Ruby Mongo ODM shipped query paths that reflect caller-supplied field names into internal method invocation, pass string criteria to server-side JavaScript, and accept operators from untrusted filter bodies — all reachable unauthenticated wherever an app forwards request data into a query builder.
2. **Authorization code that builds its check target from a parameter name the router never delivers silently falls back to the caller's own scope.** A lease API "authorized" every cross-tenant mutation because the policy wrapper looked the object up under a keyword that was always absent.

## Why this is worth an operator page

- **Field-name positions are injection sites, not just value positions.** The 9.8 Mongoid item reflects a caller-supplied *field name* into internal method resolution. Everyone tests `{"field": {"$ne": 1}}`; far fewer test `{"<method_name>": ...}` when the library itself walks the key through reflection. For any ORM/ODM/serializer in scope, send key payloads shaped like internal API surface (`__class__`, `class`, `send`, `destroy`, `delete`, `each`, ruby-ish method names in the target language's idiom) and diff errors/outcomes against a plain-attribute key.
- **Test the query-grammar sink at the library, not just the endpoint.** String criteria reaching `$where`-style evaluation means an app that *feels* safe (`Model.where(currentUser_filter)`) is exploitable if one parameter is attacker-influenced. On open-source Ruby/Mongo stacks, grep for `.where(`, `any_of`, `all_of`, `match`, `find_by` calls whose argument crosses from request handling; the May 11 [Mongoose `sanitizeFilter` page](2026-05-11-mongoose-sanitizefilter-nosql-boundary-ghsa-wpg9-53fq-2r8h.md) is the JS twin — this cluster shows the same class surviving inside the ODM itself, so the endpoint-level "we use a framework helper" excuse is not a negative control.
- **Authorization wrappers that resolve their target by a name the router doesn't deliver fail *open to the caller's own identity*.** Blazar's `authorize()` looked for `lease_id` in a context that only ever carried `id`; the `None` result didn't deny — it rebuilt the target from the requester. Operator test that costs one request: as user B, PUT/DELETE an object whose ID you learned via a list endpoint, using the exact route shape. A 2xx means the authz target never contained the object owner. In open-source targets, grep policy-enforcer code for `target_factory`/`authorize` helpers that fetch-by-keyword and check the keyword spelling against the route decorator.
- **Pair the read bug with the write bug before reporting.** Blazar's unscoped `GET /v2/leases` is medium-value alone; chained into the ID-keyed mutation bypass it is full cross-tenant control. When your sweep finds an unscoped list, immediately replay its IDs against the object's update and delete verbs — and report them as one chain.
- **Clock-derived tokens are scriptable ATO, not theory.** `md5(microtime())` is ~1M candidates/second — cheap to precompute when the server leaks its clock via the `Date` header. This is the same family already on the wiki (AVideo `uniqid()` pairing codes, Easy Appointments salt+timestamp mail links, Fluent Forms entropy): **for any recovery/verification/2FA token, ask what entropy source mints it; anything time-derived gets a window-probability script.** Evidence shape: candidate-generator source + hit-rate table + one successful reset on your own lab account.
- **`unserialize()` without `allowed_classes` is a class-instantiation oracle for authenticated low-privilege users.** Sweep every user-influenced value that gets base64-decoded then deserialized (cookies, `cb`-style opaque params, export/restore formats). Even without a published gadget chain, arbitrary instantiation on a target with common frameworks installed is a reportable boundary — and the *absence* of the second argument is a two-line grep in open-source PHP.
- **Enumerate actions inside a handler, not just handlers.** Azkaban's `fetchSchedule` skipped the check every sibling action in the same servlet performed — the fix for one action's CVE historically touches only that action. For `?action=` / servlet-dispatch apps, build the full action list from source or error fuzzing and run the authorization matrix per action, per project.
- **Silent encryption-schema failure is a data-at-rest finding with no alert.** CSFLE skipping embedded-model fields means "encrypted" columns sit in cleartext forever. If you get any read access to a Mongo deployment advertised as using CSFLE, spot-check whether documented-encrypted fields are actually ciphertext — especially inside subdocuments/arrays. Same audit rule applies to any "policy generated from annotations" system (RBAC manifests, CSP headers built from decorators): **verify the generator's coverage, don't trust the declaration.**

## Validation workflow (authorized scope only)

!!! warning "Disposable models and owned accounts only"
    Run ORM probes against a lab Mongo instance with synthetic documents and a disposable app; never probe production query paths — operator-injected `$where` and reflection sinks can mutate or destroy data (the 9.8 item's impact *is* record removal). Recovery-token scripts run only against accounts you own on a lab install. Deserialization probes use inert marker objects, never RCE chains.

1. **ORM grammar battery (lab).** Against any app that forwards request data into query helpers: (a) value-position operators (`{"$ne":null}` etc.); (b) string criteria where an object is expected; (c) key-position probes shaped like library internals; (d) nested-attributes payloads naming a *foreign* record ID. Record status/body/DB-side effect per case; the nested-attributes IDOR proof is a foreign row gaining an attribute linking it to your account.
2. **Authz-target probe.** For every object route taking `{id}`: from a second tenant, PUT then DELETE an object ID obtained from a list endpoint. 2xx = authorization target never bound to the object. Then re-run the same verbs against your own object as positive control.
3. **List-scoping check.** Request every collection list as the lowest-privilege account; count foreign-tenant rows. Any unscoped list immediately feeds step 2.
4. **Token-entropy audit.** Identify the token source in the recovery/reset flow (source read if open; else behavioral: request N tokens, compare prefixes/lengths, correlate with server `Date`). For any time-derived candidate, script a bounded precompute window (minutes, not days) against your **own** lab account and report the hit rate.
5. **Deserialization-sink grep (open-source PHP targets).** Map values that reach `unserialize`/`unserialize`-equivalents; confirm `allowed_classes` argument presence; where absent, instantiate a harmless lab class whose constructor writes a marker file (inert proof only).
6. **Action-matrix enumeration.** Extract every `action=`/method of each servlet/dispatcher; run authenticated cross-project reads for each; build the 403-vs-200 table. `fetchSchedule`-style misses are the ones fixes forget.

## Reporting checklist

- For ORM reflection/operator items, pin library version and the exact request that crosses the boundary; separate *disclosure* from *destruction* claims — the 9.8s here claim both, most apps only expose the read path.
- For authz-target fallback, include the positive control (own object, 2xx) beside the cross-tenant result (foreign object, 2xx) and the list-endpoint screenshot that yielded the ID; state the fix version (Blazar 17.0.1).
- For predictable tokens, report the entropy source, candidates-per-window, probe rate observed by any rate limit, and one owned-account reset — never a third-party account.
- For CSFLE cleartext, quote only a synthetic canary value and name the field path (e.g. `embedded[].secret_field`); the finding is that the schema generator dropped the rule, not the data.
- For cache-semantics folds, keep proofs on two synthetic callers with random canaries; `Set-Cookie` values in evidence must be fake.

## September 20 follow-up: token-entropy and whitelisted-RPC siblings (3 GHSAs + Frappe)

- **NivoCart predictable reset tokens** (CVE-2026-94107, [GHSA-g4x6-pg76-867r](https://github.com/advisories/GHSA-g4x6-pg76-867r), 8.1): `forgotten.php` mints recovery codes as `substr(md5(mt_rand()), 0, 10)` with **no rate limit and no expiration**. `mt_rand()` is a 32-bit-seeded PRNG — the 10-hex-char output is brute-forceable offline once you bound the request time from the server `Date` header; knowing an admin email = admin ATO. Same script shape as the Cotonti item above; the "no rate limit" wording means the window is as wide as you want it.
- **ezBookkeeping TOTP replay** (CVE-2026-94112, [GHSA-j95g-6g2h-3f33](https://github.com/advisories/GHSA-j95g-6g2h-3f33)): passcodes are **never invalidated after use** — a captured code authenticates repeatedly for ~90 s. Audit axis for any 2FA flow: after a *successful* code use, replay it immediately on a second authorization attempt in your own lab account; success = one-time-code-is-not-one-time. A phishing/proxy position that sees one code gets a 90-second ATO lane, not a dead token.
- **Dancer2 silent CSPRNG fallback** (through 2.1.0, [GHSA-ccc2-34g9-j7rg](https://github.com/advisories/GHSA-ccc2-34g9-j7rg)): `SessionFactory::generate_id` **silently** falls back to a SHA-1 over `rand()`, module path, counter, PID, memory address, and a `List::Util::shuffle` string (also `rand()`-seeded) when `Math::Random::ISAAC::XS`/`Crypt::URandom` are missing. Every input is low-entropy or observable (PID ranges, address layout). Durable rule for session-ID audits — **a secure-default library can degrade silently on a thin deployment**: collect N session IDs from a target, run entropy/duplication/sequence checks on the IDs themselves; don't trust the framework name. Same "silent security-feature failure" class as the Mongoid CSFLE cleartext item.
- **Frappe/ERPNext whitelisted-method permission drift** (CVE-2026-94113, [GHSA-m9g7-gc6x-55x7](https://github.com/advisories/GHSA-m9g7-gc6x-55x7)): `get_projectwise_timesheet_data`, `get_timesheet_detail_rate`, and `get_timesheet` are `@frappe.whitelist()` callables that **skip doctype permission checks** → any authenticated user enumerates billable time logs, project names, and billing amounts. Frappe's entire RPC surface is `/{app}/{method}` over whitelisted functions — enumerate the callable registry (source grep on open installs; `/api/method/` probing on live ones) and run the authorization matrix per callable. This is the Azkaban sibling-action axis generalized: **in RPC-registry frameworks, the route list is the function list, and decorators per function drift independently.**

## September 22 follow-up: order-timestamp-derived download tokens (Concrete CMS Community Store)

- **Concrete CMS Community Store < 2.7.8 digital-download tokens** (CVE-2026-95653, [GHSA-4m3m-829w-5q37](https://github.com/advisories/GHSA-4m3m-829w-5q37), 7.5): download tokens are derived from the **order creation timestamp** instead of a CSPRNG, and order/file IDs are sequential — unauthenticated attackers enumerate IDs, recompute tokens from the (often visible or range-bounded) order time, and pull other customers' purchased digital goods. This is the Cotonti `md5(microtime())` pattern wearing an e-commerce costume: the *derivation input is public or bracketable infrastructure metadata* (order times appear on receipts, invoices, "ordered on" UI, and drift by at most a day across a batch). Sweep rule for every token-bearing URL (download, receipt, invoice, sharing link): ask what entropy source generated the token; if the answer correlates with anything the site itself displays, brute the ±1-day window × ID range offline against one lab-purchased item to prove the class without touching real customers' purchases.

## September 22 follow-up: array-shaped credentials on the login form reach the SQL grammar

- **Pagekit CMS ≤1.0.18 unauthenticated SQLi via `credentials` array** (CVE-2026-88756, [GHSA-38cq-4qpv-62wf](https://github.com/advisories/GHSA-38cq-4qpv-62wf)): the public `POST /user/authenticate` endpoint hands the **`credentials` array** straight to the query layer, so operator-structured values (`username[op]=...` form-syntax arrays, JSON objects where the handler expects scalars) are parsed as query grammar instead of quoted strings → unauthenticated SQL injection from the login form itself. This is the SQL twin of the Mongoid caller-operator smuggle above and the Mongoose `$ne` class: **the auth form is a query-builder sink**.
- Probe heuristic: on every login/register/forgot-password/2FA-verify field, re-submit with the scalar replaced by an array (`user[]=`, `user[eq]=`, JSON `{"user":{"op":"LIKE"}}` variants) and diff responses/timing for grammar interpretation. Legacy PHP frameworks with array-to-WHERE helpers (Phalcon-family query builders, framework `where(['column'=>$array])` semantics) are the prone population.
- EOL framing: Pagekit is archived/end-of-life — there is no upgrade path, so a live Pagekit instance with a public login form is an unpatched SQLi primitive; treat "CMS vendor archived the project" as a severity multiplier in reports, matching the stagnant-ML-loader rule from the June 30 model-parser page.

## September 23 follow-up: client-supplied sort columns cross into SQL through the pagination interceptor (MyBatis-Plus `concatOrderBy`)

- **TDuckCloud tduck-platform ≤ 5.3 unauthenticated SQLi via `orders[0].column`** (CVE-2026-95829, [GHSA-rj23-5g4f-59vx](https://github.com/advisories/GHSA-rj23-5g4f-59vx), exploit public): the app-level `PaginationInnerInterceptor` config concatenates the client's requested **sort column** into the `ORDER BY` clause (`concatOrderBy`) — sort parameters cannot be parameterized as bind values, so anything the interceptor doesn't whitelist rides into SQL text. This is the reusable Java/Spring leg of the query-grammar class: **MyBatis-Plus `PaginationInnerInterceptor` with a passthrough `orderBy`/`column` field is an ORDER BY injection sink**, present in a very large installed base of admin-panel/form-builder software (tduck-family, ruoyi-family, and countless derived projects). Sweep rule for any Java/Spring target: (1) on every list/table endpoint, replace the sort parameter value with benign grammar probes (`(select 1)`, `(CASE WHEN (1=1) THEN id ELSE title END)`, timing functions) and diff result ordering/latency; (2) the derived-project population means the same vulnerable config line ships across many distinct vendor products — one tduck finding predicts sibling products built on the same scaffold; (3) ORDER BY position commonly defeats WAF/ORM escaping tuned for WHERE clauses, so test sort fields even when filter values test clean. Lab-bounded: read-only ordering/timing canaries on owned instances; the public exploit exists — do not replay third-party exploit bytes against production.

## September 23 evening follow-up: `uniqid()` as a business-object identifier = unauthenticated guest-order PII reads (Isotope eCommerce ≤2.9.10)

- **Isotope eCommerce (Contao) through 2.9.10** derives **order identifiers from `uniqid()`** — a time-derived, non-CSPRNG hex string — and guest order lookup performs **no ownership verification**: supply a guessed/reconstructed `uid` and read billing address, customer data, and purchased files. Same script shape as Cotonti/AVideo/NivoCart above, new target class: **order/quote/invoice/receipt identifiers on storefronts are enumerable identifiers, not just recovery tokens**. Sweep rule: order numbers/references that look hex/timestamp-shaped (uniqid = 8-hex seconds + 5-hex microseconds) or sequential get a window-generation script before you conclude the guest lookup is safe; guest-facing lookup endpoints (order status, download links, invoice PDFs) must be tested with *synthesized* IDs, not just adjacent IDs, because "hard to guess" is the only defense these objects have when the ownership check is missing.

## September 21 follow-up: library-level TOTP replay is the default, not the exception

- **nginx-ignition TOTP reuse within the validity window** (CVE-2026-61630, [GHSA-hf33-q6cf-c66f](https://github.com/advisories/GHSA-hf33-q6cf-c66f)): the app validates codes with the widely-used `pquerna/otp` Go package, which **does not track already-consumed codes** — the maintainers' stated position (issue #61) is that single-use enforcement is each application's job, and most applications skip it. So the ezBookkeeping replay axis above is not a one-off bug but the **library default**: unless the app explicitly persists used codes per user per window, the code works repeatedly for ~30 s. Operator procedure upgrade: when you hold one TOTP from a phishing/proxy position, **use it twice** in your own lab-equivalent flow — first success proves capture validity, second success proves the app inherited the library default and you have a reuse lane, not a one-shot token. Report the class as "package X ships no consumption tracking; app Y adds none" with the package name in the finding — it predicts the same bug across every other app on that package.
