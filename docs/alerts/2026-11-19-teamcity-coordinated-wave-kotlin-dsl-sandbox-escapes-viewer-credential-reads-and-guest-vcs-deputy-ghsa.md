# TeamCity wave (82 GHSAs): Kotlin DSL sandbox escapes, viewer-tier credential reads, guest VCS deputy

Source: hourly offensive-security scan, GitHub Security Advisories unreviewed wave published 2026-11-19T12:32Z, JetBrains coordinated advisory set. Fixed in TeamCity 2026.2.1 and 2026.1.5 (a few legs 2026.2 / 2026.1.4 / 2025.11.8). CVE-2026-132954 through CVE-2026-133057, third same-product coordinated wave this quarter after the August 5 agent-polling KEV page and the November 18 21-GHSA wave on [TeamCity agent-polling protocol authority validation](2026-08-05-teamcity-agent-polling-authority-cve-2026-63077.md), so the same-product re-sweep rule keeps paying.

**Wave in one line:** the Kotlin DSL settings sandbox leaked through six distinct callback and class-loading legs, the lowest project roles turned out to read or use server-side credentials they were never supposed to touch, guests could push commits with stored VCS credentials, and roughly sixty stored-XSS advisories mapped every settings and health-report page in the UI.

The remaining ~57 advisories (CVE-2026-132954 through CVE-2026-133057) are a stored/reflected XSS cluster covering Triggers, VCS root settings, checkout rules, cloud profile editors, health reports, diff views, agent popups, the Promote dialog, thread dump page, and roughly fifty other UI surfaces. One page is not the finding; the coverage map is (rule 5).

## Durable rules

1. **A sandbox is a surface inventory, not a property.** Six independent Kotlin DSL sandbox escape legs (public reflection, boot classpath, script definitions, UI patches callback, context parameters callback, compiler arguments) in one release means the sandbox's deny rules were written per-callback, and every callback a subsystem registers is a new escape candidate. On any product with a config-code sandbox (CI DSLs, low-code scripting, report generators): enumerate the registration sites for hooks/callbacks/extensions a trusted config can define, then test execution from each one separately. A sandbox escape found on one leg says nothing about the other five.
2. **Read the settings archive at every role you hold.** Viewer-tier download of the full project settings archive (133025) plus protected-parameter recovery in the parameter editor (133030) means the config export path and the display path have different ACLs. On any CI or SaaS console, request the admin-shaped artifacts (settings export, YAML/DSL source, archive download) with the lowest token you have; a 200 with a config body is the finding.
3. **Server-held credentials are deputy surfaces; test them from below.** Guests pushing VCS labels with stored credentials (133029), cross-project AWS connection use (133048), and foreign OAuth secret reads (132985) all say the same thing: enumerate every integration holding server-side credentials (VCS roots, cloud profiles, OAuth connections) and attempt use/read from roles below the owner. This is the November 18 viewer-uses-Kubernetes-credentials rule extended down to guest.
4. **Token identity folds wherever the username is normalized.** Privilege escalation "via username handling in token authentication" (133027) belongs next to Fleet's case-folded token columns from the same week: at the token boundary, test case variants, trailing whitespace/dots, and Unicode folds of the username against your own low-priv token. A fold that maps your identity onto an admin string is ATO without a password.
5. **A coordinated XSS dump is a UI coverage map for the real bugs.** Sixty XSS advisories naming specific pages (notification rules, thread dump, promote dialog, cloud profile editors) tell you exactly which forms persist attacker-influenceable strings into admin browsers, and those same forms are where the RCE legs live this wave. Feed the page names from a public XSS cluster back in as your functional-testing checklist before probing deeper boundaries on the same screens.
6. **Log maskers have their own escape syntax.** Caret breaking the password masker on Windows (132986) is the shell-escape-character-as-masker-bypass pattern: when testing log exposure of any parameter, include the hosting OS's escape/quote characters (`^`, `%`, `&`, `$`) inside the value.

## Replayable validation boundaries

- Disposable TeamCity lab at a vulnerable band (2026.1.x below 2026.1.5 / 2026.2.x below 2026.2.1), synthetic projects and tokens. All RCE, DSL, VCS, and debug-run legs are lab-only with inert markers (canary file writes, no real command payloads, no outbound calls).
- Role-matrix legs (settings download, protected parameters, cloud profile disclosure, REST user details) are safe as read-only evidence on customer-approved instances: request with your lowest-tier token, record status plus field names, redact values in evidence.
- Deputy legs: prove with lab-owned VCS roots and synthetic OAuth/AWS connections pointing at your own callbacks; never use live stored credentials or reach third-party infrastructure.
- Username-fold leg: your own synthetic accounts in a lab realm; compare token-auth outcome per username variant in a decision table.
- XSS cluster: do not plant script payloads in shared CI dialogs; on authorized targets stay at reflected-parameter and CSP-observable proof.
- SVN cert leg and TFS helper binding: fingerprint on approved targets (banner, listener bind, version), verify behavior only in lab.
