# Apache Storm wave (3 GHSAs): placement oracle, log symlink read, DRPC impersonation bypass

Source: hourly offensive-security scan of GitHub Security Advisories, 2026-11-11T15:31Z wave. All three legs fixed in Apache Storm 3.2.0; GHSA severity fields are unset, so price by capability, not label.

Apache Storm's coordinated trio exposes the multi-tenant distributed-scheduler trust model in three complementary ways: the cluster's own inventory endpoints leak other tenants' infrastructure placement, the log-aggregation service resolves attacker-placed symlinks into an arbitrary file read, and the DRPC HTTP endpoint trusts a client-supplied identity string instead of consulting the configured impersonation authorizer. Together they describe a standing post-foothold ladder for any authorized engagement against a shared Storm cluster: map, read, act-as.

## Why this matters for operators

- **Scheduler inventory APIs are pre-foothold lateral maps.** The Nimbus leg is the durable generalization: every cluster manager that shows "where my workloads run" (YARN ResourceManager, Mesos master, Nomad, Kubernetes dashboards, Slurm, Jenkins agents) tends to scope the *view* by session, not by tenant. After obtaining any low-privilege credential on a multi-tenant scheduler, enumerate the placement/assignment endpoints for foreign tenants' workloads before touching the workloads themselves. Host+port+owner+resource tuples per foreign topology are a targeting map for pivot selection, service fingerprinting, and timing attacks against co-resident tenants. Sweep rule: for every list/assignment endpoint, replay with a minimal-privilege principal and diff returned object ownership against the caller's authorization.
- **Log viewers that resolve symlinks are a standing container-read primitive.** The Logviewer leg is the write-somewhere-then-read-anything pattern the wiki keeps meeting in archive/extraction contexts, expressed through the filesystem instead of an archive: the attacker controls a directory the privileged reader walks, the reader dereferences links the attacker planted, and the containment model ("workers only see their own logs") never considered link resolution. Generalizes to every product with a log-aggregation or artifact-serving daemon (CI log viewers, build-artifact servers, notebook log routes, container log APIs): canary test = place a symlink in your writable log/artifact directory pointing at a marker outside it, then request it through the viewer. If the viewer serves it, the read is arbitrary up to the daemon's privileges.
- **A user parameter that selects an identity IS an impersonation request.** The DRPC leg is the cleanest shape: an endpoint takes `user` (or `on_behalf_of`, `owner`, `principal`) from the request body and executes restricted functions as that user, while the cluster has a real impersonation authorizer that the sibling code paths do consult. Audit rule per transport: enumerate every endpoint that accepts an identity-shaped string and check which authorizer (if any) gates adoption of that identity. Sweep battery: replay the same DRPC-style request with (a) your own user, (b) a foreign lab user, (c) a superuser name, (d) the parameter absent, and diff. The Storm fix (3.2.0) routes adoption through the configured authorizer; the pre-fix differential is the proof.
- **Same-product, three-boundary inventory discipline.** Placement (read), logs (read), DRPC (act): the trio shows a single product exposing all three legs of a post-auth ladder at once, each in a different daemon (Nimbus, worker/Logviewer, DRPC server). When one leg of a distributed system is advisorially broken, sweep the sibling daemons' surface immediately; the trust model error usually repeats across the daemon family.

## Validation workflow (authorized labs only)

!!! warning "Lab clusters, disposable topologies, marker files only"
    Run against a Storm (or comparable scheduler) deployment you are authorized to compromise. Submit only synthetic topologies you authored; place only marker/symlink canaries in your own worker's log directory; use two disposable lab users for the impersonation matrix. Never read real tenants' logs, configs, or service-account material; never invoke DRPC functions that mutate live systems.

1. **Placement oracle:** with a minimal lab principal, call the Nimbus supervisor/assignment views for a supervisor hosting a second lab user's synthetic topology. Evidence: returned tuple table (topology, host, port, owner) versus the caller's authorization scope. Foreign rows present = finding; redact real hostnames in evidence.
2. **Logviewer symlink read:** as topology owner, plant a symlink inside your worker log dir pointing at a marker file outside the log root (owned by you). Request it through the Logviewer HTTP UI/API. Evidence: link-entry path vs served content hash; the fixed-build differential is the negative control. Stop at read of your own marker; do not enumerate host configs.
3. **DRPC impersonation matrix:** register a synthetic DRPC function whose execution log records the identity it ran as. Replay requests as self / foreign lab user / superuser-name / param-absent. Evidence: identity recorded at execution per case, plus confirmation that the configured impersonation authorizer logs were never consulted pre-fix.
4. **Version banding:** Storm version from Nimbus UI/API banner; 3.2.0 is the fix line for all three legs. All three legs failing together indicates an unpatched 3.1.x-or-older cluster; the trio itself is a fingerprint.

## Reporting checklist

- Product and exact version (all three legs fixed in 3.2.0).
- Per leg: the daemon (Nimbus / Logviewer / DRPC), the transport, the auth state of the caller, and the principal whose scope was exceeded.
- For the placement leg: the ownership-vs-visibility diff table, with foreign values redacted.
- For the log leg: symlink entry path, resolved target (yours), and served-content confirmation.
- For the DRPC leg: the identity-decision matrix (a)-(d) and the authorizer-consultation evidence.
- Bounded impact language: placement disclosure is targeting intel, not access; symlink read is bounded by the Logviewer process privileges; DRPC adoption is bounded by the restricted-function inventory, prove the function class you can reach.
