# KEV wave 2026-09-09→16: edge VPN/firewall, mail gateway, NAC management plane, router, and package-infrastructure exploitation

Source: CISA KEV catalog additions 2026-09-09 through 2026-09-16 (catalog 2026.09.16, 1713 entries, including the 20:05Z Acronis addition), cross-checked against GitHub advisory mirrors.

Eleven new KEV entries in eight days concentrate on the **perimeter/authentication tier and package infrastructure** (the catalog's Sept 14–16 additions are included below, now twelve with the Acronis hosting-plugin entry). For authorized operators this is a sweep-order signal: these are the internet-facing assets customers will be asked about, and several expose durable validation-boundary lessons rather than one-off CVEs.

## October 7 follow-up: WatchGuard Fireware OS BOVPN-over-TLS client config injection → root on the connecting Firebox (CVE-2026-86131 / GHSA-hrq5-fh6w-qjmh, 9.8)

Fireware OS's **BOVPN Over TLS client** configuration handling code-injects: an attacker who **controls the remote VPN server** executes arbitrary commands as root on the connecting Firebox. The attacker moves from "VPN peer" to full appliance root by feeding config material to the client side of the tunnel.

- This is the mirror image of this page's perimeter-VPN focus and a durable new axis: **the VPN *client* on your target network is the target, and the "untrusted internet peer" is the attack position.** Config negotiation data crossing a TLS tunnel into shell/command construction on the appliance = root RCE regardless of tunnel crypto. Red-team relevance: a branch/teleworker Firebox configured to dial a BOVPN-over-TLS server an operator can stand up (or MITM if the client doesn't pin) converts to root on the hub-side appliance — treat VPN *client* configurations discovered during internal recon as attack-path seeds, and on authorized appliance engagements test whether the client accepts server-supplied config fields without identity gating beyond the server's own choice.
- Validation boundary: lab-owned Fireboxes only; proof shape is config-handling evidence and version fingerprint (Fireware build), never against customer appliances. Generalizes alongside the page's KEV-precedent rule: IKE/IPsec perimeters were the audit target; TLS-tunnel *client* config parsers are the same class with the roles swapped.

## Sweep implications

1. **Two of the eleven are parser/state-machine bugs in identity-adjacent fields** (RouterOS username, btest related-channel) — the same "grammar check happens after the trust decision" pattern already documented on the wiki's library and appliance pages. RouterOS is a recurring engagement fixture: add username-syntax and pre-auth protocol-state probes to the network-internal checklist (lab-owned routers only).
2. **Cisco Secure Email Gateway joins the mail-security RCE class** — a crafted *email* reaching a SQL/eval sink with root execution reframes email as an unauthenticated attack input, not just a phishing vector. For authorized assessments of mail infrastructure, this is now a first-class test target (synthetic messages, isolated appliances).
3. **JFrog's pair is the cleanest reusable lesson**: validate scope-authorization and issuance-path separately from signature validity and feature flags. Both apply to any artifact registry, package proxy, or internal API gateway.
4. **NetScaler alternate-path bypass is the third-generation pattern** (post-Citrix-FRAMESET era): sibling route-family enumeration, not just the flagship CVE route, is the durable validation workflow on NetScaler appliances.
5. **Cisco ISE extends the "API gateway ≠ management UI" class to the NAC tier.** CVSS 10.0, unauthenticated, no workarounds, and active exploitation at KEV pace: an API endpoint's auth control diverged from the web-management interface it fronts, and Cisco's own IoC hunt lives in the `ise-kong` API-gateway access log. ISE/PIC is almost always in-scope on enterprise network assessments because it brokers NAC/VLAN/posture decisions — treat its API surface as a first-class enumeration target with per-route-family positive/negative controls, version fingerprint against the patch matrix (3.1 P12 / 3.2 P11 / 3.3 P12 / 3.4 P7 / 3.5 P4), and confine any active probing to lab appliances.

## Validation boundaries

!!! warning "Ownership and lab discipline"
    Every product above is a customer perimeter device. Only test systems you own or have explicit written authorization to assess; prefer version/config fingerprinting for production, and confine any active validation to lab appliances with synthetic repos, marker files, and lab routers. Never read GitLab config/keys, never send crafted messages through production mail gateways, never exercise RouterOS privesc on operational networks.

## October 3 follow-up: RouterOS webfig pre-auth integer-underflow root RCE (CVE-2026-84411)

- **`GHSA-xj4h-hf2x-2q43` / [CVE-2026-84411](https://github.com/advisories/GHSA-xj4h-hf2x-2q43)** (CVSS 9.8, [ICSA-26-272-06](https://www.cisa.gov/news-events/ics-advisories/icsa-26-272-06)): the RouterOS **web management service** contains an integer underflow in HTTP request-body handling that is reachable **before authentication** — a single crafted request yields arbitrary code execution as root (or DoS). Not yet in KEV as of catalog 2026.10.02; watch for addition.
- Why it matters on this page: this is the **third RouterOS trust-boundary hit this quarter** after the two September KEVs (username-syntax policy-mask privesc CVE-2026-86060, pre-auth `btest` related-channel memory leak CVE-2026-67277). The pattern is now a product-level one: RouterOS splits its pre-auth attack surface across **protocol parsers (SSH login grammar, Winbox/btest) and the HTTP management plane**, and each family got its own boundary bug — an engagement checklist that probes only one family will miss the class.
- Operator axes:
  1. **HTTP body-length arithmetic on management interfaces is a pre-auth memory-safety surface** — same "length/size computed after the trust decision" grammar as the KEV'd btest underflow, now in the web path. Where the web interface is reachable (`80/443/8080` defaults, often on WAN on consumer/SMB gear), version-fingerprint first (`/jshttp/` routes, `www-router` banners, `login.cgi` presence) and confirm patch level against the MikroTik changelog rather than probing body-grammar on production.
  2. **Route-family parity applies inside one service too**: this page's NetScaler lesson (enumerate sibling route families) has a webfig twin — the same HTTP server may front `/rest/`, `api.php`/`rpc.php`, and the login flow with different auth gates and different request parsers; test each independently.
  3. **ICSA-to-GHSA-to-KEV lag is your head-start window**: the ICS advisory is public and GHSA is mirrored before KEV lands; perimeter appliances with ICSA + critical GHSA but no KEV yet are where the durable checklist updates come from (this page was built that way for CVE-2026-86060/67277).
- Validation boundary: lab-owned RouterOS only for anything past fingerprinting; on authorized engagements, version evidence + reachability of the management plane is the report item, not crafted requests.

## October 4 follow-up: NetScaler CTX697096 cluster detail + SAML-gated CVE-2026-88779 (CTX697174)

The Sept 27 zero-day pair (CVE-2026-88771 unauth RCE, CVE-2026-88772 DTLS-gated overflow, both KEV'd) shipped inside an eight-CVE bulletin, [CTX697096](https://support.citrix.com/external/article/CTX697096/citrix-netscaler-adc-and-citrix-netscale.html), and on Oct 3 Citrix published [CTX697174](https://github.com/advisories/GHSA-56r3-m27m-8p62) / [CVE-2026-88779](https://github.com/advisories/GHSA-56r3-m27m-8p62) (CVSS 8.7, memory overflow → pre-auth DoS) as a fast-follow days after the exploited zero-days. Detail has now landed — the tracked wave on this product family converts into a durable checklist.

- **Citrix publishes the precondition as exact config patterns — the appliance config dump is the attack-surface map.** CTX697096 names, per CVE, the `show config` lines that decide exposure: `add vpn vserver ... SSL` **without** `-dtls OFF` = CVE-2026-88772 applies (DTLS is on by default on VPN vServers); `add lb vserver ... DTLS` / `add lb vserver <name> ORACLE` = 88772/88776; LB/CS/VPN/auth vServers of type HTTP/SSL = smuggling CVE-2026-88773 (9.3) + URL-normalization policy-bypass CVE-2026-88774; non-HTTP L7 features on LB/CS/CGNAT-LSN/NAT64 = 88777; Enhanced ISN Generation disabled = TCP ISN-prediction CVE-2026-88778. On an authorized engagement, map each vServer in the customer's config to its applicable pre-auth sink family before touching anything — feature-precondition = attack-surface triage, and "flag absent = feature enabled" default-on gates (DTLS) are the easiest misses.
- **SAML config is the feature gate for CVE-2026-88779**: exposure requires the appliance configured as SAML SP (`add authentication samlAction`) or SAML IdP (`add authentication samlIdPProfile`) — which is nearly every enterprise Gateway fronting Entra ID/Okta SSO. Availability-only impact, but unauthenticated, low-complexity, and no mitigation short of patching. **Update (catalog 2026.10.04): CISA KEV'd CVE-2026-88779 the day after CTX697174 shipped** (added 10-04, due 10-07, forensic-triage required, ransomware use "Unknown") — the "no in-the-wild activity yet reported" line in the advisory window lasted under 24 hours, so treat the SAML-gated pre-auth path as actively exploited, and note the KEV shortDescription still only claims DoS while the requiredAction demands forensics triage — KEV addition on an availability-classified CVE is CISA telling you the real impact chain is worse than the label. Operator value is twofold: (1) on perimeter assessments, `samlAction`/`samlIdPProfile` presence is a cheap version+config fingerprint that tells you whether the box is on the 14.1-73.41/13.1-64.28-or-later build line; (2) the same SAML-brokered AAA surface is where the deep identity axis lives — cross-reference the [SAML assertion attack-surface methodology](../methodology/saml-assertion-attack-surface-testing.md) when SAML actions are present; the DoS CVE is the tripwire that says the SAML parser is actively being audited by others.
- **Two build lines in one week = per-CVE version fingerprinting.** 14.1-73.37 (Sept 27) vs 14.1-73.41 (Oct 3): patch-level evidence must be the exact build, not the branch. Same rule as the Airflow per-advisory fingerprint: a box "on 14.1 latest last month" is still in range for the fast-follow CVE. Fingerprint builds via existing passive routes (`/rns.js`, redirect URL params) before claiming anything.
- **The bulletin's non-memory items feed two existing wiki classes**: CVE-2026-88773 is a front-end-vs-origin desync candidate at the LB tier (pair with the Undertow/smuggling parser-differential methodology; single-connection canaries only, lab backends), and CVE-2026-88774 is URL-normalization-before-policy-evaluation — WAF/security-rule bypass grammar on the load balancer itself; test normalization differentials against policy-boundary routes with inert canary URLs.
- Validation boundary: every item above is a production perimeter appliance. Config-pattern mapping comes from customer-provided config output or lab appliances; no crafted requests against live Gateways. Build/reachability evidence is the report item.

## October 9 00:3xZ follow-up: CVE-2026-107406 — third SAML-gated NetScaler memory overflow, and the affected-range *is* the fingerprint (critical, GHSA-x62m-6223-4vq2)

Imported into GHSA 2026-10-09T00:31Z: another NetScaler ADC/Gateway memory overflow → RCE-or-DoS, again gated on SAML configuration, but with a **stranger affected-range shape** that carries its own operator lesson.

- **Two-sided version window:** for IdP-only exposure (`add authentication samlIdPProfile`) the range is *between* builds — 14.1-73.37 **through** 14.1-73.41 inclusive, and 13.1-64.23 through 13.1-64.28 inclusive (plus FIPS/NDcPP twins). For SP-or-IdP exposure the range is *before* 14.1-73.37 / the older 13.1 lines. **A bounded window that starts at the previous bulletin's fixed build means the fix itself regressed** — the Sept 27→Oct 3 fast-follow pattern (88779) repeating: the remediation for the earlier SAML overflow reintroduced the class inside the same SAML code path.
- **Operator rules:** (1) **When a vendor ships fix N of a memory bug in a gated parser, treat builds [fix N .. fix N+1] as a second hunt window** — regression CVEs live exactly in that interval, and a box "patched to the latest last week" is more exposed than one on the older line. (2) Per-Vserver `samlAction`/`samlIdPProfile` mapping from the Oct 4 leg above now decides *which* of the SAML CVEs applies — same config dump, three overflow legs, one SP/IdP role split. (3) Fingerprint evidence stays passive (build via existing routes, customer config output); no crafted requests against live Gateways. Not in KEV as of catalog 2026.10.08 — watch for the KEV fast-follow that 88779 got within 24 h.
