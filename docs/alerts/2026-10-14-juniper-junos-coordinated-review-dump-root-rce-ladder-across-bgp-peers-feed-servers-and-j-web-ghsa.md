# Juniper Junos coordinated review dump (100+ GHSAs): semi-trusted protocol peers, impersonated helper servers, and a read-only SNMP credential that reaches root

**Wave in one line:** Juniper shipped a Cisco-style coordinated security-review dump — more than 100 advisories in a single 18:32Z window, dominated by Junos OS / Junos OS Evolved per-daemon memory corruption — and the interesting part for an authorized engagement is not the count but the *trust inventory* it publishes: configured BGP/EVPN/BMP peers, HTTPS feed servers, SDX deployment servers, DHCP servers, GRE tunnels, SNMP read communities, and the J-Web management plane all have root-RCE legs attached.

**Signal:** GitHub Security Advisories published the Junos wave at **2026-10-14T18:32Z** (anchor advisory [GHSA-34c5-5qc5-99pf](https://github.com/advisories/GHSA-34c5-5qc5-99pf) / CVE-2026-101954, JSA112187); the published feed carries 100+ advisories in this window with the same Junos daemon tail repeating past the API pagination ceiling. As with the NGINX (Oct 14 15:3xZ) and Cisco (Oct 7) review dumps, **GHSA package version fields are empty** — fix bands live only in the vendor JSA, so product/version fingerprinting comes from the device itself (`show version`, `show configuration | display set` for feature gates), not from the advisory. None of these CVEs were in CISA KEV at catalog 2026.10.13 at scan time.

## Durable operator axes

1. **The review dump IS the trust-surface map.** The advisory set names its owning daemon (rpd, srxpfe, httpd, kmd, authd, phcd, ipfd, sdxd, vgd, iked, l2cpd, l2ald, jdhcpd, cfmd, bfdd, clksyncd, TWAMP client, PFE). That list is an engagement checklist: each named process is a separately fingerprintable listener or outbound channel. Same review-dump rule as the Oct 7 Cisco NGOAM page — pivot empty GHSA version fields to the vendor JSA (here JSA112187), and fingerprint the *device*, not the advisory.
2. **Protocol peers are semi-trusted principals with root reach.** Three 9.8 legs are triggered by *configured BGP-class peers* (EVPN-VPWS advertisements, BMP route monitoring, flowspec re-advertisement). On authorized assessments of service-provider/enterprise backbones, an established eBGP session from any transited AS is a remote-code path, and **feature gates are the fingerprint**: BMP enabled (`show configuration protocols bmp`), update-threading, EVPN-VPWS instances — check the config for feature enablement before ranking which legs are live, exactly like the NGINX config-shape rule the same day. "protocol-valid route advertisements" in the advisory text means the input passes the protocol state machine before hitting the overflow — fuzzing at the *schema-valid* boundary, not the malformed-packet boundary, is where these live.
3. **Helper-server return channels are unauthenticated parsers.** ipfd (HTTPS feed server), sdxd (SDX/SRC deployment TCP), phcd (DHCP) are all *outbound-initiated* relationships whose *responses* parse attacker data as root or root-adjacent. Impersonating a configured feed/deployment/DHCP server — via DNS takeover, stale feed URL, or adjacent-network rogue DHCP — yields root RCE without ever touching the management plane. Sweep rule for any network appliance: enumerate every configured outbound fetch (`services`, feed URLs, auto-deploy, phone-home, NTP/DNS/DHCP dependencies) and treat each as an unauthenticated inbound listener at root privilege; test feed transport authenticity with lab-controlled impersonation only.
4. **Read-only credentials that cross into execution.** `authd`: an SNMP **read** community + AAA enabled = root code execution via one packet. A monitoring-only credential is an RCE prerequisite — inventory SNMP read strings, TACACS/RADIUS shared secrets, and monitoring-plane accounts as attack-path material, not just "info-level" findings. Same containment-by-privilege-tier theme as the Brocade SAN waves.
5. **J-Web is the standard forgotten perimeter.** The anchor 9.8 (unauthenticated J-Web/NETCONF → root config access) plus the httpd 9.8 make "is J-Web exposed, and on which interface" a first-class recon question on any Juniper in scope, with the virtual-domain/`/webui` route family as the alternate-surface sweep. Post-auth legs (iked VPN-client → root, authenticated network attacker PAN-OS-style management RCEs) confirm: on these appliances, *post-auth ≠ low impact* — every authenticated surface is a root candidate.
6. **Same-wave perimeter context, tracked:** a 9.8 in the same window — [GHSA-6rc3-jwq8-jm3v](https://github.com/advisories/GHSA-6rc3-jwq8-jm3v) / CVE-2026-76519, Cisco Secure Email Gateway **AMP file-reputation feature**: unauthenticated crafted email attachment → arbitrary file write → root on the underlying OS. The security-inspection engine is itself the pre-auth parser and mail flow is a free, unfiltered input channel to it — when any mail-security appliance is in scope, the *inspection feature* (not the admin UI) is the primary surface. Kept as a tracked note here (single leg, no new axis) rather than its own page.

## Validation boundaries

- Route-advertisement, IKE, GRE, SNMP, and DHCP legs go only on lab or customer-expressly-approved gear; most legs crash or own the routing engine — a worker-crash-equivalent here is an outage. Config-feature inventory (`show configuration protocols`, SNMP/AAA state, feed URLs, J-Web exposure via `show configuration services`) is passive and safe; exploitation is not, absent explicit approval.
- Feed/DHCP/SDX impersonation proofs stay in lab VLANs with synthetic servers and marker canaries; never intercept a live feed or deployment channel in production.
