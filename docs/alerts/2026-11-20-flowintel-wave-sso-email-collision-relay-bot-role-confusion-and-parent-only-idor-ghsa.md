# FlowIntel wave (30 GHSAs): one SSO email claim reaches accounts across every IdP

Sources: the coordinated FlowIntel advisory set published 2026-11-20T12:31Z, all fixed in FlowIntel 4.1.0: [GHSA-f6mh-j93f-5j88](https://github.com/advisories/GHSA-f6mh-j93f-5j88) (SSO identity and organisation trust), [GHSA-65wf-xjf6-m9m4](https://github.com/advisories/GHSA-65wf-xjf6-m9m4) (Analyzer authorization bypass), [GHSA-wwpx-288c-mcq7](https://github.com/advisories/GHSA-wwpx-288c-mcq7) (note variables, chatbot tooling, argv leak), [GHSA-hw2q-68qg-xxc5](https://github.com/advisories/GHSA-hw2q-68qg-xxc5) (TLS verification disabled, critical), [GHSA-f579-2pq9-h77f](https://github.com/advisories/GHSA-f579-2pq9-h77f) (child-record IDOR), [GHSA-qff4-hjm3-chhm](https://github.com/advisories/GHSA-qff4-hjm3-chhm) (cross-org directory), [GHSA-j75p-gp7g-fq36](https://github.com/advisories/GHSA-j75p-gp7g-fq36) (session lifecycle), [GHSA-m7v5-67mr-9whw](https://github.com/advisories/GHSA-m7v5-67mr-9whw) (stored XSS trio), [GHSA-fjj8-3qgh-4vgv](https://github.com/advisories/GHSA-fjj8-3qgh-4vgv) (credential disclosure), [GHSA-8325-prhg-m22r](https://github.com/advisories/GHSA-8325-prhg-m22r) (Matrix relay privilege escalation), [GHSA-mrjg-wcmv-396q](https://github.com/advisories/GHSA-mrjg-wcmv-396q) (GET-route CSRF), [GHSA-pmfg-8m4x-mx4h](https://github.com/advisories/GHSA-pmfg-8m4x-mx4h) (connector credential confusion), [GHSA-62h3-gr7x-5ww9](https://github.com/advisories/GHSA-62h3-gr7x-5ww9) (Docker build hygiene).

**Wave in one line:** FlowIntel, a self-hosted SOC case platform built on Flask and MISP, shipped thirteen boundaries at once before 4.1.0, and the crown leg is that every SSO provider (Keycloak, Entra ID, SimpleSAML) resolves a *claimed* email address to an existing local account regardless of how that account was originally created, so any attacker who can mint an identity at any supported provider with a victim's email owns the victim's account and private case data.

!!! warning "Authorized scope only"
    Validate only against disposable FlowIntel instances you control with synthetic cases, users, and organisations. The chatbot tool and AI report legs can call real MISP connectors, so prove against mocked or lab MISP endpoints. Never read real case data, credentials, or webhook tokens from a shared deployment.

## Why this is worth an operator page

FlowIntel is exactly the class of product bug hunters hit in self-hosted enterprise scopes: analyst tooling that aggregates threat intel, mail, and identity from several trusted systems, wires them together with name-based matching, and treats its own automation as a trusted caller. Each leg below is a reusable sweep rule, and most transfer to any multi-tenant Flask app with SSO and integration bots.

- **Cross-provider email collision is account takeover when email is the join key ([GHSA-f6mh-j93f-5j88](https://github.com/advisories/GHSA-f6mh-j93f-5j88), high).** Keycloak SSO accepted *unverified* email claims, and all three SSO providers could resolve a claimed email to an account created through a *different* sign-in method. The sweep rule: for every product with more than one identity source, build the matrix {provider} x {email verified?} x {local account created by: local password / other SSO / invite} and attempt login from the provider that never issued the account. Any cell where "identity from IdP A resolves to account created by B" returns a session is the finding. Verified-email checks must run on *every* provider path, and email-to-account mapping must record provenance, not just value. Same-day lineage: the Nov 12 Fleet wave's `utf8mb4_unicode_ci` token columns and the Nov 17 EGroupware idp-param leg (CAST Imaging page) are both identity-join-key defects at different layers.
- **Role mapping by group *display name* is self-service privilege escalation ([GHSA-f6mh-j93f-5j88](https://github.com/advisories/GHSA-f6mh-j93f-5j88)).** Entra ID role mapping keyed on group display names, so any tenant member could create a group named `FlowintelAdmin` and inherit the admin mapping. Audit rule: for every IdP-to-app role mapping, ask whether the claim it keys on is *writable by the claimant*. Group names, org display names, and profile fields are claimant-writable in most tenants; group object IDs and role IDs are not. Same leg for the organisation-provisioning variant in the same advisory: SSO provisioning reused any organisation whose *display name* matched a user-controlled profile name, granting the new user that org's private cases, and case sharing resolved organisations by name with a *first-match query*, so ambiguous names silently resolve to the wrong org. Name-as-foreign-key anywhere is the grep target; ask "what happens when two rows share this name?" for every name-keyed lookup.
- **Authorizing the parent URL while fetching the child by ID is the universal IDOR shape ([GHSA-f579-2pq9-h77f](https://github.com/advisories/GHSA-f579-2pq9-h77f), high).** Task notes, subtasks, URL tools, assignees, timeline events, case connectors, and connector module operations were all authorized by the *case or task in the URL* and then operated on a child record with no ownership check against that parent. The probe is mechanical: for any `/case/<id>/...` or `/task/<id>/...` route that also accepts an object ID in body or query, replay with the parent ID you own plus a child ID from someone else's case, and diff 200-vs-403. The connector variant (combine an authorized case with a foreign connector link) shows the rule extends to *reference pairs*: when an operation joins two caller-supplied identifiers, verify the join edge, not just the endpoints.
- **A relay bot authorizes with its own role and trusts editable profile fields ([GHSA-8325-prhg-m22r](https://github.com/advisories/GHSA-8325-prhg-m22r), medium).** When the Matrix relay forwarded API requests on behalf of a represented user, authorization checks evaluated the *relay bot's* elevated role while handlers acted as the low-privilege user, so Read Only users performed writes through the relay. Worse, relay authority was recognized by matching the caller's *editable profile name and email* against the expected bot identity, so an ordinary user who renamed their profile to the bot's name was recognized as the trusted relay. Rules: (1) **delegating proxies must authorize the represented principal, not the transport credential**; any "acting on behalf of" header (MATRIX-ID style) combined with a service credential is the fingerprint, and the probe is a lowest-role account calling through the relay path; (2) **never authenticate a trusted integration by user-editable fields**; identity binding must use protected identifiers (bot ID, API key, HMAC), and the audit is grepping trust decisions for profile/name/email comparisons.
- **LLM tool surfaces without an allow-list are SSRF with the app's own credentials ([GHSA-wwpx-288c-mcq7](https://github.com/advisories/GHSA-wwpx-288c-mcq7), high).** The chatbot API tool let the model invoke *any* FlowIntel API endpoint, including administrative routes and state-changing GET operations, with no allow-list or path validation, so anything that influences the model's instructions (untrusted case content, imported MISP attributes) becomes an indirect API caller. The same advisory adds two more agent-adjacent legs: note variable references resolved using the *viewing user's* privileges rather than the destination case's audience, so a shared or imported note could embed references to private cases and pull that data into AI report requests, exports, and MISP sends; and AI report generation passed the Ollama bearer token plus full case content as **command-line arguments** to a child process, exposing both in the system process table to any local user. Rules: (1) enumerate every model-facing tool surface and check for a path allow-list; state-changing GETs reachable by the model are double findings given the CSRF leg below; (2) **data-reference resolution needs an audience check at every tier** (view-time, render-time, send-time), not just at the reference author's write time; (3) `ps aux` on any AI feature is a five-second recon step: secrets in argv are world-readable on every shared host. This page's July 26 agent-approval doctrine (tool annotations are claims not controls) extends cleanly to "model tool access is a route family, audit it like one."
- **Session lifecycle as a whole attack surface ([GHSA-j75p-gp7g-fq36](https://github.com/advisories/GHSA-j75p-gp7g-fq36), high).** The session ID was a bare numeric user ID. Consequences all shipped together: remember-me cookies survived password change, no session rotation on any login path (fixation), self-service email/password change did not verify the current password (any live session escalates to full account control), and admin password resets revoked nothing (no session/API-key invalidation). Rule: run the **session lifecycle decision table** on any app with a profile page: {issue, login, SSO login, password change, email change, admin reset, logout} x {old cookie still valid?, old API key still valid?, other sessions affected?}. Every "yes, still valid" cell where the spec expects revocation is a finding, and "password change does not require the current password" converts XSS to persistent ATO.
- **Flask-WTF CSRF guards cover only non-GET, so a GET-destructive route is CSRF by construction ([GHSA-mrjg-wcmv-396q](https://github.com/advisories/GHSA-mrjg-wcmv-396q), medium).** Fourteen destructive routes (case deletion, case merging, task deletion, connector deletion, taxonomy status changes) accepted GET in addition to or instead of POST, skipping token validation entirely. Sweep rule: for any framework where CSRF protection is verb-gated, `curl -X GET` every state-changing route you can enumerate from the UI or route map; `<img src=...>` proof with a disposable case is enough. This is the mirror image of the Nov 17 Flagr method-blind-allowlist rule: verb gating on the *guard* side is as dangerous as verb blindness on the *auth* side.
- **UI-hidden is not API-hidden ([GHSA-fjj8-3qgh-4vgv](https://github.com/advisories/GHSA-fjj8-3qgh-4vgv), high).** The notification page and alert API returned webhook URLs, signing secrets, IMAP credentials, and delivery logs to non-admin users because the template merely hid the form while the JSON stayed in the initial payload, including historical webhook URLs carrying live bearer tokens. Standing rule: always fetch the *raw* page source and the underlying API for admin panels with a low-privilege account; client-side visibility is a rendering decision, not an authorization one.
- **Integration credential scope confusion ([GHSA-pmfg-8m4x-mx4h](https://github.com/advisories/GHSA-pmfg-8m4x-mx4h), medium).** Connector instance metadata and connectivity checks accepted instance IDs with no visibility check; template serialization leaked attached connector instances regardless of caller permission; editing a connector URL did not require re-authenticating its API key (reuse of another user's key against a new endpoint); and outbound MISP keys were accepted for *incoming* alert authentication, collapsing the outbound-integration and inbound-alert-source credential classes. Rules: (1) credential *edit* flows that change the destination without re-proving the credential let an attacker redirect someone else's stored key, the same destination-swap shape as the Temporal proxy leg on the Sept 21 internal-deputy page; (2) sweep every credential for direction separation: try each integration key at each opposite-direction endpoint.
- **TLS verification off across the whole integration stack ([GHSA-hw2q-68qg-xxc5](https://github.com/advisories/GHSA-hw2q-68qg-xxc5), critical).** All MISP HTTPS calls plus SMTP STARTTLS and IMAP used unverified SSL contexts, so any on-path position captured MISP API keys and mail credentials or injected threat-intel data. Operator note: for any appliance/platform whose value is ingesting third-party feeds, `ssl_verify=False`, `verify_mode=CERT_NONE`, or `ssl._create_unverified_context()` in the shipped source is a critical-class finding with a trivial static proof; run the grep on the repo before any network testing.
- **Stored XSS by post-sanitizer re-serialization ([GHSA-m7v5-67mr-9whw](https://github.com/advisories/GHSA-m7v5-67mr-9whw), medium).** Already-sanitized notes and imported MISP attribute values were fed through the timeline library's autolinker, which rewrote them into generated HTML anchors where a quote broke out of the attribute context; the search highlighter spliced `<mark>` between regex-matched angle brackets *inside attribute values*; and three analyzer selection endpoints returned session-stored JSON with `Content-Type: text/html`, so the browser HTML-parsed attacker-stored strings. Rule: sanitization at write time does not survive every read-time transformer; audit each post-sanitize rendering step (autolinkers, highlighters, markdown re-renders) as its own sink, and check Content-Type honesty on any endpoint that echoes stored strings.
- **Cross-org directory leak through inconsistent config enforcement ([GHSA-qff4-hjm3-chhm](https://github.com/advisories/GHSA-qff4-hjm3-chhm), high).** With `LIMIT_USER_VIEW_TO_ORG` enabled, several user-lookup endpoints (by ID, last name, Matrix ID, role listings) skipped the org filter, and OrgAdmins could pull any user's task assignments including private case titles. Rule: a config toggle that restricts data access must be verified at *each* endpoint class the feature touches; enumerate every read path for the restricted entity, because feature flags are usually enforced at the primary list route and forgotten on lookup-by-alternate-key siblings.
- **Cross-tenant write-through into Analyzer saves ([GHSA-65wf-xjf6-m9m4](https://github.com/advisories/GHSA-65wf-xjf6-m9m4), high).** Saving analyzer results accepted caller-supplied case/task IDs with no membership check, stored results were retrievable by UUID by any authenticated user, and the save handler continued past failed sub-operations (partial writes). Same parent/child and unowned-UUID-read rules as above, plus: **enumerate "save/export to" endpoints separately**, they are create-paths wearing read-path permission checks.
- **CI hygiene tail ([GHSA-62h3-gr7x-5ww9](https://github.com/advisories/GHSA-62h3-gr7x-5ww9), medium).** The project's own Docker build used actions/checkout with defaults (persistent tokens). Included as the standing supply-chain checklist item for the product's install path: inspect the shipped workflow files, they are part of the trust surface.

## Replayable validation sequence (lab)

1. Stand up FlowIntel < 4.1.0 with two disposable organisations (ORG-A, ORG-B), synthetic cases with a canary note in each, and mocked MISP/SMTP/Ollama endpoints you own.
2. **SSO collision:** create a local-password account for `canary-a@lab.test` in ORG-A; register the same email on a lab Keycloak (or SimpleSAML) IdP with email-verification off; log in via SSO and confirm you land in the local account with its private cases. Record the matrix cell that broke.
3. **Relay impersonation:** with a Read Only account, (a) call a write endpoint through the relay path with the relay API key plus a MATRIX-ID header naming another user, (b) rename your own profile to the configured bot name and check whether you are treated as the trusted relay. Marker-only writes into your own lab case.
4. **Parent/child IDOR:** as a member of case P1, request `/...?child_id=<id from foreign case P2>` for notes, subtasks, timeline events, and connectors; diff 200-vs-403 per endpoint into a table.
5. **Session lifecycle table:** issue, log in (local + SSO), change password without the current password, have the admin reset the password; replay the old cookie and old API key after each step.
6. **GET-CSRF:** replay every destructive route as GET with a victim cookie against a disposable case; one `<img>` tag demo is sufficient evidence.
7. **TLS:** `grep -Rin "verify\|CERT_NONE\|_create_unverified" flowintel/` on the pinned source; static proof, no MITM needed.
8. For the chatbot leg, confirm the tool surface's endpoint scope with a mocked model response that attempts an admin route; never let a lab model touch a live MISP connector.

## November 20 second wave (17 more GHSAs, 15:31Z): workflow-state locks, relationship-edge disclosure, and a shared MCP session

The same product's coordinated release continued at 15:31Z with seventeen further advisories, all fixed in the same 4.1.0 band (GitHub batch-split fingerprint: two publication waves, one release). This page's same-product re-sweep rule paid off: the second half shifts from identity/SSO to **workflow state machines and disclosure through relationship edges**, and adds the strongest agent-infra leg of the whole set.

- **State-machine locks enforced only on the primary transition route ([GHSA-6fj2-w9x4-h525](https://github.com/advisories/GHSA-6fj2-w9x4-h525), [GHSA-wqqj-6vp9-vr75](https://github.com/advisories/GHSA-wqqj-6vp9-vr75), [GHSA-xpc9-m388-64hr](https://github.com/advisories/GHSA-xpc9-m388-64hr), [GHSA-4jh2-w84h-r7c5](https://github.com/advisories/GHSA-4jh2-w84h-r7c5), all high/medium).** Tasks in restricted states (Requested / Rejected / Request Review) inside privileged cases were locked against non-approvers *on the main status route only*. Non-approvers could still: mark tasks Finished (status change **implicitly completes**), create a new task with the `completed` flag pre-set, reach completion via UUID aliases or Matrix delegation, self-unassign from a restricted task, reorder a list (moving restricted siblings implicitly), link/unlink/create/delete MISP objects referencing a restricted task, run modules on it, convert its attached file into a note (file-content extraction through a read-adjacent action), and delete its evidence files with no role check at all. Rule: an attribute-gated lock (status/state column) must be enforced at **every code path that touches the locked row**, so enumerate side-effecting operations *on other resources* that accept a restricted-object ID (reorder lists, relation tables, converters, module runners) and replay them with a low-privilege account. The implicit-completion-via-status-field and pre-set-flag-at-create shapes are the two lazy-audit tells to probe first.
- **Workflow side effects skip the check their primary action enforces ([GHSA-m23c-w8mh-qw7w](https://github.com/advisories/GHSA-m23c-w8mh-qw7w), [GHSA-vqwr-2mq3-3rw5](https://github.com/advisories/GHSA-vqwr-2mq3-3rw5)).** Reopening a completed task silently *revived the parent case* (status reset, finish date cleared) with no case-level privilege check; and template-based task/case creation skipped the privileged-case check entirely when no acting user was supplied (template path = "system" caller), landing tasks directly in active state inside privileged cases. Rules: (1) **audit side effects, not just actions**: for every state transition, find the cascading writes (parent status, counters, timestamps, notifications) and test them independently with an account that lacks the primary action's role; (2) **absent-actor branches disable role checks** (the Oct 7 Craft `checkToken` boolean-never-checks-purpose and the Oct 6 Payload disabled-setting-at-router family), so anything that makes the actor optional (templates, imports, webhooks, schedulers) is its own test matrix.
- **Disclosure through relationship edges when object reads are correctly gated ([GHSA-7mgj-jw63-p32h](https://github.com/advisories/GHSA-7mgj-jw63-p32h), [GHSA-cg67-q5p3-j6qq](https://github.com/advisories/GHSA-cg67-q5p3-j6qq), [GHSA-63w8-q684-42jr](https://github.com/advisories/GHSA-63w8-q684-42jr), [GHSA-4phx-qqf8-xj5f](https://github.com/advisories/GHSA-4phx-qqf8-xj5f), [GHSA-7gxx-hc5r-xmhw](https://github.com/advisories/GHSA-7gxx-hc5r-xmhw)).** Private case IDs, titles, and descriptions leaked through four *edges*: linked-case objects serialized into the accessible case's JSON (the serializer never received the acting user), case history enumerating linked/unlinked/forked case references across five output paths (browser, API, text download, markdown download, report timeline), MISP correlation listing matching cases without visibility checks, and classification-usage endpoints (taxonomies, tags, galaxies, clusters) returning usage data for all cases including private ones. The calendar leg is the parent-check variant: task calendar and ICS feeds filtered on task assignment/org membership but never rechecked *parent case* visibility. Rules: (1) build the **edge enumeration list** (links, history references, correlation matches, usage/aggregate stats, shared tags, calendars, ICS/report/attachment exports) and probe each with a user who owns exactly one accessible object on the edge; a serializer or exporter that never sees the acting user identity is the code smell to grep; (2) every alternate *render format* (ICS, CSV, markdown export, report generator) is a separate authorization path from the API view it mirrors. This is the presentation-layer twin of the Sept 18 derived-index denormalization rule: the object ACL held, the graph around it leaked.
- **Check-at-subscribe vs check-at-deliver: revoked access keeps delivering ([GHSA-qc34-rp79-2x7r](https://github.com/advisories/GHSA-qc34-rp79-2x7r), [GHSA-x938-2hpf-43gm](https://github.com/advisories/GHSA-x938-2hpf-43gm)).** Recurring reminders were generated and listed for users whose case access had been revoked (authorization ran at subscription time only); alerts linked to private cases stayed fully readable and reviewable by connector owners without re-checking case membership, with an added TOCTOU where a review-status update's response could disclose private case data whose access was concurrently revoked. Sweep rule: for every stored subscription/ownership/grant relationship (notifications, webhooks, alert links, saved views, API keys), run the **revocation replay table**: grant, receive, revoke, then trigger generation *and* call the display/list endpoint; the display path skipping the re-check is the usual half of the bug (stale-snapshot family, cf. the MISP correlation trio on the Sept 21 precedence page).
- **Privilege-hierarchy check missing under a passing scope check ([GHSA-h543-v96j-6mrj](https://github.com/advisories/GHSA-h543-v96j-6mrj), [GHSA-wwp2-cg34-gwvg](https://github.com/advisories/GHSA-wwp2-cg34-gwvg), both high).** Org admins could delete *and* edit platform-admin accounts in their own organisation: the code verified same-org scope but never compared privilege tiers, and the browser admin view lacked the check the REST API already had (UI-vs-API authz drift again). Rule: when the only gate is a tenancy/scope predicate, attempt every operation against **higher-privilege principals inside the same scope** (delete, edit, lock, role change); hierarchy comparisons and scope comparisons are separate checks that both have to exist.
- **Shared MCP session plus process-wide environment variable = cross-user agent identity bleed ([GHSA-w3q8-9828-cgcr](https://github.com/advisories/GHSA-w3q8-9828-cgcr)).** The chatbot passed per-user API credentials to a child process through a single shared MCP session and one ambient `FLOWINTEL_API_KEY` process env var, so concurrent tool invocations could execute under *another user's* identity (lower-privilege user reading a higher-privilege user's private cases), a revoked/deleted user kept operating on the cached ambient credential, and the parent process env accumulated user secrets. Rules: (1) for any product bridging a chat UI to MCP/tools, the **concurrent-identity probe** is now a standing test: fire two users' tool calls in overlapping windows and check which credential lands on the wire (owned-callback sink, never real tokens); (2) `grep -rn 'os.environ\[' --include='*.py'` (or `process.env.x =`) for *writes* of request-scoped secrets to process-global state is the one-line fingerprint, since any later child process inherits them; (3) revocation doesn't reach ambient copies, so the deleted-user/stale-key replay from this page's session-lifecycle table extends to agent bridges.
