# OpenStack Mistral wave (4 GHSAs): the orchestrator ships its own exec primitive

**Wave in one line:** The orchestrator ships its own exec primitive, share grants outlive their owner's control, and the maintenance controller has no policy

Source: hourly offensive-security scan of GitHub Security Advisories, 2026-10-08 (wave published 2026-10-08T18:32Z, four advisories for OpenStack Mistral `through 23.0.0`).

Mistral is OpenStack's workflow/orchestration service — an API that, by design, runs actions on your behalf. All four legs are authorization/trust-boundary failures inside that design, and each generalizes to every workflow engine, job scheduler, CI orchestrator, or "automation" service you test: the engine's own feature set is the exploitation surface, and the sharing/membership plumbing is where tenancy quietly breaks.

## Why this is an operator page

1. **Orchestrators ship built-in exec primitives — enumerate action inventories before hunting injection.** `std.ssh_proxied` is not an injection bug in the classic sense: the *documented feature* (`ProxyCommand`, an SSH config option whose entire purpose is running a local program) is passed user input straight into `paramiko.ProxyCommand()`. Audit rule for every workflow/automation product: pull the built-in action/module catalog (`std.*` here; Ansible modules, CI step libraries, scheduler plugins elsewhere) and look for actions whose legitimate semantics *include* local process launch, file write, or URL fetch. Fingerprint on an authorized cloud: `POST /v2/actions/std.ssh_proxied/run` reachability, or simply list the action namespace through the API. Because the command runs before the SSH connection is established, even a bogus gateway/target proves execution — the cleanest possible lab-bounded proof shape.
2. **"Ops" controllers are the policy-free zone.** The maintenance leg is the recurring pattern of a management controller that clears auth context "because it's maintenance": no policy check at all, gated only by holding *any* valid token. Sweep rule: on any multi-tenant API, enumerate `/maintenance`, `/admin`, `/health`, `/service`, `/status` controller families and test each with the lowest-tier token you can buy. A cross-tenant `PAUSED` switch is an availability finding with a governance angle (a single project member can halt every tenant's automation pipeline), and the read leg discloses cluster operational state.
3. **Resolve-then-write without an ownership predicate is the supplied-scope-vs-owned-scope shape in its rawest form.** The write-path leg is the same invariant as the October 8 DolphinScheduler legs on the [Sept 18 ignored-scope page](2026-09-18-ignored-scope-parameters-kcp-identity-header-smuggling-convoy-perses-obot-ghsa.md): the handler authorizes *something*, resolves a resource by a query that isn't scoped to the authorized tenant, then mutates whatever row came back. The collision-adoption variant is sharper: if creation of a name-colliding object can **move a foreign resource** into your scope, name-collision probing (`GET` candidate names, then workbook creation) doubles as cross-tenant resource enumeration *and* sabotage — the owner's update failures are a side effect worth knowing about before you touch a live cloud.
4. **Sharing grants need owner-side lifecycle control or they become standing backdoors.** The membership leg is the durable one for every product with a "share to another tenant/user" feature: the grant-creation path defaulted the scope field to the *accepting* project instead of the *owning* project, producing an access row the owner cannot see or delete, from which a third party can derive full read/execute on private content. Audit battery on any share/membership/invite API: (a) can an acceptor re-grant further memberships/shares it did not create? (b) which tenant ID does the new grant row carry — the owner's or the acceptor's? (c) as the resource owner, enumerate every access path to your own resource and try to revoke each one — any row that answers to a different project's revoke call is a persistence primitive an attacker who compromises the lowest-trust acceptor can plant.
5. **Deployment-shape gate:** only deployments exposing the Mistral API are in scope (leg C note) — same class as the Splunk Patroni leg: internal OpenStack service ports (`8980` for Mistral API, executor/conductor processes) appearing on a host is itself the finding before any exploit.

## Replayable validation boundaries (lab/authorized-cloud only)

- **Leg A:** in a devstack/lab cloud, run `std.ssh_proxied` with `proxy_command` set to an inert marker (`touch /tmp/mistral-cmd-marker` equivalent, or a command that prints `id`) and confirm execution as the `mistral` executor user from a plain project-member token. Never target a production cloud's executor host; proof is the marker + `id` output in the lab.
- **Leg B:** with a lowest-tier token, `GET /v2/maintenance` (state read), and only in an isolated lab, toggle `PAUSED` then restore `OK` — record that no policy error was returned. On a shared cloud, the read alone is the finding; do not pause production workflow processing.
- **Leg C:** two disposable projects you own; publish a synthetic action in project B, then from project A run the write path with the resolved identifier and show project B's definition changed. Collision-adoption proof likewise between your own two projects only; never adopt/rewrite real tenant resources.
- **Leg D:** three disposable projects (owner / acceptor / third). Owner shares a private workflow containing only a synthetic marker to acceptor; acceptor creates the further membership naming the third project; third accepts, reads/executes the marker workflow; owner-side list/revoke calls are shown blind/failing. Clean up by revoking from the acceptor side.
- Evidence: token role used per call, raw request paths, DB-visible state transitions described in words (no live credentials, no real tenant workflow bodies).

## October 19 follow-up: Semaphore UI — task-environment JSON lets the `task_runner` role override protected Ansible variables → server-user RCE ([GHSA-6cr7-7xqc-c37c](https://github.com/advisories/GHSA-6cr7-7xqc-c37c) / CVE-2026-112305, high, through 2.19.16)

Semaphore UI (web UI for Ansible/Azure/Terraform) lets users with the **`task_runner` role** supply arbitrary keys in the task environment JSON, which merge over **protected** Ansible variables. Setting `ansible_ssh_common_args` with a `ProxyCommand` (or `ansible_connection=local`) executes commands **as the Semaphore server user** — exposing the project's encryption keys, SSH private keys, and stored secrets. This is the orchestrator built-in-exec family again, arriving through a *variable-merge* door instead of a named action.

Durable rules:

1. **"Protected variables" are a merge-precedence claim, not an enforcement point.** Grep any automation UI for a user-editable vars/env/extras JSON that lands in an Ansible `extra_vars`/environment structure, then ask which keys are blacklisted vs which are *system-owned*. Ansible's own config chain makes `ansible_ssh_common_args`, `ansible_connection`, `ansible_python_interpreter`, and `ansible_become*` execution selectors — a runner-tier role supplying them is supplying a command line. Probe battery (lab): task env `{"ansible_connection":"local","ansible_become":false}` + a `command: id` task → server-user output; then `ansible_ssh_common_args=-o ProxyCommand=touch-marker` → marker file, no SSH connection required (same clean-proof shape as the Mistral `std.ssh_proxied` leg above).
2. **Audit the runner-tier role, not just admin.** `task_runner` is the *lowest* meaningful role in Semaphore. Every automation platform (Semaphore, AWX, Rundeck, Jenkins, Ansible Semaphore clones, CI runners) should be tested with the lowest role that can create a run: can it touch connection/backend/interpreter variables? Genealogy: Rundeck `cmd.exe` quoting leg (June 9 shell-quote page), Argo repo-server ProxyCommand (May 4 page), OpenStack Mistral `std.ssh_proxied` (same page as this fold) — ProxyCommand-as-primitive is now a four-product family.
3. **The blast radius of an automation server is its keyring.** The server user holds Vault/SSH/encryption material for every managed project; treat server-user code execution as credential-store compromise for the whole estate, and enumerate what the service user can read (`~/.ansible`, project `.semaphore` stores, stored Vault tokens) in the lab proof.

Validation boundary: own lab Semaphore instance, inert marker commands, fake key files placed by you; never inject `ProxyCommand` against real managed hosts or read live key material.

## October 21 follow-up: Manila public-share verbs — "public" scopes discovery, not mutation; eight controller legs one invariant ([GHSA-xm2x-8fhq-8hpv](https://github.com/advisories/GHSA-xm2x-8fhq-8hpv) / CVE-2026-71195, critical, before 23.0.1)

Multiple Manila API operations on **public shares** authorize against the caller's own project context, then load the foreign share by UUID **without re-authorizing against the share's actual owner**. Any authenticated project member can: `allow_access` (grant data-plane read/write on another tenant's share), `deny_access` (revoke the *owner's* access rules), `update_access` (escalate ro→rw), `create_share_backup` (copy the victim's share data into a backup under the **attacker's** project), `soft_delete`/`restore` (drive the owner's recycle-bin workflow), create/update/delete export-location metadata, and list access rules — which discloses **IPs, usernames, and CephFS keys**. Same-wave Cinder leg [GHSA-rgvg-xc9j-2jxv](https://github.com/advisories/GHSA-rgvg-xc9j-2jxv) / CVE-2026-93856 (medium, through 29.0.0): v3.3 *List messages* returns other projects' non-expired user messages to a project-scoped member/reader — resource UUIDs across the tenancy line.

Operator reading:

1. **"Public" is a discovery-scoping claim, not a verb-scoping claim.** The share UUID is *visible by design* — the IDOR precondition has zero enumeration cost — so every verb that accepts that UUID is an IDOR candidate. Battery on any "public/shared" resource in any product (shares, public repos, public dashboards, shared documents): take the public item's ID from the public listing, then run the *full write-verb inventory* (access grant/revoke/escalate, copy/export/backup, delete/restore, metadata CRUD, listing/read of access material) as a different authenticated principal. Expect per-verb results, not a single verdict — Manila's controller set was individually written, so some legs fail while others succeed.
2. **A "create copy/export into a caller-owned container" verb turns a missing ownership check into a full data-copy exfil channel.** `create_share_backup` under the attacker's project is the cleanest shape of this class: no read-back primitive needed, the platform builds you a copy. Standing grep for any product with backup/export/snapshot/fork verbs: does the verb verify the *target* resource's owner or only the caller's right to make backups? Sibling genealogy: the Fission storage-archive and ONLYOFFICE downloadfile legs, and the Payload duplicate-op leg that copies hidden field values.
3. **Access-rule/listing endpoints on shared resources are credential oracles.** Manila's access-rule listing leaks CephFS keys and data-plane usernames — the *listing* verb, not the exploit verb, carries the secrets. On any share/ACL feature, read the listing response of a foreign resource for embedded credentials, not just authorization state.
4. **Cross-project leaks on *list* calls are the low-noise variant of this page's resolve-without-ownership invariant.** Cinder's Messages leak needs only a member/reader role and one versioned API call (`/messages` on v3.3) — worth replaying every list endpoint with a project-scoped low-tier token and diffing returned UUIDs against your own project's inventory. Same cloud, same theme as Keystone's credential-API leg on the Sept 16 IdP page: authenticated ≠ scoped.
5. **Product re-sweep rule holds again:** this is the second OpenStack service wave on this wiki in two weeks (Mistral Oct 8, Manila/Cinder Oct 21) — when one service of a coordinated OSS stack yields authz GHSAs, enumerate sibling services' public/share feature APIs immediately; controllers across the same codebase family share the authorize-context-then-load-foreign anti-pattern.

Validation boundaries: two disposable projects you own on a devstack/lab cloud; share contents = synthetic marker data only; backup-into-attacker-project proof read back from *your own* project then deleted; never exercise write verbs against shares belonging to other tenants on a live cloud, and never list real tenants' Cinder messages as anything but your own project.
