# Mobile app-auth forgery chains and privileged-credential-platform boundaries

Source: hourly offensive-security scan, 2026-09-20. GitHub advisories [GHSA-9f8w-25xq-gfm7](https://github.com/advisories/GHSA-9f8w-25xq-gfm7) / [CVE-2026-86553](https://nvd.nist.gov/vuln/detail/CVE-2026-86553) and [GHSA-5vgr-9q5r-pvpj](https://github.com/advisories/GHSA-5vgr-9q5r-pvpj) / [CVE-2026-86552](https://nvd.nist.gov/vuln/detail/CVE-2026-86552) (SmartLife/ZTE app backends), [GHSA-5256-r6g6-4j2j](https://github.com/advisories/GHSA-5256-r6g6-4j2j) / [CVE-2026-90971](https://nvd.nist.gov/vuln/detail/CVE-2026-90971), [GHSA-hfw6-c783-wrw2](https://github.com/advisories/GHSA-hfw6-c783-wrw2) / [CVE-2026-90969](https://nvd.nist.gov/vuln/detail/CVE-2026-90969), [GHSA-xp86-5592-qh57](https://github.com/advisories/GHSA-xp86-5592-qh57) / [CVE-2026-13327](https://nvd.nist.gov/vuln/detail/CVE-2026-13327), [GHSA-m9jg-rh2h-mw5m](https://github.com/advisories/GHSA-m9jg-rh2h-mw5m) / [CVE-2026-84850](https://nvd.nist.gov/vuln/detail/CVE-2026-84850) (Devolutions Server), and [GHSA-c2cc-g2j3-9qhg](https://github.com/advisories/GHSA-c2cc-g2j3-9qhg) / [CVE-2026-76672](https://nvd.nist.gov/vuln/detail/CVE-2026-76672) (HPE SD-WAN Orchestrator).

Three clusters from the Sept 20 06:30Z wave and the late-processed Sept 15 updated-feed items generalize into durable hunting patterns: **app-authentication parameters as the only server-side authorization on mobile backends**, **credential-vault products whose own features leak the vault**, and **read-only roles on management planes that reach token-bearing integrations**.

## 1. SmartLife app backends: dynamic app-auth params as forged capability (2 GHSAs)

[GHSA-9f8w-25xq-gfm7](https://github.com/advisories/GHSA-9f8w-25xq-gfm7) / [CVE-2026-86553](https://nvd.nist.gov/vuln/detail/CVE-2026-86553) (8.5, CVSS scope-changed): the SmartLife app generates application authentication parameters **at runtime inside the client process**. With those parameters, an attacker calls `/account/verify.serv` to resolve **any registered email → real account ID**, then spoofs the app-auth fields together with the victim account ID to **reset the target's password** — full ATO with no user interaction. Twin record [GHSA-5vgr-9q5r-pvpj](https://github.com/advisories/GHSA-5vgr-9q5r-pvpj) / [CVE-2026-86552](https://nvd.nist.gov/vuln/detail/CVE-2026-86552): the same forged app-auth params let anyone complete `/account/person/signup.serv` registration with **any arbitrary email address — ownership never verified**.

Vendor advisory context: ZTE support bulletins [2171542593031840100](https://support.zte.com.cn/zte-iccp-isupport-webui/bulletin/detail/2171542593031840100) and [460174866982102946](https://support.zte.com.cn/zte-iccp-isupport-webui/bulletin/detail/460174866982102946).

Operator value:

1. **"App authentication" is not user authentication.** When the only thing gating an account endpoint is a client-computed app ID/nonce/signature (not tied to a per-user session), extracting that algorithm once from the APK/frida-hooked runtime yields a *service-level capability* that authorizes requests for **every** user. Treat any request parameter that is identical across your own accounts but required by the backend as this class.
2. **The chain that turns a low-severity oracle into an ATO:** `verify.serv` (email → account ID, unauthenticated-but-app-auth-gated) + password-reset endpoint that trusts the *asserted* account ID + forgery-tolerant app-auth = complete takeover. Enumerate oracles are only findings when you trace the ID into the next endpoint's authorization check — run the resolver→sink trace, like the Blazar read-bug-feeds-write-bug pattern.
3. **Signup without ownership verification** (CVE-2026-86552) is its own durable axis: registering an unowned email provisions attacker state *inside* the victim's identity namespace — check what downstream flows trust "this email is already verified at signup" (auto-login, device binding, family-share invites).

Safe validation boundaries:

1. Authorized scope only (program explicitly covering the app/backend). Instrument **your own** two accounts: A = attacker-controlled email, B = second owned email as the "victim".
2. Extract the app-auth generation once from your own installed app (frida hook on the signing/param function or static review) — capture the *algorithm shape* for the report, never publish live parameter values.
3. Prove `verify.serv` with the decision table: {valid app-auth, A email} → ID; {valid app-auth, B email} → ID; {removed/tampered app-auth} → reject. The oracle verdict is the ID-diff, not any PII beyond the synthetic account ID.
4. Prove the reset leg **only against account B you own** and stop at the token/email-arrival boundary; do not complete takeovers of third parties. Negative control: fixed backend rejects verify/reset without user-bound session auth.
5. Signup axis: register only emails on domains you control (catch-all), then check whether the product's flows treat the address as ownership-verified; delete the synthetic accounts.

Reporting heuristic: title as **"app-authentication parameters forgeable from client → account-ID resolution oracle + unowned-email registration on <backend>"**; include the endpoint matrix (which `.serv` routes accept app-auth-only), the ID-diff decision table, and the version/app-build fingerprint. The scope-changed CVSS on the ATO record is justified — say why (client-extracted capability authorizes actions in other users' accounts).

## 2. Devolutions Server: the credential vault's own features leak the vault (4 GHSAs)

- [GHSA-5256-r6g6-4j2j](https://github.com/advisories/GHSA-5256-r6g6-4j2j) / [CVE-2026-90971](https://nvd.nist.gov/vuln/detail/CVE-2026-90971) (6.5): SSRF in the **VMware synchronization feature** — a low-privileged authenticated user submits a crafted **connection definition for datacenter discovery** and obtains **other users' credentials** plus reaches internal/cloud-metadata endpoints.
- [GHSA-hfw6-c783-wrw2](https://github.com/advisories/GHSA-hfw6-c783-wrw2) / [CVE-2026-90969](https://nvd.nist.gov/vuln/detail/CVE-2026-90969) (6.5): vault entry **listing endpoint accepts password-disclosure parameters** even though the caller lacks the view-password permission → cleartext passwords for entries the UI would hide.
- [GHSA-xp86-5592-qh57](https://github.com/advisories/GHSA-xp86-5592-qh57) / [CVE-2026-13327](https://nvd.nist.gov/vuln/detail/CVE-2026-13327) (8.3): **LDAPS connections to Active Directory accept spoofed/self-signed domain-controller certificates** → network-positioned attacker intercepts privileged directory-service credentials.
- [GHSA-m9jg-rh2h-mw5m](https://github.com/advisories/GHSA-m9jg-rh2h-mw5m) / [CVE-2026-84850](https://nvd.nist.gov/vuln/detail/CVE-2026-84850) (4.8): the **shared HTTP client used by sync/integration features** skips certificate validation → intercept/tamper on outbound TLS.

Operator value:

1. **Feature-triggered server-side fetch is the vault's SSRF surface.** Datacenter/hosts "discovery", sync, and integration features all take a *connection definition* — a server-controlled fetch target — from a low-privilege user. On any credential manager, PAM, or CI secret store, enumerate every feature that says "test connection", "discover", "sync now", and treat each as an SSRF candidate whose *response channel* (stored entries, error text, created objects) you must identify before claiming disclosure. CVE-2026-90971's "obtain other users' credentials" means the discovery result was written somewhere the attacker can read — map discovery-result storage first.
2. **Permission checks belong on the endpoint, not the UI.** The vault listing accepting caller-supplied "include password" params without the view-password grant is the parameter-ABSENT/presence-mismatch family again: run every list endpoint in **decision-table mode** — UI-default params vs disclosure params vs stripped params, as a principal *without* the capability. The UI hiding a column proves nothing about the API.
3. **Products that aggregate credentials must validate certs on every outbound leg, including "infrastructure" legs (LDAPS, sync clients).** A network-position attacker (lab VLAN, cloud-adjacent) MITMs the vault-to-DC channel and captures privileged bind credentials — a *passive* enterprise-domain attack worth checking on engagement LANs where you can spoof/responsive-name the DC hostname. Test only in approved labs; the durable check is a certificate-validation matrix per outbound feature (does it pin? chain-verify? accept self-signed?).

Safe validation boundaries:

1. Owned Devolutions Server instance (≤ 2026.2.16 for positive controls) with two synthetic users and vault entries holding **fake marker credentials** (never live passwords — the disclosure test proves presence-by-marker, not real secrets).
2. SSRF: submit a connection definition pointing at **your owned callback**; record whether the fetch originates from the server, which port/host, and where the response lands (entry fields, error strings, stored discovery rows). Metadata-endpoint probing only if the scope explicitly allows it; otherwise stop at the owned callback.
3. Password-param test: as the no-view-password user, call the listing endpoint with and without disclosure parameters; capture the field-presence/absence table with marker values redacted.
4. Cert-validation items: lab CA + spoofed listener on a network segment you control; the finding is "connection succeeded with invalid cert" from client logs — never capture live bind credentials on a production DC.

Reporting heuristic: frame Devolutions items as **"credential aggregation platform crosses its own authorization/crypto boundary"**, not generic SSRF/XSS. Quote only marker values; version-pin (2026.2.16). Related: the Sept 16 Delinea Secret Server padding-oracle/SAML-reuse cluster — the standing axis is *secrets managers need their own adversarial pass; the vault is the highest-value host on the network*.

## 3. Read-only role reaching token-bearing integrations (HPE SD-WAN Orchestrator)

[GHSA-c2cc-g2j3-9qhg](https://github.com/advisories/GHSA-c2cc-g2j3-9qhg) / [CVE-2026-76672](https://nvd.nist.gov/vuln/detail/CVE-2026-76672) (9.9, HPE advisory [hpesbnw05135en_us](https://support.hpe.com/hpesc/public/docDisplay?docId=hpesbnw05135en_us&docLocale=en_US)): an authenticated **read-only** user sends a specially crafted request to the **cache synchronization endpoint** and the response discloses **sensitive third-party API tokens and credentials** used for integrations — enabling lateral movement to external security platforms.

Operator value:

1. **Read-only ≠ low-value on integration-bearing management planes.** Orchestrators, SIEMs, ticketing, and CI admins store machine credentials for *other platforms*. Audit every sync/cache/webhook/internal-API endpoint as: which roles may call it, and does the response serialize integration config (tokens, service-account keys) rather than business data? The role that can *see cache* can often *see tokens*.
2. **Crafted-request wording means the disclosed fields are parameter- or state-gated** — sweep the endpoint with alternate method, alternate payload shape, and priming actions (trigger a sync, then read) rather than a single default GET.
3. Lateral-movement framing for reports: token disclosure from platform A grants API authority on platform B — chain it explicitly (token → what can B do?) with only synthetic/replayed-structurally-invalid probes; never use a disclosed live token against the third-party platform.

Safe validation boundaries: authorized appliance labs only; proof = canary token you seeded into the integration config re-appearing in the crafted response for the read-only principal. Positive/negative pair: read-only sees marker; anonymous and a non-integration role do not.
