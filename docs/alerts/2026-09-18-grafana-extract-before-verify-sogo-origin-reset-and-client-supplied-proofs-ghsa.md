# Extraction-before-verification, Origin-derived reset links, and client-supplied proofs (Sept 17 21:31Z / Sept 18 00:31Z waves)

Source: hourly offensive-security scan of GitHub Security Advisories (reviewed + unreviewed), 2026-09-17T21:31Z and 2026-09-18T00:31Z waves.

The durable axis across these records is **a trusted pipeline step that fires before — or instead of — its own verification gate**: Grafana extracts plugin archives before signature verification, SOGo builds password-reset URLs from a request-supplied header, and two WordPress plugins accept a client-supplied string as proof of payment or ownership. In each case the control exists, is even correct in isolation, and simply never gates the operation that matters.

## Why this is worth an operator page

- **"Verified" is not "verified-before-use".** The Grafana record is the cleanest instance of an ordering bug the wiki keeps meeting (Nuclei mtime-cache Sept 16, plugin signature paths throughout): the signature check is real, but it runs *after* the dangerous side effect (extraction), so the archive has already written outside the sandbox before anyone looks at it. Audit rule for every install/import/load pipeline: enumerate the order of (fetch → extract/write → verify → activate), and test whether the verify step can be made irrelevant by a payload that survives extraction. For supply-chain shape: an operator installing an *apparently legitimate* plugin is affected — so on authorized engagements, the question "does this Grafana ingest third-party archives?" is itself a finding on hosts with plugin-management access.
- **`Origin` is the sibling of `Host` in token-link construction.** Every reset/invite/verification-link generator that formats `${scheme}://${authority_from_request}` is a token-exfiltration primitive. SOGo shows it via `Origin`; the Apostrophe page shows it via `Host`; the Nezha page shows it via `redirect_uri`. The probe generalizes: fire the recovery request against a lab target with a hostile `Origin` **and** a hostile `Host` and inspect the generated link (or the outbound email through an owned recovery mailbox) before touching real users.
- **Client-supplied strings accepted as payment/ownership proof are always a BOLA/ATO ladder.** Amelia's customer endpoint lets a low-privilege plugin role reset passwords of *any* customer — and because WordPress users who ever booked become Amelia customers, the plugin boundary reaches back into core-account authority. Recon heuristic for any SaaS-y WordPress plugin: map plugin-internal object collections (`/users/customers/<id>` style) and test cross-object reads/writes from the lowest authenticated plugin role, checking whether any plugin-side mutation (password reset, email change) affects the core WordPress session.
- **Post/listing status states are unauthenticated disclosure targets.** Motors' handler leaks draft/pending/private/future content anonymously. When inventorying `wp-admin/admin-ajax.php` actions, enumerate the handler's status parameters (`post_status`, `status`, `state`) and request non-public values explicitly — publish-only fuzzing misses this class entirely.

## Validation workflow (authorized scope only)

!!! warning "Lab installs, owned mailboxes, disposable objects"
    The Grafana fixture requires a dedicated lab instance you are authorized to compromise — the validation is a real file write and real code execution. Never run it against a production dashboard, and never use real plugin-signing keys.

1. **Grafana ordering proof (lab only):** on a disposable Grafana, install a crafted plugin archive containing chained relative symlinks that land a benign marker executable outside the plugins directory. Evidence: resolved-path table (archive entry → symlink chain → final outside path), marker file ownership/mode, and the *single fact that extraction completed while the signature error was still reported*. Stop at "arbitrary write + binary dropped"; do not escalate the Grafana process or persist.
2. **Grafana surface triage (no exploit):** version fingerprint (login page / `/api/health`), whether third-party plugin installation is possible (`grafana-cli`, `GF_INSTALL_PLUGINS`, preinstall config presence), and whether signature enforcement is configured at all. Presence-only facts for the report.
3. **Reset-link header probe (lab only):** on an authorized SOGo (<5.12.11), submit a recovery request for a *lab* address you control with `Origin: https://<owned-callback>`; record the emailed link's authority. Repeat with hostile `Host` and with both headers absent. Decision table: header → emitted link authority → token present? Never target real mailboxes; redact tokens from all evidence.
4. **Amelia-class BOLA:** two disposable lab users — one `wpamelia-provider`, one customer-holder. From the provider token, read and modify the other customer's record and attempt the password-reset action against a *lab* core account, recording whether a core WordPress session/credential changes. Marker-only mutations; snapshot and restore rows.
5. **Motors-class status disclosure:** on an authorized site, call `mvl_ajax_dealer_load_cars()` (admin-ajax, no cookie) and compare returned listings against a logged-in control, restricted to a seeded lab listing in `draft` status. Presence-only proof (post ID + status), never bulk-extract real listings.

## September 22 follow-up: the origin leg can also be a request *parameter*

- **Gladys Assistant <5.1.0 reset-link poisoning via `origin` parameter** (CVE-2026-93340, [GHSA-47ff-wp9w-g26c](https://github.com/advisories/GHSA-47ff-wp9w-g26c), 6.8): the `forgot_password` endpoint accepts a **client-supplied `origin` parameter with no server-side validation** and embeds it in the emailed reset link — an unauthenticated attacker requests recovery for any account (including administrators) with their own origin and receives the victim's valid token. Third spelling of the same primitive: SOGo used the `Origin` **header**, Apostrophe the `Host` **header**, Nezha the `redirect_uri`, and Gladys a plain body/query **parameter**. Sweep generalizes accordingly: for every recovery/invite/verification flow, test hostile authority in `Origin`, `Host`, **and** every plausible body/query key named `origin`, `redirect`, `host`, `base_url`, `referer` — and the parameter-absent control.

## Reporting checklist

- Exact product/plugin version, transport (`grafana-cli` vs API vs env var; admin-ajax action name; REST route), and auth state per leg.
- For ordering bugs: the pipeline sequence table (fetch/extract/verify/activate) with the observed side effect placed at each step — the finding is the *position* of the write, not just the write.
- For header-derived links: which header controlled which URL component, and the token-bearing-vs-token-less variant of the generated link (redacted).
- For plugin BOLA: the minimum authenticated role, the object-collection route, and whether the plugin-side mutation reaches core-account authentication.
- Bounded impact language: extraction-with-write-outside-install-dir is "arbitrary file write → code execution as the service account" only when the dropped binary execution path is shown; an unauthenticated draft-listing read is disclosure, not ATO.
