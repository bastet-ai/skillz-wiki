# AsyncHttpClient coordinated wave: client-side credential-crossing primitives — stale-target replay writes one host's request into another host's TLS tunnel, digest downgrade leaks cleartext passwords, plaintext HTTP overwrites Secure cookies, and NTLM pool keys keep leaking identities

Source: hourly offensive-security scan of GitHub Security Advisories, 2026-10-08 (wave published 2026-10-08T16:08–16:50Z, ten advisories for `org.asynchttpclient:async-http-client` plus one moby DoS, CVE-2026-107212-adjacent band CVE-2026-107226–107231 / 107280–107285, fixed across **3.0.12 / 3.0.13 / 3.0.14** and **2.16.1**; 2.x is EOL — two legs never get a 2.x fix).

One theme: **this is the mirror image of the server-side pages — every leg is a bug in an outbound Java HTTP client, and each one moves credentials, cookies, requests, or authenticated sockets across a host, scheme, or identity boundary the application believes is enforced.** AsyncHttpClient is embedded across Java enterprise stacks (service integrations, API gateways, crawlers, SDKs), and several legs are "long-standing behaviour, not a recent regression" — vulnerable deployments are everywhere and silent. Several legs also fingerprint their own patch level through behavior, which is directly reusable recon.

## Why this is an operator page

1. **Client-side bugs are a hunting ground you can test entirely on your own infrastructure.** No customer target is needed to prove any leg here: an owned origin that emits crafted 401s, an owned plaintext HTTP host, an owned listener behind your own CONNECT-tunneling proxy, a lab JVM running the pinned versions. That makes this class ideal for building reusable, report-ready evidence kits before you ever touch scope — and for bounty scopes that include vendor integrations (anything Java that embeds AHC).
2. **The critical leg gives you a generic credential-crossing probe for any Java service integration.** Failover-`ResponseFilter` and retry-on-IOException are *documented, ordinary* usage — meaning many deployments reproduce the replay by design. Target-shape fingerprint: a service that (a) configures client credentials or a proxy, and (b) fetches URLs that a lower-trust user can influence. The advisory names the exact shape for the pool-key leg (Kerberos identity + user-supplied URLs).
3. **Fix-history differentials are a free version fingerprint.** Three legs are explicit incomplete-fix residuals (pool key ← GHSA-vvp4-63h8-v5pm; public suffix ← CVE-2026-55688; caller-header ← CVE-2024-53990), and one trigger exists only on 3.0.12 (trailing-backslash realm). When you control the server side of the wire, the client's behavior *is* a version probe: does a nonceless `Digest` challenge get answered with `Basic` (≤3.0.12-era or unfixed), does `realm="C:\"` still yield a digest response, does a `Set-Cookie` from your plaintext host survive into the next TLS request? Decision table beats banner grabbing for headless Java backends.
4. **Cookies are two independent policy layers — storage and retrieval — and fixing one doesn't fix the other.** Both cookie legs are storage-side failures behind a retrieval-side check (`Secure` filtered on send; unrelated-domain rejected on store). Every cookie jar you audit gets both matrices: arrive-scheme × Secure-flag × overlay/delete on store, and domain-scope including public suffixes.
5. **The "scheme flag" is the seam.** The ws:// credential leak happened because CONNECT-tunnelling keys on "secured URI" while the proxy-auth gate keys on the same boolean without excluding WebSocket — one boolean consumed by two branches with different sibling handling. Same genealogy as the July 30 URL-policy page's branch-sweep rule: enumerate every consumer of a trust boolean separately; correctness in one branch proves nothing about the next.

## Replayable validation boundaries (lab-only)

- **Replay/credentials leg:** lab JVM + AHC ≤3.0.12, two origins you own (A with a fake `Authorization` credential, B as listener). Drive (i) a `ResponseFilter` failover A→B and inspect what B receives (expect A's path/Host/auth if vulnerable), (ii) pooled-connection crossover by re-requesting A after a replay and watching which listener serves it, (iii) http→https replay proving the cleartext branch. Fake credentials only; the marker is which listener sees which header.
- **Digest downgrade:** serve `Digest realm="x"` with and without `nonce=""` and the `realm="C:\"` form from an owned origin; capture whether an `Authorization: Basic` arrives (base64 of your lab password proves the class).
- **Cookie legs:** owned `insecure.example.com`-shaped host on lab DNS setting `SID=canary; Secure; Domain=<lab-suffix>` over plaintext, then observe the next HTTPS request's cookie jar; separately test `Domain=` values that are public suffixes (`co.uk`, your lab `.local` analogues). Fixation/overwrite/delete battery, synthetic values.
- **Pool-identity leg:** lab KDC or NTLM test server, two lab principals sharing a username across realms, one client; assert whether an uncredentialed request draws the authenticated socket (server-side identity log is the verdict).
- Never point any of this at third-party origins, real proxies, real IdPs, or production Java services; prove credential crossing to your own listeners only.

## October 8 17:1xZ follow-up: Pydantic AI cloud-metadata blocklist defeated by an IPv6 zone identifier — third guard iteration on the same URL field (CVE-2026-107289 / [GHSA-vmxc-h2x2-jmf3](https://github.com/advisories/GHSA-vmxc-h2x2-jmf3), medium, `pydantic-ai` >=1.56 <1.107.6 / >=2.0b <2.44.0)

Where an app opts a URL into local access (`FileUrl(force_download='allow-local')` or `web_fetch_tool(allow_local_urls=True)`), the *always-blocked* cloud-metadata guard compared IPv6 addresses by **Python `IPv6Address` set membership — and Python folds the `%zone` identifier into equality/hashing** — while the network stack **ignores the zone for non-link-local destinations**. `http://[fd00:ec2::254%251]/` is not in the blocklist as a set member and still connects to IMESA metadata, leaking IAM short-term credentials. This is the *third* remediation of the same field (after CVE-2026-46678, CVE-2026-48782, themselves follow-ups to CVE-2026-25580).

Durable axes (generalizes this page's fix-differential rule and the April 30 n8n IPv4-mapped-IPv6 leg):

1. **A blocklist is only as canonical as its comparison function.** Every IP/host blocklist gets the spelling battery per class: alternate encodings (IPv4-mapped IPv6, octal/hex forms), scope/zone decorations (`%251`, `%eth0`), Unicode/IDNA spellings, and case variants. The fingerprint to grep in Python: blocklist membership checks on `ipaddress` objects (zone hashes in), versus `socket` connections (zone ignored out). Guard pass ≠ stack agreement.
2. **After the *n*th advisory on one field, assume the *n+1*th guard has a new unmodeled spelling.** Pydantic AI's `web_fetch`/`FileUrl` fetch boundary has now been remediated four times; on any AI-fetch surface, replay the *entire* historical bypass corpus for that product on the current version instead of testing only today's spelling. (Same same-product re-sweep rule as the PraisonAI waves.)
3. Proof discipline: canonical link-local/metadata ranges only in a throwaway cloud lab or via an owned resolver serving the zone-scoped spelling to your listener — never live production metadata endpoints.
