# Bouncy Castle .NET parser, oracle, and constraint-bypass wave (Oct 2 09:31Z)

Source: hourly offensive-security scan of GitHub Security Advisories, 2026-10-02. ~20 GHSAs published 09:31Z for **bc-csharp before 2.7.0** ("Legion of the Bouncy Castle Inc."), plus three Java BC pre-1.86 items in the same wave. Companion pages: [July 1 BC CTR keystream](2026-07-01-bouncy-castle-ctr-keystream-boundary-ghsa.md), [Aug 3 BC crypto-policy boundaries](2026-08-03-bouncy-castle-crypto-policy-boundaries-ghsa.md).

Why this matters to an operator: bc-csharp is embedded in .NET apps, Windows services, CMS document pipelines, PKI tooling, and IoT/OT management stacks. This wave is a complete catalogue of **what an attacker gets when a product parses untrusted crypto objects with this library**: padding oracles that recover plaintext keys, PKIX name-constraint bypasses for enterprise-pivot certificates, a forged-attribute-certificate auth bypass, and a resource-exhaustion inventory reachable pre-authentication.

## Decision oracles: decrypt-and-report paths are key-recovery machines

| Component | GHSA / CVE | Oracle |
| --- | --- | --- |
| CMS RSA PKCS#1 v1.5 key transport (`KeyTransRecipientInformation.UnwrapKey`) | [GHSA-xx4m-xv2j-xx6g](https://github.com/advisories/GHSA-xx4m-xv2j-xx6g) / CVE-2026-63573 | Invalid padding rejected with a **distinct "bad padding" exception** instead of the RFC-required random-key substitution → textbook **Bleichenbacher adaptive chosen-ciphertext**: submit modified captured `EnvelopedData`, read the error taxonomy, recover the content key. |
| IES/ECIES block-cipher mode (`IesEngine.DecryptBlock`) | [GHSA-6w4x-4wpp-m6r4](https://github.com/advisories/GHSA-6w4x-4wpp-m6r4) / CVE-2026-63567 | Decrypt + PKCS#7 padding strip happen **before MAC verification**; padding failure returns a different message and *skips the MAC computation* (also a timing differential) → **CBC padding oracle** on any app that surfaces decrypt errors. |

| CCM AEAD (`CcmBlockCipher`, CMS `EnvelopedData` paths) | [GHSA-499v-wjw6-fvpx](https://github.com/advisories/GHSA-499v-wjw6-fvpx) / CVE-2026-15999 | Decrypt accepts an `AlgorithmIdentifier` whose `aes-ICVlen` is **zero or outside the RFC 5084 set** (tag length is validated only on *encrypt*); on-path attacker swaps parameters to a zero-length tag → content modification without detection. |

| CCM unverified-plaintext release | [GHSA-v84x-v65q-m82v](https://github.com/advisories/GHSA-v84x-v65q-m82v) / CVE-2026-103601 | Failed decryption **leaves recovered plaintext in the caller's output buffer** (buffer reuse/logging oracle → chosen-ciphertext decryption service). |
| Raw DH agreement (`DHAgreement.CalculateAgreement`, MTI/A0) — **critical** | [GHSA-m2m9-m35w-rfxg](https://github.com/advisories/GHSA-m2m9-m35w-rfxg) / CVE-2026-63569 | Peer ephemeral value raised to the static private key with **no range/subgroup check**: crafted small-order/out-of-range value makes both parties compute a key the on-path attacker already knows, and leaks the static private key modulo small factors of p−1. |

**Operator rules.**

1. **Error taxonomy is the probe.** For any endpoint that decrypts attacker-supplied crypto objects (CMS in document/email pipelines, ECIES in device provisioning, PFX upload forms), the finding is not "vulnerable library" — it is *does a padding failure produce a different response than a MAC/tag failure?* Differential battery: untampered / padding-corrupted / MAC-corrupted / truncated inputs; compare status, exception class, message text, and latency. A per-class differential = key-recovery oracle; report the exact differentiating field.
2. **Parameter-bearing AlgorithmIdentifiers are attacker-chosen and often only validated on the encrypt path.** Sweep every AEAD/KDF/PBE algorithm parameter (`aes-ICVlen`, PBKDF2 iterations, scrypt `N/r/p`, OAEP label) through the **decrypt/verify direction** with degenerate values (0, 1, 2^31−1, out-of-set enums).
3. **Test static-DH APIs for small-order inputs.** If a product calls raw DH agreement (not the authenticated TLS stack), submit a `g^(p−1)`-style order-1 element as the peer ephemeral and check whether the session proceeds.

## PKIX validation bypasses (enterprise-pivot class)

| URI (`uniformResourceIdentifier`) constraints | [GHSA-3248-8mh4-pcmr](https://github.com/advisories/GHSA-3248-8mh4-pcmr) / CVE-2026-63576 | Host extracted by **string slicing without isolating the RFC 3986 authority** — a URI with `@` or `:` in path/query/fragment userinfo makes the string compared against constraints differ from the real host. |
| DNS/email constraints, excluded subtrees | [GHSA-mx2f-845p-2h26](https://github.com/advisories/GHSA-mx2f-845p-2h26) / CVE-2026-103602 | **Trailing-dot root label** (`evil.example.com.`) fails to match an excluded subtree written without the dot → excluded names validate. |
| Attribute certificates (`PkixAttrCertPathValidator`) | [GHSA-cwfr-988g-hf77](https://github.com/advisories/GHSA-cwfr-988g-hf77) / CVE-2026-63571 | The RFC 3281 validation routine checks holder/issuer paths, validity, extensions, revocation — and **never verifies the attribute certificate's own signature**. A forged AC naming a trusted issuer grants whatever roles the app reads from its attributes. |
| PKCS#12 chain building | [GHSA-g2c8-ppvq-rq73](https://github.com/advisories/GHSA-g2c8-ppvq-rq73) / CVE-2026-63570 | Chain loop follows AuthorityKeyIdentifier links **without visited-set and without checking signatures**; two certs whose AKIs point at each other = infinite loop (CPU + OOM). |

**Operator rules.**

- **Name constraints are the least-tested PKIX control.** If an engagement yields any issuance capability from an enterprise intermediate (even a "locked-down" name-constrained one), test the three shapes above against a lab verifier before concluding the constraint actually confines you: prepend-RDN, authority-slicing URI (`uri:user@real-host?` shapes), trailing-dot FQDN. Constraint enforcement is verifier-side: also test client-side validators (TLS libraries, document signers, code-signing policy chains) separately from the CA's own issuance checks.
- **Attribute/role certificates: does the validator verify the signature at all?** Any app granting privileges from X.509 ACs or holder-issuer bindings deserves a forged-AC test with an issuer name copied from a real AA. Zero cost, and the validation-stack skip is exactly what this advisory proves is plausible.
- **Path-building loops that trust unsigned identifier links are DoS + confusion primitives.** Feed AKI-cycle pairs to any PFX/PKCS#12 loader.

## Pre-authentication work-before-authentication: the resource-exhaustion inventory

The recurring shape across this wave: **cost/length parameters are read from the untrusted object and consumed before any MAC, password, or signature can reject the input.** That ordering — work first, authenticate later — is the audit predicate, not "is it a DoS."

| --- | --- | --- |
| ASN.1 (`Asn1InputStream`/`Asn1StreamParser`) | [GHSA-xp76-rp77-x5w9](https://github.com/advisories/GHSA-xp76-rp77-x5w9) / CVE-2026-103600 | No depth bound; ~2,000 nested SEQUENCEs (**8 KB DER**) exhaust the default .NET thread stack → **uncatchable** `StackOverflowException` kills the whole process. Any cert/CRL/CMS/PKCS#7 accepting path is a crash switch. |
| PKCS#12 load (`Pkcs12Store.Load`) | [GHSA-v54c-wxx6-mjh6](https://github.com/advisories/GHSA-v54c-wxx6-mjh6) / CVE-2026-63572 + [GHSA-7c84-x75c-5j8m](https://github.com/advisories/GHSA-7c84-x75c-5j8m) / CVE-2026-63575 | MacData/PBE iteration count taken from the file up to ~2^31 → KDF runs **before the MAC or password is checked**; zero/negative count wraps the loop through ~2^32 iterations. A 75-byte PFX ties up a worker for minutes. |
| Encrypted private keys (`PbeUtilities`, PBES1/PBES2/PKCS#12 PBE/CMS PBE) | [GHSA-4583-5v2w-p3vq](https://github.com/advisories/GHSA-4583-5v2w-p3vq) / CVE-2026-63578 | Same shape on `ENCRYPTED PRIVATE KEY` PEM upload forms. |

**Operator rules.**

- **Fuzz battery for every untrusted ASN.1/PKCS/OpenPGP consumer** (cert/CRL upload, PFX import, S/MIME handler, OpenPGP key server, DTLS listener, CMP enrollment endpoint): depth-nested SEQUENCEs (8 KB → process death on .NET defaults), max-length five-octet subpacket headers, iteration-count 2^31−1 and −1, HSS/LMS level-count 2^32, DTLS fragments declaring 16 MB with zero payload. These are the shapes with *published, specific* thresholds now — they are one-liner generators, and pre-auth ones.
- **"Cap-before-derive" is also an audit rule for integrators**: when a product embeds this library, its own wrappers frequently reintroduce the unbounded constructor path (the PBMAC constructor split is the exemplar — the safe API exists, the default one is unsafe).

## Java BC (before 1.86) adjacent legs

- **NTRU secret-dependent division** ([GHSA-frjj-v5w4-68pc](https://github.com/advisories/GHSA-frjj-v5w4-68pc) / CVE-2026-18036): `modQ`/`mod3` helpers used integer `%` on secret operands where the reference implementations are deliberately division-free — variable-latency division on the **decapsulation path** (dividend derives from the private key). Post-quantum KEM side channel in the *reduced-secret handling*, not the core math — audit pattern: check every modular reduction in a PQC port against the reference's division-free construction.
- **MLS signed/unsigned leaf index** ([GHSA-x7w3-c4mv-whm4](https://github.com/advisories/GHSA-x7w3-c4mv-whm4) / CVE-2026-17507): RFC 9420's `uint32 leaf_index` held in a signed `int`; a wire value with the top bit set is a *legal encoding* (interop vectors round-trip the full range), and signed comparison against leaf count makes **any negative index pass the membership check** → any group member DoSes the whole group via unbounded `directPath` arithmetic. Axis: **signed/unsigned parse differential** — same family as the negative-length/offset items on the parser pages; a spec says "full uint32 range decodes", so the fix must reinterpret, not reject-on-negative. (MLS roster-trust companion to the Oct 2 Discord libdave item on the messaging-SDK page.)
- **KDF cost parameters from untrusted input** ([GHSA-m3x3-p27c-whhp](https://github.com/advisories/GHSA-m3x3-p27c-whhp) / CVE-2026-17508): PBMAC1 iteration count, scrypt `p` (bounded `N`/`r` but scratch scales with `r×p`, evading the memory ceiling), raw JCA PBKDF2, bcrypt rounds read from an OpenSSH v1 key's own `kdfoptions` — the Java twin of the .NET work-before-authentication class; OpenSSH rounds now capped via `org.bouncycastle.openssh.max_rounds`.

## Validation workflow (lab scope only)

!!! warning "No production crypto endpoints"
    All oracle and exhaustion proofs run against lab builds/disposable services you own with synthetic keys and certs. Bleichenbacher/padding-oracle proofs need only enough iterations to show the differential exists (a handful of classification queries), not full key recovery. Never run memory-exhaustion shapes against shared or production hosts — allocate in a constrained VM and measure.

1. **Oracle decision table:** for each decrypt endpoint, submit untampered / padding-corrupt / tag-corrupt / truncated variants; table status+message+latency per class. Any separation = oracle; stop there.
2. **Parameter-degeneracy sweep:** replay CMS/PKCS structures with `aes-ICVlen=0`, iterations 0/−1/2^31−1, scrypt p unbounded — assert the decrypt direction validates parameters, not just encrypt.
3. **Lab PKIX constraint harness (Java/Go, no network):** build a name-constrained test CA with openssl, issue prepend-RDN, trailing-dot, and authority-sliced URIs certs; run the target verifier and diff accept/reject vs RFC 5280 expected.
4. **ASN.1 depth generator:** 8 KB nested-SEQUENCE DER sent to cert/CRL/CMS ingestion in a lab process with default thread stack; observe StackOverflow vs caught exception (this also tells you whether the app's host swallows crashes).
5. **PFX micro-DoS timer:** 75-byte PFX with negative MacData iterations against a lab PFX import form; measure worker occupancy with a stopwatch, not a profiler.

## October 2 late-wave follow-up: wolfSSL cert-validation pack — the same constraint/verdict axes in an embedded TLS stack

A wolfSSL ≤5.9.x pack landed in the 21:33Z updated-feed wave. Distinct library, same three invariants this page was built on (constraint enforcement is verifier-side; the verdict object can lie; work-before-auth ordering):

- **Name-constraint state machine resets on an unconstrained intermediate** (CVE-2026-89133 / [GHSA-vrp7-vcfx-j447](https://github.com/advisories/GHSA-vrp7-vcfx-j447), default build): an unconstrained CA tier between a name-constrained intermediate and the leaf **resets validation state** → certs for out-of-scope hostnames accepted. Second verifier-side name-constraint bypass family this week (BC .NET trio above); the prepend/tail-dot/URI-slicing battery should now include this **chain-shape** leg: constrained intermediate → unconstrained tier → leaf.
- **CN-fallback gate tests the wrong predicate — an incomplete fix of CVE-2026-6731** (CVE-2026-89134 / [GHSA-p2xv-vrwq-543q](https://github.com/advisories/GHSA-p2xv-vrwq-543q), 9.1): the Subject-CN-as-dNSName fallback is gated on `altNames == NULL` instead of "no **dNSName** SAN", so a cert carrying only `registeredID`/`iPAddress` SANs skips name constraints on its CN. Audit rule: fix-gating predicates deserve their own differential — present each SAN-type combination (none / dNSName / non-dNSName / mixed) and diff which leg consults the constraint.
- **`MatchTrustedPeer` ignores the public key** (CVE-2026-93302 / [GHSA-22fm-4q7r-f7w4](https://github.com/advisories/GHSA-22fm-4q7r-f7w4), 8.2): with `WOLFSSL_TRUST_PEER_CERT` (default in autoconf builds: nginx, haproxy, stunnel, apache, bind, rsyslog…), a **forged CA clone with the same subject but a different key** passes peer verification → (D)TLS server-auth bypass once the attacker knows which peer certs are loaded. Peer identity pinned by *name* not *key* is the X.509 twin of the non-secret-identifier-as-credential class (Fleet, Oct 1).
- **A failed verify poisons the shared CertManager for every sibling consumer** (CVE-2026-89135 / [GHSA-m732-8qwx-39wm](https://github.com/advisories/GHSA-m732-8qwx-39wm)): an `X509_verify_cert` failure **permanently plants the unverified attacker CA** in the shared store consulted by native TLS, OCSP, CRL, and direct verifies. One rejected-then-cached object = persistent validation bypass across unrelated features. Sweep rule: for any verify-then-cache path, attempt verify-with-bad-material → re-verify-good-request and check whether trust changed state; caches keyed on parsed names that store failed verdicts are state-corruption primitives.
- **Split verify inverts error precedence under `WOLFSSL_SMALL_CERT_VERIFY`** (CVE-2026-94418 / [GHSA-q4rg-xp99-jj6q](https://github.com/advisories/GHSA-q4rg-xp99-jj6q), low CVSS / high practical): signature check runs separately from parse and the result merges **only when parse returned 0**, so parse errors mask signature failure and validity-date/name-constraint checks are reached without a passed signature — a self-made cert with the trusted CA's subject as issuer and garbage signature bytes is accepted. "Override date errors" policies become total bypasses when the split ordering inverts.
- **Out-of-order ChangeCipherSpec installs known-key read keys** (CVE-2026-93304 / [GHSA-vpg5-xh2g-4x3c](https://github.com/advisories/GHSA-vpg5-xh2g-4x3c)): a TLS/DTLS 1.2 client accepts CCS before ClientKeyExchange, derives read keys from the *deterministic null* master secret, and checks the server Finished against it → an on-path attacker completes the handshake in place of the server and injects data the client accepts as authentic. CCS-injection regression family (the 2014 RFC 7507 class) alive in a current embedded stack; DTLS clients exposed by datagram ordering alone. Tester note: handshake-state probes (early CCS, early Finished, record reordering) belong in any embedded-firmware TLS battery, lab MITM position only.

Collective fingerprint: wolfSSL underpins appliances, printers/cameras, OT gateways, and load/edge daemons shipped via distro autoconf builds — for any binary that strings to `wolfSSL`, the six legs above are one battery: chain-shape constraint reset, SAN-type matrix, trusted-peer clone, poisoned-verify replay, split-verify garbage signature, early-CCS injection. All proofs: lab MITM/disposable endpoints, synthetic CAs.

## October 3 09:31Z follow-up: Java BC before 1.86 — credential-binding omission, index-zero name constraints, OpenPGP authority gaps, and an always-false comparison

The 09:31Z Oct 3 wave published ~10 GHSAs for **Bouncy Castle for Java before 1.86** (plus LTS 2.73.13 for the JNI item) — the Java twin of this page's .NET wave, and it lands on the same invariants (binding is verifier-side; verdict objects can lie; parse-equality is not authority).

- **MLS credential never bound to the leaf's signature key — admission under a victim's identity (critical)** ([CVE-2026-71885 / GHSA-jch3-5j66-88vx](https://github.com/advisories/GHSA-jch3-5j66-88vx)): `LeafNode.verify()` checked the leaf signature against the `signature_key` carried in the leaf itself while the X.509 credential chain was **stored but never parsed or validated** — RFC 9420 §5.3 requires the end-entity cert's public key to match `signature_key`. An attacker presents *another party's certificate* as its credential, signs with an unrelated key, and is accepted under that identity through `KeyPackage.verify()` and the Group leaf-validation path; where a deployment admits external commits without an independent credential-admission check, an **unauthenticated** attacker joins the group under a victim's identity. Sibling leg: **external-commit Remove proposal had no joiner binding** ([CVE-2026-71890 / GHSA-jc55-7frr-fv5r](https://github.com/advisories/GHSA-jc55-7frr-fv5r)) — `validateExternalCachedProposals` counted proposal types and bounded the removed leaf index but never checked the removed leaf had anything to do with the joiner (RFC 9420 §12.2 self-remove rule deliberately skipped on this path with nothing put in its place). Durable rule: **a credential that is parsed-but-not-verified is absent** — for any protocol carrying cert+key pairs, diff *what the verifier actually compares* (key-to-identity, key-to-signature) against what the spec requires; then test admission with a swapped-in foreign credential on lab group members. This is the same subject-not-key class as the wolfSSL `MatchTrustedPeer` leg above, one layer up the stack.
- **`PKIXCertPathReviewer` skips name constraints on the leaf — loop bound excludes index zero; and it disagrees with `CertPathValidator("PKIX","BC")` on identical input** ([CVE-2026-71889 / GHSA-hqqj-v58h-gr7x](https://github.com/advisories/GHSA-hqqj-v58h-gr7x)): `checkNameConstraints` walked with `index > 0` (the CA-only bound), but index zero is the **target cert** in standard `CertPath` ordering — RFC 5280 §6.1.3(b)/(c) never ran against the leaf's DN or SAN; a chain violating its own issuing CA's NameConstraints reports `isValidCertPath()` true with an empty error list. Third verifier-side name-constraint bypass family this week (after the .NET trio and the wolfSSL chain-shape leg), and the **two-verifier differential** is the probe: same library ships two PKIX paths with *no shared code* that disagree — a product using the reviewer instead of the PKIX validator silently drops leaf constraint enforcement. Audit rule: for any app embedding BC, check **which** verifier class the product calls; decision-table the same chain through both when source is visible.
- **OpenPGP: key flags are decoration unless the verify path consults them — two legs.** (1) Third-party certification accepted from **any component key** of the issuing certificate without the `CERTIFY_OTHER` flag — a **SIGN_DATA-only online signing subkey** issued a positive User ID certification over attacker-controlled identities ([CVE-2026-71886 / GHSA-7hrr-mw36-px4x](https://github.com/advisories/GHSA-7hrr-mw36-px4x)): `getCertificationBy()`/`getDelegationBy()` match the issuer key ID against *every* key and verify the binding chain + signature, nothing checks authority-at-signing-time. (2) A signing subkey whose binding signature **omits the Key Flags subpacket** fell back to inheriting the **primary's** `SIGN_DATA` via a different resolution path than the one that enforces cross-certification, so the missing Primary Key Binding signature check was skipped ([CVE-2026-71887 / GHSA-cwf6-pghv-hq93](https://github.com/advisories/GHSA-cwf6-pghv-hq93)). Durable axes: **capability flags that the verify path doesn't re-read are advisory** — test whether a low-authority key (sign-only subkey, no-flag binding) can perform high-authority operations (certify, delegate); and *same-structure-two-resolutions* (flag lookup falling back to parent when absent) is the subpacket twin of the fail-open parse pattern on the Sept 20 media page. Battery: build keys with every flag/subpacket omission combination and run the certification + binding verification matrix.
- **Truncated OpenPGP message = clean end-of-message; SEIPD v1 released cleartext with no integrity check at all** ([CVE-2026-85515 / GHSA-8hgf-w73g-3x6v](https://github.com/advisories/GHSA-8hgf-w73g-3x6v)): truncation was detected, then `nextPacketTag()` translated the `EOFException` into end-of-stream, so the packet stream "finished normally"; consumers releasing streaming cleartext get attacker-truncatable messages. Axis: **EOF-as-success in streaming parsers** — append-truncation probes to any decrypt/verify stream and diff "error reported" vs "clean short message"; RFC 9580 §13.7 permits partial release *only with* a clear truncation error.

Axis for integrators: JNI native wrappers mutating "read-only" Java arrays — in-place crypto call patterns are the detector; key material destroyed mid-session is both a confidentiality and correctness bug, and the differential (pinning vs copying JVM flags) is the reproduction lever.

## October 4 18:3xZ follow-up: default-insecure TLS helpers in shared SDK/client code (gopay, go-micro, Cockpit CMS)

Three same-wave advisories are the *default-flag* twin of this page's wrong-predicate pack — verification isn't mis-implemented, it's switched off in a helper every integrator inherits.

- **gopay payment SDK before 1.5.119 — `defaultClient()` sets InsecureSkipVerify in `pkg/xhttp/client.go`** ([CVE-2026-105218 / GHSA-8f6w-7m2h-mfwg](https://github.com/advisories/GHSA-8f6w-7m2h-mfwg), critical): merchant credentials, signatures, and transaction data cross a TLS leg that accepts any certificate; payment/refund/order-query *responses* are also modifiable in transit. On-path MITM impersonates the payment provider API to the merchant app — the response-modification leg means an attacker can flip a payment-status answer, not just read it.
- **go-micro before 6.0.0 — shared TLS helper sets `InsecureSkipVerify: true` by default** ([CVE-2026-105216 / GHSA-p6q5-cmw8-pqqg](https://github.com/advisories/GHSA-p6q5-cmw8-pqqg), critical): one helper, three planes — gRPC transport, HTTP, RabbitMQ broker, and Consul/etcd registry traffic all inherit the flag, so auth tokens and service credentials are interceptable mesh-wide from any network position inside the fabric. A single default silently de-authenticates the entire service-mesh trust model.
- **Cockpit CMS 2.12.0–<2.14.1 — `cron.php` web-worker restart request skips cert verification** ([CVE-2026-105217 / GHSA-7gf3-cfh5-c772](https://github.com/advisories/GHSA-7gf3-cfh5-c772), low CVSS but durable shape): the outbound call to `site_url` carries the worker/web token, so an on-path attacker on that leg steals the token and can start the web worker themselves. Shape to reuse: **an admin/config-stored URL as the destination of an unverified outbound request that embeds a privileged token** = token-theft pivot from a network position, even when the token's own endpoint is well-authenticated.

Durable rules: (1) **library-default bypasses are invisible to app-level config review** — `defaultClient()`/shared TLS helper names are the grep targets (`InsecureSkipVerify`, `verify=False`, `VERIFY_NONE`, `rejectUnauthorized: false`) *in dependency source*, not just app config; any Go/Python/Node SDK shipping a default client deserves this grep before you trust its transport. (2) **One shared helper = blast-radius multiplier**: count how many transports/planes inherit the flag (go-micro: RPC + broker + registry) — a default-on-insecure helper in mesh middleware is a fabric-level MITM primitive, and pentest evidence only needs one intercepted inter-service call to prove it. (3) The token-in-unverified-outbound-request shape pairs with the Xray empty-ServerName leg above: both steal or bypass at the *client construction site*, which is where audits stop looking. Validation stays passive/lab: on-path position on your own lab mesh or a synthetic merchant callback harness; never intercept live payment or production mesh traffic.

## October 6 follow-up: sequoia-openpgp — missing key-flags subpacket defaults to permissive capability inference (CVE-2026-42784 / GHSA-g33h-rrj9-75qv, high)

sequoia-openpgp inferred key capabilities for older certificates **when the key flags subpacket is absent**, producing a capability view that differs from stricter implementations — the confusion **bypasses the back-authorization (back-signature) check**, so an attacker can bind an arbitrary subkey to someone else's certificate and forge signatures attributed to the primary key holder.

- This wave's invariant restated for OpenPGP: **a missing security-relevant subpacket must resolve to the most restrictive capability, and implementations must agree on the resolution.** The BC legs above were explicit-check misses (unbound credential, index-zero skip, unchecked flag); sequoia is the *default-inference* variant — same verifier-disagreement outcome as the PKIX two-verifier leg (hqqj), reached by omitting a subpacket instead of misparsing one.
- Operator probe for any OpenPGP-family verifier under test (authorized lab only): craft a keypair where the subkey binding signature is forged in the no-key-flags state, present it to (a) the target library, (b) reference GnuPG, and diff accept/reject — a library that accepts where GnuPG rejects is the finding. Same two-verifier decision-table method this page used for the CMS authAttrs MAC-coverage leg.
- Generalization for format audits: for every optional security field in a wire/hybrid format (PGP subpackets, SAML conditions, X.509 extensions, JWT claims), enumerate the **absent-field branch** of each consumer — absent-→-allowed is this week's recurring miss (sequoia here, Keycloak claim-verification legs, the SPIP omitted-`secu_`-param dispatch on the Oct 5 Joomla page's family).

## October 6 23:3xZ follow-up: PyJWT accepts OKP JWKs whose declared public key doesn't match the private key (GHSA-x33g-cr3x-6449 / CVE-2026-102275)

PyJWT 2.1.0–2.14.0 `OKPAlgorithm.from_jwk()` checks that `x` is *present* but, when `d` is also present, builds the Ed25519/Ed448 key from `d` **without verifying the public key derived from `d` matches the declared `x`**. A JWK can therefore carry one public identity while all crypto operates on a different key — in DPoP integrations this lets a stolen sender-constrained access token be used **without the legitimate holder's private key** (construct a JWK declaring the victim's `x` but supplying any private `d`; the proof binds to `d`, the identity reads as `x`). Fixed 2.15.0.

- This is the **inconsistent-field branch** sibling of this page's absent-field branch rule: audits already sweep what happens when a security-relevant field is *missing*; this leg asks what happens when two coupled fields are *present but disagree*. For every paired/derived field in a token or key format (`x`/`d`, `kid`/key-material, `alg`/key-type, JWE `alg`/`enc`), enumerate the mismatch case — validators that check presence-of-each and use-of-one never test the cross-check.
- Operator probe for DPoP/sender-constrained stacks under authorized test: submit a JWK with mismatched `x`/`d` through the token path and observe whether validation resolves identity from `x` while signing with `d`; the differential is a valid-looking DPoP proof from a key nobody authorized. Prove with synthetic keypairs only, never real captured tokens.
